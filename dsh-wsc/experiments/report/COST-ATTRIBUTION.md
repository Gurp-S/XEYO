# 成本归因：为什么分数正常了，步数 / 压缩次数 / token 仍然高

测量对象：`b-fix-3`（9/9，2346s，213 请求，842K 输入）对照 `a-1`（原生 compaction-basic，8/9，36 请求，165K 输入）。
数据来源：`~/.dsh/wsc/compactions.jsonl`、会话事件流（`compaction/summary`、`assistant/message.usage`）、`lib/checkpoint.js` 常量。

## 1. 事实：压缩频率按步数算是一样的，贵在步数

| 指标 | a-1（原生） | b-fix-3（WSC 修复臂） |
| --- | --- | --- |
| 请求数（步） | 36 | 213（5.9×） |
| 压缩次数 | 11 | 68（6.2×） |
| **每几步一次压缩** | 3.3 | 3.1 |
| 输入 token | ~165K | 842K（5.1×） |
| 单次请求 prompt（中位） | 20.3K | 17.0K |
| 压缩后首个请求 prompt（中位） | 21.5K | 16.4K |

结论一：压缩**频率**没变（都是每 3 步左右一次）。次数多 6× 是步数多 6× 的机械结果。真正的自变量是**步数**。

## 2. 步数多 6×：检查点信息量只有原生的 1/5，模型靠重读重建状态

| 指标 | a-1 | b-fix-3 |
| --- | --- | --- |
| 检查点正文（中位字符） | 13,730 | 2,398（selective 2,721 / 回退 1,502） |
| 工具调用数 | 69 | 277 |
| 读类调用 | 32 | 131 |
| **重复读同一路径** | 17（最多 4 次） | 92（最多 16 次） |

b-fix-3 的检查点按段落拆（均值 2,398 字符）：

| 段落 | 字符 | 占比 |
| --- | --- | --- |
| Prior checkpoint（历史嵌套回显） | 1,245 | **52%** |
| Selected excerpts（选材原文） | 692 | 29% |
| Recorded judgments | 292 | 12% |
| Tool calls / Verification / Files | 148 | 6% |

即每次压缩真正新增的信息 ≈ 692 + 292 ≈ **984 字符 ≈ 250 token**，而原生摘要中位 13.7K 字符。模型拿不到"已经做了什么、文件现在什么状态"，只能重读（92 次重复读、最多同一文件 16 次）；重读又立刻把上下文从 16.4K 顶回 19.2K 的告警线，于是 3 步后再压一次——小载荷 → 重读 → 压缩 → 小载荷，自增强闭环。

## 3. 结构性根因（三条，均未被前两个修复触及）

1. **段落级配额把载荷压在 ~1K 字符**：`lib/checkpoint.js` 的 `caps = {selected: 1200, judgments: 320, verification: 220}` 与 `MAX_SECTION_ITEMS.judgments = 12`、`verification = 8`，加上 `share = budget × weight / totalWeight` 的分摊，即便选材返回 4–9K token 的 JSON，渲染出来也只有 700 字符原文 + 292 字符判断。
2. **Prior checkpoint 递归回显吃掉 52% 预算**：`prior: 1` 条目按 1200 字符上限整块内联上一份检查点，而上一份自身又内联它的上一份——实测嵌套缩进 30 空格（约 15 层）。信息在衰减、回显在膨胀；只抬总预算会被回显吃掉。
3. **32% 的压缩回退到确定性摘要**（b-fix-3：21 次 `checkpoint-rejected` + 1 次 `unusable-selection`，回退版正文中位 1,502 字符），这些轮次几乎没有选材内容。回退本身不报错，所以分数不掉，只掉效率。

## 4. 另一个非缺陷但限制上限的事实

预算 24,000 token 里，system prompt + 工具 schema + 保留尾段（`retainRatio 0.16 × 24000 = 3840`）+ 检查点 ≈ 16.4K 是压缩不掉的底盘，可用余量只有 ~2.8K。原生组同构（压缩后 21.5K vs 阈值 24K，余量 2.5K），所以这一条不解释 A/B 差异，但说明"提高保留比例"的空间有限。
