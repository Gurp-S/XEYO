# 修复与验证：控制段截断 / 选材预算

对应 `ROOT-CAUSE.md` 的两条根因。两个缺陷都做成**默认值可调的配置项**，默认值从旧值改为修复值，旧值可显式配置回去。

## 1. 改了什么

| 位置 | 缺陷 | 修复 |
| --- | --- | --- |
| `lib/checkpoint.js` | 控制段按 800 **字符**截断，任务原文（1344 字节）只留下前 802 字节，`--watch` 等要求被切掉 | `controlItemCap`，默认 `4000`，按 **UTF-8 字节**计 |
| `engine.js` | 选材请求 `max_tokens: 4096`，长 JSON 被截断 → 解析失败 → 回退确定性摘要 | `selectionMaxTokens`，默认 `16384` |

两者都进 `Config`（`cordis.patch.yml` 可覆盖）：

```yaml
wsc:
  controlItemCap: 4000
  selectionMaxTokens: 16384
```

默认值即修复值（已确认口径）：所有人默认拿到修复，需要复现旧行为时把上面两项写回 `800` / `4096`。收益已由第 5 节的 A/B 证明，故不再停留在旁路。

账本新增两列遥测，每次压缩一行（`$DSH_HOME/wsc/compactions.jsonl`）：

- `control: { sourceBytes, keptBytes, cap }` —— 截断是否发生、发生多少
- `selection: { attempted, parsed, quotes, droppedAmbiguous, droppedFacts, hasOutput, finish, outputTokens, maxTokens, fallbackReason }` —— 回退的确切原因（`no-output` / `unparsable` / `checkpoint-rejected` / `null`）

## 2. 单元测试

`node --test tests/*.test.mjs` → **79 pass / 0 fail**。新增 4 条覆盖：默认 cap 为 4000、按字节计量、cap 可配置回退到 800、遥测字段形状。

## 3. 真机 A/B：离线复放（不消耗模型额度）

B 组三个会话的每一条消息与每一次 `compaction/summary` 都在会话日志里，因此可以把**真实压缩输入**原样取出，用同一个 builder 跑两遍，只改 cap。

```
node tools/replay-checkpoint.mjs <session.jsonl.zstd>
```

| 会话 | 压缩次数 | 携带控制段的次数 | cap=800 保留 | cap=4000 保留 | `--watch` 存活 |
| --- | --- | --- | --- | --- | --- |
| runs-b-1 | 24 | 1（首次） | 802 / 1344 B | 1372 / 1344 B | 800 ✗ → 4000 ✓ |
| runs-b-2 | 96 | 1（首次） | 802 / 1344 B | 1372 / 1344 B | 800 ✗ → 4000 ✓ |
| runs-b-3 | 20 | 1（首次） | 802 / 1344 B | 1372 / 1344 B | 800 ✗ → 4000 ✓ |

三点结论：

1. 控制段只在**第一次**压缩里存在（此后任务原文已进历史检查点），所以首次截断会被后面每一次检查点继承——这与 B 组三个会话全部丢 `--watch` 一致。
2. 三个会话的截断位置完全一致（802/1344），不是随机抖动，是硬编码上限。
3. cap=4000 时 1372 > 1344 是缩进与标记开销，即**全文保留**。

## 4. 选材预算的真机证据

`b-fix-1`（修复已装，`selectionMaxTokens: 16384`）中 14 次成功选材的输出 token：

```
9444  7810  7794  7172  7002  6652  5745  5171  5096  4361  3559  3549  3513  3209
```

**10 / 14 超过 4096**。旧上限下这些请求必然在 4096 处被切断、JSON 不完整、解析失败并回退——与 B 组 69% 的回退率对得上。

同一次运行里 8 次回退，`fallbackReason` 全部为 `checkpoint-rejected`（选材结果没有把源压到阈值以下），**没有一次是 `unparsable`**：截断型回退消失，剩下的回退是另一个（策略层）问题，遥测现在能直接指出。

## 5. 端到端重跑：分数回到 A 组水平

判别项 `--concurrency and --watch are supported`：修复前 B 组 **0/3** 通过，修复后 **2/2** 通过（A 组 3/3）。`b-fix-3` 连 A 组唯一失败的 `--watch rebuilds after a source change` 也过了。

运行中的账本实测（真机，非复放）：两次运行的首个压缩都是

```
control: {"sourceBytes":1344,"keptBytes":1372,"cap":4000}
```

即任务原文 1344 字节全量进入检查点——修复前同一位置是 802/1344，`--watch` 被切掉。

## 5.1 归因结论

1. **正确性损失 = 控制段截断。** 控制段只在首次压缩出现，800 字符上限把任务要求切掉，之后每份检查点都继承残缺的任务描述；上限放开到 4000 字节后，判别项从 0/3 变成 2/2。这是治本修复：改的是截断机制本身，不是绕过它。
2. **回退率高 = 选材输出上限。** 16384 下 10/14（b-fix-2）成功选材的输出超过 4096，旧上限必然截断；修复后 `unparsable` 型回退消失，剩余回退全部是 `checkpoint-rejected`（策略层，另一回事）。
3. **成本差距没有被这两个修复解决。** 修复后仍是 65–68 次压缩、76–84 万输入 token、约 40 分钟；A 组是 15–30 万 token、8–15 分钟（原生压缩不写这本账）。检查点正文依旧只有 2.3K 字符量级（原生摘要约 28K），模型仍要靠反复重读文件重建上下文（步数 190–213 vs A 组 36–71）。也就是说：**这两个缺陷解释了「做错」，不解释「做贵」**；「做贵」的根因在检查点容量/引用预算，是下一件事。
4. 21–22 次 `checkpoint-rejected` 说明选材虽然不再被截断，但结果经常没把源压到阈值以下而整体回退——这是选材策略（quota 分配）问题，遥测已经能直接定位。
