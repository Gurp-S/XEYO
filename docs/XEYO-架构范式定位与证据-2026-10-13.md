# XEYO 架构范式定位与证据（2026-10-13）

> 问题：XEYO 当前更接近 Workflow、ReAct、Plan-and-Execute，还是 Hybrid？
> 本文按「哪部分是什么 / 源码证据 / 为什么这样选」三段回答，全部结论以磁盘源码为准（HEAD 工作区，`python/` 为引擎根）。
> 所有行号为本文写作时实测值。

---

## 0. 一句话结论

**Hybrid，但主干是 ReAct。**

- **产线只有两条路**：① 模型自决的 ReAct 主循环（唯一常驻路径）；② Plan 模式闸门（opt-in，人批准后**回落到同一个 ReAct 循环**继续跑）。
- **Workflow 形态的机器（LLM 分解 + 确定性 DAG 调度）代码完整、测试覆盖，但当前没有产线调用方**——属储备，不属产线。
- **引擎自身的确定性管线（预算 / 权限 / 压缩 / 回溯）不是 agent 范式**，它们是执行层强制机制，不参与规划，也不出现在模型注意力里。

判定口径：范式归属看**「谁决定下一步」**。XEYO 的结构性选择是——**所有路线决策归模型，引擎只在执行层拒绝**。

## 2. 源码 / 机制证据

### 2.1 主干 = ReAct

**循环骨架**：`engine/query_loop.py:972` `while True:` → `:973 turn_runtime.prepare_next_turn()` → `:1695 async for chunk in model.stream(api_messages, tool_schemas, abort)` → 收集 `tool_uses` → 执行 → 工具结果写回 `MessageStore` → 回环。

**终止权在模型**：模型返回不含工具调用的文本即 `completion_event`（`:2248`、`:2769`）。引擎侧硬停只有三条：abort（`StoppedEvent(reason="aborted")`）、预算（`reason="budget"` / `max_turns`）、收尾窗（`forced_wrap_up`）。状态机集中在 `engine/turn_runtime.py:14` `TurnDecision = Literal["continue","wrap_up","stop_aborted","stop_budget"]`，`prepare_next_turn:36` 只做这四态判定——**引擎没有任何「该往哪走」的判定分支**。

**没有强制的 Thought 字段**：循环里不存在 `thought` 字段的强耦合；推理走独立 delta 通道（`ReasoningDelta` / `AssistantDelta`，见 `msgtypes/events.py`），与工具调用解耦。这一点是「ReAct 而非自制 DSL」的直接体现。

**观察回填是原始结果，不是引擎转述**：工具结果经 `engine/tool_observation.py::observation_payload`、`engine/execution_facts.py::tool_receipt` 落成 `tool_result_message`（`query_loop.py:2735`），只带事实字段（status / execution receipt），不带引擎点评。

**环境状态走 T_now 单一注入点**：`query_loop.py:999` 注释「T_now v2 边界（唯一注入时机）」；`prompt/pre_llm_inject.py:1-13` 模块 docstring 明写「易变块只进 T_now；禁止插入 system 左段（保住 KV 前缀）」——即环境事实（时间、模式、inbox、计划指针）作为**状态**注入，不作为**指令**注入。

### 2.2 Plan-and-Execute 的唯一形态 = 闸门

**模式定义**：`permissions/policy.py:81` `_AGENT_MODES = ("agent", "plan", "ask")`；`:125` `PLAN_ONLY_ALLOW = frozenset({"ExitPlanMode"})`（注释：ExitPlanMode 非 ENABLED 工具，模式特例留在 policy）；`:126-130`：

```
_MODE_TOOL_ALLOW = {
    "agent": None,                       # 全量
    "ask":   READONLY_ALLOW | READONLY_ASK_ALLOW,
    "plan":  READONLY_ALLOW | READONLY_ASK_ALLOW | PLAN_ONLY_ALLOW,
}
```

**plan 模式如何限制**：`permissions/policy.py:410-438` `tool_allowed_in_mode` —— 非 agent 模式下，写工具按 `is_read_only` 旗标逐个判定（`:436` `tool_flag(tool, "is_read_only", default=False)`）。即**plan 模式把写工具从 schema 里摘掉**，而不是提示模型「先别写」。只读白名单由 `tools/meta.py:430-434` 从 `TOOL_META.read_only` 派生（单一来源，不是手写清单）。

**ExitPlanMode 只在 plan 模式可见**：`query_loop.py:610-621` 定义 schema；`:625-640` `_plan_tool_schemas()` 过滤现有工具表并在 `current_agent_mode() == "plan"` 时追加 `_EXIT_PLAN_MODE_SCHEMA`。

**闸门全流程**：`query_loop.py:2143-2230`

1. `:2143` `if current_agent_mode() == "plan" and exit_plan_use is not None:`
2. `:2146` 取消投机 early 任务（`_cancel_early_tasks`）——其它工具一律跳过
3. `:2155-2162` 计划正文取自 `ExitPlanMode.input.plan`，缺失则回退 assistant 文本；仍空 → 合成 `is_error=True` 的 tool_result + `FinalEvent`（`:2163-2171`）
4. `:2177-2186` `default_plan_engine().create(...)` → `PlanPendingEvent`
5. `:2187-2191` `await plan_engine.wait(pending.request_id)`（挂起等人工）
6. `:2205-2227` **批准分支**：写 `"Plan approved. Implement the approved plan."` 的 tool_result → `set_agent_mode("agent")` → `continue`

**关键点：第 6 步没有换 executor。** 批准后仍是同一个 `while True` 循环，带着 `approved_plan` 继续走 ReAct——所以它是**闸门**（gate），不是「plan 阶段 → execute 阶段」的两段式架构。

**计划的生命周期（批准后衰减）**：`query_loop.py:2745-2759` —— 批准后本 query 内**首次成功写盘**即调用 `prompt/pre_llm_inject.py::approved_plan_decays_on`，全量计划块静默、切成「实施中」指针块（`plan_pointer = True`）。即计划不是持续复述的指令，而是「契约仍在」的轻在场事实。

**挂起存储**：`engine/plan.py` —— `PlanEngine` 进程内、按 `turn_id` 索引、带 TTL（`PENDING_PANEL_TTL_SECONDS`）；`:76-88` `cancel_pending_for_session` 在 interrupt 时按**拒绝**处理并唤醒等待者（否则回合会挂死到 TTL）。

**入口是用户**：`python/slash/registry.py:147-148` `/mode <agent|plan|ask>`；HTTP 侧 `server/routers/chat.py` 透传；`engine/query_engine.py:738` / `query_loop.py:924` 每回合 `set_agent_mode(agent_mode)`。**没有「引擎自动进入 plan 模式」的代码路径。**

### 2.3 子代理：产线形态 ≠ 储备形态

**产线形态：模型在 ReAct 里派活，子代理自己也是 ReAct**

- 工具声明：`tools/agent_tool/prompt.py:4-17` DESCRIPTION ——「Spawn a short-lived scoped sub-agent… Multiple Agent calls in ONE turn run concurrently when their scopes are independent.」
- 并发机制：`tools/agent_tool/agent_tool.py:113-115` `is_concurrency_safe() -> True`（注释：同轮可并行多个 Agent，磁盘冲突由 WriteStore content-hash 收敛）；`tools/orchestration.py:85 partition_tool_calls` 按 `is_concurrency_safe` 分区（`:82` 缺失/异常默认 False，失败即关闭）。
- 子代理本体：`engine/subagent_runner.py:181 run_subagent` docstring「spawn 一个子 agent 并驱动 **query_loop**」⇒ 子代理是 ReAct 的递归实例，不是另一个范式。
- 递归与裁剪：`agent_tool.py:28 MAX_DEPTH = 1`（禁孙代理）；工具白名单由 `tools/meta.py:438-443` `SUBSET_TOOL_BASELINE` / `FORBIDDEN_SUB_TOOLS` + `engine/scheduler.py::build_tool_whitelist` 按 `scope` 裁剪（空 scope = 只读硬门禁）。
- **决策权**：`tools/agent_tool/prompt.py:20-24` 注释自陈「只告知事实（用户开启了 multi-agent），**不教模型怎么拆活——拆不拆、何时派由模型自决**」；`MULTI_AGENT_HINT` 正文只有一句「用户开启了 multi-agent（多代理）模式。」

**储备形态：LLM 分解 + 确定性 DAG（代码在，但没接产线）**

- 分解器：`engine/subagent_runner.py:995 _DECOMPOSE_INSTRUCTION`「你是多 Agent 任务编排器：**只拆任务，不写代码、不调工具**」→ 模型输出 `[{"id","desc","depends_on","scope","required_tools","timeout_s"}]`；`：1357 decompose_tasks_stream` 流式产出（先「分配说明」文本，再 JSON），`：1468 decompose_tasks` 为其包装。
- 执行器：`engine/scheduler.py:243 class Scheduler` docstring「确定性调度器（事件驱动 DAG + 文件级冲突 + 并发上限 + 超时 + 按 session checkpoint）」；模块头 `:1` 首句「**确定性多 Agent 调度器（非 LLM）**」。
- DAG 机制：`:44 depends_on`；`:108-122` 拓扑排序与就绪队列；`:320/347` 依赖未完成即不启动；`:727` 「depends_on 数据面：把已完成上游结论注入下游 prompt」；`MAX_DECOMPOSE_TASKS = 8`（`:27`）、`MAX_PATCH_RETRIES = 3`（`:26`）；`:1085 run_task_batch` 批量入口。
- **产线调用方核查（关键）**：全树 `grep -rn "decompose_tasks"` 仅命中定义处与 `tests/`；`run_task_batch` 同样只被 `tests/test_multi_agent_p1.py`、`tests/test_multiagent_hardening.py` 调用；`server/session_pool.py:1040 scheduler_for`（注释「HTTP 层做多任务分发的入口」）在 `server/` 内**无任何调用点**；`server/routers/` 下无调度器路由，`chat.py:1006-1023` 只做遗留 checkpoint 的**清理**。
- ⇒ 结论：**「LLM 分解 → 确定性 DAG 执行」这条链是储备，不是产线。** 产线的「多代理」= 模型在同轮发多个 `Agent` 工具调用。

**另一条储备**：`coord/`（`worker_pool.py` / `worktree.py` / `reconciler.py`）——`coord/reconciler.py:1-16` docstring「单点串行收敛…唯一允许写主分支的角色…三路合并（merge-base）…reopen 硬顶 `REOPEN_LIMIT` 熔断转 blocked」。`docs/面试知识书/07-第六册-扩展与多智能体.md:407-410` 明确「有两种范式，**一种在产线，一种在储备**…储备范式是跨进程 worker 池…**默认 backend 是 memory（进程内），不是真正的跨进程**」。

### 2.4 引擎确定性管线：不是 agent 范式

这几项常被误算进「Workflow」，但它们的共同特征是**不参与规划、不进模型注意力**：

- **预算 / 收尾**：`engine/budget.py:107 class BudgetTracker`（`:110` max_turns 限制的是模型 API 请求次数）、`engine/turn_runtime.py` 四态闸。
- **权限三态**：`permissions/policy.py:60-77 PolicyDecision`（decision / reason / prompt / matched_rule），`:80 _PERMISSION_MODES = ("always","risk","never","allow")`。
- **循环熔断**：`engine/loop_breaker.py:1` docstring 首句直接写明「循环熔断（LoopBreaker）—— 工具准入层的『**无进展路径持续报错**』（**铁律 #3 的执行层形态**）」，动作唯一：「该次调用不执行」，返回中性结果型 ToolResult，措辞零劝导。缘起是 2026-09-14 事故（同一条 Bash 连续重复 166 次）。
- **上下文压缩**：`memory/runtime.py` + `synaptic/`（WSC），`prompt/pre_llm_inject.py:1-13` 的 KV 前缀纪律。
- **回溯**：`rewind/hotpath.py`（v3 热路径，`python/ARCHITECTURE.md` 标注为现行默认）。

## 3. 为什么这样选

### 3.1 依据是项目自己的铁律（`AGENTS.md` 设计理念，2026-09-08 定稿）

> 总原则：**注意力里只出现信息，不出现导演**。
> 1. **只给信息**：模型可见的一切文本只承载状态/结果/事实。禁止建议、劝导、评价、奖励、惩罚、以及「应该/优先/不要再」式编排文本。
> 2. **模型自决**：调度、规划、执行的全部决策由模型自己做；**引擎不规划路线、不纠偏、不点评**。
> 3. **限制只在执行层**：引擎的限制永远存在，但只在执行层表达……报错措辞必须是中性结果型。
> 4. **能静默就不说话**：引擎自己能完成的事一律静默完成。
> 5. **弱模型护栏不做在引擎文本里**：护栏 = 执行层机制（DENY、报错、折叠）。

### 3.2 从铁律到结构的三条推论

1. **铁律 2 直接排除「引擎写死 workflow DAG」**。若引擎持有固定流程或自动规划器，路线决策就离开了模型 ⇒ 违反「引擎不规划路线」。故 Workflow 只能以**模型可主动调用的工具**形态存在（`Agent` 工具 / `decompose` 储备），不能成为主链路的常驻结构。这解释了为什么 `Scheduler` 写得完整却不上产线——它一旦接进主链路，就变成「引擎规划路线」。

2. **铁律 1 + 2 排除「强制先规划再执行」**。若每回合强制 Plan→Execute，等于引擎规定了两阶段路线，且要往注意力塞计划模板文本。故 Plan-and-Execute 被降级为**用户可选的模式闸门**：进入 plan 模式是人的选择（`/mode plan`），计划内容是模型自己写的，批准权在人，批准后**回落原循环**（`query_loop.py:2220` `set_agent_mode("agent")` + `continue`），引擎不新增执行阶段。

3. **铁律 3 决定「限制怎么做」**。plan 模式摘写工具用的是 `tool_allowed_in_mode` 的 schema 过滤（`policy.py:410-438`），不是提示词劝阻；循环失控用的是 `loop_breaker` 的「持续中性报错」（`loop_breaker.py:1` 自陈「铁律 #3 的执行层形态」）。⇒ 所有约束都在**执行层**，模型注意力里看不到「你应该…」。

### 3.3 这些铁律是机器执法的，不是口头约定

- **禁导演词有测试**：`python/tests/test_loop_ledger.py:26` `_FORBIDDEN = ("应该", "建议", "请", "勿", "优先", "推荐")`，`:41` / `:307` 对引擎产出的可见文本逐词断言。⇒ 「只给信息」是可回归的硬约束。
- **旁路优先有硬规矩**：`AGENTS.md` 硬规矩 4「新行为先以旁路形态（feature flag / 独立模块 / 钩子）上线验证收益，**有数据证明收益后才并入主链路**」。⇒ 储备路径（`Scheduler` / `coord` / `decompose`）停在储备状态，本身就是这条规矩的执行结果，不是半成品。
- **flag 是单一来源**：`engine/flag_definitions.py:4-15` `FLAGS` 字典（`XEYO_EXECUTION_FACT_CONTRACTS` 等）+ `:18 enabled(name)` 统一解析默认值/环境变量，`snapshot()` 可导出「默认值 / 生效值 / 来源 / 含义」——即每个旁路开关都可被审计。

## 4. 一处需要纠正的旧结论

上一轮口头回答把 `subagent_runner.decompose_*` + `engine/scheduler.py` 归为「子代理层的产线 Workflow」。**该归属不准确**，本次逐调用方核查后更正为：

| | 旧说法 | 实测 |
|---|---|---|
| `decompose_tasks*` | 产线路径 | **仅被 tests 调用**（全树 grep 无产线调用方） |
| `Scheduler` / `run_task_batch` | 子代理执行器 | **仅被 tests 调用**；`session_pool.scheduler_for` 无调用点 |
| `chat.py` 的 scheduler 相关代码 | — | 只做遗留 checkpoint 清理（`:1006-1023`） |

不影响主干结论（ReAct + Plan 闸），但「Workflow 是产线成分」应改为「Workflow 是储备成分」。产线的多代理 = 模型同轮多个 `Agent` 调用，每个子代理各跑一个 ReAct。

## 5. 为什么不是另外三个「纯」选项

- **不是纯 Workflow**：没有引擎持有的固定步骤序列。主循环的下一步永远由模型输出决定（`query_loop.py:1695` 之后无路线分支）；`Scheduler` 那种确定性 DAG 未接产线。
- **不是纯 Plan-and-Execute**：没有强制的规划阶段。plan 模式是 opt-in 的用户模式，且批准后**不切换 executor**（`:2220` 只切模式 + `continue`），计划本身还会在首次写盘后衰减成指针块（`:2755-2759`）。
- **不是纯 ReAct**：ReAct 无法解释三个真实存在的产线机制——① plan 模式的人批准闸（`engine/plan.py` 整套挂起/唤醒/TTL）；② 工具可用性随模式**结构性**变化（`policy.py:410-438` 摘工具，而非提示）；③ 引擎侧的四态回合硬停与执行层熔断（`turn_runtime.py` / `loop_breaker.py`）。这三者是「引擎在执行层强制」的成分，ReAct 定义里不含。

⇒ 准确标签：**ReAct 内核 + 可选 Plan 闸 + 子代理级 ReAct 递归 + 引擎执行层强制**。若必须用一个词，是 Hybrid，且混合的重心明确偏向 ReAct。
