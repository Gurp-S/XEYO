## 4. T4-0 实测（14 会话 / 112 对相邻状态点，工具台 `_wsc_out/_wsc2_phase40.py`、`_wsc2_phase40b.py`）

| 臂 | 公共前缀占比 p10/p25/**med**/p75/p90 | 整段 tok | 每枪必须重发 tok |
|---|---|---:|---:|
| V2 现状（CURRENT REQUEST 在前、段内按最近触碰倒序） | 0.005 / 0.042 / **0.138** / 0.435 / 1.0 | 839.5 | 583.5 |
| V2 稳定段序 + 稳定排序键（模拟，未改库） | 0.039 / 0.155 / **0.325** / 0.535 / 1.0 | 839.5 | **495.5** |
| V1 生产热层（整份，同点同尺） | 0.111 / 0.231 / **0.496** / 0.701 / 0.765 | 12,410 | **6,673** |

行数账（每对）：V2 新增 7 / 消失 3 / 留下 20.5；V1 新增 204 / 消失 172.5 / 留下 182。
"126/126 每枪都变"在这批点上是 **100/112 变**（12 对完全相同）。

**破坏前缀的是哪一段**（V2 分歧首段分布，112 对）：
CURRENT REQUEST 32、WORKING SET 21、UNRESOLVED 20、（无变化 13）、CONSTRAINTS 12、OPEN REQUESTS 9。

四条结论：

1. **V2 输在占比、赢在绝对量**：占比 0.138 vs V1 0.496，但每枪重发 583 tok vs 6,673 tok
   ⇒ V2 的重发面只有 V1 的 **8.7%**。传输层要优化的是这个绝对量，不是把占比追平 V1。
2. **单号排序键是主要自伤**：现状段内按"最近触碰"倒序 ⇒ 一条旧事实被 `mark_used` 就整段重排。
   模拟里只改顺序（段序把易变段后置 + 段内 `(created_index, fact_id)`，逐字保持与生产相同的行文本）
   就把占比 0.138→0.325、重发 583.5→495.5 tok（**−15%**）。
   ⇒ "只追加"与"稳定排序"在这批数据上**逐位相同**（新事实天然落在段尾），不需要两套机制。
3. **大头在差分，不在排序**：留下 20.5 行没变却被整段重发 ⇒ T4-2/T4-3 的理论上限是把
   495 tok 压到"新增 7 + 消失 3 行"的量级。这才是 Phase 4 的主收益来源。
4. **CURRENT REQUEST 该不该排到最后**是模型可见顺序的取舍（V1 也是把 `[REQUESTS]` 排在固定段之后），
   不该由"更稳定"这一条理由替作者定 ⇒ 留给用户裁（§6 D4）。

## 5. 对工单门槛的一处修订建议

T4-1 原判据写的是"公共前缀占比 ≥0.85"。T4-0 表明**单纯排序改动到不了**（0.325，上限受
"每对总有 1~2 行易变段在前部"制约）⇒ 建议改成两条一起判：

- T4-1：**每枪必须重发的 tok 下降**（目标 ≥10%，实测模拟值 −15%）且占比不降；
- 占比 ≥0.85 这条**挪给 T4-3 的 B 臂**（差分台账才可能做到，因为未变段可以整段不重发）。

  要不要？不要的话 T4-1 只剩"段内稳定排序"，收益约在一半以内。
- **D1/D2/D3 已裁**：占比当主判据（¥ 只给区间）；先 B 后 C；付费冒延后单独问。

## 8. Phase 4 **判死**（2026-09-23 当日，用户质疑后用量本验证）

用户原话：「WSC 简单来说就是压缩算法，压缩就那么一次，只要不影响正常的就 OK，所以追求命中率
用处不大；压缩必然破坏前缀，只要压缩后 3 枪命中率回来即可。」——**这句话是对的，而且不用猜，
账本能量**。

### 8.1 我错在哪

我把"**离线渲染文本每枪变了多少字节**"直接当成"**每枪要花多少钱**"。这两者中间隔着**厂商前缀缓存**，
而我没验。`_wsc_out/_fold_recovery.py` 用真实厂商账本量了一次：`~/.xeyo/usage/events.jsonl` 的
`cache_hit/cache_miss` 是**厂商回报**的 `prompt_cache_hit_tokens`（`python/usage/pricing.py:150`），
不是我们的估算。

### 8.2 实测（9,053 条真实请求 / 175 会话，其中 94 会话有折叠事件；总 ¥132.558）

| 桶 | n | prompt tok 中位 | **miss tok 中位** | **命中率中位** | ¥ 占比 |
|---|---:|---:|---:|---:|---:|
| 折叠后第 1 枪 | 2,295 | 40,133 | **1,041** | **0.969** | 19.2% |
| 折叠后 ≥7 枪（稳态） | 278 | 340,374 | **197** | **0.999** | 7.9% |
| 该会话从未折叠 | 6,451 | 46,538 | 1,238 | 0.969 | 72.3% |
| 折叠后第 2…6 枪 | 15/7/3/2/2 | — | 3,619 / 5,418 / 8,289 / 3,691 / 606 | 0.75~0.98 | ~0.6% |

三条读法：

1. **折叠破坏的前缀只有 ~1k tok/枪**，而一次请求的 prompt 中位是 40k ⇒ 命中率 0.969。
   稳态更是 miss 197 tok、命中 **0.999**。
2. 我在 T4-0 里追的目标是 **88 tok/枪**（583.5→495.5）。放到真实请求上是 **0.2%**，
   而且稳态 miss 只有 197 tok ⇒ 这 88 tok 大概率本来就被缓存吸收了。⇒ 排序/差分台账**没有钱**。
3. **"3 枪回来"这条本账本量不出来**，但不是因为没发生：94 个会话里有 3,373 次折叠
   ⇒ 平均每 3~4 枪就折一次，`k≥2` 的桶只剩 15/7/3/2/2 条样本。**折叠太密把恢复曲线吃掉了**。
   这句话要说准，不能挑对自己有利的读数。

### 8.4 一处旧账的更正（就是我为什么会被自己的记忆带偏）

我脑子里挂着一条"p7 真跑：折叠枪未命中面 **9,725** vs 平枪 **1,839**"，据此认定折叠枪的前缀损失很大。
去 `fold_events.jsonl` 核了一遍：那批数只有 **12 行、且全来自同一个会话**（`raman-fitting__tgFZgk9__agent`），
字段是 `transition`（max 9,721）/`region_tokens`（max 6,100）/`saved_net`（max 5,961）——
**都是"我们自己账面移动了多少 token"，不是"厂商未命中多少 token"**。
所以那句"折叠枪未命中面 9,725"从一开始就是口径错标：它是**压缩量**，不是**计费未命中面**。
本节表里的 1,041 / 197 才是后者（厂商回报的 `cache_miss`）。

⇒ 两条硬结论：① 以后引用"未命中面"必须写清查的是 `events.jsonl` 的 `cache_miss`
还是 `fold_events` 的 `region/transition/saved_net`，两者差一个量级；② 折叠当枪的**厂商实测样本
仍然只有 1 个会话 12 次**（工单 #11 未还），任何"折叠经济学"的普适说法都没有数据底座。

### 8.5 这轮真正该记住的一句

**压缩的成本不在"每枪重发"，在"那一次折完之后头里还剩没剩对东西"。**
所以力气回到：V2 的头能不能替 V1（质量轴，§6/§12/§14/§15 那套召回/precision），
以及 72% 的花费落在从未折叠的会话上（覆盖面轴，与"TB 跑分从来没开 WSC"同一条）。

### 8.6 方法论（这条比结论长）

口径陷阱的第四个兄弟：发射量≠厂商请求（1.7×）、状态段≠整份投影、model 乐观 8~9%，
这次是 **渲染文本变化量 ≠ 计费未命中量**。凡是拿"我们生成了多少字节"去推钱，
中间必须先插一步"**厂商实际未命中多少**"，而这一步在本仓库**有账可查**，不该省。
