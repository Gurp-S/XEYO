## 1. 为什么现在只做传输层

#31 把 V2 的文件语义补平到 V1 之后，尺寸优势被削掉一半（§12 整份比 0.5400→0.5642、
状态段比 0.0688→0.0943），而 Phase 1 那条"相邻两枪 126/126 状态哈希全变"一直挂着。
⇒ 语义层已到位，剩下的钱只在**每枪必须重发多少**。

## 2. 目标函数（D1 已裁）

主判据 = **相邻两枪的公共前缀 tok 占比**（字符级最长公共前缀，再按生产尺 `memory.token.token_len`
折算；每台探针启动时自检 `prod == wsc2`，不许用 `len/4` 冒充）。
理由：前缀命中是厂商计价的唯一入口。¥ 只按 DeepSeek 命中/未命中 30× 价差换算成**区间**，
**不当判据**，且必须带上"发射量≠厂商请求（实测 1.7×）"这句。

## 4. T4-0 实测（14 会话 / 112 对相邻状态点，工具台 `_wsc_out/_wsc2_phase40.py`、`_wsc2_phase40b.py`）

| 臂 | 公共前缀占比 p10/p25/**med**/p75/p90 | 整段 tok | 每枪必须重发 tok |
|---|---|---:|---:|
| V2 现状（CURRENT REQUEST 在前、段内按最近触碰倒序） | 0.005 / 0.042 / **0.138** / 0.435 / 1.0 | 839.5 | 583.5 |
| V2 稳定段序 + 稳定排序键（模拟，未改库） | 0.039 / 0.155 / **0.325** / 0.535 / 1.0 | 839.5 | **495.5** |
| V1 生产热层（整份，同点同尺） | 0.111 / 0.231 / **0.496** / 0.701 / 0.765 | 12,410 | **6,673** |

行数账（每对）：V2 新增 7 / 消失 3 / 留下 20.5；V1 新增 204 / 消失 172.5 / 留下 182。
"126/126 每枪都变"在这批点上是 **100/112 变**（12 对完全相同）。

**破坏前缀的是哪一段**（V2 分歧首段分布，112 对）：
CURRENT REQUEST 32、WORKING SET 21、UNRESOLVED 20、（无变化 13）、CONSTRAINTS 12、OPEN REQUESTS 9。

四条结论：

1. **V2 输在占比、赢在绝对量**：占比 0.138 vs V1 0.496，但每枪重发 583 tok vs 6,673 tok
   ⇒ V2 的重发面只有 V1 的 **8.7%**。传输层要优化的是这个绝对量，不是把占比追平 V1。
2. **单号排序键是主要自伤**：现状段内按"最近触碰"倒序 ⇒ 一条旧事实被 `mark_used` 就整段重排。
   模拟里只改顺序（段序把易变段后置 + 段内 `(created_index, fact_id)`，逐字保持与生产相同的行文本）
   就把占比 0.138→0.325、重发 583.5→495.5 tok（**−15%**）。
   ⇒ "只追加"与"稳定排序"在这批数据上**逐位相同**（新事实天然落在段尾），不需要两套机制。
3. **大头在差分，不在排序**：留下 20.5 行没变却被整段重发 ⇒ T4-2/T4-3 的理论上限是把
   495 tok 压到"新增 7 + 消失 3 行"的量级。这才是 Phase 4 的主收益来源。
4. **CURRENT REQUEST 该不该排到最后**是模型可见顺序的取舍（V1 也是把 `[REQUESTS]` 排在固定段之后），
   不该由"更稳定"这一条理由替作者定 ⇒ 留给用户裁（§6 D4）。

## 5. 对工单门槛的一处修订建议

T4-1 原判据写的是"公共前缀占比 ≥0.85"。T4-0 表明**单纯排序改动到不了**（0.325，上限受
"每对总有 1~2 行易变段在前部"制约）⇒ 建议改成两条一起判：

- T4-1：**每枪必须重发的 tok 下降**（目标 ≥10%，实测模拟值 −15%）且占比不降；
- 占比 ≥0.85 这条**挪给 T4-3 的 B 臂**（差分台账才可能做到，因为未变段可以整段不重发）。
