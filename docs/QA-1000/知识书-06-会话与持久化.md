## 2. 为什么用 JSONL（`persistence.py` 62 行）

```python
def default_sessions_dir() -> Path:
    override = os.environ.get("XEYO_SESSIONS_DIR", "").strip()
    if override: return Path(override).expanduser()
    return Path.home() / ".xeyo" / "sessions"

def transcript_path(session_id, *, sessions_dir=None) -> Path:
    return (sessions_dir or default_sessions_dir()) / f"{safe_session_filename(session_id)}.jsonl"
```

**五个收益**：追加即落盘（**O(1) 而非 O(n)**）· 崩溃只损尾部（前半完好）· 可轮转（改名即可）· 可重放（事件化回溯直接追加）· 可人工查看（`tail`/`grep`）。

**不选数据库**：单机单用户、写已串行化、无跨会话查询需求（除 `ws_index` 那种小索引）。SQLite 只用于**派生索引**。

### 2.1 文件名安全化（**有真实缺陷**）

```python
    for ch in raw:
        if ch == ":": parts.append("__")            # 冒号 -> 双下划线（可识别替换）
        elif _SAFE_CHAR.match(ch): parts.append(ch) # 白名单 [A-Za-z0-9._-]
        else: parts.append("_")
    name = "".join(parts).strip("._") or "session"
    if len(name) > _MAX_FILENAME:                   # 180
        digest = hashlib.sha256(raw.encode()).hexdigest()[:16]
        name = name[:160].rstrip("._-") + "_" + digest
```

★ **「截断 + 哈希」的组合是关键**：只截断 ⇒ 不同 id 映射到同一文件（静默串会话）；只哈希 ⇒ 失去可读性。

★★ **但该函数不是单射（面试可指出的缺陷）**：

| id A | id B | 替换后 |
|---|---|---|
| `s:1` | `s__1` | 都是 `s__1` |
| `a/b` | `a_b` | 都是 `a_b` |
| `S1` | `s1` | Windows 上**同一文件**（大小写不敏感） |

修法（结构性）：**始终带短哈希后缀**（`name[:120] + "_" + sha256[:16]`），把「可读前缀」与「唯一性」彻底分离——而不是继续增加替换规则。

## 3. 写入路径（**最高频面试题**）

### 3.1 全貌

```
调用方：去重（按 message id 的内存集合）          ← 去重在提交侧，不在写入线程
      -> submit_async_append（入队，带单调 seq）
后台线程：取整批 -> 按 path 分组 -> 锁内 { mkdir + rotate 检查 + append + flush + fsync }
调用方判定：flush_pending_sync(timeout) 用「写入 seq >= 提交 seq」
退出：atexit 排空（2s）+ 写入线程 daemon=True
```

### 3.2 两个序号与 flush 判据（`record_transcript.py:41-45,183-191`）

```python
# 后台写入队列：(seq, path, line)。seq 单调递增，用于 flush 判定「全部落盘」。
_pending: list[tuple[int, str, str]] = []
_cv = threading.Condition()
_submitted_seq = 0 ; _written_seq = 0

def flush_pending_sync(timeout: float = 5.0) -> bool:
    """阻塞等待所有已提交行落盘；返回是否在超时前排空。"""
    deadline = time.monotonic() + timeout
    with _cv:
        while _written_seq < _submitted_seq:
            if time.monotonic() >= deadline: return False
            _cv.wait(0.2)
        return True
```

★★ **判据必须用序号，不能用「队列为空」**——出队与真正写盘是两件事；用队列空判断会在「已出队但未 write 完」的窗口里**误判成功**，这正是「flush 假成功」的经典写法。

★ 返回值语义：`True` = 超时前排空；`False` = **超时**（**不代表丢失**，但**不能假设已落盘**）。反模式：`if not flush(): pass`（把 False 当噪音）或 `assert flush()`（磁盘繁忙时崩掉会话收尾）。

### 3.3 两把同步原语（**面试常问的分离**）

| 原语 | 保护对象 | 持有时间 |
|---|---|---|
| `_cv = threading.Condition()`（`:43`） | **内存队列与序号**（`_pending` / seq） | 短（入队/出队） |
| **`_disk_lock = threading.Lock()`**（`:36-39`） | **磁盘操作**：`mkdir + rotate + append + fsync` | 长（含 fsync，几十毫秒） |

`_disk_lock` 的注释（G107）给了它存在的**具体理由**：

```
# 防止 rotate(rename 当前→归档)与另一路 append 交错:写者把行追加进已轮转的
# 归档或新文件出现重复/丢行。
```

★ 若合并成一把锁：`fsync` 期间会**阻塞入队** ⇒ 写者被 I/O 拖住、队列积压。

### 3.4 批量写的分组（`:143-157`）

```python
def _write_batch(batch):
    by_path = {}                                  # 按 path 分组（一进程可服务多会话）
    for _seq, path, line in batch: by_path.setdefault(path, []).append(line)
    for path, lines in by_path.items():
        with _disk_lock:
            p.parent.mkdir(parents=True, exist_ok=True)
            _maybe_rotate(p)
            with p.open("a", encoding="utf-8") as f:
                f.writelines(lines); f.flush(); os.fsync(f.fileno())
```

| 点 | 理由 |
|---|---|
| 按 path 分组 | 避免「每行开一次文件」 |
| `open("a")` | **不重写已有内容**（O(1) 写的前提） |
| `flush()` + **`fsync()`** | flush 只把缓冲推到 **OS page cache**；**fsync 才要求落盘** |
| 批次边界 | 由「队列当前全部」决定 ⇒ 高负载批更大、空闲逐行写 |

★ **同 path 组内顺序 = 入队顺序**（batch 按 seq 递增取出）⇒ 会话消息顺序有保证。

### 3.5 去重记账（`:33-34,220-233`）

```python
_known_ids_cache: dict[str, set[str]] = {}     # 按 transcript 路径缓存已写 id

def _resolve_known_ids(path, known_ids):
    """优先复用调用方传入的 known_ids，并写入路径级缓存。"""
    if known_ids is not None:
        _known_ids_cache[key] = known_ids
        if not known_ids and path.is_file():    # 空集合 => 从磁盘补齐
            known_ids.update(_load_written_ids(path))
        return known_ids
    ...
```

★ **架构决策：去重在提交侧、异步写只负责写**。收益：写入线程无跨会话状态、判重不依赖磁盘。代价：**多进程缓存不一致**（各自知道自己全部 id）⇒ 跨进程写同一会话会产生**重复行**。
★ 注释契约（`:171`）：「调用方**必须已完成去重记账**（`known_ids` 就地更新）」。

### 3.6 崩溃窗口（**面试压轴**）

四层缓冲：① Python 缓冲（`flush()` 关掉）→ ② OS page cache（**`fsync()` 关掉**）→ ③ 盘自带写缓存（硬件）→ ④ 稳定介质。

**四个丢尾窗口**：

| # | 窗口 | 能否关掉 |
|---|---|---|
| 1 | 行还在**内存队列**里（SIGKILL/断电，`atexit` 没跑） | ❌ async 结构固有 |
| 2 | 已出队但**未写** | ❌ 同上 |
| 3 | 已写但**未 fsync** | ✅ 已由 `os.fsync` 关掉（G107 修复核心） |
| 4 | fsync 返回但**盘缓存未落** | ❌ 硬件层 |

★ `atexit` 只等 **2.0s**（`flush_pending_sync` 默认 5.0s），且写入线程是 **daemon=True**（主线程退出即被强杀）⇒ 这是「**尽力窗口**」而非保证。
★ **正确的工作立场**：不承诺「不丢」（转录是「尽力持久化的权威记录」）+ 缩小窗口（flush+fsync、atexit 排空）+ **用未闭合修复兜住可用性**（会话能继续）；关键节点（回合边界）才同步 flush 并**检查返回值**。

## 4. 轮转与归档链

### 4.1 阈值与代数

```python
def _max_transcript_bytes() -> int:
    """默认 32MB，可用 XEYO_TRANSCRIPT_MAX_BYTES 覆盖（下限 1MB）。"""
    return max(1024, int(raw)) if raw else 32_000_000
_ROTATION_KEEP = 2
```

★ 阈值按**字节**而非条数（单条消息可以很大）；`max(1024, ...)` 下限防「阈值设 0 ⇒ 每次写都轮转」。

### 4.2 命名与读取顺序（**反直觉**）

```python
def rotated_transcript_paths(path):   # 按「最旧 -> 最新」：old2, old1
    return [path.with_name(path.name + f".old{i}") for i in range(_ROTATION_KEEP, 0, -1)]
def transcript_read_paths(path):      # [归档…]（存在者）+ 当前
    return [p for p in rotated_transcript_paths(path) if p.is_file()] + [path]
```

★ **`i` 越小越新**（`.old1` 比 `.old2` 新）；轮转方向是「`.old1` → `.old2`、当前 → `.old1`」。
★ `rotated_transcript_path`（单数）是兼容旧调用方的便捷函数（只给 `.old1`）。

### 4.3 轮转实现（顺序不能错）

```python
    olds = rotated_transcript_paths(path)   # [old2, old1]
    if olds[0].is_file(): olds[0].unlink()  # ① 先删最旧
    for i in range(len(olds) - 1):
        if olds[i].is_file(): os.replace(olds[i], olds[i+1])   # ② 从旧到新挪
    os.replace(path, olds[-1])              # ③ 当前 -> old1
```

| 顺序错法 | 后果 |
|---|---|
| 先挪当前再挪归档 | `old1` 被覆盖 ⇒ **丢一代历史** |
| 从新到旧挪 | 覆盖 `old2` |

★ 用 `os.replace`（**同卷原子改名**）而不是「复制 + 删除」（非原子、临时双倍空间）。
★ 整段包 `try/except OSError` 只记 `debug` ⇒ **轮转失败不阻断写入**（最坏是文件继续变大，而不是写不进去）——可用性优先。

### 4.4 读侧必须读归档（`record_transcript.py:100-102` + `hydrate.py:119-133`）

```python
    rows = []
    for p in transcript_read_paths(path): rows.extend(load_transcript(p))
    return messages_from_rows(resolve_transcript_rows(fold_surface_rows(rows), path))
```

**顺序必须是「最旧 → 最新」**，因为：① 消息列表要时间序；② `fold_surface_rows` 依赖「从可见面**末尾反向**定位 `shadow_from`」（顺序错则定位错）；③ `_load_written_ids` 也遍历同一函数。

★ 由此推出**轮转阈值不能太小的第二个理由**：每次恢复要读**全部归档 + 当前**（≤96MB），32MB × 3 就是「磁盘 vs 恢复速度」的平衡点。

### 4.5 回滚必须清归档（**已删内容复活**）

```python
def discard_rotated_transcripts(path):
    """删除轮转归档，防止 rollback 截断后 GET/hydrate 把已删回合再拼回来。
    返回已删除路径的字符串列表（便于审计）。当前 ``path`` 本身不动。"""
```

**故障机制**：回滚（物理重写）通常只处理**当前** jsonl；归档里的旧行还在，而读侧会把归档一起读回来 ⇒ 用户看到「我回滚了但那些回合又出现了」。

★ 危害不只是体验：① **用户以为删掉了**（隐私/合规：以为删了敏感对话）；② **上下文复活**（已删内容重新进模型上下文，影响未来行为）。
★ 残留风险：删除失败只 `_logger.debug` ⇒ **清归档失败是静默的**，而失败后果正是「复活」。方向应为「降级留审计」（对照 `tool.spill` / `memory.aging.advance` 都有审计）。

## 5. 大内容外置（`transcript_blobs.py` 115 行）

```python
def blob_threshold_bytes() -> int:   # 默认 32_768（XEYO_TRANSCRIPT_BLOB_THRESHOLD，下限 512）
def blobs_dir(anchor):  return anchor.parent / f"{anchor.stem}.blobs"
def blob_file(anchor, message_id): return blobs_dir(anchor) / f"{message_id}.json"
```

**写入**（同步、原子）：

```python
    payload = json.dumps(content, ensure_ascii=False).encode("utf-8")
    digest = hashlib.sha256(payload).hexdigest()
    tmp = target.with_suffix(".json.tmp"); tmp.write_bytes(payload); os.replace(tmp, target)
    return (f"{message_id}.json", f"sha256:{digest}", len(payload))
```

★ **同步写**的理由：外置是「行写入的前置条件」（行里要放 `content_ref`）⇒ 必须**先 blob 后行**（写序正确：反过来每次崩溃都产生悬空引用）。

**行内留下**：`content_ref`（文件名）+ `content_hash`（`sha256:<hex>`）。

**还原**（`resolve_transcript_row`）：行内 `content` 优先 → 否则按 `content_ref` 读；`path = blobs_dir(anchor) / Path(ref).name`（**只取 basename，防路径逃逸**）；缺失/坏 JSON → `content = ""`。

★ **三处缺口（面试可指出）**：① 空串与「真·空内容」**不可区分**；② **无审计**；③ 有 `content_hash` 却**不校验** ⇒ 无法发现「blob 被换成别的内容」。改进：可辨识占位（`[blob missing: <ref>]`）+ 审计 + 哈希校验，同时保持「不阻断恢复」。

**五个不一致窗口**：① blob 写好行没写 = **孤儿 blob**（无 GC）；② 行写好 blob 没写 = **悬空引用**；③ blob 写一半（半 JSON）；④ 外部改/删；⑤ 都成功但内容不符（不检测）。

## 6. 水化（hydrate）与会话恢复

### 6.1 四步流水线（`hydrate.py:119-151`）

```
① 读全部归档 + 当前（时间序）        OSError -> 返回 []
② fold_surface_rows（影子化已回滚行） 无 marker 时恒等（老日志兼容）
③ resolve_transcript_rows（blob 还原）缺失/坏 -> 空内容
④ messages_from_rows（行 -> Message + 未闭合修复）  坏行跳过
```

★ 顺序收益：**先 fold 再 resolve** ⇒ 被隐藏的行不必解析 blob（省 I/O）。
★ ④ 不可省：它补上「**合法消息序列**」这一不变量（见 6.2），否则下游 provider 会报错。
★ 配套 `surface_rows_for_session`（`:136-147`）产出**与 hydrate 同一视图的 rows**（供 todo 恢复、回溯目标定位消费）——「同一可见面两个出口」。

### 6.2 未闭合工具调用的修复（**面试高频**）

```python
		for uid, name in uses:
			if uid in have: continue
			if name in readonly:
				text = f"[{name}] TOOL_NOT_STARTED — 上一进程在工具开始前中断；该调用未执行。"
			else:
				# F5 裁决：纯事实；防重放副作用由引擎执行层承担
				# （write_store missing_read 门 / unchanged 短路 / 语法门）。
				text = f"[{name}] TOOL_OUTCOME_UNKNOWN — 上一进程中断且该调用可能已执行。"
			out.append(tool_result_message(uid, name, text, is_error=True))
```

| 工具类型 | 文案 | 语义 |
|---|---|---|
| **只读**（`READONLY_ALLOW`） | `TOOL_NOT_STARTED` | 未执行（可安全重跑） |
| 其它（有副作用） | `TOOL_OUTCOME_UNKNOWN` | **可能已执行** |

★ 三条设计要点：① **合成而非丢弃**（丢掉 `tool_use` 会让消息序列非法）；② 标记 `is_error=True`（「这条没有可靠结果」本身是**事实**）；③ **不替模型做决定**——不在文案里写「请重试/不要重试」，防重放靠**执行层门**。
★ 若把有副作用的调用也说成「未执行」，会诱发**重复副作用**（重复提交/删除）。

### 6.3 防重放的三道执行层门（跨到 B03/B04）

| 门 | 机制 | 覆盖 |
|---|---|---|
| `write_store` 的 `missing_read` 门 | 写必须有 base hash；无读记录 → 拒绝 | 文件写（走 Write/Edit） |
| `unchanged` 短路 | 内容与磁盘一致 → 跳过落盘 | 同上 |
| base hash / 语法门 | 内容变或 base 不符 → 拒绝/提示 | 同上 |

★ **覆盖边界**：`Bash` 命令（安装、网络请求）、`SendToWeChat`、外部 API 调用**没有 base hash 语义** ⇒ 重放 = 真的又做一次。所以**不承诺「恢复后不重放副作用」**，而是靠「权限 ASK + 可撤销（rewind/快照）」兜底。

## 7. 事件化回溯（`surface.py` 150 行）

### 7.1 两条回溯路径的取舍

| 维度 | v2 物理重写 | v3 事件化 |
|---|---|---|
| 日志大小 | **小**（真删） | 大（行还在） |
| 恢复成本 | 低（不必 fold） | 每次读多一遍 fold |
| **可撤销** | ❌ | ✅ `rewind_undo` |
| 可审计 | 弱 | ✅ 完整历史 |
| 一致性风险 | 高（归档也要清，否则复活） | 低（只追加） |
| append-only | 破坏 | 保持 |

★ **两者互补而非替代**：事件化给「可撤销 + 可审计」，物理重写给「日志体积」。衔接的安全性依据：`active_markers` 的 docstring ——「fold 对『marker 在、影子首行缺失』**保守不隐藏**，因此**回填 active marker 永远方向安全**」。

### 7.2 fold 的语义（`:68-102`）

```python
		if op == _OP_REWIND and rid not in undone:
			frm = str(row.get("shadow_from") or "")
			if frm in visible:
				idx = len(visible) - 1 - visible[::-1].index(frm)   # 末尾反向定位
				hidden_by[rid] = visible[idx:]                       # 保存连续一段
				visible = visible[:idx]
		elif op == _OP_REWIND_UNDO and rid not in undone:
			undone.add(rid)
			back = hidden_by.get(rid)
			if back: visible.extend(back)                            # 顺序 = 原日志顺序
```

| 规则 | 说明 |
|---|---|
| `rewind` | 从可见面**末尾反向**定位 `shadow_from`，其自身**与之后全部可见行**被影子化（对齐 v3「target 一并被移除」） |
| `rewind_undo` | 恢复该 marker 影子化的行，**恢复顺序 = 原日志顺序**；重复 undo **幂等**（`undone` 集合） |
| 找不到 `shadow_from` | **保守不隐藏任何行** |
| 无 id 的行 | **原样透传**（fold 不参与其可见性判定） |

★ 三处**保守分支**的「若反向」后果：① 找不到就清空 ⇒ **误删不可逆**；② 给无 id 行编临时 id ⇒ 与持久 id 体系混用、回溯指错行；③ `rid` 空也建条目 ⇒ `hidden_by[""]` 被所有空 rid marker **共用**、隐藏集合错乱。
★ 共同原则：**数据不完整时 fold 选择「少做事」（= 少隐藏，安全侧）**。
★ 「无 id 行透传」还有一个隐含收益：**fold 与行 schema 演进解耦**。

★ **fold 的正确性依赖一条协议前提**（非实现内自证）：注释写「服务端在追加 undo marker 前已**保证 marker 之后无新可见行**，因此 extend 不会造成乱序」。若该前提被破坏，undo 后会出现「新行 + 恢复的旧行」**顺序错乱**——fold 自身**不校验**这一点。

## 8. workspace 归属索引（`ws_index.py` 130 行）

```python
def index_path() -> Path: return _sessions_dir() / "_workspace_index.jsonl"
def _read_all() -> dict[str, str]:   # {session_id: workspace_id}（**后行覆盖前行**）
_cache: dict[str, str] = {} ; _loaded = False
def _ensure_loaded():                # 懒加载一次
    if not _loaded: _cache.update(_read_all()); _loaded = True
```

| 设计点 | 说明 |
|---|---|
| 位置 | 与转录**同目录**（`~/.xeyo/sessions/`） |
| 语义 | **一对一映射**（`out[sid] = wsid`，后写胜） |
| 坏行 | `json.loads` 失败 → `continue`（脏行不让整份索引失效） |
| 读失败 | `except OSError: return dict(_cache)`（**不丢已有知识**、不抛错） |
| 写入 | `record_session_workspace`：「同会话同工作区**幂等不写盘**」，失败只 debug |

★ **为什么不扫转录**：转录里**没有**工作区信息，而「按工作区列会话」是 UI 高频需求；扫描成本 O(会话数 × 文件大小)。
★ **「幂等不写盘」很重要**：会话每轮都登记，不判重会让索引无限膨胀。
★ **跨进程一致性缺口**：`_loaded` 是进程级一次性 ⇒ 他进程追加的行**本进程看不到**（直到重启）。与 `timeout_map._OVERRIDES` 的 lazy singleton 同一模式。
★ 语义局限：无法表达「会话曾属于 A，现在在 B」或「属于多个工作区」；若需要，应改成**带时间戳的事件行**。

## 9. 内存消息存储与状态对象

### 9.1 `MessageStore`（55 行）

| 层 | 特点 |
|---|---|
| 内存态 `MessageStore` | 快、进程内、可追加与截断；进程退出即失 |
| 持久态 transcript | 追加写、权威、可跨重启恢复 |

★ **两者不是等价关系**：「转录 = 全部事件（含被 fold 影子化的行），内存态 = 当前可见面」——所以「以谁为准」要按用途区分。
★ 由「转录权威」推出的正确性要求：**内存态每次变更都必须同步到转录**，否则重启后状态回退。

### 9.2 `SessionState` 与 `cwd`

**状态对象的判据**（面试好用）：

```
若这条信息丢了，能否从转录重建？
  能   -> 属于状态（派生，丢了没关系）
  不能 -> 必须进转录（权威）
```

`state.py`(102) 侧另有 `os_path_fallback`（`:87-101`）⇒ **状态要容忍路径形态差异**（长路径、相对路径、不同分隔符）。

`cwd.py`(72) 四项 API：`get_original_cwd()`（会话启动目录，不变）/ `get_cwd(*, _skip_context=False)`（当前目录，默认走**会话上下文**）/ `set_cwd(...)` / `reset_cwd_for_tests(...)`。

**三层解析优先级**：显式传入（工具 `working_directory` / `context.cwd`）> 会话级 `WorkspaceContext.cwd` > `os.getcwd()`。
★ **必须优先走会话上下文**：`os.getcwd()` 是**进程级**的，多会话并发会**串目录**（`filesystem.default_permission_context` docstring 明确写了这条理由）。
★ `_skip_context` 供需要「真值而非会话视图」的调用方；`reset_cwd_for_tests` 说明 cwd 是**隐式全局状态**。

## 10. 三种「内容落盘」机制对照（**面试常问的对照题**）

| 维度 | **转录轮转** | **blob 外置** | **spill 落盘** |
|---|---|---|---|
| 位置 | `sessions/*.jsonl.oldN` | `sessions/<stem>.blobs/*.json` | `~/.xeyo/spill/<session>/*.txt` |
| 触发 | 单文件 > **32MB** | 单条 content > **32KB** | 工具输出超预算（registry 16k 或工具自带） |
| 目的 | **控制单文件大小** | **保持行瘦** | **保留证据** |
| 谁读回 | hydrate 自动拼（**透明**） | `resolve_transcript_row`（**透明**） | **模型显式 Read**（不透明，需行动） |
| 保留期 | 2 代 | 随会话目录 | **7 天**（`XEYO_SPILL_RETENTION_DAYS`） |
| 失败降级 | 只记 debug（文件变大） | 给空内容（恢复不失败） | **原样返回不截断**（宁可超预算，不可假证据） |

★ **三者的失败方向不同，因为失败后果不同**——这是这张表最该记住的一点。
★ 统一原则：**内容有多个副本时必须说清谁是权威**（本项目答案：转录/文件是权威；轮转只是搬运、blob 是外置、spill 只是证据）。

## 11. 崩溃点状态矩阵（面试压轴）

```
① submit_async_append（入队）        -> 内存
② _write_batch 开始（取批）          -> 内存
③ write_content_blob（外置）         -> 磁盘
④ 行写入 jsonl（writelines/flush）    -> page cache
⑤ fsync                              -> 稳定介质
```

| 崩溃点 | blob | 行 | 恢复表现 | 需要修? |
|---|---|---|---|---|
| ①/② | 无 | 无 | 该消息**不存在**（少一轮） | 不需要（未提交） |
| ③ | **有** | 无 | **孤儿 blob**（不可见、占空间） | ✅ 需 GC（**当前无**） |
| ④ 批中崩 | 有 | 部分 | 部分行在、最后一行可能残缺 | 需「坏行跳过」+ 未闭合修复 ✅ |
| ④' `tool_use` 无 result | 有 | 有 | hydrate 补 `TOOL_OUTCOME_UNKNOWN` ✅ | 已处理 |
| ⑤ 前断电 | 有 | 有（cache） | 可能丢最后若干行 | ❌ 无法完全避免 |
| surface marker 之后 | — | marker 在 | fold 正常隐藏 ✅ | 已处理 |
| **物理重写中途** | — | 部分删/归档未清 | 内容**部分复活** | ❌ 需原子化（写新文件 + `os.replace`，再清归档） |

★ 复现方法（可答）：**fault injection** —— monkeypatch `_write_batch`/`os.replace`/`fsync` 抛异常或 `os._exit`，逐点崩后跑 `hydrate`，比对「期望可见面」与「实际可见面」。

## 12. 「同一 ID 出现两次」的成因总账（面试压轴）

| # | 成因 | 机制 | 区分方法 |
|---|---|---|---|
| 1 | **去重失效**（两路都判「未写过」，竞态） | 同一 id 写两行 | `grep` 计数同一 id 是否两行 |
| 2 | **跨进程写同一会话** | 两进程缓存互不知情 | 看是否有两进程同时打开、行时间戳是否交错 |
| 3 | **undo 被执行两次**（幂等失效） | 磁盘每行唯一，重复只在 **fold 恢复时 append 两遍**（若两条 undo 的 `rewind_id` 不同） | **直接看 jsonl 原始行**——不重复 ⇒ 是 fold 侧问题 |
| 4 | **轮转与 append 交错**（无锁时） | 行同时进归档与当前 | 在 `*.old1` 与当前文件里**分别** grep |

★ 第 3 条最易误诊为「去重失效」（它**不在磁盘上**，只在恢复后出现）。修法：fold 的幂等应按「**被恢复的段**」而不是按 `rewind_id` 去重；或服务端保证 undo 只追加一次。
★ 可机器校验的不变量建议：**「任一 row id 在 fold 输出中至多出现一次」**。

## 13. 规模化与隐私（面试压轴）

### 13.1 10 万会话下的成本（`ws_index` + `record_transcript`）

| 操作 | 复杂度 | 先崩的地方 |
|---|---|---|
| 列某工作区会话 | 首次 **O(索引行数)**，之后 O(1) | 索引全量读（无增量） |
| 打开一个会话 | O(该会话总字节，≤96MB) | 恢复读全部归档 |
| 记录一轮 | O(1) 写 + O(1) 判重 | — |
| **首次写入前的去重集合** | **O(该会话全部行)** | **冷启动延迟**（长会话要扫全部行） |
| blob | 每会话多个小文件 | **目录项爆炸**（不只是字节成本） |

改进方向（按性价比）：索引按 workspace 分片 · 去重集合持久化或「读尾 N 行」 · blob 按 id 前缀分桶 · 恢复只读必要归档 · 冷会话归档打包。
★ 架构观察：本项目存储设计**偏向「单会话可用性」而非「大规模扫描」**（单机单用户会话数天然有限）。

### 13.2 隐私与越权面

| # | 暴露面 | 现有防护 |
|---|---|---|
| 1 | Agent 读**其他会话**的转录 | ✅ `readable_extra_roots` **只放宽当前会话**（B07-0319） |
| 2 | 转录**内容含敏感信息**（用户粘贴的密钥等） | ⚠️ 无内容级防护 |
| 3 | blob 目录可枚举 | ⚠️ 与 1 同域 |
| 4 | 索引泄漏会话清单（`session_id → workspace_id` = 路径信息） | ⚠️ 同目录无保护 |
| 5 | **多用户共享安装** | ❌ 无应用层防护（需独立 `XEYO_HOME` / OS 账户） |
| 6 | **删除不彻底**（回滚只清当前文件，归档/blob 残留） | ✅ 有 `discard_rotated_transcripts`，但 **blob 不清**且失败静默 |

★ 核心认识：**会话存储本质上是一份「用户的私人对话数据库」**，但当前实现把它当「普通工作文件」（同目录、无加密、无 ACL、删除不彻底）。单机单用户可接受；**部署形态一变（共享机/多用户/远程通道）威胁模型就完全不同**。

## 14. 易错点清单

1. `.old1` 比 `.old2` **新**；读取顺序是「最旧 → 最新」。
2. flush 判据是 **seq 比较**，不是「队列为空」。
3. `flush()` 只到 page cache，**`fsync()` 才落盘**。
4. `atexit` 只等 **2s**，写入线程是 **daemon** ⇒ 尽力窗口。
5. `_disk_lock`（磁盘）与 `_cv`（队列）是**两把**原语，合并会让 fsync 阻塞入队。
6. 回滚必须**清归档**（否则已删内容被读侧拼回来）。
7. blob 必须**先写 blob 后写行**（写序正确性）。
8. `MessageStore` 与转录**不等价**（转录含被 fold 影子化的行）。
9. `safe_session_filename` **不是单射**（`s:1` vs `s__1`；Windows 大小写必撞）。
10. `is_session_persistence_disabled` **缺三态**（`None` 与 `False` 不可区分）。
11. fold 依赖协议前提「undo 前无新可见行」，**自身不校验**。
12. 去重与 `_disk_lock` 都是**进程内** ⇒ 多进程写同一会话会产生重复行。
13. `_loaded` 是进程级一次性 ⇒ 他进程追加不可见。
14. 孤儿 blob **无 GC**；`content_hash` 写了但**未校验**。
15. 物理重写的「重写 + 清归档」是**两步** ⇒ 中途崩会部分复活。
