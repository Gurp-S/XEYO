### XEYO-QA-0017 FREE_PORT 的实现与副作用

| 能力域 | 子模块 | 考查点 | 难度 | 问法 | 来源依据 |
|---|---|---|---|---|---|
| 入口与启动 | 端口清理 | `:FREE_PORT` 子过程 | 困难 | 代码阅读 | `XEYO.bat::FREE_PORT` |

**面试官提问**
阅读 `XEYO.bat` 的 `:FREE_PORT` 子过程：

```bat
:FREE_PORT
REM T30: backend cleanup by pid tree from the port file
if exist "%~dp0.xeyo\backend_port" (
  for /f "usebackq delims=" %%a in (`py -3.11 "%~dp0python\scripts\read_port.py" "%~dp0.xeyo\backend_port" --pid`) do taskkill /PID %%a /T /F >nul 2>&1
)
if defined XEYO_FRONTEND_PORT (
  for /f "tokens=5" %%p in ('netstat -ano ^| findstr ":%XEYO_FRONTEND_PORT% " ^| findstr LISTENING') do taskkill /PID %%p /T /F >nul 2>&1
)
exit /b 0
```

请回答：
（1）它清理哪两类进程？依据分别是什么？
（2）为什么后端用「pid 文件」而前端用「`netstat` 反查」？
（3）`/T` 与 `/F` 各是什么含义？缺了 `/T` 会有什么后果？
（4）它被调用了几次？分别在什么时机？
（5）这段逻辑存在什么风险？如果端口文件里的 pid 已被复用给无关进程，会发生什么？

**参考答案要点**

**（1）清理的两类进程**

| 目标 | 依据 |
|---|---|
| 上一次运行的 XEYO 后端 | `.xeyo/backend_port` 里的 `pid` 字段（`--pid` 参数读出） |
| 占用前端端口（`XEYO_FRONTEND_PORT`，默认 5173）的进程 | `netstat -ano` 输出中该端口处于 `LISTENING` 的行，第 5 列（`tokens=5`）= PID |

**（2）为什么两端策略不同**
- **后端**：XEYO **自己启动**它，启动时把 pid 写进了端口文件，因此有一个**精确、权威、可跨次运行**的 pid 来源。用 pid 比用端口更准——开发态后端可能因端口后移监听在非预期端口，按端口找会漏。
- **前端**：Vite dev server 是 `npm run tauri:dev` 内部拉起的**子进程**，`XEYO.bat` 不持有它的 pid，也没有写 pid 文件。端口是唯一可用的**外部标识**，只能 `netstat` 反查。
- 共同目的：**防「残留监听者」**——上次崩溃/强杀后进程仍在，本次启动会因端口占用而后移（甚至反复后移），表现为「每次启动端口都不一样」。

**（3）`/T` 与 `/F`**
- `/F` = Force，**强制终止**（不做优雅关闭）。
- `/T` = Tree，连**子进程树一起终止**。
- 缺 `/T` 的后果：只杀父进程，子进程成为孤儿继续持有端口。而后端是典型**多进程结构**（uvicorn worker、`start /b` 拉起的外壳下还有 python），前端也一样（node → vite → esbuild）。**只杀父进程等于没杀**——端口仍被占，问题原样复现。所以 `/T` 在此不是优化，是**必要条件**。

**（4）调用次数与时机**
两次：
1. **启动前**（`AFTER_NPM` 之后、`START_LLAMA` 之前）——注释「Free stale listeners on both the backend and frontend port first (port-occupied fix)」，目的是**清场**，为本次启动腾出端口。
2. **`tauri:dev` 退出后**（`popd` 之后）——目的是**收尾**，避免退出后残留监听者污染下一次启动。

**（5）风险**
最大风险是 **PID 复用（PID recycling）**：`.xeyo/backend_port` 是磁盘上的**陈旧**文件，若上次异常退出且该 pid 已被系统分配给**无关进程**（Windows 上 PID 会复用），`taskkill /PID <pid> /T /F` 会杀掉无关进程；且因带 `/T`，可能连带杀死整棵子进程树——破坏面被放大。现有实现的缓解是**弱的**：只 `>nul 2>&1` 吞掉错误，**没有任何「pid 是否仍属于 XEYO」的校验**（如比对进程命令行/可执行路径）。严格说属**待改进项**。

次级风险：`netstat | findstr ":%PORT% "` 的模式匹配可能误命中（模式末尾有空格可避免 `:51730` 类误配，但会同时命中 `127.0.0.1:5173` 与 `[::]:5173` 两条，属正常）；若其它服务恰好监听 5173，也会被杀。

**深化讲解**（面试官参考，不要求候选人全说）
本题四层递进：机制 → 设计动机 → 参数语义 → 边界风险。第（2）问考「为什么同一目的用了两种手段」，答案必须落到「谁持有 pid」这一信息层面；第（3）问看似基础，但「缺 `/T` 等于没杀」是常见知识盲点；第（5）问要求**不满足于「实现了清理」而指出误杀风险**——这是资深 QA 与普通背诵者的分界。

### XEYO-QA-0022 llama 端口占用的处理策略

| 能力域 | 子模块 | 考查点 | 难度 | 问法 | 来源依据 |
|---|---|---|---|---|---|
| 入口与启动 | 可选旁车 | 复用 vs 重启 | 困难 | 场景设计 | `XEYO.bat::START_LLAMA` / `:STOP_LLAMA` |

**面试官提问**
`XEYO.bat` 处理 llama-server 端口占用时，策略是「复用」而不是「杀掉重启」：

```bat
set "LLAMA_UP="
for /f "tokens=5" %%p in ('netstat -ano ^| findstr ":%XEYO_LLAMA_PORT% " ^| findstr LISTENING') do set "LLAMA_UP=1"
if defined LLAMA_UP (
  echo   llama-server already running on :%XEYO_LLAMA_PORT%, reuse.
  exit /b 0
)
```

而退出时 `:STOP_LLAMA` 又会把该端口上的进程杀掉。请分析：
（1）为什么 llama 用「复用」而 XEYO 后端用「杀进程树」？
（2）这套「复用 + 退出时杀」的组合存在什么缺陷？
（3）`for /f` 循环里只做 `set "LLAMA_UP=1"`（不用 `%%p`），说明这段代码的意图是什么？

**参考答案要点**

**（1）为什么策略不同**

| 维度 | XEYO 后端 | llama-server |
|---|---|---|
| 启动成本 | 秒级（FastAPI + 惰性工具导入） | **分钟级**（加载 GB 级 GGUF 到显存，`--no-mmap` 更是全量载入） |
| 谁启动的 | 必然是本次或上次 `XEYO.bat` | 可能是**用户手动**启动并长期驻留的工作服务 |
| 复用收益 | 低（重启很快） | **极高**（避免重复加载模型） |
| 杀掉代价 | 低 | 高（用户可能正在用它跑别的任务） |

所以：后端**清场优先**（保证端口与配置一致），llama **复用优先**（尊重昂贵资源与用户意图）。

**（2）组合策略的缺陷**
①**「复用」判断过宽**：只检测端口上有 `LISTENING` 进程就认为是 llama-server，**没有校验进程身份**。若其它程序恰好占用 8080，脚本会打印「llama-server already running, reuse」并跳过——实际 llama 根本没起，而用户被误导。
②**「退出即杀」会杀掉别人的进程**：若那个 8080 上的服务是用户自己启动并希望长期保留的（或根本不是 llama-server），`:STOP_LLAMA` 会在 `XEYO.bat` 退出时把它 `taskkill /T /F` 掉。**「复用」与「退出时杀」逻辑上矛盾**——你承认它可能是「别人的/已存在的」，却又在退出时把它当自己的资源回收。
③**归属不清的状态**：代码没有记录「本次是否由我启动」（例如一个 `XEYO_LLAMA_STARTED=1` 标志）。正确做法应是**只回收自己启动的资源**：`:START_LLAMA` 成功启动时置标志，`:STOP_LLAMA` 仅在标志存在时才杀。
④**存在并发窗口**：若 `XEYO.bat` 被并发启动两次，两实例都可能在「检测」与「`start`」之间进入启动分支，导致端口冲突。

**（3）`for /f` 只 set 标志的意图**
```bat
for /f "tokens=5" %%p in (…) do set "LLAMA_UP=1"
```
循环体不用 `%%p`，说明作者**不关心 pid**，只关心「是否有任何一行匹配」。`tokens=5` 仍必须写——它同时起**过滤表头行**的作用（表头 `协议  本地地址  外部地址  状态  PID` 的第 5 列为空 → 不产生迭代）。因此这行本质是**用 netstat 做布尔存在性检测**，`%%p` 是形式上的占位。更简洁的写法可加 `& goto :llama_checked` 提前退出；当前实现会把所有匹配行跑一遍（幂等，无害但低效）。

**深化讲解**（面试官参考，不要求候选人全说）
本题价值在**发现「复用 + 退出杀」这对语义矛盾**。很多脚本都有这种「看起来完备、语义上冲突」的组合。能指出「没有归属标志 → 会杀别人的进程」，即达到资深 QA 水准。第（3）问是纯代码手感题：读懂「用 `for` 实现 `if`」的写法。

**原因（批处理注释已直说）**：让每次运行的日志路径**唯一**，使「上一次运行遗留的持句柄者」**无法锁住同名文件**，从而不会因**文件共享冲突（file-sharing violation）**阻塞新一次启动。

**不加随机 tag 的具体故障链**：
1. 日志路径固定为 `%TEMP%\xeyo-python.log`。
2. 上一次运行的后端进程**没有正常退出**（崩溃、被 `taskkill` 时句柄未释放、或残留孤儿进程仍在写日志），Windows 上该文件被以**非共享写**方式打开。
3. 用户再次双击 `XEYO.bat`，命令 `start "XEYO-Python" /b py -3.11 -u -m server > "%XEYO_PY_LOG%" 2>&1` 需对同一路径**重定向写入**（等价于以写方式打开）。
4. 由于文件被独占锁定，重定向**失败**：`start` 可能报错、或新建进程立刻因 stdout 句柄无效而失败。
5. 表现：后端**起不来**，`wait_health` 25 秒超时，报 `ERROR: FastAPI did not become healthy on port 8000`——**但日志文件里可能什么都没有或全是旧内容**。排障者看到旧日志会得出完全错误的结论（最恶劣的一点：**错误的证据比没有证据更危险**）。
6. 恶性循环：因为无法写日志，下次排障依然拿不到新证据。

加随机 tag 后，新一次运行写入 `xeyo-python_<另一个随机数>.log`，**绕过锁**，且不会把新旧日志混淆。

**深化讲解**（面试官参考，不要求候选人全说）
这是一个非常典型、非常实用的设计细节，考的是「**故障的二次伤害**」意识：就算进程能起来，**日志被旧的锁死**也会让排障彻底失去抓手。随机化是解决「单实例文件锁」的最轻量手段（无需清理逻辑、无需重试）。

补充两点：
- `echo` 到 `%TEMP%` 而非仓库目录，避免污染工作区、也避免仓库被写文件（与「严禁 `git add -A`」的洁癖同源）。
- `if not defined XEYO_PY_LOG_TAG` 允许外部显式指定 tag（便于把多次运行的日志归档到固定名字），是**可覆盖的默认值**。

### XEYO-QA-0028 薄壳 venv 事故的根因

| 能力域 | 子模块 | 考查点 | 难度 | 问法 | 来源依据 |
|---|---|---|---|---|---|
| 部署与发布 | 自包含运行时 | 2026-09-10 事故 | 困难 | 场景设计 | `README.md:53-57` |

**面试官提问**
XEYO 曾发生一次发布事故：安装包在目标机器上「文件俱在，但 `python.exe` 启动即失败，界面统一显示『无法连接后端』」。请说明：
（1）根因是什么？
（2）为什么「复制项目 `.venv`」这种看似自然的做法会失败？
（3）事故的现象为什么具有误导性（用户与开发者会分别得出什么错误结论）？
（4）正确的替代方案是什么？

**参考答案要点**

**（1）根因**
发布包里内嵌的 Python 运行时是**薄壳（thin shim）**，不是自包含运行时。`Scripts/python.exe` 实际只有约 270KB，只是一个 **launcher**；真正的 `python3xx.dll` 与标准库**留在构建机的 base 解释器**中，通过 `pyvenv.cfg` 的 `home=` 指向构建机路径（如 `C:\Users\<someone>\AppData\Local\...`）。目标机没有该 base 解释器，于是 `python.exe` 启动即失败。

**（2）为什么「复制 `.venv`」会失败**
这是 **venv/virtualenv 的设计使然**，不是操作失误：
- `venv` 的语义是「**引用**一个 base 解释器 + 隔离 site-packages」，不是「**复制**一个解释器」。
- 因此 `.venv` 目录里天然**没有** `python3xx.dll`、没有完整标准库，只有指向 base 的配置。
- 该模型在**同一台机器**上工作正常（base 一直在），所以开发机上跑得好好的、复制到别处就崩——**本地无法复现**。
- 复制 `.venv` 人为把「同机可用的引用」变成了「跨机失效的引用」：这正是「薄壳」属性被暴露的瞬间。

**（3）现象的误导性**
- **用户侧**：看到「无法连接后端」，自然归因于**网络或端口**（防火墙、端口被占、后端没启动），于是去查网络、换端口、关杀毒软件——**全部无效**，因为根因在解释器。
- **开发者侧**：更危险的是「错误只写进 stderr」（`README.md:55` 原文：Tauri 壳拉不起后端，**错误只写进 stderr**，界面统一显示「无法连接后端」）。而发布包在终端用户机器上**没有可读的 stderr**——错误信息被静默吞掉，开发者拿到的是「连不上」，**看不到 `ModuleNotFoundError` / `DLL load failed` / `pyvenv.cfg` 路径不存在**这类决定性证据。
- 综合效果：**一个确定性的、100% 可复现的启动失败，被伪装成了一个环境相关的、看起来偶发的连接问题**。这直接导致排障方向系统性偏差。

**（4）正确方案**
改用 [python-build-standalone](https://github.com/astral-sh/python-build-standalone) 的**可重定位 CPython**：
- 自带 `python3xx.dll` + 全套标准库 + VC 运行时；

### XEYO-QA-0029 pyvenv.cfg 的 home 陷阱

| 能力域 | 子模块 | 考查点 | 难度 | 问法 | 来源依据 |
|---|---|---|---|---|---|
| 部署与发布 | 自包含运行时 | `pyvenv.cfg` 解析 | 困难 | 故障排查 | `scripts/build_slim_venv.py`（自包含断言）、`README.md:57` |

**面试官提问**
构建自包含 Python 运行时时，`pyvenv.cfg` 里有一行：

```ini
home=.
```

但有人写成：

```ini
home = .
```

（`=` 两侧各加一个空格）

请说明：为什么后者会导致**所有第三方包 `ModuleNotFoundError`**？这个故障为什么特别难排查？

**参考答案要点**

**根本原因：解析后的基准路径为空**

Python 启动时读取 `pyvenv.cfg` 来决定 venv 的「基准前缀（base prefix）」，进而决定要往 `sys.path` 里加入哪些目录（标准库路径、`site-packages` 等）。该解析对**格式敏感**：

- 必须写成 `home=.`（**`=` 两侧无空格**），解析得到基准路径 = 当前目录（可重定位）。
- 写成 `home = .` 时，按 CPython 的解析逻辑，键名会被识别为 `home `（带尾空格）或值解析为空，最终**基准路径解析成空**。
- 基准路径为空 → 计算出的标准库路径与 **site-packages 路径全部失效** → venv 内的第三方包**不在 `sys.path` 上**。
- 结果：`import fastapi` 之类全部 `ModuleNotFoundError`，**尽管文件确实在磁盘上**。

**为什么特别难排查**
1. **症状与原因错位**：报错是 `ModuleNotFoundError: No module named 'fastapi'`，而 `fastapi` 目录**明明存在于 `.venv/Lib/site-packages/`**。第一反应必然是「依赖没装」「装错解释器」「pip 装到别处」，于是反复重装依赖——**全部无效**，因为问题不在包是否存在，而在**路径是否被挂载**。
2. **`pyvenv.cfg` 不在视野内**：它是个几行的配置文件，极少有人想到去读。
3. **只有 `sys.path` 能暴露真相**：唯一有效的诊断是 `python -c "import sys; print(sys.path)"`——会看到**缺少 site-packages 条目**。不打印 `sys.path` 就永远在猜。
4. **空格不可见**：`home=.` 与 `home = .` 在编辑器里几乎无差别，code review 极易放过；而这是**功能性差异**而非风格差异。
5. **本地不可复现**：构建机上有完整 base 解释器，可能恰好「歪打正着」能跑；只在目标机或干净环境暴露。

**正确做法（结构性防复发）**
`scripts/build_slim_venv.py` 应内置断言：**构建时检查 `site-packages` 是否真的在 `sys.path` 上**（`README.md:57` 明确列出该断言）。这样格式错误在**构建期**就失败，而不是在用户机器上变成「连不上后端」。

**深化讲解**（面试官参考，不要求候选人全说）
这是一道「一行配置全文崩」的典型题，考三件事：①理解 `pyvenv.cfg` 的作用（决定基准前缀 → 决定 `sys.path`）；②掌握唯一有效的诊断手段（打印 `sys.path`）；③理解「格式敏感性」的工程含义——**空格是语义的一部分**。

**三条断言**（依据 `README.md:57`）

### XEYO-QA-0040 slash manifest 漂移检查

| 能力域 | 子模块 | 考查点 | 难度 | 问法 | 来源依据 |
|---|---|---|---|---|---|
| 门禁与 CI | 生成物一致性 | `--check` 模式 | 中等 | 机制解释 | `.github/workflows/ci.yml`、`python/ARCHITECTURE.md:48`、`README.md:150` |

**面试官提问**
CI 与本地门禁都会执行 `python -m slash.export_manifest --check`。这条命令在检查什么？为什么必须存在？如果开发者忘记提交生成物会发生什么？请说明正确的开发流程。

**参考答案要点**

**在检查什么**
**漂移（drift）**：`python/slash/registry.py`（斜杠命令表，**SSOT**）与**已提交的生成物** `*/generated/slashManifest.ts` 之间是否一致。`--check` 模式**只校验不写盘**：重新生成一份，与仓库中已提交的对比，不一致则非 0 退出 → 门禁红。

**为什么必须存在**
XEYO 有**四个表面**共用同一份斜杠命令清单（`README.md:141`：「GUI / tui / Python CLI / 微信四表面共用 `python/slash/registry.py` 统一 manifest」）。清单以**代码生成**方式分发到各前端（`slash/export_manifest.py` → `gui/src/generated/`、`tui/src/generated/slashManifest.ts`）。

生成式工作流有一个固有风险：**源改了、生成物忘了提交**。此时：
- Python 侧行为（`slash/dispatch.py`）改了；
- 前端仍用**旧清单**渲染，表现为「命令列表里没有新命令」「补全提示与实际不符」，或更糟——**前端显示的命令在服务端已改名，点了报错**；
- 而且这种不一致**不会**被 typecheck 或 vitest 发现（类型都对，只是内容旧）。

`--check` 就是把这个「静默不一致」变成**构建期硬失败**。

**忘记提交的后果**
CI 的 `python` job 在 `Slash manifest drift` 步骤非 0 退出 → **CI 红**。开发者必须在本地跑 `py -3.11 -m slash.export_manifest`（不带 `--check`，即写盘模式）重新生成并提交。

**正确开发流程**（`python/ARCHITECTURE.md:45-49` / `README.md:150`）
1. 改表：编辑 `python/slash/registry.py`；
2. 生成 TS：`py -3.11 -m slash.export_manifest`；
3. **把生成的 `*/generated/slashManifest.ts` 一起提交**；
4. 服务端执行逻辑（若涉及）改 `python/slash/dispatch.py`；
5. 跑门禁确认 `--check` 通过。

**深化讲解**（面试官参考，不要求候选人全说）
本题核心是**生成物与真源的一致性保障**。常见做法是把 `generated/` 写进 `.gitignore`，XEYO 相反——**生成物入库**，从而让差异在 diff 里可见、在 CI 里可校验。这是「生成物入库 + drift 检查」这一对标准实践。

`--check` 是**纯文本一致性**校验，不依赖网络与数据库，因此适合作为门禁项（零假红、确定性）。



**评分要点**（对照候选人口述逐项打分）
- **及格**：能说出上面的主体结论与关键常量/枚举，不得编造行号。
- **良好**：能说出每个字段/每道闸的**作用对象**（它管什么、不管什么），而不只是背清单。
- **优秀**：能把本题结论与同类机制对比（指出它们各自管什么），并在追问下拿出 `文件:行号` 作证。

**典型弱答**（听到这些就得分不高）
- 只报清单/只报数字，说不出“它为什么存在”；
- 把本题的机制当成全局机制（跨模块张冠李戴）；
- 编造行号或「大概就是某某函数里」而拿不出证据（本题可追问到具体 `文件:行号`）。

**参考答案要点**

**作用**
- `group: ci-${{ github.ref }}`：以 **git ref**（分支/标签引用）为并发组键。**同一分支**上的工作流共享一个组，不同分支各自独立。
- `cancel-in-progress: true`：当同一组内**新的运行**启动时，**取消仍在进行的旧运行**。

**典型收益**
1. **省资源与省时间**：连续 push 三次到同一分支，只有最后一次会真正跑完，前两次被自动取消，不再排队串行执行、不浪费 runner 分钟数。
2. **结果更快反馈**：开发者不必等「三个已经过期的 commit」依次跑完，才能拿到最新 commit 的结论。
3. **避免误导性的中间结论**：否则会收到「旧 commit 失败」的通知邮件，实际它早已被覆盖。

**与 XEYO `FREE_PORT` 的相似性**

两者处理的是**同一类问题：同一「标识位」被多个竞争者占用时的取舍策略**。

| 维度 | GitHub Actions `concurrency` | `XEYO.bat::FREE_PORT` |
|---|---|---|
| 冲突资源 | 同一 ref 上的 workflow run | 同一端口（8000 / 5173） |
| 冲突来源 | 连续 push / 重复触发 | 上次运行的残留监听进程 |
| 策略 | **保新弃旧**（取消 in-progress） | **清旧保新**（`taskkill` 后重新启动） |
| 目标 | 让最新的结论胜出，不浪费算力 | 让本次启动能拿到端口 |

即：`cancel-in-progress` 是「取消旧的让新的跑」，`FREE_PORT` 是「杀掉旧的让新的起」——**都是「新优先（newest-wins）」策略**，只是作用对象一个是 workflow run、一个是 OS 进程。

差异在**确定性来源**：Actions 用 `github.ref` 作组键，是**平台提供的可靠标识**；而 `FREE_PORT` 依赖 `.xeyo/backend_port` 这个**磁盘文件里的 pid**（陈旧、可能被复用，见 0017 第（5）问风险）。

**深化讲解**（面试官参考，不要求候选人全说）
本题考查「从 CI 配置读出运行时语义」的能力，以及**跨领域的模式识别**——把 GitHub Actions 的并发控制与本地脚本的端口清理抽象成同一个「资源竞争 + 策略选择」问题。

值得补充的边界：
- `concurrency` **只做互斥与取消，不做排队**。如果想「排队而非取消」，应设为 `cancel-in-progress: false`。
- 组键用 `github.ref` 时，**PR 与其源分支**可能不是同一个 ref（PR 是 `refs/pull/N/merge`），因此「同一分支连 push + 开 PR」可能并行跑两份 CI。要用更粗的粒度可改用 `github.head_ref || github.ref`。
- 与 `cancel-in-progress: true` 搭配时，若工作流**有部署等副作用步骤**，取消可能留下半完成状态——XEYO 的 CI 全是只读检查，因此该风险为零。

| | 第三条（准入） | 第四条（事故） |
|---|---|---|
| 触发时机 | **新功能进入**时 | **缺陷已被引入**后 |

**（3）0028 薄壳 venv 事故满足的规矩**

| 规矩 | 是否满足 | 依据 |
|---|---|---|
| 1 提交门 | ⚠️ **形式满足、实质失效** | 门禁全绿（`tsc`/`vitest`/`pytest` 都过），但事故发生在**门禁完全不覆盖的环节**（安装包构建），所以「全绿」没有拦下它——见 0041 |

| 3 新功能准入 | ✅ **典型满足** | 修复没有把「检查运行时」硬塞进主链路，而是在**构建脚本内**加断言——旁路形态、无运行时开销、可独立度量 |
| 4 事故模板 | ✅ **完全满足** | ①结构性根因 = venv 是**引用**而非**复制**；②哪条规则让结构上不再发生 = `build_slim_venv.py` 的**三条自包含断言**（缺 DLL / site-packages 不在 sys.path / pyvenv.cfg 外指 → 构建失败）；③回归测试 = 构建期断言本身即测试，且需在**无 Python 干净机器**验证 |

**（4）最容易被绕过的是第 2 条（开工检查）**

理由：
①**它没有机械化载体**。第 1 条有 `check.ps1`／`ci.yml`，第 4 条有模板与 `docs/` 事故文档，第 3 条有 `*_shadow.py` 等物理落点；而第 2 条只有「先看 `git status`」这一句**人的纪律**。
②**违反它不会立刻报错**。忽略它就写代码，代码照样能跑、门禁照样能绿——直到 `git commit` 时才发现卷入了他人在途改动，而那时**修复代价已经产生**（需要拆提交或回滚）。
③**在多会话并行的工作方式下风险最高**。同一工作区被多个会话同时编辑时，`git add -A` 一旦执行就会把他人改动一起提交。这正是 XEYO 运维里形成的对策——**一律 `git commit -m "..." -- <path>` 路径限定提交，严禁 `git add -A`**——其本质是在**补第 2 条的机械化短板**。
④**它没有回归测试**。第 4 条要求「回归测试怎么写」，而第 2 条无法用测试表达（它是对**工作区状态**的检查，不是对**产品行为**的检查）。

### XEYO-QA-0050 四表面共用 slash registry 的意义

| 能力域 | 子模块 | 考查点 | 难度 | 问法 | 来源依据 |
|---|---|---|---|---|---|
| 项目总览与架构 | 多表面架构 | 统一 manifest 的价值 | 困难 | 场景设计 | `README.md:141,150`、`python/ARCHITECTURE.md:45-49` |

**面试官提问**
`README.md:141` 写着：「**多表面**：GUI / tui / Python CLI / 微信四表面共用 `python/slash/registry.py` 统一 manifest」。

请分析：
（1）「四表面共用一份 manifest」具体是怎么实现的（从 Python 表到各端可用的链路）？
（2）相比「每个表面各自维护一份命令表」，这个设计规避了哪些具体缺陷？
（3）这个设计引入了什么**新的风险**？由什么机制兜住？
（4）如果要把这条链路改造成运行时动态发现（各端启动时向后端拉清单），会失去什么？

**参考答案要点**

**（1）实现链路**

```
python/slash/registry.py            ← SSOT：命令的唯一权威定义
        ↓  py -3.11 -m slash.export_manifest
*/generated/slashManifest.ts        ← 派生物：编译期生成的 TS 清单
        ↓  各端 import
gui/src/generated/slashManifest.ts  ← GUI（React + TS）
tui/src/generated/slashManifest.ts  ← TUI（Ink + React）
        ↓  （CLI 与微信侧）
python/slash/dispatch.py            ← 服务端执行逻辑（与 registry 同侧）
```

`python/ARCHITECTURE.md:45-49` 三步：
1. 改表：`slash/registry.py`
2. 生成 TS：`py -3.11 -m slash.export_manifest`（CI 跑 `--check`）
3. 服务端执行：`slash/dispatch.py`

即**「单一真源 + 编译期生成 + 服务端分发」**三层。

**（2）规避的具体缺陷**

| 若各端各自维护一份 | 共用一份 manifest 的表现 |
|---|---|
| **命名漂移**：GUI 叫 `/help`、TUI 叫 `/h`、CLI 叫 `--help`，实现各自为政 | 命令名**由一处定义**，四端必然一致 |
| **参数漂移**：某端支持 `--json`、另一端不支持，用户跨端体验断裂 | 参数 schema 同源，差异只在"该端能否渲染"，不在"命令是否存在" |
| **能力漏配**：新增命令后忘记在某端补上（尤其微信这种非主流端） | 生成即全端同步，**不存在「漏补某端」** |
| **服务端不认识**：前端能列出 `/foo` 但 `dispatch.py` 里没有，点了报错 | `registry.py` 与 `dispatch.py` 同侧，注册即可执行 |
| **文档漂移**：README 的命令表与实现长期不一致 | 命令表可从同一份 manifest 推导 |

核心收益：**把 N 个表面的一致性从「N 份人工同步」降为「1 份真源」**。

**（3）引入的新风险与兜底机制**

| 风险 | 说明 | 兜底机制 |
|---|---|---|
| **生成物过期（drift）** | 改了 `registry.py` 但忘记重新生成并提交 TS → 前端用旧清单，**静默不一致** | **CI 与本地门禁都跑 `python -m slash.export_manifest --check`**，不一致直接红（见 0040） |
| **生成器本身的缺陷** | 若 `export_manifest.py` 有 bug，四端**同时**出错（单点故障从「某端」放大到「全端」） | 生成器有独立测试；`--check` 保证确定性（同输入同输出） |
| **生成物入库的维护负担** | `generated/` 入库意味着每次改命令都要多提交一个文件，diff 噪音 | 由 `--check` 保证正确性；噪音是可接受的代价（换来一致性可校验） |
| **多语言类型对齐** | Python 表与 TS 清单的类型必须能互转 | 生成器负责映射；TS 侧类型由生成代码携带 |
| **已发布产品无法热更新清单** | 装着旧版 exe 的用户，其前端清单是**构建时**固化的 | 属**已知约束**：命令集变更需发新版本（与「release 版无 Vite dev server」同源，见 0018） |

**（4）改成运行时动态发现会失去什么**

若各端启动时向后端拉取清单（而非编译期生成）：

**会失去的：**
1. **离线可用性**。编译期生成意味着**前端不依赖后端就能渲染命令列表**（补全面板、帮助面板立即可用）。动态发现下，后端未就绪时命令面板是空的——而 XEYO 的启动链路里前端与后端是**并发**拉起的（0020 中后端甚至可能比 Rust 壳先起好），这会造成启动期的体验空洞。
2. **类型安全**。TS 清单是**静态类型**的产物，编译期即可发现「前端引用了不存在的命令」。动态发现只能拿到运行期对象，类型退化为 `any`/运行时校验。
3. **确定性构建**。编译期生成 → 同样的源码产出同样的前端产物（可复现构建，与 `XEYO_PBS_TAG` 同理）。动态发现 → 前端产物不变但行为依赖后端版本，**构建产物不再自描述**。
4. **`--check` 这类门禁失效**。没有生成物就没有「漂移」概念，也就**失去了一个零成本的一致性门禁**（0040）——改回动态发现等于把关禁能力丢掉。

**会得到的（需要诚实列出）：**
- 无需重新构建即可下发新命令（对已发布产品是真实收益）；
- 少一个生成步骤与一份入库文件。

**权衡结论**：XEYO 选了**编译期生成**，与它的产品形态一致——**本地运行、可离线、强类型前端**。命令集变化频率远低于会话内容变化频率，因此「为热更新而牺牲离线与类型安全」不划算。

**深化讲解**（面试官参考，不要求候选人全说）
本题四问构成一条完整的架构权衡链：**机制 → 收益 → 代价 → 反事实推演**。

第（2）问的关键是把「一致性」具体化为**五类可命名的漂移**（命名/参数/漏配/服务端不认/文档），而不是笼统说「更统一」。

第（4）问是本题的区分点：要求**同时列出收益与损失**（不能只说变差），并给出**有依据的权衡结论**（命令集变化频率低 + 本地可离线 + 强类型前端 → 编译期生成胜出）。



**评分要点**（对照候选人口述逐项打分）
- **及格**：能说出上面的主体结论与关键常量/枚举，不得编造行号。
- **良好**：能说出每个字段/每道闸的**作用对象**（它管什么、不管什么），而不只是背清单。
- **优秀**：能把本题结论与同类机制对比（指出它们各自管什么），并在追问下拿出 `文件:行号` 作证。

**典型弱答**（听到这些就得分不高）
- 只报清单/只报数字，说不出“它为什么存在”；
- 把本题的机制当成全局机制（跨模块张冠李戴）；
- 编造行号或「大概就是某某函数里」而拿不出证据（本题可追问到具体 `文件:行号`）。
