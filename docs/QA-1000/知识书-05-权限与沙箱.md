## 1. 六层权限模型（先背这张图，再答细节）

```
① 能力面裁剪     按模式移除工具（只读模式移除 Write/Edit；scope=[] 的子 agent 同）
       ↓                防「模型看到它」；不防幻觉调用（下层兜）
② 角色与档位     preset（readonly / workspace-write / full）+ 审批模式（always/risk/never）
       ↓                防「用户意图错配」；full 不等于关闭硬拦
③ 三态裁决+挂起  allow / ask / deny；ask 挂起 + TTL + 授权持久化
       ↓                防「不确定的操作」；不防规则本身写错
④ 硬拦（绝对值） 密钥 / 危险路径 / 受保护元数据 / worker 沙箱（不可被批准）
       ↓                防最高危目标；不防清单外的新型敏感文件
⑤ 执行层约束     路径狱（双 realpath）+ write_scope + WriteStore（base hash/锁/租约）
       ↓                防路径逃逸与并发覆盖；不防 TOCTOU 与系统调用层绕过
⑥ 系统层边界     容器 / 沙箱 / 文件系统 ACL / 网络策略
                     ★ 真正的安全边界；**本项目最大空白（无文件系统沙箱）**
```

★ **答题要点：每一层都要说「不防什么」**。只说机制不说边界，会被判为「背过资料但没设计过」。

## 2. 三态裁决（`filesystem.py:32-35`）

```python
class PermissionDecision(str, Enum):
    ALLOW = "allow"
    DENY = "deny"
    ASK = "ask"
```

**为什么必须三态**（不能折成两态）：

| 折法 | 后果 |
|---|---|
| 折进 ALLOW | 静默放行危险操作 |
| 折进 DENY | 一类操作**永远无法被用户批准**（「写工作区外文件」在用户同意时应当允许） |

★ ASK 是**有独立生命周期的状态**（挂起 → 回执/超时），不是「延迟的 DENY」——证据：`pending_ttl.py` 为它定义了三套结果文案。

**决策对象**（`policy.PolicyDecision`，`:54-72`）：`decision` / `reason` / `path` / `prompt`（供弹窗展示）/ `matched_rule` / **`choices`**（三选 ASK：`("deny","remind","allow")`）/ `peer_summary` / `mcp_target`。

## 3. 路径狱与硬拦（`filesystem.py` 435 行，**全文精读**）

### 3.1 路径判定：为什么两侧都要 realpath

```python
	abs_path = normalize_case_for_comparison(os.path.realpath(expand_to_abs(path, cwd=base)))
	for root in roots:
		abs_root = normalize_case_for_comparison(os.path.realpath(os.path.abspath(...)))
		if abs_path == abs_root or abs_path.startswith(abs_root + os.sep): return True
		if abs_path.startswith(abs_root.rstrip("\\/") + "/"): return True   # 混合分隔符容错
```

docstring：「两侧都按 realpath 解析：工作区内的符号链接若指向外部目标，比较时落在真实目标上，**防止借 symlink 逃出工作区写文件**」。

四个细节各有理由：`expand_to_abs` 的 `abspath` **折叠 `..`**；`normalize_case_for_comparison` = `.lower()`（Windows）；拼 **`+ os.sep`**（否则 `/ws-evil` 会被判在 `/ws` 内）；额外认 `/` 风格前缀（混合分隔符）。

### 3.2 三道硬拦（结果强度不同，**这是重点**）

| 判定 | 清单 | 结果 |
|---|---|---|
| `is_secret_path` | `_SECRET_DIRECTORIES = {.ssh, .kube, .gnupg, .aws}`（**刻意不含 `.git`**）+ `DANGEROUS_FILES`(14) + `DANGEROUS_SUFFIXES = (.pem,.key,.p12,.pfx)` | **硬 DENY**（不可批准） |
| `is_dangerous_path` | `DANGEROUS_DIRECTORIES = {.git, .ssh, .kube, .gnupg, .aws}` | **ASK**（可批准） |
| `protected_metadata_reason` | `PROTECTED_METADATA_NAMES = {.git, .xeyo, .agents}`（**只对工作区内**） | **硬 DENY** |

★ **为什么 `.git` 不在 `_SECRET_DIRECTORIES`**（注释 `:98-100`）：`is_secret_path` 是**无条件硬 DENY**；若把 `.git` 放进去，「读 `.git/config`」这一合理用例会被永久钉死。所以 `.git` 走**三条不同的路**：

| 场景 | 期望 | 靠谁 |
|---|---|---|
| 工作区内**写** `.git/…` | 硬 DENY | `protected_metadata_reason` |
| 工作区内**读** `.git/config` | **ASK** | `is_dangerous_path` |
| 工作区**外**的 `.git` | 边界判定 | `path_in_allowed_working_path` |

★ **`protected_metadata_reason` 是组件级扫描**（`:346-352`），注释记录了修正 G78：「原只查首组件，`sub/.git` 被降级为 ASK——**嵌套仓库/子模块的 git 元数据与顶层同等受保护**」。这是「同一资产两种保护等级」这一典型漏洞信号的修复。

★ 密钥清单的**泛化 + 豁免**（`:161-168`）：

```python
	if base_l in DANGEROUS_FILES: return True
	if base_l.startswith(".env") and not any(base_l.endswith(s) for s in (".example",".sample",".template",".dist")):
		return True     # .env 任意变体（G77: 原仅 3 个显式条目）
```

代价：`.envrc` / `.environment` 误伤（方向仍对：凭据泄漏代价 >> 误拦成本）。

### 3.3 读裁决 vs 写裁决（**含一处真实矛盾**）

```python
# 读：四层
① allowed 根 = 工作区 + readable_extra_roots()
② 工作区边界（区外 DENY，除非 _max_outside_allowed() 最高档）
③ is_secret_path  -> 硬 DENY      ← 无条件执行！
④ is_dangerous_path -> ASK
默认 ALLOW

# 写：两件写专有 + 复用读
① is_secret_path -> 硬 DENY
② protected_metadata_reason -> 硬 DENY
③ return check_read_permission_for_path(...)     ← 复用
```

★ **① 的顺序意义**：密钥判定在边界之后且**无条件执行** ⇒ 即使最高档放宽了区外，**密钥仍被硬拦**（「放宽不能穿透硬拦」）。

★★ **③ 是一处真实矛盾（面试加分）**：`readable_extra_roots`（`:191-244`）的注释写「**仅用于读裁决；写裁决不得包含**」，但写裁决在最后一步**复用了读裁决**，而读裁决**内部**会追加这份额外根 ⇒ **写裁决实际上也享受了放宽**。这是「注释与调用链不一致」，值得作为改进项提出（修法：写裁决不调读裁决，或读裁决增加「是否含额外根」参数）。

`readable_extra_roots` 的四条受控点：**只读** · **只当前会话**的转录（不放宽整个 `sessions/`——否则跨会话横向越权） · 只列**实际存在**的文件 · 失败**静默**（权限门不因辅助目录计算而崩）。

### 3.4 两处未覆盖的真实边界（面试压轴）

**① realpath 的 TOCTOU**：`realpath` 在**判定时**解析，`open` 在**之后** ⇒ 窗口期把路径组件换成指向 `/etc` 的 symlink 即可逃逸。与 WebFetch 的 DNS rebinding 同类（换载体）。且**路径不存在时 realpath 不解析链接**（判定退化为弱化版）。
修法：① 判定后把 **canonical path 一路传下去**做 I/O；② `O_NOFOLLOW` / 打开后比对 `peername`→inode；③ `openat` 语义逐级打开；④ 回滚侧兜底（只能补救）。

**② 多 allowed 根下元数据保护失效**：`protected_metadata_reason` 只看**单个 `cwd`**（`relpath` 以 `..` 开头即放行，`:344-345`），而路径狱支持**多个 allowed 根** ⇒ 位于「第二根」下的 `.git` 在元数据判定里被当区外放行、在路径狱里却是区内——**两条判定对同一路径结论相反**。

## 4. 审批模式与单向性（`policy.py` + `runtime_mode.py`）

```python
_PERMISSION_MODES = ("always", "risk", "never", "allow")   # 四档
_STRICTNESS = {"always": 3, "risk": 2, "never": 1}         # 严格度可比较
_AUTO_WRITE_MODES = frozenset({"never", "allow"})          # 免确认由两者共同表示
```

`normalize_mode`：`allow` → `never`（不是第五档）；非法/空 → 返回 `None`。
`strictness()`：未知值返回 **0**（比 `never` 更「松」，所以**永远不会赢过**任何合法值 —— 方向安全）。
`stricter(a,b)`：返回较严者 —— 这是全项目单向性的公共基础。

### 4.1 单向性：收紧即时、放宽延后（`runtime_mode.py`）

```python
# set()：写活值；若比基线更严，同步抬升基线        -> 收紧即时
	if baseline is not None and strictness(normalized) > strictness(baseline):
		self._baseline[session_id] = normalized
# begin_turn()：turn 边界拍定基线 = 活值 or 默认 or "risk"
# effective()：轮内取「基线 vs 活值」中更严者        -> 放宽延到下一 turn
	return requested if baseline is None else stricter(baseline, requested)
```

**它防的具体场景**：用户「批准删除 → 系统开始执行 → 顺手把模式调到 `never`」，若放宽即时生效，**同轮剩余调用会被静默放行**。

★ 并发细节：读路径（single-key get）**依赖 GIL 原子、不加锁**；写路径与 turn 边界（跨两个 dict 的复合更新）**用一把锁**。

### 4.2 广播快照 ≠ 权限（`:14-18,107-154`）

```
模型同步（增量快照 + supersedes）……快照只是广播，**不透支任何权限**——
真开关始终在 ToolRegistry 准入 gate。
```

四条设计：① **广播 ≠ 授权**；② **只在 turn 首广播**（`mark_turn_broadcast`：仅轮首有活值且未广播 → 避免弱模型在回合中途被新增背景块带偏）；③ 增量 + `supersedes` 措辞（防多份快照并存）；④ **纯状态陈述**（docstring：「刻意去掉一切引导/要求性措辞」）。

### 4.3 权限 preset（`presets.py` 18 行）

`PERMISSION_PRESETS = {readonly, workspace-write, full}`，默认 `workspace-write`。

★ **`full` 不等于关闭权限**——docstring：「full **只放宽「确认频率」**，不触碰 deny 黑名单 / 密钥 / `.git/.xeyo/.agents` 硬保护 / worker 沙箱」。

## 5. 挂起与授权（`store.py` 508 行 / `pending_ttl.py` 53 行）

### 5.1 挂起三态 + 超时（`pending_ttl.py`）

```python
PENDING_PANEL_TTL_SECONDS = 180.0     # 普通确认
PENDING_DANGER_TTL_SECONDS = 60.0     # 危险操作（reason/matched_rule 命中 danger/secret/protected）
PENDING_REMINDER_BEFORE_S = 30.0      # 到期前提醒（GUI 倒计时高亮）
# AskUserQuestion -> None（不超时，由用户显式关闭结束）
```

★ **危险操作 TTL 更短**的双重理由：① 悬着的「删除工作区外文件」批准窗口本身就是风险（用户回来可能习惯性点同意）；② 更短 ⇒ 更快落到默认拒绝（方向安全）。

★ **`AskUserQuestion` 不超时**的原因：它是「问信息」而非「求授权」——**授权有默认答案（拒绝），信息没有默认答案**。兜底不靠 TTL 而靠：外部取消（面板关闭 → `cancelled`）+ 回合级 timeout/abort + 工具语义限定。

★ `ttl_for_request` 判「危险」靠 `reason`/`matched_rule` 的**关键字匹配**——「用文案判风险」是脆弱点（可追问）。

### 5.2 三条结果文案必须分开（`:31-45`）

| 情况 | 文案要点 |
|---|---|
| 用户**显式拒绝** | `the user **explicitly rejected** this action. **Do not retry** the same call; adjust the approach or ask the user.` |
| 面板关闭 / Esc / 停止 | `cancelled: the user **dismissed the approval panel** before deciding. Do not retry the same call without asking.` |
| **审批不可用**（超时/协调器缺失） | `unavailable: the request **timed out without a decision** and was treated as rejected.` |

★ 三分的必要性：**后续动作不同**（显式拒绝≠重试；面板关闭要先问；超时是**环境问题**不是用户态度）。★ 第三条的 `was treated as rejected` 同时给出**结果**与**性质**。★ 三条都**无劝导**（符合引擎文本纪律）。

### 5.3 挂起存储与幂等（`store.py:1-33`）

```
key = request_id，保存 pending 请求与唤醒信号；支持超时与幂等 resolve。
同一 request_id 只能被处理一次。
桌面 / 微信 resolve 均走本 store，成功时写 ``permission.resolved`` 审计。
三选 peer ASK：``user_choice`` 为 allow / deny / remind；旧客户端只传 approved。
```

★ **`remind` 让状态机不是二元终态**（它表示「稍后再提醒我」= **仍未决**），所以幂等实现必须能表达「第三种终态之外的第四种状态：仍在等」。
★ 审计**成对**：`permission.pending` ↔ `permission.resolved`（**allow/deny 都记**）。docstring 说明曾经有两套命名（`approval.asked/decided`），**已收敛为一套**（避免双写）。

## 6. write_scope：子 agent 写范围（`write_scope.py` 157 行）

**三态语义**（docstring `:1-6`）：

```
None  -> 主会话，不按 scope 限制（仍走工作区/策略门禁）
()    -> 子 Agent 未声明 scope -> 禁止 Write/Edit
非空  -> 写路径必须落在任一 scope 前缀下
```

`write_scope_deny_reason` 两个原因码：`write_scope_empty`（本来就不能写）与 `write_scope_denied`（能写但这条路不在范围内）。

`normalize_worker_scope(raw, cwd)` → `(paths, read_only, reason)` 做**三类收束**：

| 类 | 判定 | 处置 |
|---|---|---|
| 过宽 | `.` / `./` / 仓根 / **盘符根**（`C:`、`C:/`、`/`、`\`） | 丢弃 + `broad=True` |
| 仓外 | `rel` 以 `..` 开头或绝对路径 | **当作无效，不扩大权限** |
| 可收束 | 仓内绝对路径 | 收成**相对 cwd 前缀** |

最终：`broad and not out` → `([], True, "scope_too_broad")`（全过宽**整体降只读**）；否则保留合法项 + reason 标注。

★ **盘符根为什么比仓根更危险**：范围到**整个文件系统**（含系统目录、用户目录、其他项目、`~/.ssh`），且 `C:` 这种写法**形似相对路径**，必须**单独判**（不能只判 `.`）。

★ 与 `Agent.scope` 的分工：**工具面移除**（模型看不到）→ **上下文层白名单**（能写但受限）→ **执行层拒绝直写**（`write_store is None` 且 `get_write_scope() is not None` 时抛 `RuntimeError`，B04 已确立）。三层不是冗余，是**同一约束在不同层次的表达**。

★ 多 agent 并发写同一文件的权限语义（面试压轴）：`scope` 是**允许集合、不是所有权**（`["src/a"]` 与 `["src"]` 都允许写 `src/a/x.py`）。正确性由**写路径三层**保证：`base hash` 校验（后写者基于旧内容 → 拒绝）+ 分片锁 + 租约。缺口：**当前模型无法表达「这块归 A、不归 B」**（需独占标记或 worktree 隔离）。

## 7. 仓库策略文件（`workspace_policy.py` 257 行）

`.xeyo-policy.json` 四个开关面：

| 维度 | 取值 | dataclass 默认 |
|---|---|---|
| `bash` | default / ask / allow / deny | `"default"` |

另有 `bash_escalate`（渐进强制，**推荐 3 / 上限 5**，`0`=关）与 `bash_job_memory_mb`（**下限 64**）。

★ **`remote_bash` 只有 ask/deny** 是刻意的：远程通道**不允许配置成自动放行**（远程入口的持有者身份更难确认）。
★ docstring 声明「缺省文件 = 对外安装默认 `bash=ask`/`write=ask`/`remote_bash=ask`」，而 dataclass 字段默认是 `bash="default"`/`write="risk"` —— **两处口径不同**（「文件缺失」vs「文件存在但未写该键」），面试可追问。
★ **T25 fail-closed**：坏文件（解析失败）一律**回退收紧默认并记审计**；`exists` 属性语义是「**存在且解析成功**」。
★★ **为什么必须 fail-closed（真正理由）**：策略文件是**仓库里可提交的文件**，若「坏文件 = 无策略」，那么「**让文件解析失败**」就成了一种降权手段。即同时防误配置与**防绕过**。
★ 单向性方向（docstring `:8-10`）：「放宽只能走用户侧（env / grant store / preset），**仓库策略不再反客为主**」。

## 8. 兼容层与执行期标记

### 8.1 ASK → DENY 的两处降级

```python
# filesystem.enforce_decision（:356-367）
	ALLOW -> (ALLOW, "allowed")
	ASK   -> (DENY,  "needs_confirmation")     # 与真 DENY 的 "denied" 不同！
	DENY  -> (DENY,  "denied")
```

★ **保留 reason 区分**：调用方/日志能看出「这是缺 UI 而不是规则禁止」。`gate.py`(71) 是同类兼容层（docstring：「真实裁决已收敛到 `permissions.policy.evaluate_policy`」，「供旧测试与不走 `ToolRegistry` 挂起流程的调用方使用」），其 `_deny_reason` 还把 `needs_confirmation` **映射回可读路径原因**（`path_outside_working_directory` / `dangerous_path`）。

★ **判断一个兼容层该留还是该删**（方法题）：① 还有调用方吗？② 它是**薄**适配层（只做形态转换）还是**复制了一份逻辑**？③ 会不会成为绕过点？④ 删掉成本？——**薄适配层可留（危险的是复制逻辑的那种）**；本处的真实风险是**误用**（生产路径走它 ⇒ 用户无法批准任何需要确认的操作）。

### 8.2 `preapproved`：双重裁决的产物（`filesystem.py:12-29`）

```python
_preapproved_ctx = contextvars.ContextVar("xeyo_permission_preapproved", default=False)
def permission_preapproved() -> bool:
	"""Registry 已 ALLOW / skip_ask 后执行工具时为 True，避免工具内 ASK→DENY。"""
```

工具内的读/写入口在遇到 ASK 时**只信这个标记**（`:414-415,433-434`）：

```python
	if decision == PermissionDecision.ASK:
		return permission_preapproved()
```

| 设计点 | 理由 |
|---|---|
| **ContextVar**（非全局布尔） | 并发会话/协程隔离（与容器路由用 ContextVar 防串线同一理由） |
| `contextmanager` + `finally: reset` | 异常路径也复位 ⇒ 不产生「一次批准 → 后续永久免批准」的**标记泄漏** |
| `default=False` | 方向安全 |

★ **工具内那次检查仍有必要**（不是冗余）：① 工具可能被**非 registry 路径**调用（单测 / CLI 直连 / 子 agent 独立执行，`gate.py` 正是为这类调用方保留）；② **参数解析层不同**（registry 看原始 dict，工具内看解析后的 dataclass，`_extract_path_from_input` 同时支持两者）；③ fail-safe 方向。

## 9. 判定的基准：cwd 从哪来（B07 与 B08 的交界）

`filesystem._tool_cwd` 三层：① `context.cwd` > ② `tool._cwd` > ③ `os.getcwd()`。
`default_permission_context` 在无显式 cwd 时**刻意绕开模块级全局 cwd**，改读会话级 `WorkspaceContext`（docstring：「避免多并发会话读取模块级全局 cwd 而**串目录**」）。

★ 追问点：`grep` 权限用的 cwd 与「工具实际运行的目录」不一致时，**判定的对象与实际操作的对象不同**（相对路径解析基准不同）。结构性方向：判定后把解析出的**绝对路径**一路传下去（与 realpath TOCTOU 的修法同构）。

## 10. 越权面总账（面试压轴，按可利用性排序）

| # | 绕过面 | 现有防护 |
|---|---|---|
| 1 | **判定与使用的 TOCTOU**（realpath/symlink） | ❌ 未覆盖 |
| 2 | **判定基准不一致**（权限 cwd ≠ 执行目录） | ⚠️ 靠调用方传对 cwd |
| 3 | **多 allowed 根下元数据保护失效** | ❌ 未覆盖 |
| 4 | **`XEYO_ALLOW_PROTECTED_METADATA`**（进程级 env、不分会话/路径、**无审计**） | ⚠️ 默认关但粒度粗 |
| 5 | **Bash 是独立通路**：密钥保护只在**路径裁决**层，而 Bash 以**命令字符串**为输入；`printenv`/`env` 在只读白名单里 ⇒ **环境变量里的密钥完全不经路径判定** | ❌ 结构性缺口 |
| 6 | 密钥清单不完备（14 文件名 + 4 后缀 + 4 目录） | ⚠️ 泛化 + 模板豁免 |
| 7 | 策略文件坏文件若 fail-closed 未实现 ⇒ 制造解析错误即可降权 | ✅ 已 fail-closed |
| 8 | 包外写入者（Bash / 外部编辑器 / 构建链）不经权限门 | ❌ 结构外 |
| 9 | 仓库策略放宽用户权限 | ✅ 已被单向性约束 |

**纵深防御四层**：① 应用层（三态 + 路径狱 + 硬拦，需补 TOCTOU 与多根一致性）→ ② 会话层（mode/preset/store 活状态 + 单向性）→ ③ 执行层（`write_scope` + `WriteStore` + 快照）→ ④ **系统层（容器/沙箱/ACL/网络策略）＝ 本项目最大空白**。

★ 核心认识：**应用层权限不是安全边界**——它防「模型走错路」，不防「恶意进程」。

## 11. 易错点清单

1. ASK 不是「软拒绝」（它是独立状态机，有挂起/TTL/回执/四态）。
2. `allow` 不是第五档（归一为 `never`）。
3. `full` preset **不等于**关闭权限。
4. `_SECRET_DIRECTORIES` **不含 `.git`**；`.git` 的保护分三条路（区内写/区内读/区外）。
5. `enforce_decision` 的 ASK→DENY 保留 `needs_confirmation`（与 `denied` 不同）。
6. `strictness()` 对未知值返回 0（永不赢过合法值）。
7. `AskUserQuestion` 不超时；权限确认 180s、危险 60s。
8. `preapproved` 用 ContextVar 且必须 `finally` 复位（否则标记泄漏）。
9. `normalize_preset` 会静默回退**可写档**，所以 `RuntimePresetStore` 用原始名校验 + 拒绝。
10. `protected_metadata_reason` 只对**工作区内**生效（`..` 开头即放行）。
11. 密钥判定在边界之后且**无条件执行**（最高档放宽区外也不放行密钥）。
12. 写裁决复用读裁决 ⇒ 额外可读根**实际也放宽了写**（与注释矛盾）。
13. `remote_bash` 只有两档（无自动放行档）。
14. 仓库策略「不再反客为主」（放宽只能走用户侧）。
