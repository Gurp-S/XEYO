### 2.1 转述准确的部分（文档【官】标注全部成立）

### 2.2 文档**漏掉**的两条官方事实（实施时会踩）

1. **thinking 模式下 `temperature` / `presence_penalty` / `frequency_penalty` 全部无效**——
   官方原文：*"Thinking mode does not support the `temperature`… please note that, for compatibility with existing software, setting these parameters **will not trigger an error but will also have no effect**."*
   → 你们 `openai_compat.py` 在 `self._temperature is not None` 时发 `temperature`（第 193-194 行）。**在 thinking 开启后这是个静默无效参数**——不报错，但你以为是贪心采样其实不是。这对**分数可复现性**是直接威胁，S6 记录生效值时必须一并记这个。

2. **`top_p` 在 thinking 模式下有 0.95 下界**——低于 0.95 会被抬到 0.95；非 thinking 模式固定 1.0 且忽略传值。
   → 若将来有人用 top_p 调参做 A/B，两臂的实际采样分布不同，结论不可比。

## 三、③ 轨迹复算（推翻「零命中」）

### 3.1 实测数字

扫描 `TerminalBench/run/` 全部 88 份轨迹：

| 指标 | 实测值 | 文档值 | 判定 |
|---|---|---|---|
| 轨迹份数 | **88**（1 题无轨迹） | 89 | 微差 |
| `reasoning_content` 命中份数 | **59** | **0** | ❌ **文档错** |
| reasoning 字符占比 | **91.6%**（8,866,042 / 9,679,635） | ~94% | 方向对，微差 |
| 可见正文 P50 | **483 chars ≈ 138 tok** | 155 tok | 方向对，微差 |
| 真实 API 报错（400 / must be passed back） | **0** | 0 | ✅ 文档对 |

> 唯一被关键词扫出的 `custom-memory-heap-crash` 经逐字检视：命中串出自模型正文的英文句子 *"…ensures libstdc++ facet allocation is not through the custom heap **cannot be modified**."*，**不是 API 报错**。

### 3.2 ★ 为什么文档会得出「零命中」——两族 schema 分裂

88 份轨迹**不是同一套格式**，按 mtime 干净分成两族：

| | **A 族** | **B 族** |
|---|---|---|
| 份数 | 59 | 29 |
| 单份时间 | 09-06 01:19 → 13:13 | 09-06 15:45 → 09-07 13:15 |
| 顶层 schema | `steps[]` + `final_metrics` | `transcript[]` + `usage` |
| agent 标识 | `terminus-2` 风格 | **XEYO 引擎自产** |
| `reasoning_content` | **59/59 有** | **0/29 有** |
| 单条字段 | 有 `reasoning_content` | 仅 `id/role/ts/content`（+`narration`） |

**关键**：B 族的 `transcript[]` 条目字段 = `{'content','id','narration','role','tool_call_id','ts'}` ——
**与 `msgtypes/message.py` 的 `Message` 字段逐一对应，且正在缺 `reasoning`。**

也就是说：

> **B 族 29 份轨迹没有 `reasoning_content`，不是因为「没进强制校验区」，而是因为 XEYO 引擎的 `Message` 结构里根本没有这个字段 → 落盘时结构性丢弃。**

### 3.3 这一发现的三个连带结论

**① 问题 1 从「推断」升级为「实测证据」。**
文档问题 1 的证据是代码行号（【码】）。现在我有了**运行期实证**：B 族 29 份轨迹（覆盖 29 题、跨 09-06 15:45 → 09-07 13:15 约 21 小时）**全部无 reasoning 落盘**，而这 29 题合计 output tokens 非零。→ **思考 token 花了、内容确实丢了。**

**② 问题 3 的机制诊断要重写。**
文档说「请求里从未显式声明 thinking → 恰好没进强制校验区」。**真实机制更简单也更危险**：
- 适配器 `xeyo_harbor_agent.py:162` 传 `provider="openai"`；
- `openai_compat.py:184` 的 `if self._provider == "deepseek"` 分支**不成立** → `thinking` 字段**从未发出**；
- 而 A 族（terminus-2 自产，59 份）**有** reasoning_content → 说明**厂商默认确实开着 thinking**；
- 既然开了 thinking 且**请求带 tools**，按官方文档就**已经**进了强制校验区；
- **那为什么没 400？** —— 因为 XEYO **从不回传、也从不声明**，走的是「厂商按默认开、但请求侧当非 thinking 处理」的**未定义夹缝**。

**所以「当前没有正在流血」这个判断的可信度要下调**：不是「安全区」，是「依赖厂商宽松处理的未定义行为」，且**A 族的存在证明厂商默认是开的**。一动就炸的判断成立且应加强。

**③ 数据规模要更正**：88 份（不是 89），且**两族混合统计出的占比是有偏的**——A 族 59 份是 terminus-2 跑的，B 族 29 份才是 XEYO。**91.6% 这个数跨了两套引擎**，严格说不能直接当作 XEYO 的思考占比。若只算 B 族，reasoning 占比是 **0%**（因为没落盘）——这恰恰是问题本身。

### 4.2 五组实验、11 次调用结果

| 组 | 设计 | 文档预期 | **实测** |
|---|---|---|---|
| **A** | 带 tools，不回传 reasoning | **400** | **200**（重复 4 次全部 200） |
| **B** | 带 tools，原样回传 | 200 | 200 ✅ |
| **C** | 无 tools，不回传 | 200 | 200 ✅ |
| **D** | ★ **显式 `thinking:{type:enabled}`** + `reasoning_effort:high` + 带 tools + **不回传** | **400** | **200**（重复 2 次全部 200） |
| **E** | ★ **官方文档同款多轮 tool 循环**（get_date→get_weather→答），显式 enabled，**全程不回传** | **400** | **sub1/sub2/sub3 全部 200**，完整走完 |
| F | 对照：显式 `thinking:{type:disabled}` | — | 200，`reasoning_content` 长度 **0**、`reasoning_tokens` 为 None |

### 4.3 A 臂细节（最关键的对照）

```
t1 = 200, reasoning_content 有内容 (75 chars), 1 个 tool_call
t2 = 200（丢掉了 reasoning_content）→ 正常完成，content 100 chars
```

**第二轮不仅没报 400，还正常答完了。** 重复 4 次，结果稳定。

### 4.4 F 组的意义（额外收获）

显式 `disabled` 时 `reasoning_content` 长度为 **0**、`reasoning_tokens` 为 **None**；而不声明时 `reasoning_content` 有内容（A 组 t1 = 75 chars）。

→ **双向确认**：厂商默认档确实是 **enabled**（官方文档说法被实测印证），且 `disabled` 能真正关掉。
→ 这同时**反证了问题 4 的诊断**：TB 轨迹里有 reasoning 内容，说明适配器传 `provider="openai"` 时**确实没发出 `thinking`**，厂商走了默认 enabled 档。

### 4.5 结论与如何解读

**实测结论**：「不回传 `reasoning_content` → 400」在本时点/本模型/本账号**未复现**。

**三种可能解释**（**无法从本轮数据区分，不得当作结论**）：
1. 厂商对 `deepseek-v4-flash` 尚未启用该强制校验（文档描述的是设计要求，落地有延迟）；
2. 校验只在更长的历史 / 特定模型（如 `deepseek-v4-pro`）/ 未来版本触发；
3. 校验的触发条件比文档描述的更窄。

**★ 但《最终方案》自己已经预置了这条预案**，原文写：

> **风险：A 臂可能不报 400**（若该模型/档位不强制）。此时**不能据此认为"不用做"**——需按文档要求做保守实现（原样回放），仅把"强制校验"的结论降级。

**这条预案现在正好适用，应当正式启用。** 即：
- **仍然做 S1/S2/S3**（原样采集 + 原样回放）——理由从「避免 400」转为「**历史保真 + 消除每轮重推**」；
- **S6（显式声明 thinking）的紧迫性下调**——它不再是「不解就炸」的前置；
- **收益主张必须完全依赖 4.3 的 A/B（Σoutput）**，不能拿「协议合规」当理由。
