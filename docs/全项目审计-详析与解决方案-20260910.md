## 一、三条横切模式：具体说明

这三条不是并列的清单项，而是**同一个病灶的三个切面**——XEYO 的架构正确性很高，但**"谁拥有真相"这件事没有被机器执法**：能力可以有两份实现、机制可以没有消费方、写入可以绕过主链，全都靠人记得。

### 模式 1：双轨并行 —— "同一件事，两套实现，两个 bug 面"

**具体清单（5 处，均经核实）**

| # | 双轨 | A 轨 | B 轨 | 危害 |
|---|---|---|---|---|
| 1 | **回滚** | v3 `RewindHotpath`（在线主路径） | v2 `RollbackService`（`/rollback/*` 降级端点） | 两者内存对齐契约不同：`drop_engine` vs `resync_after_rewind`，改一处漏一处 |
| 2 | **MCP 执行** | `mcp__<server>__<name>__<hash>` 直挂（走 `registry.run`，有编排/预算 seam） | `Mcp` 网关 `action=call`（`mcp_gateway.py:171` 直接 `target.execute`，仅 4KB 裁剪） | 同一能力两套计量与审计语义 |
| 3 | **ASK 面板** | `permissions/store.py`（权限 ASK：有审计、有 TTL） | `permissions/ask_store.py`（AskUserQuestion：**零审计**，`resolve` 无鉴权） | 同构重复，一个有一份没有 |
| 4 | **C2 压缩决策** | formula 压力∧收益门（`runtime.py:1546-1596`） | `a_star=="C2"` decide 分支（`:1606-1645`）+ `force_compact`（`:1883-1924`） | 三处各自维护 cursor 前进/事件记账 |
| 5 | **SSE 消费** | GUI（TS 类型 + 分片 store） | TUI 内**自己就有三份**：`sse.ts`（17 类）+ `App.tsx:581`（permission_pending）+ `runJson.ts:98` | 服务端 20 类事件，任何一端加了新事件，另外四处静默失明 |

**根因**：没有"单一真相源"的机器约束。新机制上线时，旧机制因为"还有测试在跑"而被保留（如 Scheduler、v2 回滚），从此两套一起腐化。

**为什么危险**：每处双轨都是**两个独立的 bug 面**。修 A 轨的补丁不会流到 B 轨——而 B 轨往往正是"降级路径"，恰恰在 A 轨出问题时才被启用。

**解决方案（分层，按代价递增）**

1. **立即可做——加"双轨登记表"**（零风险，纯文档 + 测试）：
   建 `python/tests/test_single_source_of_truth.py`，把上述 5 组写成显式清单（A 轨文件 + B 轨文件 + 主从裁定 + 责任人）。
   测试内容不是"断言逻辑"，而是**断言 B 轨的存在被登记过**——新增第二实现而没登记即红。
   代价：~半天。收益：把"靠人记得"变成"机器提醒"。

2. **中期——定主从并冻结**（按 5 处的独立价值分别裁定）：
   - #1 回滚：**砍 v2 或明确降级为"仅测试工具"**（把 `/rollback/*` 从生产 app 摘掉，只在 pytest fixture 里 import）。v2 的 preflight 能力已被 v3 的 `GET /rewind/checkpoint/{id}` 覆盖。
   - #3 ASK 面板：**合并为一套 store**，AskUserQuestion 复用权限 store 的审计 + TTL。这是净减代码，不是净增。
   - #4 C2：**收敛为单一 `decide_c2()` 函数**，三个调用点都只调它。这是 §二·P1-8 的核心。
   - #2 MCP：**网关单路径**（直挂工具改为"注册但只经网关调用"），或反向——明确裁决其一。这是 09-04 审计的 P1 建议，至今未做。
   - #5 SSE：**抽共享事件 schema**（见 §四·新增1 的具体方案）。

3. **长期——术语表**：`Turn`（模型轮 vs submit）、`v2/v3`、`run/submit` 三组同名异义写进 `AGENTS.md`，新代码禁止再用歧义名。

### 模式 2：写了没接线 —— "代码在，消费方不在"

**具体清单（7 处，均 grep 核实零生产消费者）**

| 模块 | 规模 | 现状 | 判定 |
|---|---|---|---|
| `engine/scheduler.py` | 1110 行 | `run_task_batch`/`prepare_for_resume` 引用只在 `tests/`；生产只借用其 `Task`/`scope_conflicts` 数据结构 | 主执行链死代码 |

| `codeindex/cgraph.py` | 287 行 | 零 import，docstring 自认"离线证据门原型" | 脚手架残留 |
| `memory/cache_profile.py` | 20 行 | docstring 自述"仅占位，不含实现" | 占位 |
| `tools/stub.py` | — | 返回 "not implemented yet"，无调用者 | 死代码 |
| `clear_wrap_window()` | — | 定义了但全仓无调用（`wrap_window.py:46`） | 死代码 |
| `incomplete_tool_uses` | — | 3 个写入点，**零消费点** | 半成品 |
| `memindex.edges` | — | `add_edges` 有写，`edges_for` 无非测试调用者 | 有写无读 |
| `write_store._apply_multi` | — | 全仓无调用方 | 死代码 |

**根因**：**"先写好，接线以后再说"的开发顺序** + 测试跟着实现写（实现了就测），于是**测试覆盖率反而成了死代码的掩护**——`scheduler.py` 有 50+ 用例高强度覆盖，绿灯给出"这东西在工作"的假象。

**为什么危险**：
- 阅读成本：新人（或 3 个月后的你）会以为调度器在工作，从而在别处做出错误假设；
- 维护成本：每次重构都要顾着这些永不执行的分支；
- **最危险的是 `incomplete_tool_uses`**：它意味着崩溃恢复时**未配对的 tool_use 不会被修复**——这是个真实的功能缺口，不是卫生问题。

**解决方案（一律二选一，不允许"再放放"）**

对每一处只允许两种处置，且必须显式记录：

```
接线  → 加一个真实生产调用点 + 一条端到端回归测试（不是单元测试）
删除  → git rm + 在 CHANGELOG 记录"未接线模块清理"
```

**具体建议（按性价比）**：

| 模块 | 建议 | 理由 |
|---|---|---|
| `incomplete_tool_uses` | **接线**（最高优先） | 这是真缺口：崩溃后未配对 tool_use 应触发 `_fill_missing_tool_results`。旧审计已指出它与 `hydrate._repair_unclosed_tool_uses` 语义重叠，应**收口到一个修复入口** |
| `scheduler.py` | **删除主执行链，保留数据结构** | DAG 调度器思路与现状（协程 gather 涌现并发）冲突；保留 `Task` 等被复用的类型，删 `Scheduler.run/_dispatch/_persist/load_state` |
| `stage_clock.py` / `stub.py` / `cache_profile.py` / `cgraph.py` | **删除** | 纯脚手架，无落地意图（cgraph 若确定要做，改名为 `_prototype_cgraph.py` 并加显式 TODO 归属） |
| `clear_wrap_window` | **接线或删** | 见 §二·P1 相关条目：它是 wrap 状态的收尾缺口 |
| `memindex.edges` | **接线或删表** | 建表+写入却不读，纯写放大 |
| `write_store._apply_multi` | **删除** | 且它有个真 bug：多文件写中途失败不回滚（"multi-file partial"），既然无调用方，删掉最安全 |

**加一条防复发机制**：CI 里加**死代码探测**——对 `python/engine`、`python/memory`、`python/codeindex` 跑 `vulture`（或 `pyflakes` + 自写"函数定义但零引用"扫描），把新增的未接线函数挡在门外。代价：半天；收益：结构性防复发。

### 模式 3：旁路绕主链 —— "引擎维护的不变量，被单点抵消"

**具体清单（3 条旁路 + 1 条隐性）**

| 旁路 | 绕过了什么 | 证据 |
|---|---|---|
| `server/workspace_fs.py` 直写 | 权限 + rewind + 审计（三链路全绕） | `:196-239` |
| 后台 bash job（晋升后） | rewind（产物不可回滚）+ abort（解绑）+ 超时（24h=无） | `job_registry.py:38/254`、`destructive_guard.py:28-31` |
| WriteStore 写路径 | rewind Before 快照（写的是 `memory.journal`，另一本账） | `write_store.py:25/307` |
| bash_tool 重定向写文件 | rewind（只记 `_note_bash_write_target`） | `bash_tool.py:671` |

**关键理解**：这四条合起来意味着——

> **rewind 只覆盖三个文件工具的写入。**任何通过 Explorer 编辑器（GUI 用户）、后台作业、子 agent（WriteStore）、bash 重定向产生的文件变更，**回滚时都不在账上**。

后果分两种：
- **残留**：回滚后这些改动仍在（用户以为退回去了，其实没有）；
- **撕裂纹**：如果这些改动依赖被回滚的文件（如改了 A、又在 B 里 import A），回滚后工作区进入不一致状态。

**根因**：**"写入口清单"没有单一事实源**。09-04 审计已指出这条（"补偿/快照覆盖面按写入口划分而非按数据面划分"），但修复需要"所有写入口都配合"，而写入口散落在 4 个模块，没有机器清单。

**解决方案（这是本报告技术含量最高的一条）**

**核心思路：不要在 4 个写入口各加一次 rewind 调用（必然漏），而是把 rewind 的记账下沉到"文件系统写原语"这一层。**

具体分三步：

**Step 1（必做，~2 天）——建立写入口登记表 + 机器执法**

新建 `python/tests/test_write_path_registry.py`，显式列出所有能修改工作区文件的入口及其覆盖状态：

```python
WRITE_PATHS = [
    # (入口, 是否进 rewind, 是否进审计, 是否经权限)
    ("tools/file_write_tool",        True,  True,  True),
    ("tools/file_edit_tool",         True,  True,  True),
    ("tools/notebook_edit_tool",     True,  True,  True),
    ("engine/write_store",           False, True,  True),   # ← 缺口，标记
    ("tools/bash_tool(redirect)",    False, False, True),   # ← 缺口，标记
    ("server/workspace_fs",          False, False, False),  # ← 最大缺口
    ("server/job_registry(promoted)",False, False, False),  # ← 缺口
]
```

测试断言：**任何 `False` 必须在缺口白名单里**——新写入口若默认不进 rewind 且未登记，测试即红。
这与模式 1 的"双轨登记表"同构，可以合并成一个"架构不变量登记"测试文件。

**Step 2（核心修复，~3-5 天）——把 rewind 记账下沉到共享原语**

现状：`record_file_mutation`（rewind Before 快照）被**手动调用**在 3 个工具里。改为：

```
所有工作区写 → 统一经 write_store / 一个共享的 "workspace_write_gate"
             → gate 内部自动：① 权限裁决 ② Before 快照 ③ 审计 ④ 落盘
```

这样：
- `workspace_fs` 改调 gate（而不是裸 `path.write_text`）；
- WriteStore 内部调 gate（而不是只写 `memory.journal`）；
- bash_tool 的重定向写目标——**这是最难的一处**，因为 shell 重定向发生在子进程内，引擎无法拦截。可行做法：bash 命令执行前，**若命令含重定向操作符且目标在工作区内**，执行前对该目标做一次 Before 快照（与 `destructive_guard` 同一思路，实际上 `destructive_guard` 已经做了 rm/mv 的快照，扩展它覆盖重定向即可）。

**Step 3（加固，~1 天）——后台 job 的 timeout 与 abort 收口**

- `job_registry.py:38` 的 `JOB_NO_TIMEOUT_MS = 86_400_000` 改为**可配置上限**，默认建议 30 分钟（`XEYO_JOB_MAX_TIMEOUT_MS`），并在 job 状态里暴露"已运行时长"；
- 明确**job 与 session abort 的关系**：当前设计是"会话 abort 不杀 job"（42 号冻结口径，`:296-299` 注释）。这**是刻意的产品决策**，不是 bug——但需要补一条：**会话被回收时（而非 abort 时）应提示仍有 N 个 job 在跑**，避免用户以为已停。

## 二、6 项 P0：具体说明 + 解决方案

### P0-1　`workspace_fs` 直写绕过引擎三链路

**现象**：`PUT /v1/workspace/file`（写文件）与 `DELETE /v1/workspace/file`（支持 `recursive=true`）直接落盘，不穿权限、不进 rewind、审计失败静默吞。

**根因**：这是**有意设计的直写通道**（注释称之为"直写旁路"），服务于 GUI Explorer 编辑器的即时保存——模型不在链路上，所以「引擎权限」这一环在语义上确实不适用（没有 tool_use 可供裁决）。

**★ 修正首轮描述**：它不是"忘了接线"，而是一个**有明确用途的旁路**，问题在于**它的安全边界没有配齐**：

| 应有 | 现状 |
|---|---|
| 进 rewind（用户手动编辑也该能回滚） | ✘ 完全没有 |
| 进审计（谁在什么时候写了什么） | △ 有 `_audit_write`，但 `except: pass` 吞掉失败 |
| 默认只读开关 | △ 有，但**默认关**（即默认允许写） |
| 路径约束 | ✔ `resolve_in_workspace` + `_EXCLUDED_DIRS` |
| 大小上限 | ✔ `_MAX_TEXT` |

**影响面**：本机任意进程（在 loopback 门禁下）可写删工作区任意文件，且**用户无法用 rewind 撤销**；`recursive=true` 可整棵删目录。

**解决方案（分两步，先止血后收口）**

**Step 1（止血，~0.5 天，建议立刻做）**
```python
# workspace_fs.py:37-39
def _workspace_fs_writes_allowed() -> bool:
    # 反转默认：只有显式开启才允许直写
    raw = os.environ.get("XEYO_WORKSPACE_FS_WRITABLE", "").strip().lower()
    return raw in ("1", "true", "on", "yes")
```
同时把 `_audit_write` 的 `except Exception: pass` 改为 `except Exception: _logger.warning(...)`。

> 注意：反转默认会**改变产品行为**（GUI 编辑器保存会失败），所以需要**同批改前端**：`explorerStore.saveFile` 在写失败时给出明确提示。这是"默认拒绝 + 显式开关"的标准做法，建议连同 §三·P0-6 一起做为"开源前的安全默认值"批次。

**Step 2（收口，~1 天，随模式 3 Step 2 一起做）**
把 `write_file`/`delete_path` 改为调共享 write gate（自动获得 rewind + 审计），这样 GUI 手动编辑也进回滚账本。

**验收**：①默认档下 `curl PUT /v1/workspace/file` 返回 403；②开启开关后写入的文件出现在 rewind 检查点里。

### P0-2　`usage.py` 开放 SSRF 代理面

**现象**：三个端点（`/v1/models`、`/v1/usage`、`/v1/usage/balance`）接受 `X-Base-Url` 请求头，值**原样拼接**后发请求。

```python
# deps.py:72-76 —— 无任何校验
def _resolve_base_url(provider: str, base_url: str | None) -> str:
    if base_url and base_url.strip():
        return base_url.strip().rstrip("/")   # ← 原样返回
```

三个端点里最危险的是 `balance`（`usage.py:79-92`）：它用 `urlopen` 直连，且带上 `Authorization: Bearer <api_key>`。

**根因**：`X-Base-Url` 的**用途是合法的**——让用户指向自建代理/中转站（如 one-api、new-api），这是真实需求。问题在于**没有把它约束在"用户已配置的可信端点"上**，而是接受任意请求头。

**影响面**：
1. **带凭据的 SSRF**：本机任意进程可让 XEYO 带用户的 API key 请求任意地址 → key 外泄；
2. **内网探测**：`http://169.254.169.254/`（云元数据）、`http://localhost:PORT/`（扫本机服务）。

**解决方案（~0.5 天，三选一，推荐 A+B 组合）**

**A. 白名单化（推荐主方案）**
不信任请求头，改为**只接受设置里已保存的 baseUrl**：
```python
# deps.py
def _resolve_base_url(provider: str, base_url: str | None) -> str:
    preset = PROVIDER_PRESETS.get(provider, {}).get("base_url", ...)
    if not base_url:
        return preset
    # 只允许：① 官方 preset ② 用户在 settings 里显式保存过的地址
    if _is_user_configured_base_url(base_url):
        return base_url.strip().rstrip("/")
    raise HTTPException(403, "base_url not in configured allowlist")
```
配套：`POST /v1/settings` 保存 baseUrl 时做一次校验（scheme 必须 https/http，**拒绝私网 IP 与 link-local**）。

**B. scheme/地址过滤（必须叠加的底线）**
即使走白名单，也在拼接前加：
```python
_SCHEME_ALLOW = {"http", "https"}
_BLOCKED_HOSTS = {"169.254.169.254", "metadata.google.internal"}

def _assert_public_url(url: str) -> None:
    u = urlparse(url)
    if u.scheme not in _SCHEME_ALLOW:
        raise ValueError("scheme not allowed")
    infos = socket.getaddrinfo(u.hostname, None)
    for info in infos:
        ip = ipaddress.ip_address(info[4][0])
        if ip.is_private or ip.is_link_local or ip.is_loopback:
            raise ValueError("private address not allowed")
```
> 注意：`is_loopback` 会挡掉本地 llama.cpp / `provider="local"` 场景。所以 **A 与 B 要配合**——用户显式配置的本地地址（`XEYO_ALLOW_LOCAL_MODEL=1` 档）走白名单放行，其余一律挡。

**C. 统一到 WebFetch 已有的 SSRF 门（最优，若时间允许）**
`tools/web_common.py:19-73` 已经有一套完整的 SSRF 防护（scheme 白名单 / 私网 / metadata IP / DNS 逐地址复查 / 每跳重定向复检）。**把 usage 的三个端点改为复用这套原语**，而不是新写一份——这既修了洞，又消掉了"两套 SSRF 逻辑"的新双轨。

**验收**：①`X-Base-Url: http://169.254.169.254/` 返回 403；②`X-Base-Url: https://api.deepseek.com/v1` 正常；③用户在设置里保存过的自建中转地址正常。

### P0-3　Tauri 自定义 command 可写全盘

**现象**：4 个 command 只校验"路径非空且是绝对路径"，然后就对任意位置操作：

| command | 校验 | 后果 |
|---|---|---|
| `save_text_file`（`:483-490`） | 仅非空 | `std::fs::write` 任意绝对路径 |
| `create_directory`（`:579-586`） | `abs_path`（仅判绝对） | 任意目录创建 |
| `git_init`（`:589-593`） | 同上 | 任意位置 `git init` |
| `git_clone`（`:596-607`） | 同上 | 任意位置克隆 |
| `reveal_in_folder`（`:494-511`） | 仅非空 | `raw_arg` 拼 `/select,"path"`，引号可被破坏 |

**根因**：`abs_path()`（`:540-550`）的语义是"确认这是绝对路径"，**不是**"确认这在允许范围内"。名字叫 `abs_path` 而不是 `assert_within_workspace` 本身就说明了这个函数的定位偏差。加上 capabilities 没有给自定义 command 加 ACL，且 **pet 窗口与主窗口同权**，任意一侧被 XSS 即全盘可写。

**影响面**：模型若能影响文件名（它会生成文件名），用户点一下「在资源管理器中显示」或前端调 `save_text_file`，即可写全盘任意位置。这是**从"模型可影响输入"到"任意文件写入"的完整链路**。

**解决方案（~1 天）**

**Step 1 —— 加工作区边界断言（核心）**
```rust
/// 与 abs_path 的区别：这个函数回答"是否被允许"，不是"是否绝对"。
fn assert_within_workspace(path: &str, root: &Path) -> Result<PathBuf, String> {
    let dest = abs_path(path)?;
    let canon_root = root.canonicalize().unwrap_or_else(|_| root.to_path_buf());
    // 注意：目标可能不存在（新建文件），所以 canonicalize 父目录
    let parent = dest.parent().ok_or("路径无父目录")?;
    let canon_parent = parent.canonicalize()
        .map_err(|e| format!("父目录不可解析：{e}"))?;
    let resolved = canon_parent.join(dest.file_name().ok_or("路径无文件名")?);
    if !resolved.starts_with(&canon_root) {
        return Err(format!("路径越出工作区：{}", dest.display()));
    }
    Ok(resolved)
}
```
> **用 canonicalize 是必须的**：否则 `workspace/../../../etc/passwd` 这类含 `..` 的路径能通过 `starts_with` 检查。这是该修复的关键点。

**Step 2 —— 修 `reveal_in_folder` 的参数边界**
`raw_arg` 拼 `/select,"{path}"` 时，路径含 `"` 会破坏参数边界。改为转义内部引号，或改用 `std::process::Command::arg` 传规范化后的路径（explorer 也接受 `/select,` + 独立参数形式）。

**Step 3 —— 加 per-window ACL**
`capabilities/default.json` 目前只约束插件。把 5 个 fs/git command 从"全局可调"改为"仅主窗口可调"，pet 窗口走单独的 capability（若 pet 确实需要 `reveal_in_folder`，就只给它这一个）。

**验收**：①`save_text_file("/tmp/x", "y")` 返回"路径越出工作区"；②`save_text_file(workspace + "/a/b/c.txt")` 正常；③含 `..` 的逃逸路径被挡。

### P0-4　预览 iframe 仍 `allow-same-origin`

**现象**：
```jsx
// BrowserPreviewPanel.tsx:347
sandbox="allow-scripts allow-same-origin allow-forms allow-popups
         allow-popups-to-escape-sandbox allow-downloads"
```
```json
// tauri.conf.json:32
"frame-src 'self' http: https: data: blob:"
```
且 `normalizeUrl`（`:24-40`）**放行任意 scheme**：
```javascript
if (/^[a-z][a-z0-9+.-]*:/i.test(trimmed)) return trimmed;  // data: / javascript: 全部通过
```

**根因**：`allow-same-origin` 与 `allow-scripts` **同时存在**时，sandbox 基本失效——iframe 内的脚本可以移除自己的 sandbox 属性，获得与父页面同源的能力。而这里父页面是 Tauri 主窗口，同源即等于拥有 Tauri IPC 的访问权（`withGlobalTauri` 若开启则更直接）。

**影响面**：模型通过 `xy.ui` 的 `browser` action 可以指定任意 URL（`dispatchXeyoUi.ts:93`）。模型输出 `data:text/html,<script>...</script>` → 直达可执行上下文 → 可调用 Tauri command（含 P0-3 那些无边界 command）。

**★ 与 P0-3 是组合拳**：P0-4 提供入口，P0-3 提供破坏力。**两个一起修才闭合**。

**解决方案（~0.5 天）**

**Step 1 —— 移除 `allow-same-origin`（必做，一行）**
```jsx
sandbox="allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox allow-downloads"
```
> 副作用：移除后 iframe 变成 opaque origin，**对绝大多数预览场景无影响**（预览本地 dev server 页面不需要同源）。若发现某个功能依赖同源，说明该功能本身有问题。

**Step 2 —— `normalizeUrl` 加 scheme 白名单**
```javascript
const ALLOWED_SCHEMES = new Set(['http:', 'https:']);
function normalizeUrl(raw: string): string | null {
    // ... 现有逻辑
    if (/^[a-z][a-z0-9+.-]*:/i.test(trimmed)) {
        const scheme = trimmed.slice(0, trimmed.indexOf(':') + 1).toLowerCase();
        return ALLOWED_SCHEMES.has(scheme) ? trimmed : null;   // data:/javascript:/file: 一律拒绝
    }
    // ...
}
```

**Step 3 —— CSP `frame-src` 收窄**
```json
"frame-src 'self' http://127.0.0.1:* http://localhost:* https:"
```
去掉 `data:` 与 `blob:`。保留 `https:` 是因为用户可能预览线上站点；若要更严，可改为"仅 localhost + 用户确认过的域名"。

**Step 4（可选加固）—— `shell:allow-open` 加 scope**
`workspaceOpen.ts:75` 目前 `open(absolutePath)` 无校验。改为只允许 `http/https` 或工作区内路径。

**验收**：①`data:text/html,<script>alert(1)</script>` 在预览面板被拒；②`http://localhost:5173` 正常预览；③iframe 内 `parent.document` 访问抛 SecurityError。

### P0-5　后台 bash 作业：无超时 + 解绑 abort + 绕过 rewind

**现象**（两段代码，各有其问题）
```python
# job_registry.py:38 —— "防僵尸"的 24 小时上限
JOB_NO_TIMEOUT_MS = 86_400_000
```
```python
# job_registry.py:303-318 —— adopt_bash 的 _produce：无任何超时检查
while proc.poll() is None:
    time.sleep(0.2)          # ← 无限等待，只靠 job_kill 或进程自然退出
```

**根因**：**"后台语义"被当作"不该有超时"**（注释写作"冻结口径：后台语义"）。这在产品上可以理解（后台作业本来就可能长跑），但把"不设超时"实现为"完全没有上限"，就变成事实上的无保护。

**影响面**：
1. `while proc.poll() is None` 是**每 200ms 轮询的忙等线程**——若 job 卡在交互式等待（等 stdin），它会永远转下去；
2. `destructive_guard.py:28-31` 自认后台 job 路径**不做 before 快照** → rm/mv 类后台命令**不可回滚**；
3. abort 解绑是**刻意的产品决策**（`adopt_bash` 注释明写"会话 abort 不杀 job——42 号冻结口径"），这部分**不是 bug**，但缺少"还有 job 在跑"的提示。

**解决方案（~1 天）**

**Step 1 —— 给 job 加上限（保留"后台不设短超时"的产品语义）**
```python
# 不做"3 分钟超时"（那会改变后台语义）；做"可配置的物理上限"
JOB_MAX_TIMEOUT_MS = int(os.environ.get("XEYO_JOB_MAX_TIMEOUT_MS", str(6 * 3600_000)))  # 默认 6h
```
在 `_produce` 里改为带 deadline 的等待：
```python
deadline = time.monotonic() + JOB_MAX_TIMEOUT_MS / 1000.0
while proc.poll() is None:
    if time.monotonic() > deadline:
        handle.kill()
        return STATUS_FAILED, f"job exceeded max runtime ({JOB_MAX_TIMEOUT_MS}ms)"
    time.sleep(0.2)
```
> 默认值取 6h（而非 30min）是刻意的：**不破坏"后台作业可以长跑"的产品承诺**，只挡真正的僵尸。24h 的问题不是"太长"，而是"等于没有"。

**Step 2 —— 后台 job 纳入 destructive_guard 快照**
`destructive_guard.py:28-31` 提到的"contextvars 丢失"是真问题：job 在线程里跑，拿不到请求上下文的 cwd。解法是**显式传 cwd 进 job**（`adopt_bash` 已有 `cwd` 参数），guard 用显式 cwd 而不是 contextvar。

**Step 3 —— 补"job 仍在运行"的用户可见提示**
`SessionJobsBadge.tsx` 已有，但只在会话内显示。补：**会话被回收/切换时若有运行中的 job，给一次提示**。

**验收**：①构造一个 sleep 到 6h+ 的 job，确认被终止且状态为 failed；②后台 `rm -rf` 后确认 before 快照存在；③会话切换时看到 job 提示。

### 新-3　C2 经济门 chars/4 与主干 bytes/4 不一致

**★ 修正首轮描述（重要）**

首轮审计说这是"中文场景差 3 倍的系统性失准"。**经本次数学验证，这个说法不成立。**

看公式（`memory/simulator/c2_gate.py:106-115`）：
```python
transition_miss_tok = (summary + tail) / 4.0
saved_per_turn_tok  = region / 4.0
budget = remaining_turns * saved_per_turn_tok
need   = margin * price_ratio * transition_miss_tok
return budget >= need
```

**两边都被除以 4 → 4 在不等式中约掉。** 换成 bytes/4（中文 ×3）时：
```
budget' = remaining_turns * (region*3 / 4)
need'   = margin * price_ratio * ((summary+tail)*3 / 4)
比值 budget'/need' = budget/need   ← 完全相同
```
数值验证：chars/4 下 `60000 >= 60000` 通过；bytes/4 下 `180000 >= 180000` 同样通过。**判定结果不变。**

**真实问题（降级为 P2 卫生项）**：这是**代码可读性/一致性**问题，不是行为缺陷：
- 生产 `runtime.py:1139` 已用 `token_len`（G66 修过），但 `simulator/c2_gate.py` 的 `economic_gain_ok`（生产通过 `runtime.py:1386` 调用）仍用 chars/4；
- 同一个仓库里两种写法并存 → 未来若有人改公式的**一边**（只改 `/4.0` 的其中一处），就会真的引入 3 倍偏差。

**解决方案（~1 小时，纯卫生）**

把 `economic_gain_ok` 的参数从 `_chars` 改为**无单位比例**，消除口径依赖：
```python
def economic_gain_ok(*, region_units, summary_units, tail_units, ...):
    # 参数语义改为"任意一致单位"（chars 或 tokens 均可，因为只用于比较）
    transition = summary_units + tail_units
    saved = region_units
    return remaining_turns * saved >= margin * price_ratio * transition
```
**去掉 `/4.0`**——因为它本来就不该在比例式里。这样口径争议从根本上消失，且调用方传 chars 或 tokens 都不影响结果。

**验收**：①函数体无 `/4`；②现有 C2 相关测试全绿（应当全绿，因为行为不变）。

### 新-4　`turn_snapshot.flush` 无 fsync

**现象**
```python
# turn_snapshot.py:130-136
tmp.write_text(payload, encoding="utf-8")
os.replace(tmp, path)          # ← 原子替换，但没有 fsync
```
对照 transcript 已经加了（`record_transcript.py:155-156`：`f.flush(); os.fsync(f.fileno())`）。

**根因**：`os.replace` 保证**原子性**（不会读到半个文件），但**不保证持久性**（内容可能还在页缓存里）。断电时 `os.replace` 的元数据可能已落盘、内容还没落 → 文件存在但内容为空/截断。

**影响面**：`turn_snapshot` 是**重启 recovery 的权威状态源**（`mark_crashed_as_recovery` 读它）。断电后它损坏 → 崩溃恢复判定错误（可能把正常会话判为 crashed，或反之）。

**解决方案（~15 分钟，一行级）**
```python
tmp.write_text(payload, encoding="utf-8")
with tmp.open("rb+") as f:
    f.flush()
    os.fsync(f.fileno())
os.replace(tmp, path)
```
或更规范：先 `f = open(tmp,'w')` → `write` → `flush` → `fsync` → `close` → `os.replace`。
> 若要更严（防目录项丢失），还需 fsync 父目录。但考虑到这是 Windows 为主的项目，**文件级 fsync 已足够**（NTFS 的 `FlushFileBuffers` 语义）。

**顺带建议**：项目现在有**三种持久化策略并存**（index 强制 fsync / journal 默认关 / transcript 刚补上 / turn_snapshot 没有）。建议统一到一个 `atomic_write_durable(path, text)` 工具函数（放 `common/`），所有落盘走它。这样"哪个文件该 fsync"不再需要逐个判断。

**验收**：①`turn_snapshot.py` 内出现 `os.fsync`；②断电模拟（或 `fsync` 调用断言测试）通过。

### 新-5　`_repair_unpaired_tool_calls` 中间插入破坏前缀缓存

**现象**
```python
# query_loop.py:219-241
store.insert(j + inserted, tool_result_message(...))
```
在 submit 入口修复"跨 abort 残留的未配对 tool_call"时，**在历史中段插入**消息。

**根因**：修复逻辑需要"tool_use 之后紧跟 tool_result"，最直接的实现就是插到中间。但插入会让其后所有消息索引位移 → **KV 前缀缓存从该点起全部失效**（命中 0.02 vs 未命中 1.0，50 倍价差）。

**影响面**：窄（只在 abort 残留时触发），但一旦触发就是确定的缓存损失。且项目刚刚（09-10）在成本审计里把"少打断前缀缓存"列为两大真靶之一——这条正好是反例。

**解决方案（~半天）**

**改为"追加占位"而非"中间插入"**：
```python
# 不在历史中段插入；把补的 tool_result 追加到当前轮尾部
store.append(tool_result_message(...))
```
**风险与对策**：追加会让 tool_result 与它的 tool_use 之间隔着别的消息，可能触发厂商 400（协议要求配对）。所以需要**验证**：
- 若 provider 严格校验配对（DeepSeek thinking 模式、Anthropic）→ 不能简单追加，需用"**在 assistant 消息内补占位**"或"标记该轮为不可续"；
- 若 provider 宽松 → 追加即可。

**建议**：先做 `docs/` 里那个"双调用验证（¥≈0.01）"的实验——A 臂（不回放/配对）看是否 400，B 臂对照。**用一次真实调用确定厂商行为，再决定实现方式**。这与项目 `docs/最终方案-思考态回放.md` 的方法论一致。

**验收**：①abort 残留场景下，修复后前缀缓存 base_len 不变（或明确记录"此路径必然 miss"的理由）；②配对校验不报 400。

### 新-6　`clear_wrap_window` 死代码 + wrap 状态两套信号

**现象**
```python
# wrap_window.py:46-47
def clear_wrap_window() -> None: ...
# 全仓无调用
```
同时 `query_loop.py:825-832` 每轮 `set_wrap_window(forced_wrap_up, remaining)`，但**submit 结束后不广播 inactive**。

**根因**：新增了 `wrap_window`（剩余墙钟，commit 5f61b21）与既有的 `wrap_gap`（缺口清单）**并列**，两者都描述"收尾窗口"，但没有合并为一个状态对象，也没人收尾。

**影响面**：ContextVar 随 task 上下文残留。asyncio task 隔离通常兜底，但 `turn_runner` 复用 task 时存在跨 submit 污染窗口——即"上一轮的收尾窗状态漏到下一轮"。

**解决方案（~半天）**
1. **收尾**：在 submit 结束路径（`turn_runner` 的 settlement）调 `clear_wrap_window()`；
2. **合并信号**（可选，更彻底）：把 `wrap_gap`（有哪些缺口）与 `wrap_window`（还剩多少时间）合并为一个 `WrapState { remaining_sec, gaps }`，单一 ContextVar。这样"收尾窗"只有一个真相。
3. **加回归测试**：连续两个 submit，断言第二个开始时 `wrap_window` 已被清。

**验收**：①`clear_wrap_window` 有生产调用点；②跨 submit 的 wrap 状态不残留。

### 新-7　`tools/*/prompt.py` 的 schema description 夹带编排指令

**现象**（模型可见文本）
```python
# bash_tool.py:888
"Use to verify a deliverable works..."
# file_read_tool/prompt.py:12
"use Grep ... first"
# grep_tool/prompt.py:4
"use instead of Bash grep/rg"
```

**根因**：工具描述是**模型可见文本**，按 AGENTS.md 的铁律"只给信息，不给建议/劝导/编排"，`"use ... instead"`、`"use ... first"` 属于**编排**。但这是**与目标模型训练分布的妥协**——工具描述的"何时用"惯例上就是建议性的，且厂商 API 文档也这么写。

**★ 这是一条需要裁决的边界，不是明确的 bug。** 引擎内部（system prompt / T_now / 错误 detail）已经严格中性化，但**工具 schema 这一面没有纳入审计范围**。

**影响面**：中等——工具描述每轮常驻，是注意力里的常客。若模型因此产生"必须先用 Grep 再 Read"的僵化路径，就是 attention 漂移。

**解决方案（分两步）**

**Step 1（~2 小时）—— 先做审计，不做修改**
把 22 个 `tools/*/prompt.py` 的 description 全文导出，逐条判定：
- **纯事实**（"Returns the file contents"）→ 保留；
- **使用条件**（"when the file is large"）→ 可保留（这是信息，不是指令）；
- **编排建议**（"use X instead of Y"、"always first"）→ 标记；
- **评价**（"dangerous"、"best practice"）→ 标记。

**Step 2 —— 对标记项做"事实化改写"**
```
✗ "use instead of Bash grep/rg"        → ✓ "Searches file contents with ripgrep semantics."
✗ "use Grep ... first"                  → ✓ "Grep can locate symbols; Read can then load the region."
✗ "Use to verify a deliverable works"   → ✓ "Runs a command and returns its output."
```
关键：**把"你应该用我"改为"我能做什么"**——信息而不是导演。

**注意**：改写会影响模型行为（可能改变工具选择分布），所以按 AGENTS.md 第 4 条应**先 A/B 验证**。建议作为独立实验批次，用 `evals/` 对比工具选择正确率。

**验收**：①审计表列出全部 321 行描述的分类；②改写批次有 A/B 数据；③无净负面。
