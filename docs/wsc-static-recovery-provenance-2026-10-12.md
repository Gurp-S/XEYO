# 批次109：恢复回执的来源与持久化边界

只做静态审查及实现；测试0、编译0、API0、费用0。没有重启、部署或操作真实会话。不能用本批次证明任务连续性或质量等同。

结构性根因：hydrate合成缺失工具回执后，QueryEngine三个历史安装入口将全部消息标为known并把持久化游标移到末尾。派生行没有真实转录来源，却可能被交接和折叠消费；再次恢复还会产生随机新ID。另有环境会话ID串用，以及仅凭缺少只读回执就宣称未执行的问题。

边界：已保存原文与恢复观察分开。合成回执的ID由显式会话、调用所在原消息ID和回执逻辑正文确定；同源同观察同ID。只带内存待保存标记，模型文本和转录格式不增加标记。构造、空历史恢复、回溯替换共享registration，known排除派生行，游标从首个待保存行开始。后续普通保存或交接前同步保存走现有正文身份核对、追加队列及flush；只读恢复本身不写盘。既有行、冻结头、冷对象不改。

会话加载显式传sid；侧链使用既有scoped_session_id，不读取环境当前会话回执。侧链移除恢复异常→空历史的转换，损坏/读失败沿既有异常边界返回失败；首次没有文件仍由读取器返回空。没有显式会话身份时不借用另一上下文的证据。执行回执还须工具名一致。未知结果统一报告TOOL_OUTCOME_UNKNOWN；不凭只读属性推断未执行。正文被执行台账截断时保留其返回状态及摘要，但execution.complete=False，不能成为完整Todo提交证据。全局进程台账不加入单调用恢复结果。

静态核对的回归合同（没有执行）：

- 同一原调用恢复两次：相同事实生成相同派生ID；正常重发由既有正文证书幂等确认。
- 无结果恢复→引擎继续/手动交接：待保存游标包含恢复回执；同步保存失败仍不能推进折叠。
- A会话恢复时环境是B会话：只查询A，不采纳B的同call_id回执。
- 执行返回正文不完整或没有结果：complete=False；不把调用输入或摘要晋升为完成事实。

静态核对persist_session、主引擎增量保存、三个历史安装入口、工具结果构造及Todo完整性过滤；git diff --check通过。旧只读缺失回执测试仍期待TOOL_NOT_STARTED，与新的证据合同冲突，未运行、不用旧数字结案。

边界未闭合：无ID旧原消息的历史身份兼容、迟到真实回执与已保存未知观察的续接、UI-only写入口、明确物理删除后的缓存生命周期及实际重启/重发兼容仍需验收。四块真实效果验收保持未勾。
