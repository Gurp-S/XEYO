# 批次105：通知开销与交接准入使用同一完整请求（仅静态）

结构性根因：query_loop原先用尚未追加容量通知的请求判断是否需要交接；随后wsc_request_timing.prepare追加80%通知再测85%，可触发直接force。存在输入估参t<85%容量、追加通知后t+notice>=85%容量的区间，会绕过需要刷新任务状态的分支。80%通知的system/伪对/尾插载体也有开销，不能只数通知正文或假设不足以跨界。

规则：压缩与其连续性交接使用同一份最终组装请求作准入依据；任何由组装新增的开销不能在交接判断之后偷偷授权折叠。80%通知只改变当前请求投影，其送达仍在实际厂商成功返回后确认，不改冻结头或transcript。

修正：将原prepare内组装函数抽为同模块assemble，只组装与生成投递key，不授权fold。主循环先取得包含通知的完整request，用它判断capacity/需要交接；prepare复用这份初始组装结果，不再重复渲染通知。交接追加调用/回执或显式Compact生成新投影时废弃旧组装结果，依当前输入及cursor重新组装；force后的新请求同样重新组装并做既有最终硬容量检查。

默认prepare调用方式保持兼容；生产仅在输入未变化且未await新状态时复用初始组装。模型schema与provider-normalized估参仍沿原路径，未引入厂商精确token计量，也没有修改85%起点/80%事实通知/每次准备最多一次自动尝试。输入+输出余量硬停仍独立于85%输入触发。

静态检查涵盖无通知、待通知、已送达通知、通知跨85%、交接后输入变化、显式压缩后新cursor、声道回退再次准备和最终硬容量拒绝。应补回归：跨界时未提交状态必须先交接；交接失败不fold；未跨界只组装一次、不重复通知；交接和新cursor不能复用旧请求；失败厂商调用不消费投递key。按用户当前要求未编写或运行测试、编译、API，各项0、费用0。

修改query_loop.py与wsc_request_timing.py；只静态审查，无部署、无真实会话操作。四块最终真实验收仍开放，尤其T14d目前仍为完整请求估参，不能宣称精确容量或真实长任务漂移已通过。
