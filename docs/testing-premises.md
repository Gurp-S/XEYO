# 测试前提自检（#15）

## 一句话规约

**产品断言写 `assert`；"我这个测试赖以成立的世界"写 `assert_premise`。**

```python
from tests.premise import assert_premise

assert_premise(_tools_fingerprint() != clean, "该 env 本应漂移工具面（否则本测试测不到东西）")
```

## 为什么值得单列一个词

红的时候，人（和代理）的第一反应是"产品坏了，去修产品"。但实测里失败有相当比例**错在测试自己**：

| 实例 | 形状 |
| --- | --- |
| `files=` 断言 | 既有正确行为是"只补结论里未出现的路径"，那张卡已内联 ⇒ 红的是测试 |
| 改名漏改调用点 | 假设"只有一处调用点"，实际两处 ⇒ `NameError` 2 failed |
| 一次性全量重钉 golden | 假设"golden 只有我的 3 条在途"，实际 6 条 ⇒ 停下来等人裁 |

`assert_premise` 让这类失败在消息里就自报家门（`前提失败：…`），于是：
- 红的归属立刻可见 ⇒ 不会去改不该改的产品代码；
- `why` 强制写出来 ⇒ 半年后回看也知道"当时假设了什么"（假设本身可以被推翻，并留痕）。

## 与"错误签名不能独自证明"的关系

两者是同一条纪律的两面：错误签名告诉你**哪一行红**，不告诉你**为什么红**。
`assert_premise` 至少把"为什么可能是我错"这一支显式钉住，避免用一次红就宣布产品有缺陷。

## 配套的一条操作规约：连续手滑就重写

实测（2026-10-07，同一批内三次）：对同一个文件连续做小 `Edit` 时手滑两次
（删错换行 ⇒ `SyntaxError`；补换行时 new/old 方向写反 ⇒ 语法仍坏），第三次才修对，
而文件里还留着 `IndentationError`。处置不是继续缩小 `Edit` 范围，而是**整文件重写**（一次通过）。

理由：连续手滑意味着"我对该文件当前状态的记忆"已不可信；此时每一次 `Edit` 都是拿不可信的前提去改。
重写把前提换成了**我完整写出的内容**，可核验、可重跑。
判断门槛（避免滥用）：**同一文件连续两次修不回来 ⇒ 立刻重写**，不要试第三次。
