### 1.1 记忆与冲突

## 2. 类 A：读面无边界 ⇒ 边界移到出站（D1 + D2）

### 2.1 结构性根因

**"安全边界"被建在字符串解析上**：`bash_readonly_allow`（`bash_policy.py:653`）→ `bash_rule_decision`（`:533`）→ 默认规则（`:262`）形状只有 `{program, prefix, decision}`，**无路径维度**；`policy.py:1029` 命中即 ALLOW，整条 `_evaluate_bash`（`:891-1060`）**只有写侧有路径闸**。
在 D1 下，这条"越界"不再成立；**真正剩下的缺口是"凭据进注意力"没有任何闸**。

### 2.2 现有盲区（必须一并修，否则闸门形同虚设）

| 绕过形态 | 为什么漏 |
|---|---|
| `env` / `printenv` / `set` | 命令文本无密钥文件名，但**导出全部环境变量** |
| `rg -n "sk-" ~/` | 搜的是**内容** |
| `git log -p` / `git show HEAD:.env` | 历史里的 key |
| `cat /tmp/paste.txt` | 文件内容才是 key |
| `python -c "print(open(chr(46)+'env').read())"` | 字符串拼接躲开文本匹配 |

### 2.3 方案

**① 统一读侧裁决**（`permissions/filesystem.py`）

`check_read_permission_for_path` 语义收敛为：

```
is_secret_path(path) → DENY          # 保留硬拦（路径形态）
其余                  → ALLOW         # 删除"区外 → ASK"分支（:344-354）
```

Read / Grep / Glob / Diagnostics 共用（`check_read_permission_for_tool:472` 已是统一入口）。

**② 新增出站内容闸**（新模块 `permissions/egress_guard.py`）

```python
class EgressDecision(NamedTuple):
    action: Literal["allow", "deny"]     # D2：默认 deny
    reason: str                          # "credential_in_content" | "bulk_export_shape"
    spans: int
    kinds: tuple[str, ...]               # ("pem", "aws_ak", "gcp_key", "jwt", "kv")
```

形态分级（**不能一刀切**，否则误伤到无法工作）：

| 形态 | 处置 | 理由 |
|---|---|---|
| PEM 私钥块 / 云厂商长期密钥（`AKIA`、`AIza`、`sk-`、`ghp-`、`xox-`） | **DENY**（硬，不给确认） | 整块即凭据，无"部分可用"语义 |
| JWT / `key=value` / `Bearer` | **DENY + 要求确认**（可放行） | 可能误伤：测试夹具、文档示例 |
| 裸 hex ≥ 32 | **不拦**（仅审计留痕） | 会误伤 git SHA（40-hex），且非凭据形态 |

**正则来源**：复用 `audit/redact.py`，但**拆两支**（单一实现、两种口径）：

```python
redact_audit(text)    # 全量（含裸 hex）—— 审计/推送用，现状不变
redact_context(text)  # 高置信度子集（去裸 hex）—— 出站闸用
```

**接线点（唯一）**：`ToolRegistry.run` 的统一收口处（**一个点，覆盖所有工具**），在"结果入 MessageStore 之前"：

```
工具 execute → ToolResult
    ↓
EgressGuard.check(tool_name, result_text, ctx)     ← 新增，唯一收口
    ├─ allow → 入 MessageStore
    └─ deny  → permissions.store 的 ASK 流程（复用既有三态与面板）
                 ├─ 用户确认 → 放行该次 + 记批准位
                 └─ 未确认   → 结果替换为中性结果型文本：
                                "Permission denied: credential-shaped content in tool result (N spans: pem)"
```

**为什么必须在"入 MessageStore 之前"**：投影层（`project_for_model`）虽然更单点，但那里内容已落盘、已被别的路径（rewind / journal / 子代理侧链）读到；且每次请求都要重扫全量消息，成本线性增长。

**批准位记忆**：同 `tool + 路径 + kinds` → 记住（思路同 `store.read_dir_fingerprint`）。否则每次读同一文件都弹面板。

**③ 结构性批量导出**（命令形状即判定，**不问直接 DENY**）

`env` / `printenv` / `set` / `Get-ChildItem Env:` —— 形状本身就是"导出全部密钥"，无"确认后可用"的合理语义。落点：`bash_policy._DENY_RULES`（`bash_policy.py:38`）追加规则，措辞中性。

**④ 出口**（`curl -d @f` / `scp` / `nc`）

- 内容已知 → 复用 ② 的检查；
- 内容未知（`-d @file`）→ **DENY**（中性理由），因为无法证明不带凭据。

### 2.4 不变量测试（治本判据）

1. **正向**：任何进入模型上下文的内容，都不含 `redact_context` 可识别的**高置信度**凭据形态 —— 对 `Read` / `Bash` / `Grep` 三入口各跑一遍，样例含 `env`、`rg "sk-"`、PEM 文件。
2. **反向**：`git log` 的 40-hex SHA **不得**被拦（防 ② 把模型干活需要的东西打掉）。
3. **一致性**：`Read` 与 `Bash` 对同一路径/同一内容的裁决**必须相同**（`check_read_permission_for_path` 是唯一裁决者）。
4. **确认位**：确认一次后，同 `tool + 路径 + kinds` 不再重复询问。

## 4. 类 C：唤醒去重必须"判队列空"，不能"判任务在跑"

**根因（两条同形）**：

| 条目 | 现状 | 丢在哪 |

**第二个丢点（上一轮漏识别）**：`on_delivery_tick:622-623`

```python
if _turn_running(sid):
    return          # ← 直接 return，不 requeue；若那是最后一个 job，通知永久不投
```

### 方案：抽出共用原语（治本的关键）

新模块 `server/session_serial_queue.py`：

```python
class SessionSerialQueue:
    """per-session 串行消费者。去重判据 = "队列空"，不是"任务在跑"（Monitor 语义）。"""

    def submit(self, session_id: str, key: str, run: Callable[[], Awaitable[None]]) -> None:
        """同一 (session_id, key) 合并；已在队列中则替换 payload（后者覆盖前者）。"""

    # 内部：
    #   _queued: dict[str, dict[str, Callable]]      # 待办（key 去重）
    #   _running: dict[str, bool]
    # 消费循环（关键：取 + 清标记在同一临界区）
    #   while (item := pop_next(sid)) is not None:
    #       await item()
```

- Job delivery 用它替代 `_wake_tasks` + `_schedule_delivery_task`；
- Goal round 用它替代 `_schedule` + `st.pending`；
- busy 分支改为**不消费**：`_turn_running(sid)` → `submit(debounce_key, ...)` 重排（**不能裸 return**）。

**业界对标**：Lampson & Redell *Monitors* 的条件变量谓词循环；Erlang/OTP 单消费者 mailbox。**规则比补丁重要**——两处共用同一原语后，第三次同形 bug 在结构上不会再长。

**不变量测试**（确定性 interleaving，**禁止 sleep 撞时序**）

- 在 `fake_submit` 第一次调用内部手动触发 settlement，断言"第二次仍被调度"。
- busy 分支：`_turn_running` 恒 True 时，断言 pending **不被消费**且**仍在队列**。

## 5. 类 D：资源要有 owner，注册要有补偿

**根因**：**资源生命周期是"手写枚举"的，不是"注册制"的** ⇒ 每加一个 per-session registry 就必然漏一处清理。

### 5.1 中央生命周期注册表（本类最治本的一处）

新模块 `server/session_lifecycle.py`：

```python
class SessionScoped(Protocol):
    name: str
    order: int                                        # 清理顺序，小 → 大
    def drop_session(self, session_id: str) -> None: ...

_REGISTRY: list[SessionScoped] = []

def register(owner: SessionScoped) -> None: ...
def drop_all(session_id: str) -> list[tuple[str, str | None]]:   # (name, error) 或 (name, None)
```

**顺序约束（上一轮漏识别，且是正确性要求）**：

```
jobs(10) < synthetic_env(20) < goal(30) < inbox(40) < runtime_mode(50)
        < runtime_preset(60) < pool(70) < transcript(90)
```

**job 必须先死** —— 否则它 settle 时会写 transcript，**把刚删掉的会话目录重建出来**。

`delete_session` 改为：`drop_all(sid)` + 磁盘清理。**任何 owner 报错都不阻断**（现状 goal/inbox 报错会 503 直接中断删除 → 改为收集错误、继续删、最后一起上报）。

**结构性收益**：此后"新加 registry 忘了清理"在结构上不可能发生（元测试见下）。

**不变量测试**

- D1：两条失败分支各一测，断言 `snapshot_list(sid) == []`；+ **容量回归**（连失败 N 次后槽位仍可用）。
- D2：`for i in range(1000): _register + settle`，断言五个 dict 同步有界；+ **pending 保护**：pending 中的 job 不被 GC。
- D3：`delete` 后断言 `snapshot_list(sid) == []`、`env_for(sid) is None`、无 `running/stopping` 残留、transcript 目录未被重建。
- **元测试**：每个调用过 `register()` 的 owner 都被 `drop_all` 调用过（防漏注册）。

## 6. 类 E：事件循环里不许有同步阻塞

**根因**：物理 IO 已在后台线程，但**屏障是同步的**；且屏障是**全局**的（见 B3）。

**方案（比 AST 检查更治本）**：在 `record_transcript.flush_pending_sync` **内部**加运行时断言：

```python
def flush_pending_sync(timeout: float = 5.0) -> bool:
    try:
        asyncio.get_running_loop()
    except RuntimeError:
        pass                      # 无 loop：CLI / atexit / 后台线程，合法
    else:
        raise RuntimeError(
            "sync transcript flush called from event loop; use flush_transcript_async(path)"
        )
```

**为什么优于 AST 检查**：AST 只能查直接调用，漏掉间接路径（如 `query_loop._safe_flush_transcript`）；运行时断言覆盖**所有**路径（含未来新增的）。

**配套**：全部 async 调用点改 `await flush_transcript_async(path)`。

**不变量测试**：在 `async def` 里调 `flush_transcript()` → 必须抛；在同步函数里调 → 正常。
