# 历史消息编辑与文件回溯方案调研

在 AI 编码 Agent（如 XEYO）中，当用户编辑历史聊天消息并触发对话重新生成时，通常会遇到一个核心矛盾：**对话上下文（Chat Context）被截断重置，但工作区中的物理文件（Workspace Files）仍然保留着后续对话产生的修改**。

为了解决这一问题，市面上的主流 AI 编码工具和 Agent 探索了不同的“文件回溯（File Rollback/Revert）”机制。本报告基于公开资料调研了 Cursor、Aider、Roo Code (Cline) 和 GitHub Copilot Edits 的实现方案，并为 XEYO 提出架构建议。

## 主流工具的实现方案对比

### 1. Roo Code (Cline)：显式 Checkpoint 机制
Roo Code（原 Cline）在最近的版本中引入了明确的 **Checkpoints** 功能 [1]。
- **实现原理**：它依赖底层的 Git 机制，在对话的关键节点（如用户发送新指令前）自动创建隐藏的 Git commit 或快照。
- **交互方式**：当用户在历史消息处点击时，Roo Code 提供两个明确的选项：
  1. `Restore Files`：仅回滚文件状态到该节点。
  2. `Restore Files & Task`：同时回滚文件状态并截断后续聊天记录。
- **风险与问题**：根据社区反馈，早期的恢复逻辑曾使用过类似 `git clean -d -f` 的强制清理命令，导致用户未追踪的代码被意外删除 [2]。这表明基于 Git 的自动快照在处理用户自行创建的未追踪文件时存在较高风险。

### 2. Cursor：独立于聊天的多级撤销
Cursor 采取了“聊天与文件状态解耦”的设计哲学，但通过 Composer 模式和隐式快照提供回退能力。
- **实现原理**：Cursor 会在后台独立维护本地的编辑历史（Local Edit History），不完全依赖 Git [3]。同时也有社区工具（如 dura）利用后台隐式 Git commit 来辅助 Cursor 实现细粒度回滚 [4]。
- **交互方式**：
  - 在普通的 Chat 模式下，修改文件通常是通过 Accept/Reject 逐个确认的，聊天记录的编辑**不会**自动撤销已应用的文件修改。
  - 在 Composer（Agent）模式下，提供了 `Undo all` 或 `Revert last set of changes` 按钮，用于撤销某一轮 AI 生成的全部文件修改 [5]。
- **局限性**：社区中常有用户抱怨“撤销”操作逻辑不清晰，例如撤销是否包含 AI 新建的文件，或者重启后撤销状态丢失等问题 [6]。

### 3. Aider：纯 Git 驱动的命令回滚
Aider 是一个重度依赖 Git 的 CLI 编码助手，其回滚机制完全透明化。
- **实现原理**：Aider 强制要求在 Git 仓库中运行，并在每次 AI 修改文件后自动生成一个结构化的 Git commit。
- **交互方式**：
  - 聊天记录和文件状态是分离的。如果需要回滚文件，用户可以直接使用 Aider 提供的 `/undo` 命令，该命令本质上是执行了一次 Git revert 或 reset [7]。
  - 如果要恢复历史聊天记录，Aider 提供了 `--restore-chat-history` 启动参数 [8]，但编辑历史记录本身并不等同于自动触发 `/undo`。
- **优势**：绝对安全，因为所有的状态变更都在标准的 Git 历史中，用户随时可以用原生 Git 命令找回。

### 4. GitHub Copilot Edits：挂起状态的回滚
Copilot Edits 提供了多文件编辑的预览状态。
- **实现原理**：AI 的修改被保留在类似暂存区（Pending Edits）的内存状态中，而不是直接覆盖物理磁盘。
- **交互方式**：用户可以在 UI 上查看差异，并选择 `Keep` 或 `Undo` 更改 [9]。如果用户已经 Accept 了更改，后续的对话历史编辑通常不会自动反向修改文件。

## 方案总结与工程取舍

从市面工具的实践来看，**没有任何一款成熟的工具会在用户“单纯编辑一条历史聊天记录”时，毫无提示地静默回滚物理磁盘上的文件**。原因在于：
1. **状态不对等**：用户可能在两条聊天记录之间，手动修改了文件（如修复 typo、运行 npm install 产生 lock 文件）。静默回滚会丢失这些人工修改。
2. **数据丢失风险**：如果回滚涉及删除 AI 新建的文件，一旦判断失误（如误删用户自己新建的同名文件），将造成不可逆的数据灾难。

因此，业界主要演化出两种流派：
| 流派 | 代表工具 | 核心机制 | 优点 | 缺点 |
|---|---|---|---|---|
| **显式快照派** | Roo Code | 后台隐式 Git commit / 快照树 | 用户体验直观，一键恢复上下文和文件 | 容易误伤未追踪文件，状态树维护成本高 |
| **Git 强依赖派** | Aider | 强制每次 AI 动作生成 Git commit | 绝对安全，无缝融入开发者现有工作流 | 污染用户的 Git 提交历史，对非 Git 目录不友好 |

## 对 XEYO 的架构建议

鉴于 XEYO 当前是 Python FastAPI 后端 + React 前端的本地 Agent 架构，若要实现“历史消息编辑联动文件回溯”，建议采用**基于 Git 的显式快照与解耦确认机制**：

### 1. 引入隐藏的 Shadow Git 机制
不要直接污染用户的 `.git` 目录，而是在工作区根目录维护一个独立的影子仓库（例如 `.xy-shadow-git/`）。
- 在 Agent 每一轮输出（Turn）结束、等待用户输入前，后端自动向 shadow git 提交一次快照，并将 commit hash 绑定到该轮的 `ChatMessage` 元数据中。

### 2. 解耦的 UI 交互
当用户编辑历史消息并点击“发送”时：
- **步骤 A**：弹出当前已实现的“确认重新发送”对话框。
- **步骤 B**：如果当前消息带有 shadow commit hash，并且检测到工作区当前状态与该 hash 存在差异，则在对话框中**额外提供一个 Checkbox**：
  > `[ ] 同时将工作区文件回滚到该消息发送前的状态`
- **步骤 C**：如果用户勾选，后端通过 shadow git 执行 `git restore` 或 `git checkout`，然后再触发大模型的重新生成。如果不勾选，则仅截断聊天记录，保留现有文件状态。

### 3. 边界保护
- **未保存/未追踪文件**：在执行回滚前，必须检查工作区是否有用户手动修改但未被 shadow git 记录的脏状态（Dirty State）。如果有，必须警告用户回滚可能导致这些修改丢失。
- **大文件与二进制**：Shadow git 应配置严格的 `.gitignore`（如忽略 `node_modules`、`.venv`、大模型权重等），防止快照占用过多磁盘空间并拖慢响应速度。

## 结论
“历史消息编辑联动文件回溯”是一个高阶的 Agent 体验特性。市面上的工具通过隐式快照（Roo Code）或显式 Git 提交（Aider）来实现。对于 XEYO 而言，最安全的落地路径是：**维护底层快照，但在 UI 层面将“截断聊天”与“回滚文件”作为两个独立的、需要用户显式确认的动作**，避免造成不可逆的数据丢失。

## 附录 · 2026-08 Cursor Agent 校正（Rewind v2）

上文 §2 对 Cursor「聊天与文件解耦」的描述主要对应 **Chat Accept/Reject** 路径。  
**Agent / Composer** 路径的公开与反编译事实更接近：

1. 每轮 user 前有本地 **checkpoint**（`checkpointId` + 内容寻址 blob / 差量，不写用户 `.git`）。
2. 悬停 **Restore Checkpoint**：截断后续对话 + 恢复该拍 agent 触及文件。
3. 编辑历史消息并提交 = **Continue-and-Revert**：State Rehydration（恢复文件）+ Forward Execution（自动带着新文案继续 Agent）。

XenYon Rewind v2 产品合同见 [`docs/设计/30-回溯v2对齐Cursor口径.md`](../设计/30-回溯v2对齐Cursor口径.md)：双入口 + 默认同拍恢复 + 乐观 UI + 异步 execute；脏手改仍阻断。  
v1「厚确认窗 + 不自动重发 + 日常勾选是否回文件」已废止为考古口径。
