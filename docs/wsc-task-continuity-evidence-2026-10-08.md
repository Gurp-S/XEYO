## 修复前三问

**结构性根因**：归档体积、账单缓存分拆和当前请求窗口占用混用；缓存经济入口能在缺少当前压力时改变执行上下文。任务进度恢复、WSC 摘录、既有待办 sidecar 各用不同来源判据，成功提交状态可能被未完成输入或没有完整清单的“ok”替换。旧方案的全历史原话热保留补错了对象：缺的是步骤、决定与回执关系。失败诊断逐条强制内联也将背景失败放大成持续注意力成本。

**结构性规则**：普通 C1/C2 共用当前 keep 发射压力准入；只有带当前请求来源和匹配 cursor 的厂商回执能校准开销，旧账单数字和前折叠回执不能冒充当前容量。任务状态只来自已成功提交的结构化回执。稳定 ID 的 merge 进度更新沿用此前提交的检查点；全量替换、显式清空、全部完成结束沿用；显式新检查点覆盖旧声明。归档失败保持未知，可通过完整来源组回读；显式关联当前检查点的失败仍单列。引擎不推断任务语义、不伪造成功、不提供路线建议。

**回归**：厂商当前 context=1200、账单 hit+miss=1000000 时按 1200 记录；已折叠原文再大也不触发当前小请求折叠；容量压力仍触发保护；无出处的旧大计数不能校准新请求。失败或未返回 TodoWrite、无结构回执的确认都不替换已提交状态。合并更新保留决定/来源及原提交回执；替换、清空、完成解除沿用。任务来源缺失/冲突保持 unknown，短追问/冻结/重启保持发射前缀，实际折叠吸收已完成状态。冷组可读且保留失败调用与原结果。

**不是自动理解任务的功能**：模型提交任务状态、决定和来源，引擎保存与投影；历史缺失的更新不能靠推测补成完成。来源无法唯一匹配、缺稳定步骤 ID 的继承或缺回执均保留未知。并未解决未表达信息的识别问题。

本轮未写线上设置、原 JSONL 行、既有冻结头或既有冷对象。开启新旁路需新代重建；代内保持追加，不能让新 schema 悄悄改写旧代前缀。
