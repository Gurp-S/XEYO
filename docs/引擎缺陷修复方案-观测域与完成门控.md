## 一、三个真缺陷（都能在今天的 GUI 里复现，与评测无关）

### D1 观测域不一致：引擎断言自己没能力观测的事实
**复现（今天就能做）**：GUI 里让模型用 bash 把产物写到工作区外（`/tmp/out.json`、`D:\other\res.txt`），
然后用 TodoWrite 把该路径登记为 completed。引擎的 `Path(cwd).joinpath(path).exists()` 在宿主上看不到它
→ 输出 `[引擎核对] 产物 …: 磁盘上不存在`。**这是一条引擎自己都证不了的事实**，违反"信息必须可信"。
同一缺陷的第二个显形点：`first_sniff` 用宿主 `os.listdir` 注入"目录清单"，当工作区不在宿主
（容器/WSL/远程）时，注入的是一份模型看不到的清单。
**缺陷本质**：核对/嗅探的观测通道 ≠ 模型的动作通道。

### D2 "完成"= 模型的声明：引擎没有验证环节
**复现**：给一个"必须支持大输入/边界规模"的任务，模型用小样例自测通过即宣布完成——引擎直接接受为终态。
真实用户在 GUI 里天天遇到"模型说做好了其实没做"（产物没写、服务没起、格式不符）。
**缺陷本质**：收敛是模型的单方面声明，不是引擎拥有的状态转移。

### D3 无时间感知：临死前不落盘
**复现**：给一个 20 分钟量级的任务 + 3 分钟预算，模型会继续探索/启动长命令，直到被外部掐断，已完成的成果不落盘。
产品侧同样成立（用户 Ctrl-C / 关窗时，会话正在跑的成果会丢）。
**缺陷本质**：引擎把"预算耗尽"当唯一终止条件，没有"预算尾部优先兑现已登记交付物"的语义。

## 二、D1 方案：`tools/exec_channel.py`（先做这个，零风险）

### 2.1 接口（只读三原语，走当前活动路由）

```python
# python/tools/exec_channel.py （新；零依赖；未设置路由时与旧行为字节级等价）
Observability = tuple[bool, Any]        # (可观测, 结果)

def list_dir(path: str) -> list[str] | None:
    """活动路由下列目录名（排序后）。宿主=os.listdir；容器=docker exec ls -1a -- <path>。
    不可观测（路由失败/超时/异常）→ None。"""

def stat_path(path: str) -> tuple[bool, int] | None:
    """(是否普通文件, 字节数)。宿主=Path.is_file/stat；容器=test -f + stat -c %s。
    不可观测 → None。"""

def read_text(path: str, *, limit: int = 4096) -> str | None:
    """读一段文本（供完成门控的证据执行器用）。不可观测 → None。"""
```

- 路由判定复用 `tools/container_routing.current_container()` + `XEYO_DOCKER_CONTAINER` 回退（与 bash/job 一致）；
- 容器分支**复用** bash_tool 现有的 docker SDK 执行（把 `_docker_exec_with_timeout` 提为公共函数，不写第二份实现）；
- 路径解析责任在调用方；本模块只管"看得到就返回事实，看不到就返回 None"。

### 2.2 两处接线

| 位置 | 现状 | 改后 | 变更量 |
|---|---|---|---|
| `engine/first_sniff.py::build_first_sniff_text` | `os.listdir(abspath(cwd))`，空目录 → 注入 `(空目录)` | `exec_channel.list_dir(cwd)`；`None` → `return ""`（不注入） | ~6 行 |
| `todo_write_tool.py::_materialization_facts` | `Path(self._cwd).joinpath(path).exists()` | `exec_channel.stat_path(resolved)`；`None` → **该条不加行** | ~8 行 |

### 2.3 为什么"不影响正常使用"

- 宿主路由（= 今天的 GUI 全部使用场景）走 os/pathlib 原语，**返回值与异常语义完全一致**；
- 由现有回归套件证明：`test_pre_llm_inject.py`、`test_todo_output_facts.py` 全绿即等价性证明；
- 唯一行为差异发生在"以前会输出错误断言"的情形 → 改为沉默，属于修复而非改变。

### 2.4 验收

1. 宿主等价：既有两套件全绿；
2. 容器路由桩测：打桩 `current_container()` 返回假 id + 假 exec 输出 → 断言 first_sniff 注入容器清单、todo 按容器结果出事实；
3. 不可观测：exec 抛错 → 断言 first_sniff 返回 `""`、todo 不加行（沉默纪律）；
4. 反例测试：断言源码中不出现 `if 容器` 之类分支（用 grep 型契约测试锁死）。

## 三、D2 方案：完成门控（`engine/verification.py` + query_loop 拦截）

### 3.1 状态机与精确接入点

现状（已核）：`query_loop.py:804` 的 `while True:` 主循环；`prepare_next_turn()` 返回 False → `forced_wrap_up=True`
（`:813`）；模型无 tool_use 且有文本 → 交付 `FinalEvent`。

新增收敛入口：

```
模型无 tool_use（或 stop）
   → DONE_PROPOSED（拦截点：交付 FinalEvent 之前）
        ├─ 无可用证据（本任务产生不出确定性证据）→ 直接放行（= 今天行为，零干预）
        ├─ 证据全绿 → 放行
        ├─ 有红/证据不足 → 注入**证据事实行** → 继续本回合（verification 轮次 +1）
        └─ 验证轮次超限（默认 2）→ DONE_AS_IS（如实收敛，标 verification_failed，不伪装）
```

**关键设计**：**没有证据就零干预**。所以对"没有可验证产物/断言"的普通对话任务，
行为与今天完全相同——这是"不影响正常使用"的结构性保证，而不是靠开关。

### 3.2 证据对象（确定性，非模型生成）

```python
@dataclass
class AcceptanceItem:
    check_id: str                 # 稳定标识
    source: str                   # "artifact" | "test_suite" | "metric" | "service"
    statement: str                # 人能读懂的一句断言
    command: str | None           # 引擎可执行的验证命令（经 exec_channel）
    status: str                   # "pending" | "green" | "red" | "unknown"
    last_digest: str | None       # 输出摘要（落审计）
```

**证据从哪里来（全部确定性推导，不让模型自由发挥）**：

| 来源 | 触发条件（保守） | 断言 |
|---|---|---|
| `artifact` | TodoWrite/交付物登记里出现**磁盘路径** | 文件存在 + 规模 > 0（+ 语法有效：json/py 可解析） |
| `test_suite` | 工作区存在可识别的测试入口（pytest/npm test/Makefile check，且模型跑过它） | 重跑该测试命令 → 退出码 |
| `metric` | **任务里出现明确阈值**（"准确率 ≥ 0.62"这类可由模型自己跑出的度量） | 跑度量 → 与阈值比较 |
| `service` | 会话中出现"监听/端口/服务"类交付声明 | 端口/进程存活 |

- `metric` 与 `artifact` 的判定都是**确定性字符串/文件系统事实**（复用 `timeout_map.base_command_of` 同风格的保守解析）；
- 解析不确定 → **不立证据**（宁缺勿猜），符合"确定性事实优于启发式"。

### 3.3 证据行的措辞（复用 #9 的纪律）

证据行只能是事实，例如：

```
[引擎证据] /app/out.json: 不存在（该产物已在待办中登记为 completed）
[引擎证据] pytest -q: 退出码 1（2 failed, 5 passed）
[引擎证据] 自测最大规模 2^31 < 任务声明规模 2^47
[引擎证据] 端口 8080: 无监听进程
```

**禁止**：请/应该/建议/务必/记得/优先/补齐/建议改用…（沿用 `test_todo_output_facts.py` 的黑名单契约测试，
把 verification 的证据行也纳入同一契约）。

### 3.4 双预算

`engine/budget.py` 增 `verification_turns_used/limit`（默认 2）与独立记账：验证轮的输出 token 不计入探索预算，
**但探索预算耗尽的硬停优先于验证**（防止验证把会话拖长）。验证预算上限 = 主循环输出预算的 25%。

### 3.5 对正常使用的影响

- 无证据任务：零干预（结构保证）；
- 有证据任务：多 1 条事实行（~30 tok 输出）+ 可能的修复轮（只在"确实红"时发生）；
- 关闭方式：`XEYO_VERIFICATION_GATE=0`（默认开，但"无证据"已是天然关闭）。

### 3.6 成本（新价，见 §7）

| 项 | 量 | 新价成本 |
|---|---|---|
| L1 证据行注入 | ~30~60 输出 tok / 有证据任务 | ≈ ¥0.0002 |
| 修复轮（只失败 trial） | +1 轮 ≈ +2k 输出 tok | ≈ ¥0.008 / 次 |
| 全量 89 题期望 | 按 1/3 trial 触发修复轮 | **≈ +¥1.2~1.8（+5~7%）** |

## 四、D3 方案：收尾窗口（时间感知落盘）

### 4.1 现状（已核，不用重造）

- `budget.set_wall_deadline()` 已接；`check_wall_deadline()` 已做 80%/90% 水位**事实播报**；
- 100% 走尽且**武装**时 `_start_grace("wall")` → 共享 grace → `forced_wrap_up` →
  `_publish_wrap_guide()` 发布**缺口清单 + 剩余工具配额**（`wrap_gap`），R3' 配额窗已允许继续调用工具落盘。
- **真缺口：`arm_wall_stop(None)` 默认未武装**（适配器只播报不武装）→ 引擎知道 deadline 却不进入收尾窗。

### 4.2 三件事

| # | 内容 | 落点 | 性质 |
|---|---|---|---|
| A1 | **武装**：`XEYO_WALL_HARD_STOP=1` + `XEYO_WALL_STOP_MARGIN=90~120` | 装配（不改语义） | 产品侧等价诉求：长任务被 Ctrl-C / 关窗前的优雅收尾 |
| A2 | **收尾窗口内拒绝启动"新长命令"** | 新 `engine/wrap_window.py`（ContextVar）+ `bash_tool` 判定 | 执行层限制（非劝说） |
| A3 | **窗口内长命令族强制后台化** | `bash_tool` + `timeout_map.family_default_ms` | 执行层策略 |

**A2 细节（理念合规的关键）**：
- `engine/wrap_window.py`：`set_wrap_window(bool)` / `in_wrap_window() -> bool`，
  与 `container_routing`、`write_scope` 同构的 ContextVar，零依赖；
- 引擎在 `forced_wrap_up = True` 那一行（`query_loop.py:813`）置位，会话结束复位；
- bash_tool 判定：`in_wrap_window()` **且** `family_default_ms(cmd)` 存在（长命令族）**且** 预计时长 > 剩余墙钟
  → 返回**执行层错误行**：`命令未执行：收尾窗口内不接受预计超出剩余预算的长命令`。
- **这是限制不是劝说**：不给"建议改用 X"，不说"你应该先落盘"，只是让那条路报错 → 完全符合
  "引擎限制全部静默走执行层，判定越界不劝告，只让那条路一直报错"。
- 短命令（echo/ls/cat/写文件）**不受限** → 收尾的落盘动作永远可用。

### 4.3 对正常使用的影响

- 不武装 → `in_wrap_window()` 恒 `False` → **字节级等价于今天**；
- 武装后也只影响"预算尾部 + 长命令"这一交集；常态对话零感知；
- 产品收益：GUI 长任务被中断前会把已登记产物落盘（这是真实用户痛点，不是评测需求）。
