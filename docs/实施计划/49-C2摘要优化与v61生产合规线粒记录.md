## 3. 生成器 bug 三连（`_probe_chat` / 模型 / max_tokens）

### 3.1 第一个 bug：`_probe_chat` 忽略 `max_tokens`
- 实验（`variant_d_2500.py`）声称"2500-token 版吸收 92%"，**实际是假象**——`_probe_chat` 构造 `OpenAICompatClient` 时**没传 max_tokens**，输出无限制（15K chars）。
- 修复：`_probe_chat(..., max_tokens)` 现在真正生效（本次 A/B 探针也从此真实受限 240 tokens）。

### 3.2 第二个 bug：`evals.client.chat` 默认模型是 vision-exp
- 正式 A/B 用 `evals.client.chat`（max_tokens 生效），但**默认 `MODEL_ID = deepseek-v4-flash-vision-exp`**——它会先搬运工具调用清单（`- 工具调用: Grep id=...` ×20 行），预算浪费在 id 上 → 吸收 71%。
- 修复：`evals.client.chat` 加 `model` 参数（默认不变），`_llm_extract_summary` 显式 `model="deepseek-v4-flash"`（与 A/B 探针同模型口径）。

### 3.3 第三个坑：max_tokens 截断的真实代价
- 用 flash + 严格限制：2500 token → 5,113 chars / 71%；6000 token → 10,666 chars / **67%**（更长反而更差）。
- 结论：**预算内（受限）与自由输出是完全不同的世界**；必须扫描 find 甜点位。

## 5. 真实环境对照：LLM 摘要"吸收高 ≠ 探针高"
