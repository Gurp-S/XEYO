## 一、目标与成功标准

**目标**：修复冒烟测试暴露的 3 个严重功能缺陷（回溯丢文件/无作用、命令行在 GUI 无用、Resume 提示泄漏）与一批高/中优先级 UX 缺陷，并落地 2 个新功能占位（MCP 管理界面、沉浸模式）。

**成功标准（可验证）**：
- **回溯**：回滚"首次被 agent 修改的既有文件"不再删除而是恢复原文；continue 无检查点不假成功；`(size,mtime)` 签名漂移不再误跳过。新增 3 类此前完全未覆盖的回归测试。
- **命令行**：在 Composer 输入 `/export`、`/skills`、`/run`、`/mode` 被真实执行，未知命令提示"未知命令"，不再把 `/xxx` 当普通文本发给 LLM。
- **Resume**：断流/刷新/backfill 后用户气泡仍显示原始 cue（"继续"），而非 `[Resume] The user asked to continue…` 富化文本。
- **队列**：非 side- 会话忙时安静 202 排队并在 settle 后投递，不再误显示"后端繁忙"；区分 409/429/stuck 三种文案。
- 其余各项按各"验收"小节通过 `vi` + `pytest` + 手工冒烟。

## 三、分组实现方案（按子系统）

### 组1：回溯/回滚（P0-①）— `python/rewind/*` + `python/engine/query_engine.py`

**根因（取证确凿）**：
- **BUG-1（数据丢失）**：`rewind/hotpath.py:505-535` 删除分支只用"是否在 checkpoint.entries"区分该删/该恢复。一个**检查点冻结前从未被 agent 索引、但被首次改动**的既有用户文件，回滚时不在 checkpoint.entries、却在 index.entries → 落入 `full.unlink()`(@524) 删除。
- **BUG-2（无作用）**：`hotpath.py:410-425` `_spawn_restore` 在 continue 模式无 `checkpoint_id` 时置 `committed` 但从不恢复文件（前端弹窗却显示"文件正在后台恢复"）。成因：`query_engine.py:654` 的 `if turn_record is not None and commit:` 门控使消息未成功冻结检查点。
- **BUG-3（无作用）**：`hotpath.py:555-564` 用 `(size, mtime_ns)` 判 `managed`。索引同步异常被 `query_engine.py:990-1001` 静默 `pass`、`turn_baseline=None`(`:641-643`)、超 `DEFAULT_TURN_SCAN_LIMIT`(`index.py:374-401`) 或回滚前文件被触摸 → 签名漂移 → `managed=False` → 走 `skipped_dirty` → 文件不写回。

**修复方案**：
1. **A（治本，改删除判定）**：`_restore_checkpoint_files` 删除分支加防御——仅当该路径在目标 turn 判定为"agent 新建"（`rewind/context.py` journal 的 `before_hash is None && after_hash 非空` 且 source 记 agent-created）时才删除；否则视为"待恢复"。同时**消费 journal 的 before blob**（`context.py` 已可靠快照原文），对"检查点缺失但 journal 有 before"的路径用 before blob 写回，而非删除。删除前需经时间线"是否已存在"判定。
2. **B（修 BUG-2）**：`_spawn_restore` 无 checkpoint 时，continue 置 `partial`/`failed`，前端明确提示"无文件检查点，仅截断对话"，禁止假 `committed` + 假"后台恢复"文案。
3. **C（修 BUG-3）**：`_restore_one_file` 的 `managed` 判定改用**内容哈希**（读当前文件算 hash 与 `entry.content_hash` 比对），摒弃 `(size,mtime)`；`query_engine.py` 不再对索引同步异常静默 `pass`，失败时标记该 turn 检查点"索引未同步"并让回滚走保守路径（跳过而非删除）。
4. **D（冻结门控）**：`freeze_checkpoint` 在有用户消息且 rewind 开启时**无条件执行**，或把"无检查点"作为显式状态传播，避免 `checkpointState:'none'` 时 continue 仍承诺恢复。
5. GUI 侧对齐：`rewindV3Store.ts` 的 `serverTargetId===null` 分支（`:494-502, 550-569`），restore 报错、continue 降级提示需与后端新语义一致。

**测试**：
- 新增 `python/tests/test_rewind_hotpath.py` 回归：①既有文件本轮首次被 agent 修改 → 回滚应恢复原文（现有用例都先 `index.upsert` 预索引了，从不命中删除分支，故漏掉 BUG-1）；②continue 无检查点 → 断言不置 `committed`；③模拟索引同步异常/`turn_baseline=None`/超 scan limit/回滚前 mtime 漂移 → 断言仍恢复。
- 补充 `gui/src/stores/rewindV3Store.test.ts`：对 `restore` 报告的 `restored/deleted/skipped_dirty` 正确性增加断言。

### 组2：命令行在 GUI 无用（P0-②）— `gui/src/components/Composer.tsx` + `slashCommands.ts` + registry

**根因（取证确凿）**：解析/着色/补全都在 Composer 做好了（`Composer.tsx:462-579`），但 **`onSend`(L825) 从不调用 `parseSlashInput`/`handleComposerSlash`**——直接 `buildPayload()` 再 `sendMessage(...)` 把 `value` 原样当普通文本发给后端。斜杠真正执行只接在 `CommandPalette.tsx:204-237`（Ctrl+K 面板）。`/export` 是 server 命令（`registry.py:107-115`）、`/skill` 是本地技能直呼、`/run` 是本地执行，全走不到。`/map` 不在 registry（map 只是 `XeyoUI` 工具 `show_tool_flow` 副作用，`dispatchXeyoUi.ts:108-111`），故 `/map` 作为文本发给 LLM 永远不渲染成图。

**修复方案**：
1. `Composer.onSend`（`buildPayload` 前）加斜杠网关：`const probe = parseSlashInput(value); if (probe.isSlash) { const consumed = await handleComposerSlash(value, {sessionId, backendSessionId, workspace, onNewSession, onRetryLast}); if (consumed) return; }`。`handleComposerSlash` 已实现未知命令报错、server 命令 `POST /v1/slash`、`/run`、技能直呼改写（`slashCommands.ts:262-292`），返回 `true` 即不再走 `sendMessage`。
2. **统一两条执行路径**：`CommandPalette.tsx` 与 Composer 收敛到同一 `runSlashCommand`，避免行为漂移。
3. `/map` 处理：`python/slash/registry.py` 新增 `map` 命令（`handler='client'` 且 `surfaces` 含 `gui`），`slashCommands.ts` 的 local 分支调用 `setMapToolFlowVisible(true)`；跑 `py -3.11 -m slash.export_manifest` 重生成 `gui/src/generated/slashManifest.ts`。

**测试**：
- 新增 `gui/src/components/Composer.chat.test.tsx`：输入 `/export file.md`（mock `postSlash`）、`/badcmd`（断言"未知命令"、不触发 `sendMessage`）、`/map`（断言调用 `setMapToolFlowVisible`）。
- 新增 `gui/src/lib/slashCommands.test.ts`：`runSlashCommand` 对 `not-slash/unknown/server/local/send` 各分支。

### 组3：Resume 富化提示泄漏为用户气泡（P0-③）— `server/routers/chat.py` + `engine/query_engine.py` + 前端对账

**根因（取证确凿）**：`chat.py:348-401` `_build_enriched_resume_prompt` 生成的富化文本（`[Resume] The user asked to continue… / Original goal: … / Last stop reason: … / User cue: …`）被当作 `submit_text`（`chat.py:940-947`）传给 `engine.submit`，而 `query_engine.py:581` 把 `user_msg = user_message(text=prompt)` 直接 append 进会话 transcript。实时乐观气泡显示"继续"，但断流/刷新/backfill（`streamRecoverySlice.ts:97-135`、`preStoreHelpers.ts:112-151`）用服务端 transcript 覆盖本地时，气泡正文变为富化文本。

**修复方案**（注入与存储分离）：
- 后端：transcript/user 消息正文存**原始 cue**（"继续"），富化 prompt 仅作为模型侧注入（走 `prompt/pre_llm_inject.py` 的 T_now 注入管线，或 `submit_options` 带外传富化壳，`_submit_message_inner` 里 user 消息正文仍写 cue）。改 `chat.py:899-947` 与 `query_engine.py:572-581`。
- 兜底：`loadServerSessionMessages`/`mergeTranscriptWithLocalThoughts` 对账时，把以 `^\[Resume\]` 开头的 user 消息还原为 `User cue:` 字段内容（防御历史残留）。

**测试**：
- 新增 GUI/后端测试：断言富化 prompt **不得**作为 user 气泡渲染（现有 `test_turn_detach_reattach.py:23-45`、`test_multi_agent_p1.py:394-424` 只测"富化被正确构建"，反而固化问题）。
- 后端单测：resume 提交后 `session.messages[-1].text` 为原始 cue；对账函数能把旧 `[Resume]` 消息还原。

### 组4：队列"后端繁忙"（P1）— `server/routers/chat.py` + `server/synthetic_round.py` + `gui/src/lib/api/chatStream.ts`

**根因（取证确凿，三处边界）**：
- `side-` 会话强制不排队：`queue_if_busy` 只在非 side- 置 True（`chatStream.ts:117-119`），side 忙时后端恒 409。
- `submit_synthetic` 载荷不带 `queue_if_busy`（`synthetic_round.py:85-108`）：settle 后投递竞态里 `_busy_or_queue` 走 409 → 返回 False → inbox 项标 `stuck`，GUI chip 显示"投递失败"。
- 前端 queue 路径空处理器（`streamSendSlice.ts:180-248` `onDelta(){}` / `onDone(){}`）：若后端并非真忙只是前端本地 `active` 过期，后端正常开跑下发 delta 被空处理器吞掉 → 无 chip、无回复；竞态 409 则 `onError` 撤回气泡并弹"后端繁忙/Agent 仍在运行"（`api.ts:1025-1030`）。

**修复方案**：
1. `submit_synthetic` 载荷补 `queue_if_busy: True`（或投递端对 `pool.is_busy`/`is_running` 加短临界区一致性），避免投递竞态 409→stuck。
2. 前端 queue 路径**不空置** `onDelta`/`onDone`，挂上正常流渲染回调，使"未真正排队、直接开跑"的回合仍显示回复（`streamSendSlice.ts:180-248`）。
3. `side-` 会话明确文案"侧聊不支持排队"，别当普通"后端繁忙"。
4. 区分 409（会话忙）/429（`InboxQueueFull`，`inbox_registry.py:139-169` 上限 8）/stuck（投递失败）三种文案。

**测试**：
- 后端 `tests/test_inbox_registry.py`：投递竞态（idle 判定后又占用）不 409。
- GUI：新增 stream 测试断言"queue 竞态下仍渲染回复"。

### 组6：mermaid 不渲染（P1）— `MermaidBlock.tsx` + `mermaidRender.ts` + `XyStreamdown.tsx`

**根因（取证确凿）**：看到的是 `MermaidBlock` 的**失败回退路径**（`MermaidBlock.tsx:57-61` 置 `failed` → `:91-94` 渲染裸 CodeBlock），非渲染中。失败来源：(1) mermaid 11.16 的 `@mermaid-js/parser`（langium）在 Tauri WebView（自定义协议/CSP）加载 wasm/Worker 受限 → `import('mermaid')`(`mermaidRender.ts:33`) 或 `render()`(`:70`) reject；(2) 生成图语法不被 `securityLevel:'strict'` 接受 → `render` throw。流式期间 `lite=true`（`StreamingMarkdown.tsx:39`）先按代码块显示是设计内行为。

**修复方案**：
1. `renderMermaidSvg` 的 catch 把 `err.message` 透传，`MermaidBlock` 在 failed 分支显示"生成失败：<原因>"+ 原始代码，便于定位是 import 还是语法失败。
2. 若属 import/worker 失败：启动时 `void import('mermaid')` 预热，确认 Tauri CSP 放行 worker/wasm；或 `mermaidInit` 加 `maxTextSize`、embed 场景按需放宽 `securityLevel`。
3. 防御：`import('mermaid')` 前判断 `typeof Worker`/`WebAssembly`，能力不足给降级提示。
4. 若属语法失败（`/map` 生成图）：`render` 失败时做一次宽松 parse 并报告行/列，让生成方修正。

**测试**：`MarkdownView.test.tsx:230-234` 已有 mermaid→img；补"失败回退显示原因"用例。

### 组9：用量余额统计歧义（P2）— `gui/src/components/UsagePanel.tsx` + `python/usage/*`

**测试**：新增 sticky 回归用例：两个 sticky（上高限高+下编辑）同 stuck，断言两者 `top` 不重叠（`StickyPromptController.test.ts`/`stickyContract.test.ts`）。

## 五、边界情况与失败模式

- **rewind**：回滚期间用户手改路径（dirty）必须跳过并弹窗提示，绝不覆盖；无检查点回滚只截断对话、明示"文件不回滚"；索引未同步时走保守"跳过而非删除"，防止误删升级为数据丢失。
- **slash**：未知命令显示"未知命令 /xxx"，不把 `/xxx` 当文本发给 LLM；server 命令失败透传原因；`/map` 在 skill 环境不可用时给降级提示。
- **resume**：历史已落盘 `[Resume]` 消息在对账时被还原，不污染新会话；富化只喂模型、绝不进 UI。
- **queue**：side- 会话明确"不支持排队"；队列满(429) 与投递失败(stuck) 与 会话忙(409) 文案区分。
- **模型设置**：单模型 profile 迁移时保留 `model` 兼容字段，不破坏既有 localStorage 数据。
- **mermaid**：wasm/worker 能力不足时降级为代码块 + 原因提示，不含语义错误图撑跳 body。
- **文件树**：删除同步失效，避免残留；轮询用 mtime 差量避免高频重列。
- **sticky**：叠层偏移需防"多 sticky 同屏"溢出视口；编辑态 portal 与流内芯片几何不漂移（受 `stickyContract.ts` 约束）。
- **MCP/沉浸**：占位面板不破坏扩展层会话内"tools 数组冻结（零重缓存）"红线；沉浸退出用 Esc/XEYO CHAT 面板，不误关工作区数据未保存。
