## 一、方向（一句话）

把 **L4 长期记忆**从「扁平 markdown 全文扫」升级为「**符号级/AST 代码知识图谱**」：读代码成本从「重复解析源码」降到「图谱查询」，代码知识**可增长、可增量更新、可引用定位**。

## 二、为什么（真实缺口）

XEYO 是代码 agent（`gui/` 前端 + `cli-ts/` TUI + `python/` 引擎）。现状：

- **33-符号级代码理解**已让「读单个符号/按名找符号」变便宜（Read `symbol` / Grep `symbols`，零持久状态）；
- 但 **L4 长期记忆**仍靠 `memdir` 的 **markdown 笔记全文**，代码库知识没有结构化的「记忆面」——跨会话想找「之前修过的 `connect()` 在哪」要重新 grep/read；
- **GraphFlow**（[GitHub: Roarpeng/GraphFlow](https://github.com/Roarpeng/GraphFlow) / [npm: @roarpeng/graphflow](https://www.npmjs.com/package/@roarpeng/graphflow)）给出的是「**Memory + Hooks + Skills 三位一体**」的本地优先代码知识图谱 harness（MCP + dsh 插件，README 口径代码密集场景 ~98% token 节省）——正是这块「记忆面」的参考形态。

## 三、采纳什么（面向 XEYO 地基，不照搬）

| 层面 | 做 | 接现有地基 |
|---|---|---|
| **记忆层** | sqlite 扩一张**代码符号/引用表**（symbol → file/line、definition/call/reference 边），作为 L4 的结构化面，与现有 markdown 笔记并存（md 仍是 source of truth） | `memindex.py`（已建 sqlite `notes/fragments/edges`，A4）+ 铁律「sqlite = 派生索引」，可随时全量重建 |
| **符号理解** | 用 **33-符号级理解**（ast/tree-sitter）做结构化索引来源 | `33` 计划已落地的按需解析符号缓存模块 |
| **增量更新** | Hook 在文件改动时**增量**更新符号/边（而非每次全量解析） | 既有 tool-result 变更钩子管线 |
| **检索** | 代码知识检索封装为 Skill/工具，图谱查询替代重复源码解析 | MCP × SKILL 契约（`docs/设计/40-...`） |

**明确不迁入本轮**：v7 不新增独立「代码图谱工具面」的**会话内注册**——接入方式、是否复用 `Memory` 工具还是新工具，属立项后设计，且必须守「会话内工具面冻结」（MCP×SKILL 红线）。

## 四、为什么标「远期 v7」

结构性大改：动 L4 数据模型 + 符号索引 + 增量 hook 管线 + 可能的检索工具面，**不属于本轮（v61 采纳）落地**。正确姿势是本文件**确认方向 + 立档**，不现在动手。

## 五、证据门（立项前须过）

- **通道 B（OPE）**：在冻结真录会话上，对比「现有 L4 检索」vs「图谱检索」的**检索命中质量与 token 成本**（读代码场景），量化「代码知识可增量、可定位」的收益；
- 验收指标：代码定位检索的**命中准确率不降**、单次定位的**输入 token 节省**（对齐 GraphFlow ~98% 口径的去伪）、**增量更新不产生全量重解析**（hooks 生效）；
- 未过门槛前不写实现、不接工具面。

## 六、收益（长期，结构性）

- 读代码成本从「重复解析」降到「图谱查询」，代码知识**可增长、可增量更新、可引用定位**；
- 跨会话「之前在哪改过/定义在哪」变成**一次图谱查询**而非 grep/read 若干轮——直接服务 XEYO 的记忆检索 P0（召回、绑定）+ 跨会话共享。

## 七、边界与红线原则

- **md/source 永远优先**：图表是**派生索引/缓存**，可删除全量重建；人仍可直接编辑 md。
- **零会话内工具面漂移**：任何新工具/参数接入必须走 MCP×SKILL 契约 + `schemas()` 会话内冻结（`test_extension/test_freeze_invariants`）。
- **须先过 §五 证据门**，且 `XEYO_L5` 有回退开关。

## 八、证据门终局结论（2026-09-04）

公平重测（`python/scripts/v7_graph_gate.py`，两路径同读符号正文）判定：**❌ 未达标，图谱检索暂不接入主链路**。

| 判据 | 结果 |
|---|---|
| 命中准确率不降 | FAIL（图谱路径 3 符号未命中） |
| 假阴哨兵（单符号节省 ≥95% 或图谱 tk<50 = 漏召回） | FAIL：`_eligible_for_early` / `continueAndRevert` / `rebuild_edges`（此前的"token 节省 100%"即此假阴，非收益） |
| 总 token 节省 | 64%（数值本身被假阴抬高，不可信） |
| 增量不全量重解析 | PASS（改 1 文件重解析 1） |

**结论**：图谱索引的增量更新机制达标，但召回完整性不达标（3 符号漏召回）。后续若要重启：先修 cgraph 召回（定位 3 符号为何未入索引——疑似命名/语言覆盖缺口），重跑本门，假阴哨兵 PASS 后再谈接入。

**判据修正说明**：旧版判据"save_tot > 0 即 PASS"会把漏召回当收益；现版加入假阴哨兵（本次教训固化，sess_mtlfvp9l 发现的"节省 100% 有重大嫌疑"由此制度化）。
