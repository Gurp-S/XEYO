# WSC 批次29：搜索命中证据、文件身份与评测口径

唯一状态入口仍为 `docs/wsc-two-conversations-todo-2026-10-08.md`。上一目标轮完成卡面索引实验和分块共享，有进展；本批继续未通过召回，没有把目标改成“让单个查询跑绿”。

## 根因与结构规则

1. 冷召回评测把步骤ID `work` 称为 `task_id`；检查点没有独立任务ID字段，不能据此宣称正式任务身份验证失败。改用明确 `step_id` 查询，旧请求/失败报告保留并标为历史步骤别名判据，不改历史数字。
2. 原评测只提供Read，产品还有Grep。新增只读执行器使用产品Read/Grep，允许两种工具面配对；路径不得越过私有根，不能执行Write/Edit/Bash。判据要求真实调用取得目标定义，且来源是发布视图；程序正常返回或回执ID存在不等于取到了事实。
3. 原Grep的长行显示是行首500字符，即使命中在末尾，也会把命中截掉。单纯更小预览不能保证显示匹配证据。新增明确选择的 `matches` 视图：原生rg返回非空命中子串、文件、行号、1起始字节列；不在Python重新解释正则、不猜哪段重要。摘录不冒充整行，受限摘录标明不完整，页单位为命中记录。零宽模式没有非空子串不证明查询未命中；不喂给零命中护栏造假前提。
4. 原Grep单文件输出没有文件前缀，NUL路径协议无法发挥作用，分页会把 `1、10、11、2` 当文本顺序。任务续接旁路的content视图强制原生文件身份，排序才能依据数值行号；不是对文件名/正文特征写特例。

新行为仍由默认关闭 `XEYO_WSC_TASK_CONTINUITY` 控制。`matches` 默认不出现在工具schema，关闭时拒绝；启用后由模型自选，不把content静默替换成匹配子串，不自动再搜/补值/关闭步骤。既有content上下文语义保留，matches不支持上下文/多行时明确拒绝。没有原生位置的后端或解析失败给真实失败，不伪造列号；正则、超时、取消等生产失败保留，不能都改成“位置未知”。未验证GNU后端等价位置支持。
