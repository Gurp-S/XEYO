# 批次110：普通请求与容量压力共用一次折叠

用户指出审查扩展到UI写入/删除缓存偏离WSC优化重点。本批次不修改这两个入口，直接回到主请求的压缩时机、完整请求准入与任务连续性。原有来源生命周期TODO保留，不拿它替代主验收。

结构性根因：query_loop在遇到成功Compact回执时先force_compact，然后wsc_request_timing.prepare再检查85%并可再次force。两种触发各自拥有折叠执行点，同一发送准备可能连续推进两次；prepare从第一次折叠后的游标计量，还会把已经发生的普通折叠记录为keep。

修正规则：同一请求准备最多一次折叠，不把85%当压后目标值。主循环仍先核对并保存来源，需要时生成/提交结构化交接；随后统一prepare决定“成功模型请求或当前完整请求容量压力”，调用同一个compact回调一次。压后重建完整输入、通知身份和输出余量，超过硬容量仍报错，不连续循环折叠。Compact回执只在回调正常返回后标记消费；无可折历史仍记录no_eligible_history。

实现只改engine/query_loop.py、memory/wsc_request_timing.py。普通请求作为prepare可选参数，不改变默认调用合同；不增加状态存储或新开关，不改确定性算法、冻结前缀、旧源、冷对象和尾部结果保护。

静态核对合同（未执行）：

- 普通请求且不足85%：一个折叠回调；记录model_requested=true、fold_attempts=1、automatic_attempts=0。
- 普通请求且达85%：仍一个回调，两个触发共同满足准入。
- 无普通请求且达85%：一个回调；普通请求字段false。
- 无触发：零回调；交接与来源保存的既有前置顺序不变。
- 压后仍达85%但未超过硬容量：发送准备不会继续折叠；压后超硬容量则中止发送。
