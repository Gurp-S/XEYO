# 别人怎么做：思考态回放与裁剪的行业实践考据

> 目的：为「Claude 当一级公民（方案 B）+ 近档保留 2 轮」提供业界对标依据。
> 来源：Anthropic 官方文档（2026-09 时点）+ Roo Code / Cline / gptme / Helix 四个生产实现。
> 结论：**你的三个选择（B / 实测 / 2 轮）都有业界背书，其中「2 轮」几乎就是 Anthropic 的官方默认值。**

## 一、最重要的发现：Anthropic 官方**已经内建**了我们在纠结的裁剪策略

这条直接回答了「reasoning 是否进压缩域」在 Claude 侧的答案：

> **官方默认行为**：开启 extended thinking 但**未**配置 `clear_thinking_20251015` 策略时，API **自动只保留最后一个 assistant 轮次的 thinking block**（等价于 `keep: {type: "thinking_turns", value: 1}`）。

并且，官方给了两条关键指导：

| 官方原话（翻译） | 含义 |
|---|---|
| 「工具使用轮次内，**必需**传回 thinking 块」 | 当轮配对不可裁（硬要求） |
| 「跨轮次，**推荐**传回所有内容」 | 但推荐 ≠ 必需 |
| 「工具使用之外，**允许**省略先前轮次的思考」 | ★ **旧轮可裁，是官方明确允许的** |
| 「**你不需要自己修剪旧的思考**。传回所有 thinking 块，API 会自动过滤，只保留维持推理所需的块，**并且仅对实际展示给 Claude 的块计费**」 | ★★ 这条是**成本问题的官方答案** |
| 「但当 thinking 块**被保留在上下文中**（未被清除）时，prompt cache 得以保持，实现缓存命中并降低输入 token 成本；**当 thinking 块被清除时，缓存在清除点失效**」 | ★★★ 裁剪是有代价的：**破缓存** |

### 这三条合起来推翻了我们此前的两个假设

**假设 1 被推翻（成本）**：我们算的 ¥76.30（未命中价）**不成立**。
理由：官方明说「只对**实际展示给 Claude 的块**计费」，且默认只留 1 轮。也就是说，**把全部 thinking 传回去 ≠ 全部计费** —— API 服务端会先过滤再计费。
→ 我们那个「全量传=¥76」的推算是**客户端视角**，没算服务端过滤。这正说明**必须实测**（呼应你的第 2 项选择）。

**假设 2 被推翻（"裁了省 token"）**：**裁剪反而可能更贵**。
理由：thinking 块保留 → 缓存命中（0.02 价）；清除 → **缓存在该点失效**，后续要重新 cache write。
→ 这是一个**反直觉结论**：省 token 的直觉动作会破缓存。官方原话「Configure the keep parameter based on whether you want to prioritize **cache performance or context window availability**」—— **是"缓存 vs 窗口"的取舍，不是"省钱 vs 花钱"的取舍。**

## 二、模型分档：不同模型默认保留不同轮数（官方表）

| 模型 | `clear_thinking_20251015` 默认 keep |
|---|---|
| Opus 4.5+ / Sonnet 4.6+ | **all turns**（全保留） |
| Fable / Mythos 系列 | **all turns** |
| 更早的 Opus/Sonnet、全部 Haiku | **last turn only**（只留最后一轮） |

**解读**：Anthropic 对**强模型**默认全保留（因为强模型能从旧思考获益），对**弱模型**默认只留 1 轮（旧思考是负担）。
→ 这与我们 `policy.py:375` 注释里的顾虑（「弱模型存在旧结论指令化锚定/续写压力」）**完全同构** —— 业界独立得出了同一结论。

⚠️ **但注意**：这里「保留」指的是**保留在上下文里**（不主动清除），不是「计费」。计费仍按「实际展示的块」。

## 三、四个生产实现怎么做的（横向对照）

| 实现 | 存储方式 | 裁剪策略 | 关键教训 |
|---|---|---|---|
| **Roo Code** | 双历史：`apiConversationHistory`（Anthropic 原生格式，含 thinking+signature）与 UI 消息**分开存盘**，各自 JSON | `getKeepMessagesWithToolBlocks` 汇总时**向前回溯找 tool_use 并连带其 reasoning 块一起保留** | 存的是**原生格式**，不是转码后的 OpenAI 格式 —— 因为签名必须原样 |
| **Cline** | 同 Roo（Roo 是 Cline 的 fork），`apiConversationHistory: Anthropic.MessageParam[]` | 同上 | 保留原生 API 消息是**结构性前提**，不是可选项 |
| **gptme** | 把 signature 藏在文本里的 **HTML 注释**中 | 无 | ★ **踩过的坑**：`if sig_match and not signature` 导致**只保留第一个块的签名** → 多 thinking 块时静默数据丢失 → **下一轮 400**。修法=改成一个 block 一个 (text, signature) 对 |
| **Helix** | 全局 `signatureCache`：`map[toolCallID] → signature bytes` | 无（走原生 SDK） | ★ **踩过的坑**：走 OpenAI 兼容代理时，**OpenAI 格式没有字段承载签名** → 签名被静默丢弃 → Gemini 400。修法=侧信道缓存，组装时回贴 |

### 从这四个实现提炼出的三条硬规则

**规则 1：签名必须逐块保存，N=1 假设会静默炸**
gptme 的 bug 是最典型的样本 —— `not signature` 这种"只取第一个"的写法看起来很防御，实际是**有损的**。多 thinking 块（interleaved thinking / progress update）是**正常情况**，不是边缘情况。

**规则 2：原生格式存盘，不要转码后再存**
Roo/Cline 都存 Anthropic 原生 `MessageParam`。原因：签名绑定了原始内容，**任何转码都会破坏它**。这直接支持方案 B（原生适配器）—— 如果我们的 `Message` 只有 `{type:"reasoning", text}` **没有 signature 字段**，那 Claude 就用不了。

**规则 3：OpenAI 兼容层承载不了签名 —— 这是方案 A 的死穴**
Helix 的教训：**走 OpenAI 兼容代理时签名必丢**，只能靠侧信道缓存绕。
→ **方案 A 在 Gemini 上即使能做，也是打补丁；在 Claude 上根本拿不到签名。**

## 四、还有一个「隐形地雷」：thinking 块与历史的强绑定

Anthropic 2026 新增了一个 beta 机制 `thinking.block_binding`：

> 重放的 thinking 块**只有在它前面的 system prompt、tools、messages 全部未变时才被接受**。
> 若更早的历史变了 → 400：`Invalid signature in thinking block. The block is bound to a different conversation.`
> 新账号（2026-08-31 起）默认 `prefix_mismatch_behavior = "error"`；
> 设成 `"drop_block"` 则丢弃该块并继续。

**这对 XEYO 是个重大约束**：
- 我们的 **T_now 注入**（env_channel 尾插伪造 tool 对）、**压缩**（改历史）、**rewind**（改历史）**全部会改变历史前缀** → 都会触发签名失效。
- 官方给的解法是**「保持对话历史只追加（append-only）」**，或显式设 `drop_block`。

⚠️ 这条**与我们的架构有直接冲突**：`compact.py` 的压缩、rewind 的回溯，本质上都是**改写历史**。如果接 Claude 原生，这些机制必须显式处理签名失效（要么 `drop_block`，要么接受 400）。

## 五、对三个决策的回答

### ✅ 决策 1（Claude 当一级公民 → 方案 B）：**业界背书成立，但代价比预估的大**

四个生产实现**没有一个**走 OpenAI 兼容层来做 Claude —— 全都在存**原生格式**。这印证：想拿思考态，就必须上原生。

但必须补一条我此前没提的成本：
- `Message.content` 的 block 联合体要**加 `signature` 字段**（当前只有 `text`）。
- 要考虑 `block_binding` 与压缩/rewind/T_now 的冲突处理。
- Anthropic 的 thinking 参数**已换代**：`thinking:{type:"enabled"}` 在 Claude 4.7+ **返回 400**，要用 `{type:"adaptive"}` + `output_config.effort`。**不能照抄旧文档。**

### ✅ 决策 2（先实测）：**必须做，而且优先级更高了**

因为官方文档出现了**两个反直觉点**（只对展示块计费 / 裁剪破缓存），**纯靠推理会得出错误结论**。实测能钉死：
- reasoning 段到底计不计输入费（对应我们的 ¥76 vs ¥1.53）
- 裁剪是否真的破缓存（若破，可能**保留比裁剪更便宜**）

### ✅ 决策 3（保留 2 轮）：**命中官方甜点区**

- Anthropic 官方默认：**强模型 all / 弱模型 1 轮**。
- 官方示例里出现的配置：`{type:"thinking_turns", value: 2}` 和 `value: 3`。
- **我们选 2 轮 = 官方示例值**，既不是最保守（1）也不是最激进（all），位置合理。

**但有个前提要先澄清**：我们保留 2 轮的**动机**是什么？
- 若动机是「省 token」→ 官方说这会**破缓存**，可能反而亏。**这个动机站不住。**
- 若动机是「防旧结论锚定」→ 与 Anthropic 对弱模型的默认一致，**站得住**。
- 若动机是「省窗口」→ `compact.py` 的 aging 已经在做窗口管理了，reasoning 只是多挂一条规则，合理。

→ **建议：2 轮作为默认，但把它定义为「锚定控制」而非「成本控制」**，并在实测后用数据确认这个默认值。
