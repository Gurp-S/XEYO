# 引擎注入边界：什么是「信息」，什么是「压力」

> 2026-09-10。触发：用户提议「把当前已花费多少 token 发给模型看」。
> 本文把判定规则写死，供以后每一个"要不要往模型上下文里塞 X"的提议复用。

## 一、已有实现给出的口径（先看现状）

引擎当前注入给模型的**约束水位**（全部带上限值、全部只在有上限时出现）：

| 常量 | 文案 | 触发条件 |
|---|---|---|
| `MAX_TURN_WARNING` | `回合数已接近上限。` | 接近 `max_turns` |
| `MAX_TOOL_WARNING` | `工具调用数已接近上限。` | 接近工具调用上限 |
| `WALL_STOP_NOTICE` | `时间预算已到上限（已进入收尾窗）。` | 墙钟走尽且**武装** |
| USD 水位 | `USD 预算已用 80%（已花费 $x / 上限 $y）。` | **仅 `usd_limit > 0` 武装时** |

共同点：**"水位"只在有硬边界时才成立**——它告诉模型"离墙还有多远"，因为撞墙会发生真实后果。
没有上限时引擎什么都不发。这就是既定口径。

## 二、判定尺子（三条，全部满足才算「信息」）

| # | 问题 | 不过关的含义 |
|---|---|---|
| R1 | **它是「约束事实」还是「消费账单」？** | 没有上限的用量数字 = 消费账单 → 不是信息 |
| R2 | **模型据此能做出正确决策吗？** | 不能（不知道单价/总预算/该花多少）→ 只是噪声与压力 |
| R3 | **它会诱发哪一类行为倾向？** | 若倾向是"少做/早停"，而早停恰是我们的主要失败模式 → 有害 |

## 三、对「把已花费 token 发给模型」的裁决

**结论：不发。** 三条尺子全不过：

- **R1 不通过**：默认档下没有美元上限武装（flash 全量 89 题 ≈ ¥26，永不触发 $5 档），
  所以"已花费 X tokens / ¥Y"是**没有边界的消费账单**——不是约束水位；
- **R2 不通过**：模型不知道单价、不知道剩余额度、不知道"该花多少"。
  它无法把数字换算成任何可执行判断，只能做情绪化解读（"花多了"）；
- **R3 不通过（最关键）**：这个数字唯一能改变的行为是**提前收手**，而"早弃/自称完成/该探索时收手"
  正是我们最大的失败模式（A 类超时截断、D 类有度量不用、B 类自测域不足）。
  往上下文里塞一个只会诱发早停的激励信号，等于**引擎亲手制造失败**。

### 反例证据（项目自己的取证，两处）

1. **train-fasttext**：模型自己测出 `P@1=0.613 < 阈值 0.62`，然后**就停了**——
   给它一个"不达标的数字"，它选择放弃。花费数字没有达标线，同属"不达标信号"这一类，
   只可能更糟（连目标都没有）；
2. **成本与失败正相关**：失败题平均花费 0.55 元 vs 全局 0.37 元。
   也就是说"花得多"不是失败的原因，而是**题目难的结果**。模型看到花费上涨就收敛，
   等于把"这题难"误读成"我该停了"。

## 四、那什么可以发（正当替代）

| 想达到的目的 | 正当做法 | 现状 |
|---|---|---|
| 别让长任务跑爆预算 | **执行层硬限制 + 约束水位**（上限武装后才有水位） | 已有（`usd_limit` 水位 / `arm_wall_stop` / `max_turns`） |
| 让模型知道该压缩上下文了 | 注入**上下文窗口占用**（能力约束，决定 compact/spill） | 已有 compact 触发链；GUI 侧有用量展示 |
| 控制成本 | **由用户设上限**，而不是让模型自己心疼钱 | 已有 `XEYO_BUDGET_DEFAULT_USD`（默认关） |

关键区别：**"上限到了没有"是约束事实（可以发）；"已经花了多少"在无上限时是消费账单（不发）。**
成本该由用户的策略决定（设上限）并在执行层静默生效，而不是转成模型的心理负担。

## 五、一句话规则（后续复核用）

> 注入前先问：**"如果这个数字变了，模型该做的动作会不同吗？"**
> 会（且那个动作是我们想要的）→ 发；不会 → 别发。
> 花费数字的答案是"不会，只会少做" → 不发。

## 六、专案：A 类（超时截断）为什么不是「告诉模型输出了多少 token」

用户的直觉有真实内核：**生成确实吃掉墙钟**（实测：生成段占墙钟 88.5%，工具仅 11.5%），
所以"话多"确实挤占完成任务的可用时间。但这条提议解决不了 A 类，三条理由都是实证的：

### 1) 更直接的信号早就在发，而且更准

`engine/budget.py::check_wall_deadline` 在 80%/90% 水位播报：

```
时间预算已用 80%，剩余约 N 分钟。
```

它经 `prompt/pre_llm_inject.py` 的 `# Runtime budget notice` 块**进入模型上下文**，
且——**不需要武装也会发**（`wall_deadline_ts` 由适配器设置即生效，武装只影响 100% 时的收尾窗）。
也就是说 **p3/p4 那批 A 类失败里，模型已经看到"剩余约 N 分钟"，仍然被墙钟杀死**。

**"剩余时间（分钟）"是约束本身；"已输出多少 token"是约束的代理。** 用一个更弱的代理去提示一个
已经送达且更准的信号，不构成新机制。

### 2) A 类的真正缺口是「没有落盘机制」，不是「不知道时间」

A 类的死亡现场（rstan MCMC 92%、dna-assembly 只差 primers.fasta）是：
模型在**做正事**，只是没做完；它自认为"还在正常推进"。
知道剩余 3 分钟并不能让它落盘——需要的是**引擎保留落盘时间并强制收敛**：

- **A1 武装墙钟**（`XEYO_WALL_HARD_STOP=1` + `MARGIN`）→ 100% 时进入收尾窗（grace → `forced_wrap_up`）；
- **缺口清单**（`wrap_gap` 已有）→ 明确列出"已登记未落盘的产物"；
- **D3 已落地**：窗内时间不够的长命令立即交还控制权（实测 1.69s → 0.01s）。

缺的是"武装 + 强制执行"，不是"多一个数字"。

### 3) "让它输出变少"会把 A 类换成 B/D 类

取证 doc 记录过同题对照：`circuit-fibsqrt` 的失败尝试 **134k token 就交卷**（自测域过小），
而充分探索的同题版本 **1.44M token 解出**。**"输出少"不是优点，是另一类失败的病因。**

引擎没有能力判断"此刻的思考是浪费还是在逼近答案"——这正是"引擎不许注入奖惩/导演"的原因。
把模型往"少说少想"推，等于用 A 类换 B/D 类，净效果不确定。

### 如果仍然想加强这个方向（正当做法）

| 做法 | 性质 | 现状 |
|---|---|---|
| 提高水位密度（50%/70% 也报）或每轮附剩余分钟 | 约束事实（合规） | 可做，小改 |
| 武装 R1' 让收尾窗真的生效 | 执行层强制（合规） | 装配即生效，**优先推荐** |
| 注入"已输出 N tokens" | 约束代理 + 诱发少做 | **不做** |
