# 全仓优化点扫描（成本导向 · 2026-09-10）

> 约束：**①真引擎缺陷 ②高收益 ③不导演（不注入命令/建议/评价，不造成注意力漂移）**。
> 靶心先定：新价下 **输出 ¥4.0/M 占成本 83%**、未命中 ¥1.0/M 占 12%、命中 ¥0.02/M 占 5%（**50:1 价差**）。
> 所以只有两类真靶：**少产出 token**、**少打断前缀缓存**。以下全部经代码核实（附行号），
> 凡违红线的一律列进"不做"。

## 一、A 级：真缺陷且零注意力影响

### A1 引擎无法声明、也无法记录"思考档位"——83% 的成本处于厂商默认状态

**证据（已核）**
- `model/openai_compat.py:135` 客户端默认 `thinking="disabled"`；
- `:184` 该字段**只在 `self._provider == "deepseek"` 时才发送**，否则走 `:190` 的通用分支（只透传 reasoning_effort）；
- `engine/query_engine.py:1202` `build_default_engine()` **根本没有 `thinking` 参数**——引擎层无法表达思考档位；
- `TerminalBench/xeyo_harbor_agent.py` 传 `provider="openai"` → **`thinking` 字段从未发出** → 实际生效的是**厂商默认**（v4-flash 思考默认开，这正解释实测"输出 94% 不可见"）。

**为什么是真缺陷**
1. 引擎**不知道自己发了什么**：同一个 `build_default_engine`，换个 provider 字符串就落到不同的思考档位，代码里没有任何断言或日志记录这个差异；
2. **测量不可复现**：66.7% 那类分数是在"未声明推理预算"下取得的——厂商哪天改默认值，分数会变而我们不会知道自己改了什么变量；
3. 成本不可控：占总成本 83% 的那一项，引擎既不能声明也不能上报。

**修法（零导演）**：让思考档位成为**显式、可记录**的运行参数——客户端不再依赖 provider 字符串分支；`build_default_engine` 接受并透传 `thinking`/`reasoning_effort`；**把实际生效值写进 run 配置与日志**。不改任何提示词、不往模型注意力里放任何东西。

### A2 上一轮思考在历史里不存在 → 每轮从零重推（**修法已修正，见下**）

**证据（已核）**
- `prompt/pre_llm_inject.py:413` 注释明写："OpenAI 系厂商不回传 reasoning，历史里没有；**不回填会驱使弱模型每轮从零重推同样的内容**"；
- `permissions/policy.py:375` `reasoning_tail_enabled()` **默认关**，理由是"强模型收益≈0、**弱模型存在'旧结论指令化'的锚定/续写压力**"；
- `engine/query_loop.py:1276-1284`：开启时只取**结尾 600 字符**，且**仅工具续写轮**注入，位置是 **T_now（指令区）**。

#### ⚠️ 协议规则（2026-09-10 查证官方文档后修正）

DeepSeek Thinking Mode 文档（`api-docs.deepseek.com/guides/thinking_mode`）明文规定，**分两种情况**：

| 情形 | reasoning_content 该怎么处理 |
|---|---|
| 两轮 user 之间**没有** tool call | **不需要**回传；**传了会被 API 忽略**（老 `deepseek-reasoner` 甚至直接 400） |
| 两轮 user 之间**有** tool call | **必须**参与上下文拼接，且**在所有后续轮次都要原样回传**；不回传 → **HTTP 400**（`The "reasoning_content" in the thinking mode must be passed back to the API`）；**截断或摘要同样会触发拒绝** |

**因此正确的修法不是"塞进 content"，也不是"塞进 T_now"，而是：在协议字段层原样回传。**

- ✗ 塞进 assistant 的 `content`：协议上能发（不会被拒），但**伪造了模型自己的历史**——它会以为自己说过这些话，且可能诱发风格模仿/更啰嗦（与省 token 的目标相反）；
- ✗ 塞进 T_now 指令区（现状实现）：读起来像命令 → 这正是它被默认关掉的原因（位置错，不是信息错）；
- ✓ **新增 Message 的 reasoning 字段 + 请求构造时对"工具轮"的 assistant 消息原样带上 `reasoning_content`**：
  1. 满足官方硬要求（避免未来显式开启 thinking 后的 400）；
  2. **这才是真正的"历史保真"**——模型自己的思考回到它自己那条消息上（协议认可的位置）；
  3. 同时消除"每轮重推"对应的输出 token。

**顺带印证**：官方规则正好是"**仅工具轮需要回传**"——与引擎现有设计意图（`仅工具续写轮注入`）完全一致，说明原作者的直觉是对的，只是**实现位置跑错了**（放进了 T_now 而不是协议字段）。

**A1 与 A2 必须成对落地**：一旦把 thinking 显式声明为 `enabled`，就进入严格校验区，此时不回传 reasoning_content 会直接 400。**不能只做 A1。**

**实测现状（重要）**：89 条评测轨迹里 `reasoning_content` **零命中**，也没有 400 报错——当前"完全不传"的组合恰好没被强制校验（因为请求里未显式声明 thinking）。所以**当前没有正在流血的伤口**，但这是个"一动就炸"的耦合点，且导致 83% 成本处于厂商默认（**默认 effort=high**）状态。

**必须 A/B 量化**：同 10 题两臂，比 Σoutput（¥6）。


### A3 每轮修配对会"插入"改写历史 → 破坏该点之后的前缀缓存

**证据（已核）**：`engine/query_loop.py:803` 在 submit 入口调 `_repair_unpaired_tool_calls`；`:219-243` 实现为 `store.insert(j + inserted, tool_result_message(...))`——**插入**会让其后所有消息索引位移，前缀缓存从该点起全部失效（50× 价差）。

**修法**：改为**追加占位**（把补的工具结果挂到受影响轮的末尾）而不是中间插入。触发条件窄（仅跨 abort 残留未配对 tool_call 时），但一旦触发就是确定的缓存损失。

## 二、B 级：真缺陷、影响面窄或需产品路径

| # | 位置 | 问题 | 修法（零导演） |
|---|---|---|---|
| B1 | `tools/file_write_tool/file_write_tool.py:463`、`file_read_tool.py:576` | 参数校验失败 → 整轮重生成；报错若不能让模型**一次改对**，就反复烧输出 token | 把失败原因做成**确定性事实行**（哪一项/期望/实际），不加任何建议措辞 |
| B2 | `memory/runtime.py:1036` `apply_c2_messages` | 首次压缩把切点左侧历史整段换成一条摘要 → 一次性大 miss（属必要成本） | 只可调阈值/频次（`try_extend_c2` 已是 append-only，前缀安全） |
| B3 | `prompt/pre_llm_inject.py:632` `file_conflict_block` 用 `strftime("%H:%M")` | 尾部易变（不破前缀，只增加每轮 miss 体积） | 降频或仅在真冲突时渲染 |

**已否决的负面结论（扫描确认无问题）**：无 `finish_reason=length` 续写分支（不会重复输出）；截断后不回灌原文全文；system 左段无"求全/详尽"类措辞；重试仅发生在 `saw_any=False`（没产出就不白付输出）；`env_channel`/伪对随机 id 都在尾部，不破前缀。

## 三、明确不做（违红线，逐条给理由）

| 提议 | 为什么不做 |
|---|---|
| 默认开启"输出精简"注入（`pre_llm_inject.py:109` `OUTPUT_COMPACT_RULES` + lite 变体） | **这是纯导演**：其内容就是"思考：精简完整推理"。直接指挥模型压缩推理 = 注意力漂移，正是用户明令禁止的 |
| 设 `max_tokens` 上限截断思考 | 属"替模型截断思考"；且实测逐条可见内容 P99=1294 tok、**无截断聚集**，问题不存在 |
| 引擎自动按任务调低 `reasoning_effort` | 引擎替模型决定"想多少"；反证：同题 **134k token 失败 vs 1.44M token 解出**。要做只能是**用户显式配置** + A/B，绝不自动降档 |
| `write_store` missing_read 拒写时自动补读 | 会破坏"防盲写覆盖"的安全纪律（新建文件已免先读，够用） |
| 循环检测改为"阻断重复调用" | `loop_ledger`/`repeat_fold` 现设计是"零误杀、不拒执行"，改成阻断会把"看似重复实则必要"的调用挡掉 |

## 四、给"省钱"的结论（诚实版）

**扫描没有找到大额白烧**：装配链对前缀缓存整体谨慎，截断/重试路径都不重复投喂，重试只发生在未产出时。
钱集中在**思考 token**（占输出 94%、占成本 ~78%）。围绕它，引擎侧只有两件真事：

1. **A1**：把思考档位变成**显式 + 可记录**（修"引擎不知道自己发了什么、分数不可复现"这个真缺陷）——
   *它本身不省钱，但它把 83% 的成本从"厂商默认"变成"你的选择"*；
2. **A2**：把上一轮思考**回填到历史位**（消除每轮重推）——*这才是能直接少烧输出 token 的一条，需 ¥6 的 A/B 验证*。

优先级：**A1（零风险、修可复现性）→ A2 A/B（¥6）→ A3（窄而确定）→ B1（产品路径）**。
