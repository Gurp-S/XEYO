# WSC Phase 5 —— 目标定义与编号清单（2026-09-23）

## 1. 用户裁定（原话要点）

- 下一轮**唯一主指标 = 去噪 / 在场信息密度**；信息保留、压缩率降为**硬约束**（不得退化）。
- 去噪**两条臂都测**：① 只标注 + 段内合并（不删）；② 相关性寿命（真删）。用数裁，不靠哲学。
- 压缩率**必须看**，但它是"去噪率 × 信息保留率的合集"，定位成**信息密度**；
  并且"压缩率 = 压缩后未命中的价格 ⇒ 尽量低"。

## 2. 基率复核：折叠到底值多少（`_wsc_out/_fold_pricing.py`，只读厂商账本，零 API）

单位用 **token·枪**（少发的 tok × 后续枪数），不碰价格表就能比：

| 量 | 值 |
|---|---:|
| 可比折叠次数 | **40**（3,373 次折叠事件里，2,254 次"prompt 没变小"被跳过、10 次会话太短） |
| 移出量中位 | 2,643 tok |
| 折叠后本会话剩余枪数中位 | 13.5 |
| 单次收益中位 | **26,973 token·枪**（p25 7,420 / p75 105,146） |
| 单次代价中位（该枪比本会话基线多出的未命中） | 4,573 tok |
| **收益 / 代价（同单位）** | **5.99×**；净为负的折叠占 12.5% |

**但换成钱方向就反了**：被移出的那段本来就**已缓存**，省下的是**命中价**；而代价付的是**未命中价**。
DeepSeek 两档都是 30× 价差（flash 0.05/1.5，pro 0.15/4.5），于是：

`5.99 × (1/30) ≈ 0.20` ⇒ **按可测样本，折叠在钱上是净亏的**（收益只有代价的 ~1/5）。

同向的独立证据（既有 p8 vs attempt2 两臂，厂商实付）：多折的那臂 **45 次折叠、每请求 ¥0.0284、
命中 43.7%**；少折的那臂 **5 次、每请求 ¥0.0104、命中 84.1%** ⇒ 折得越多，每请求越贵。

两条偏差必须写清，别让这数被当成判决书：
- 代价被**高估**：4,573 tok 里含该枪本来就要发的新内容；
- 收益被**低估**：不折的话那段还会继续长大，且**不折就会溢出窗口**（这才是折叠存在的理由）。

⇒ 结论不是"折叠没用"，而是：**折叠买的是窗口，不是省钱。** 所以你的裁定自洽——
压缩率是**代价项**，越低越好、够用就折；真正要挣的是"同样的在场里塞进更多有效信息"。

样本量只有 40，且这 40 次来自能观测到净缩小的少数场景 ⇒ 要坐实钱，需要一次**配对 A/B**
（同一任务、同种子、WSC on/off 两臂，收厂商实付）。属付费项，未授权。

## 3. 主指标的定义（防"各说各话"，先钉公式）

**有效信息密度 D = 事后被复用的行数 / 热层千 tok**（分子分母同点同尺，零成本可算）。
- 分子：该行含的事实在 `t` 之后确实再被引用（沿用 §14 的事后复用金标，含 basename 匹配）；
- 分母：整段投影的 tok（生产尺 `memory.token.token_len`，探针启动自检 `prod == wsc2`）。
一个数同时惩罚"占地方"和"重复"，抓得住 V1 那个 53.6%（同一文件出现在 ≥2 段）。

硬约束两条：① 四路事后召回 **不得 < 现值 1.000**（V2）/ 0.751（V1 file）；② 热层不得超名义预算、
长会话不得溢出（压缩率当约束看，不当目标看）。

## 5. 四条跑完的实测（`_wsc_out/_wsc2_phase5.py`，126 点，零 API，未改库）

### 5.1 P5-前置：ACTIVE 的 WORKING SET 行"闲了几枪"，闲久了还会不会被复用

| 空闲枪数 | 行数 | 事后仍会被复用 | 复用率 |
|---|---:|---:|---:|
| 0（本枪刚碰） | 56 | 42 | 0.750 |
| 1 | 42 | 21 | 0.500 |
| 2–3 | 73 | 48 | 0.658 |
| 4–7 | 112 | 47 | 0.420 |
| 8–15 | 175 | 68 | 0.389 |
| 16–31 | 293 | 88 | 0.300 |
| **32+** | **959** | 123 | **0.128** |

噪音主体就是这 959 行（占在场文件行 **56%**）。但即使闲够 32 枪仍有 **12.8%** 事后会被用
⇒ **"闲够久 ⇒ 可安全删"被数据否掉**，寿命规则不存在零误删的阈值。
（第一版这里全是 0：行号→枪号只查了回执行，而触碰事件都在调用行上，查不到就当 0 枪 —— 已修，
分布才第一次有意义。）

### 5.2 P5-2 臂②（真删，扫 N）：**判死**

| N | D | tok 省 | 误删次数 | 误删率 |
|---:|---:|---:|---:|---:|
| 基线（不删） | **4.132** | 0 | 0 | 0 |
| 1 | 1.945 | 39.2% | 374 | 17.6% |
| 4 | 2.607 | 37.1% | 316 | 14.2% |
| 8 | 3.133 | 34.8% | 265 | 11.3% |
| 16 | 3.692 | 31.7% | 204 | 8.2% |
| 32 | 4.294 | 25.3% | 117 | 4.2% |

没有任何 N 同时满足"D 不降"和"误删=0"：D 只在最松的 N=32 微升 0.162（+3.9%），却要付 117 次误删；
**越积极越亏** ⇒ 按 P5-4 判死，不写退场规则、不加寿命字段，保守 KEEP 保住。

### 5.3 P5-1 臂①（不删）：钱在 V1 的**重复**，不在 V2 的**寿命**

| | 在场 tok | D |
|---|---:|---:|
| V1 现状 | 1,815,938 | 3.684 |
| V1 段内合并·上限版 | −48.4% | 7.136 |
| V1 段内合并·**安全版**（不丢带句柄的行） | **−16.8%** | **4.426** |

上限版不可实施——被丢的行里含 PATHS/PRUNED 的**句柄行**，丢了等于把"被剪节点必可拉回"丢掉，
只能当上限引用。安全版是 V1 侧真能落的一刀（−16.8% 在场、D +20%）。
V2 侧的"只标注"（#31 已交 STALE/hash/read_ranges）**不改尺寸也不删 ⇒ D 不变**，
其注意力收益离线测不到 ⇒ 不能拿标注冒充去噪收益。

### 5.4 我自定的主指标有缺陷（先自曝）

D = 复用行/千 tok **偏袒"塞得多"的臂**：V1 每点约 14.4k tok、V2 每点约 1.0k tok，
跨一个量级比 D 无意义（合并后的 V1 甚至"赢"了 V2）。⇒ 补一条 **P5-3b：同 tok 预算对照**——
两臂都裁到同一在场预算（1,000 tok/点，按各自的优先级），再比谁装的有效行多。
这才是"V2 的头能不能替 V1"的正面答案，仍然零成本。

### 5.5 四条的净结论

1. 去噪**不该靠删**（寿命阈值无一能达零误删，积极删反而拉低主指标）；
2. 去噪该靠**去重复**，而且那笔钱在 **V1 侧**（安全合并 −16.8% tok / D +20%）；
3. 主指标必须配尺寸硬帽才有意义 ⇒ 下一步 P5-3b 同预算对照；
4. V2 基线：**D 4.132 @ 1,006 tok/点**（V1：3.684 @ ~14.4k tok/点）。

## 6. P5-3b：同 tok 预算对照（`_wsc_out/_wsc2_phase5b.py`，126 点，零 API）

### 6.1 先更正一处：§5 的 D 分子其实只数到了 file

`gold["requests"]` 存的是**指纹**（`req:<fp>`），而我拿指纹去匹配行文本 ⇒ 请求类**永远不命中**，
所以 §5.3/§5.4 的 D 是"file-only"。两臂同尺、比较仍成立，但当时写的"分子只认 file/request 两类"是错的。
修好后（P5-3b 里用 `fingerprint(e.text) → 原话前 24 字` 还原）才是 file+request 两类的数。

### 6.2 覆盖率（装下的**不同**有效事实数 / 该点有效事实全集；一条事实写 20 行只算 1 条）

| 预算 tok/点 | V1 | V1+安全合并 | **V2** |
|---:|---:|---:|---:|
| 500 | 0.633 | 0.667 | **0.708** |
| 1,000 | 0.866 | 0.875 | **1.000** |
| 2,000 | 1.000 | 1.000 | 1.000 |
| 8,000 | 1.000 | 1.000 | 1.000 |

| 装满有效事实**所需** tok 中位 | 8k 预算内装不满的点数 |
|---:|---:|
| V1 **983** / V1+合并 **794** / **V2 515** | V1 23/126、V1+合并 22/126、**V2 0/126** |

### 6.3 四条读法（含不能从这张表推出什么）

1. **同样装下"事后会被用的事实"，V2 只要 515 tok/点，V1 要 983 tok/点 ⇒ 1.9× 更省**；
   且 V1 有 **18% 的点**即使给到 8k tok 也覆盖不全（那条路径在被剪区），V2 是 0/126。
2. **合并这一刀对 V1 有效且不掉覆盖**：983 → 794 tok（−19%），与 §5.3 独立测到的 −16.8% 在场 tok 同向 ⇒
   两处互印。这是 Phase 5 目前**唯一有收益、又不需要删信息**的动作，而且落在 V1 侧。
3. **但不能拿这张表说"V1 头里 87% 是废话"**：V1 整臂 14.9k tok，而覆盖满只需 983 tok ——
   多出来的 93% 买的是**可恢复性与分支结论**（PATHS/PRUNED/DECISIONS + 句柄），
   那不在本尺的分母里。这把尺只回答"状态够不够"，不回答"热层该不该只有状态"。
4. 分母很小（该点有效事实中位 **4 条**：~3 文件 + 1 请求）⇒ 覆盖率步长 0.25，
   表里的三位小数是跨 126 点的中位，不是单点的精细值。别把它当小数点后三位的证据用。

### 6.4 Phase 5 的收口判定

- 去噪主指标这条维度上：**V2 赢在"同样覆盖只需一半体积"，不赢在"能删"**（臂②已判死）。
- 可落地的下一步只有一个：**V1 侧的段内安全合并**（不丢句柄行），预期 −17~19% 在场、覆盖率不掉。
  它是 V1 的改动，按铁律要走旁路验证 + 提交门禁，且要有回归测试锁住"被合并行不含句柄"。
- V2 侧在 Phase 5 不再加机制：**#31 的标注就是终点**，寿命/删除这条线关掉。

## 7. V1 段内合并真接进生产路径的尝试：**已撤回**（附带挖出一个更严重的问题）

§5.3 / §6.2 的 −16.8%、983→794 是在探针里**模拟**合并得到的。按铁律"有数据证明收益才并入主链路"，

**§6.4 那句"预期 −17~19%"作废，以本节为准。**

### 7.2 顺带抓到的真问题：**V1 侧逐点数字被进程内会话状态污染**

撤回过程中量到：同一份语料、同一个点，**只改 session_id 就改变 V1 的输出体积**——

| 采样方式 | V1 在场 tok 中位/点 |
|---|---:|
| 一个进程内所有点共用 sid（我此前所有探针的做法） | **15.0k**（1,895,201 / 126） |
| 每点唯一 sid（真实重投影） | **10.8k**（1,359,714 / 126） |

机制在 `memory/wsc_projection.py:65` 的 `_STATE: dict[str, _Live]`（按 session_id 的进程级缓存）
+ `XEYO_WSC_FROZEN_HEAD` 默认开 ⇒ 探针把"同一段转录的多个前缀"当成同一会话的连续枪来打，
后一个点会带着前一个点攒下的 journal / 冷层状态。生产的形态不是这样（region 单调增长、每枪真重投影）。
更早还有一次同形状假象：两臂跑在同一进程时，第二臂直接拿回第一臂冻结的头，量出"零差异"。

⇒ **后果要说狠**：本文件 §5.3 / §6.2 的 **V1 臂绝对尺寸**（14.4k tok/点、983→794、"V1 装满有效事实要 983 tok"）
以及 §12 里以 V1 为分母的尺寸比，都要按"每点唯一 sid"重算才能引用。
V2 臂不受影响（`reduce_prefix` 每点独立、无进程内状态）。
所以 §6.3 的"V2 只要 V1 一半体积"暂时**不能引用**；按 10.8k 口径两臂差到 ~10×（方向对 V2 更有利，
但必须先重测再说数）。

### 7.3 待办（按新证据排序）

1. **重算 V1 臂**：§12 / §5.3 / §6.2 的 V1 侧改成"每点唯一 sid + 一臂一进程"重跑，
   然后才能重新给 V2/V1 尺寸比与"装满有效事实所需预算"两臂对照。零成本。
2. **度量台加启动自检**：同一输入在"共用 sid / 唯一 sid"两种策略下若不等，直接报错拒跑；
   凡引用 V1 尺寸必须注明 sid 策略。跨点采样不得共用 session_id。
3. V1 段内合并**搁置**：4.26% 的收益 + 两条未解释的不变量违例，不够开一个新机制。
