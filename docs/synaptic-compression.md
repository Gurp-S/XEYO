# 突触压缩（Workflow Synaptic Compression, WSC）

> 旁路形态实验。状态：**未接入生产链**。生产行为零改动。
> 落地位置 `python/synaptic/`（算法层）+ `python/tests/wsc/`（测试）+ 本文档。
> 验证结论见文末「离线回放数据」；融入决策表见「融入 XEYO 的接线方案」。

---

## 一、它是什么

突触压缩把 Agent 的执行历史当成一张**不断分叉、验证、回滚的工作流图**来压缩，
而不是当成一段聊天记录来摘要。

目标不是「把历史变短」，而是：

> **把膨胀的执行历史，压缩成一份可继续工作的最小充分状态。**

四句话概括：

1. 压缩对象是**工作流状态**，不是对话文本；
2. 保留的不是最长历史，而是从当前目标反推出来的**依赖闭包**；
3. 剪枝不是删除，而是降级成「缺口 + 可展开句柄」；
4. 整条管线由引擎**确定性**完成，不依赖 LLM 做摘要。

与 XEYO 既有 C0/C1/C2 的分野（一句话）：
**XEYO 用「位置 + KV 经济」决定留什么，WSC 用「依赖可达性」决定留什么。**

## 二、数据结构

| 结构 | 模块 | 内容 |
|---|---|---|
| 证据 DAG | `graph.py` | 节点 = 消息；四类边 `seq` / `use` / `file` / `err` |
| 文件状态表 | `filestate.py` | 观测 hash、已读区间、写后 `stale`、相关未解决错误 |
| 种子集（PIN 来源） | `seeds.py` | 目标 / 用户硬约束 / 未解决错误 / 当前 TODO / 工作集路径 |
| 剪枝卡 | `prune.py` | 结论 + 文件 + 错误签名 + 可重放命令 + `expand` 句柄 |
| 冷层 | `coldstore.py` | 句柄 → 原始文本，gzip 落盘，往返逐字节无损 |
| 热层装配 | `assemble.py` | PIN / WORKING SET / MAIN / DECISIONS / PRUNED /（可选）NEXT |

### 四类边

- `seq`（0.4）：时序相邻。
- `use`（1.0）：`assistant(tool_use) → tool_result`。**这是语法边**，对应生产链
  `memory/memindex.py` 里那张「只建表+写入、没有消费者」的 `edges`。
- `file`（0.5）：同一路径的相邻两次访问。
- `err`（0.8）：失败结果 → 之后首次触碰同一路径的调用。**这是启发式边**，
  见下文「已知弱点」。

> **refs 的来源分层**：`tool_use` 节点优先从入参 `path`/`file_path` 取；否则从
> 命令串扫路径；`tool_result` 节点优先从输出文本扫，**扫不到时继承发起它的调用**。
> 这一条不是细节——「这次结果关于哪个文件」由调用决定，不由输出文本决定。
> 早期版本漏了继承，导致失败现场抽不出路径、`err` 边整类消失。

## 三、压缩流程（9 步）

1. **建图**：`build_graph(messages)` —— 只记录，不判断重要性；
2. **文件状态**：`build_file_states(graph, messages)`；
3. **种子收集**：`collect_seeds(...)`；
4. **反向闭包**：`backward_closure(graph, seed_nodes, hops)` —— 沿 `in_adj` 反向 k 跳；
5. **五维加权**：`score_nodes(...)` —— goal_rel / unresolved / constraint / recency / replay_cost；
6. **确定性背包**：`knapsack_select(...)` —— 按「分数 ÷ **发射成本**」密度贪心；
7. **剪枝卡**：`build_cards(...)` —— 删重复留差异，带错误的卡永不丢弃；
8. **冷热迁移**：剪掉的进冷层并绑句柄，被骨架化的保留节点也绑 `node://<idx>`；
9. **组装**：`assemble(...)` —— 见下节两种模式。

### 一处关键记账修正（首轮冒烟实测发现）

预算必须按**发射成本**而不是**原文体积**记账。

初版用 `node.tokens` 计入背包预算，结果 PIN 段里那几条长用户消息按原文 token
把主链预算整块吃光（实测 `budget=0`，主链退化成只剩剪枝卡）。
现在用 `assemble.emitted_tokens`：已进 PIN 的节点 → 0；小节点内联 → 原文；
大节点 → 骨架行。同一条会话修正后 `budget` 从 0 → 317，`kept` 27 → 34。

### 三级降级粒度

| 粒度 | 落在热层的形态 | 代价 |
|---|---|---|
| 内联原文 | `#17 结论...` | 该节点完整 token |
| 骨架 + 句柄 | `#42 Read src/auth.ts 只读 expand(node://42)` | ~15 token |
| 剪枝卡 | `B37: Bash src/auth.ts 失败：… expand(branch://B37)` | ~25 token |

## 四、两种组装模式（KV 前缀的直接对撞点）

WSC 与 XEYO 最硬的技术冲突在这里：**依赖闭包不保证前缀连续**。

| 模式 | 行为 | KV 前缀 | 热层体积 |
|---|---|---|---|
| `closure` | 每轮全量重排 | **可能**断（见下） | 最小 |
| `append_only` | 稳定区字节冻结，新信息只追加增量行；追加预算超限才整层重建 | 结构性保证不断 | 单调变胖 |

`rebuilt` 的判据是严格定义的：**上一轮全文是否仍是本轮全文的字节前缀**。

这个判据带来一个反直觉但重要的实测结论：
**`closure` 并不总是打断前缀。** 当 PIN 段与工作集不变、只有区域在增长时，
新内容自然追加在尾部，`closure` 重排出来的全文恰好以旧全文为前缀，
KV 前缀**不 miss**。真正打断前缀的是中段变化——例如中途冒出一个新的未解决错误
（PIN 段变长），或者某个文件状态从「已读」翻成 `STALE`。

所以「closure 一定比 append_only 贵」是错的。贵的时刻是可枚举的：
**PIN / 工作集 / 卡片集合发生中段改写时。** 这也解释了为什么 WSC 必须把
`rebuilt` 当成一等指标报出来，而不是当成隐含假设。

## 五、已知弱点（不要当成已完成）

1. **`err` 边是启发式，不是语义。** 「读 A 之后才知道该改 B」这类语义依赖机器不可判。
   当前只做「失败现场 → 之后首次触碰同文件」的近似。这条边退化时，
   闭包会退化成「只有直连」或「全部可达」。
2. **「错误已解决」必须靠成功证据，不能靠路径重合。**
   实测反例：一条 `grep` 输出里提到 `src/auth.ts`，就足以同时满足
   「同工具（Bash）+ 同路径」——但那个失败的测试跟这次 grep 毫无关系。
   现在要求结果文本里出现成功标记（`passed` / `0 failed` / `exit code 0` …）。
   **误判「已解决」比误判「未解决」危险得多**：前者把失败现场从 PIN 里抹掉。
3. **PIN 集无上限。** 约束句多、TODO 多的会话里 PIN 会挤压主链预算。
   当前只做「overhead 超预算时告警 + 主链让位」。
4. **`weight` 与 `tokens` 严格分离。** 不要混用。生产链 `fidelity_segmenter.py`
   里的 `weight` 恒等于 `len(text)`，那是体积计权，不是价值计权。
5. **回放不含工具副作用、不含真实 KV TTL 分布。** 见文末口径。

## 六、与 XEYO 引擎铁律的冲突

引擎铁律（`AGENTS.md`）：**注意力里只出现信息，不出现导演。**

WSC 的设计文档里有一段 `[NEXT] 检查 proxy 配置`。内容本身是事实，但它在
注意力里的**位置与语气**会被读成导演（「接下来该做这个」）。因此：

- `WscParams.include_next` **默认 `False`**，该段默认不发射；
- 开启后报告必须标注，且不得作为默认配置进入主链。

同类的还有 `[DECISIONS] 已排除: …`。这条**保留**——它陈述的是「这条分支试过且
失败」这一事实，属于信息而非编排。分界线是：**陈述发生过什么 = 信息；
提示接下来做什么 = 导演。**

## 七、与设计文档的偏离（每一条都在代码注释里同步）

| # | 偏离 | 理由 |
|---|---|---|
| 1 | 剪枝卡 id 用根节点下标（`branch://B37`）而非流水号（`B12`） | 流水号随区域增长整体位移，`append_only` 模式下每轮都判定「内容变了」而被迫整层重建 |
| 2 | `[DECISIONS]` 与 `[PRUNED]` 不再重复同一条卡 | 设计文档示例里同一条分支在两段各出现一次，纯属重复计费。现在带错误的卡进 DECISIONS、其余进 PRUNED，各带句柄 |
| 3 | `[NEXT]` 默认关 | 见上节引擎铁律冲突 |
| 4 | token ≤ 48 的节点内联原文，不做骨架化 | 为省几十 token 逼模型发一次 `expand` 往返，净亏 |
| 5 | 新增三项设计文档没有的度量：关键信息针存活率、可恢复性往返、前缀连续性 | 把「98–99.5% 保留」这类自述变成可复核量 |
| 6 | TODO 只取**最后一次** `TodoWrite` 的未完成条目 | 任务树记录「现在要做什么」，不是「历史上一共写过哪些待办」 |
| 7 | 过滤引擎注入的伪用户消息（`[Resume]` / 系统提醒） | 它们不是用户意图，不能当目标或约束。未过滤时 PIN 里混入 6 条 Resume 指令 |
| 8 | 「错误已解决」要求成功标记 | 见「已知弱点」第 2 条 |

## 八、度量口径（报数前必读）

见 `python/synaptic/report.py` 的 `CAVEATS`。要点：

- 两侧 token 计量走同一套序列化（`memory.simulator.projection.emit_segment`），
  但 `wsc_tokens` 的尾部那部分与 `v61_tokens` 的尾部口径存在系统性差异，
  故 `reduction_vs_v61` 应看趋势而非绝对值。
- `hit_rate` 来自 `memory.simulator` 的 `ρ̂(C)` 模型，**不是**线上观测到的
  `prompt_cache_hit_tokens`。
- **任务成功率变化、重复错误率降低** 需要真实任务 A/B，本报告不出这些数字。
  `failure_site` 针存活率只是「失败现场是否还在热层」的代理指标。
- 回放按会话 JSONL 逐用户回合重演，`age_seconds` 固定 0（连续请求）。
- 尾部保护区用生产链同名的 `engine.compact.keep_tail_cut`，两侧完全一致。

### 关键信息针为什么不是同义反复

针从**原始历史**收割（用户消息 / 错误签名 / 文件路径 / 失败现场），
**不是** PIN 集的产物。所以「针在热层的存活率」检验的是 WSC 是否真的把关键信息
带过去了，而不是「PIN 塞满了就算完」。

## 九、融入 XEYO 的接线方案（待数据支持后再执行）

### 阶段 A（当前）— 纯离线旁路

- 算法层对生产链**零 import**，由 `tests/wsc/test_isolation.py` 机器执法；
- 只读 `~/.xeyo/sessions/*.jsonl`；零 API 花费、零生产改动。

### 阶段 B — 在线 shadow（只观察不生效）

- 接线点只有一个：`memory/runtime.py` 投影出口，开关 `XEYO_WSC=1`；
- shadow 只记录 `hot_tokens / rebuilt / 针存活率`，不改变实际发送的投影；
- 用途：拿到真实分布下的 `rebuilt` 率与 PIN 超预算率。

### 阶段 C — 并入主链

前置条件（缺一不可）：

1. 离线数据里 `closure` 的 `rebuilt` 率与命中率损耗已被量化，且确认
   可接受，或已改用 `append_only`；
2. shadow 里 PIN 超预算率 < 5%；
3. 走 `AGENTS.md` 第 4 条：新行为先以旁路形态上线验证收益，**有数据证明收益后才并入主链**；
4. 并入时在 T_now 块登记表标注归属与收益证据（若涉及模型可见注入）。

**在 1–4 全部满足之前，本模块保持旁路状态，不接线。**

### 11.3 可恢复性（硬指标，无水分）

- 被剪节点 **22472**，其中有句柄 **22472** ⇒ 句柄覆盖率 **100.00%**；
- `expand` 往返逐字节比对 **35413/35413 无损**（closure）/ **35395/35395**（append_only）⇒ **100.00%**；
- 确定性探针：取最大 5 个会话重跑，`identical: 5 / mismatch: []`。

即「剪枝不是删除，是降级成缺口 + 可展开句柄」这一条**成立**。

### 11.4 四个必须直面的负向结论（并入主链前须解决）

1. **命中率崩塌，这是最严重的发现。根因已定位，见 11.8。**
   WSC 的 ρ̂ 命中率 0.031（closure）/ 0.083（append_only），远低于 XEYO v6.1 的 0.196。
   `closure` 每轮全量重排 ⇒ 前缀每轮都变 ⇒ KV 前缀命中基本归零；`append_only`
   靠冻结前缀把它救回 2.7 倍，但仍不到 v6.1 的一半。
   **代价被绝对 token 量的下降掩盖了**：总输入成本仍从 ¥8.49 降到 ¥2.89，因为
   送出的 token 少得多——但这是「用缓存复用换 token 数量」，不是纯赚。
2. **短会话无收益。** cohort 拆分显示 <30 消息的会话压缩率仅 32.8%/32.0%，
   收益门拒绝率却高达 19.5%/22.1%——因为区域本身就小，热层固定开销
   （PIN + 文件状态表）占比过大。**结论：WSC 只该在长会话上启用**，
   短会话应直接走现有 C0/C1。
3. **`path` 针存活率仅 38.8%，但这一项是度量口径问题而非缺陷。**
   「历史上提到过的每个路径都留在热层」既不可能也不该是目标——绝大多数路径
   在后续工作中就该被淘汰。真正该看的是 `path_recent`（46.6%）与
   `failure_site`（79.1%）：前者仍偏低（近 3 轮路径都保不住），**是需要修的真问题**；
   后者 0.0% 的最低值说明存在整轮丢失失败现场的回合。
4. **`rebuilt` 率 closure 42.3% vs append_only 14.5%。**
   结构上印证了设计文档的判断：`append_only` 才是 KV 友好的形态。若并入主链，
   **`closure` 不应作为默认模式**。

### 11.5 与设计文档预测的对照（不许自述当结论）

| 设计文档预测 | 实测 | 判定 |
|---|---|---|
| token 成本降 60–90% | 全回合 mean 72.8% / median 82.3% | ✅ 成立（区间下沿） |
| Medium+ 降 90–96% | 仅长会话（≥100 消息）87.6% mean 接近 | ⚠️ **仅对长会话成立**，全局达不到 |
| 即时信息保留 98–99.5% | user 94.6 / error 99.6 / path 38.8 / failure 79.1 | ❌ **不成立**，路径类针差距大 |

### 11.8 命中率崩塌的根因（已定位，纯离线探针）

探针 `python/tests/wsc/_lcp_probe.py`（只读，零花费）：取最大的 3 个会话，逐轮算
热层与上一轮热层的**最长公共前缀（LCP）**，并定位首个失配点落在哪一段。

结论（199 回合会话 `sess_real_200turn_c2`）：

| 观测 | 值 |
|---|---|
| `[PIN]` 段逐轮变化 | **199 / 199（100%）** |
| 首个失配点落在 `[PIN]` | **199 / 199（100%）** |
| 前缀连续性（LCP / 热层长度）mean / median | **2.2% / 1.9%** |
| LCP 中位 | 57 token（热层 1336 → 9619 token） |

**根因：`[PIN]` 排在热层最前面（offset 0），而 PIN 内含每轮必变的内容。**
逐类别的逐轮变动率：

| PIN 条目类别 | 逐轮变动率 | 来源 |
|---|---:|---|
| `指令`（`task_updates`） | **93%** | `seeds.py:208` —— **就是最近 N 条用户消息本身** |
| `todo`（`todos`） | 55–100% | 最后一次 `TodoWrite` 的未完成项 |
| `未解决`（`unresolved_errors`） | 6–33% | 未解决错误签名 |
| `目标` / `约束` / `当前目标` | 稳定 | —— |

**这是双重缺陷**：

1. **冗余**——`task_updates` 逐字等于最近的用户消息，而**未被保护的尾部本来就带着它们**。
   把尾部已逐字携带的内容再钉进热层，是纯重复计费；
2. **KV 敌对**——它位于 offset 0 之后的不远处，一旦它变，**排在其后的
   `[MAIN]` / `[DECISIONS]` / `[PRUNED]`（数千 token 的稳定内容）全部前缀失效**。

**反事实量化**（同一探针，只把 PIN 里 `指令:` 行删掉再算 LCP，不改算法）：

| | mean | median | LCP 中位 |
|---|---:|---:|---:|
| 现状 | 2.2% | 1.9% | 57 token |
| 去掉 `指令:` 行 | **16.9%** | **10.3%** | **274 token** |

即：**仅此一项就能把前缀连续性提升约 7.7 倍，进入 v6.1（0.196）的同一量级。**

**由此得到一条结构性规则（本设计应补的一条，设计文档原文没有）**：

> **热层段落必须按「前缀失稳率」升序排列**——最稳定的在最前（⚠️ 不是按「逐轮变动率」：
> 只追加的段落变动率可以很高而前缀完全稳，按变动率排会把它们排到最后，适得其反）；
> **并且凡未被保护的尾部已逐字携带的内容，一律不得进 PIN。**
> 违反它的代价不是「多花几百 token」，而是**其后全部内容每轮都失去缓存**。

第二个会话（`sess_mu0mkitk_5aehjt`）验证了规则的普适性：那里 `指令` 只变 25%
但 `todo` 变 100%，去掉 `指令` 行几乎无改善（1.6% → 1.8%）——**说明只要热层最前面的
任一内容在变，命中率就归零，与具体是哪个字段无关。**

### 11.9 修复后实测（规则 1 + 规则 2）——**未达标，第二处结构缺陷已定位**

11.8 的两条规则已落到算法上（不是只做反事实测量）：规则 1 = 后继用户消息不再进 PIN
（`seeds.py`，**修正默认行为**，非变体）；规则 2 = `[PIN]` 拆成
`[CONSTRAINTS]`/`[UNRESOLVED]`/`[TODO]` 并按**前缀失稳率**动态排序
（`assemble.py::order_segments`，开关 `WscParams.stable_prefix_ordering`，默认开）。
自检：`WscResult.churn / front_break / churn_warnings`，报告出「段落逐轮变动率自检」表。

**A/B 三臂**（同一语料、同一参数，仅开关不同；两臂写不同 `--out`）：

| 臂 | 规则 1 | 规则 2 | closure 命中率 | append_only 命中率 | closure 重建率 | append_only 重建率 |
|---|:--:|:--:|---:|---:|---:|---:|
| 修复前 | ✗ | ✗ | 0.031 | 0.083 | 42.3% | 14.5% |
| `ab_off` | ✓ | ✗ | **0.071** | **0.092** | 35.4% | 14.0% |
| `ab_on`（默认） | ✓ | ✓ | **0.067** | **0.092** | 36.3% | 14.0% |

对照基线 **XEYO v6.1 = 0.196**。压缩率基本未动（closure 73.0% / append_only 71.7% 全回合均值，
median 82.5% / 80.6%），可恢复性仍 100.00%，确定性 5/5，LLM 调用 0，延迟 median 10.1 / 11.2 ms。

#### 结论一：规则 1 有效但远不够；规则 2 **不能宣称有增益**

- 规则 1 是唯一有位移的改动：closure 0.031 → 0.071（**+0.040**），append_only 0.083 → 0.092（+0.009）。
- 规则 2 在聚合口径上**是平的**：closure **0.067（开）vs 0.071（关）**，append_only **0.092 vs 0.092**。
- 但**不能说规则 2 没用**——探针证明它把次序**收敛到了最优**。199 回合会话上采用的次序是
  `[CONSTRAINTS] → [UNRESOLVED] → [DECISIONS] → [WORKING SET] → [MAIN] → [PRUNED]`（170/199 回合稳定），
  而这正好是按该会话实测前缀失稳率（0% → 6% → 14% → 28% → 83% → 97%）**单调递增**的排列。
  次序已最优、命中率却没动 ⇒ **瓶颈不在「段落怎么排」，在「段落自己是不是稳的」**。

#### 结论二：第二处结构缺陷 = `[MAIN]` 不单调，稳定前缀被它截断

探针（`_lcp_probe.py`，199 回合会话）修复后数值：

| 观测 | 值 |
|---|---|
| 前缀连续性 mean / median | **18.6% / 11.6%**（修复前 2.2% / 1.9%） |
| LCP 中位 | **324 token**（修复前 57） |

**首个失配点**落在哪一段：`[MAIN]` **102**、`[WORKING SET]` 49、`[UNRESOLVED]` 24、
`[DECISIONS]` 20、`[PRUNED]` 4。

即：LCP 越过 `[CONSTRAINTS]`/`[UNRESOLVED]`/`[DECISIONS]`/`[WORKING SET]`（合计约 324 token）后，
**恰好停在 `[MAIN]`**。原因：`[MAIN]` 由闭包评分选出的 `kept` 集渲染
（`assemble.py::render_main`），**集会随评分逐轮进出**，所以它的**段首每轮都变**
（该会话实测 `[MAIN]` 变动率 90% / 前缀失稳率 83%）——尽管它承载的**内容**大部分是只追加的。

> **段落重排解决不了这件事**：`[MAIN]` 是体量最大的段，它自身不稳，任何排列都救不了它。
> 只有让 `[MAIN]` 变成**单调（append-only）**——已发出的行冻结，只追加、不重排、不摘除——
> 稳定前缀才可能从 ~324 token 往它的体量上延伸。

**这是假设，不是结论**：修 `[MAIN]` 单调性后的命中率必须再测一次才能报数。

#### 结论三：规则 1 开了一个信息空洞（**新发现，比命中率更该先修 —— 已修**）

规则 1 的前提是「未被保护的尾部已逐字携带」，但实测**这个前提只对最后 2–3 个用户回合成立**：

| 观测（199 回合会话，末轮） | 值 |
|---|---|
| `region_end` | 1373 / 1385 条消息 ⇒ **尾部只有 12 条** |
| 被压缩区域内的用户节点（节点级，`seeds.user_nodes`） | **188 条** |
| 同上，经 `harvest_needles` **去重后**的唯一文本数 | 17 条 |
| 修复前热层里可见 | **1 条**（只有「目标:」，即首条） |
| 热层里是否有「指令:」行 | **否**（规则 1 已删） |

机制（`assemble.py::render_main`）：它**跳过 `pin_nodes`**，而 `pin_nodes` 含**全部**实质用户节点
（`seeds.py`）。于是：

- 修复前：`task_updates`（「指令」段）是这些用户原话**唯一的渲染通道**；
- 修复后：通道没了，`[MAIN]` 又不渲染它们 ⇒ 区域内用户原话在热层里彻底不可见；
- 更糟的是它们是 `pin_nodes` ⇒ 不会被剪 ⇒ **连 `expand` 句柄都没有**，即**不可恢复**。

聚合口径的签名是两个臂一致的 **user 针存活率 94.6% → 71.0%**（−23.6pp）——两臂都应用了规则 1，
所以这是规则 1 造成的，与规则 2 无关。

**修复（`[REQUESTS]` 段）**：`assemble.py::render_requests`，节点集合由 `Seeds.user_nodes` 权威给出
（不是在 `assemble` 里重新按 kind 扫图），按 `idx` 升序发射、每条附真 `node://<idx>` 句柄，
句柄在 `project.py` 里绑进冷层。修后实测（同一会话末轮）：

| 观测 | 修复前 | 修复后 |
|---|---:|---:|
| `[REQUESTS]` 行数 | — | 187 |
| 节点级渲染覆盖 | 1 / 188 | **188 / 188（100%）** |
| 句柄往返无损 | — | **187 / 187** |
| `harvest_needles["user"]`（去重）可见 | 1 / 17 | **17 / 17** |

全语料（317 文件）节点级覆盖 = **20378 / 20378 = 100.00%**，见 11.10。

> ⚠️ **两个口径别混（这里踩过一次，造成一次误报）**：`harvest_needles` 的输出做 `dict.fromkeys`
> **去重**（集合语义：这条信息还在不在），而 `render_requests` / `seeds.user_nodes` 是**逐节点**语义。
> 曾看到「区域内实质用户消息 = 17」而 `[REQUESTS]` 渲染 187 行，当场判定「在把工具结果当用户原话
> 导出」——**是误报**。真值：本会话是**合成长会话**（同一组 17 条提问**重复 11 轮**，
> 1385 行 = 200 user + 605 assistant + 580 tool，**零**伪用户消息），所以 188 → 17 是预期。
> **判真伪只能看原文**：`python/tests/wsc/_user_nodes_probe.py <session.jsonl>`。
> 审计比率的分子分母必须同源 ⇒ `req_total` 用 `seeds.user_nodes`，不写 `kind == KIND_USER`。

> **规则 1 应该被「收窄」而不是回退**：只丢掉**尾部确实已经逐字携带**的那几条；
> 区域内的用户原话必须保留一条渲染通道。**该通道必须是 append-only 的**（只追加在段尾）——
> 只要它逐轮只在尾部追加，它自身的前缀就永远稳定；其代价是它增长时会把后面的内容挤出缓存，
> 所以放在**末尾**最省。

#### 结论四：自检表在 `append_only` 下口径不对（**自检自身的缺陷**）

两个组装模式报出的 churn 表**逐字相同**（`[MAIN]` 38.1%/19.6%、`[PRUNED]` 76.4%/76.4% …），
而 `append_only` 的语义是「稳定区字节冻结」——两者不可能同值。原因：`SegStat` 统计的是
**冻结前的重新渲染文本**（`_segment_groups` 产物），不是最终 `full_text`。

⇒ **在修好之前不要用这张表判断 `append_only` 的稳定性**，它对 `append_only` 系统性高估失稳。
（聚合表里 `[MAIN]` 前缀失稳率 19.6% 与单会话探针的 83% 差这么多，也有这个原因——
短会话把均值拉平了，长会话才是问题所在。）

#### 阶段 C 判定：**仍不满足，不并入**

按 11.8 定下的判据——「命中率回到 v6.1 同量级（0.15–0.20）才有资格谈融入」：

- 实测 **0.067 / 0.092 vs 0.196**，**差了 2–3 倍**，**未达标**；
- 而且这次修复**用信息留存换命中率**（user 针 −23.6pp）：0.071 的命中率换 23.6pp 用户原话缺失，
  **这笔交易不值**。

**下一步（按优先级，均需再测）**：

1. **先补信息空洞**：把区域内用户原话的渲染通道加回来，放在热层**最末**的 append-only 段。
   这是「信息纪律」问题，优先于命中率——丢用户原话比丢缓存严重得多。
2. **再修 `[MAIN]` 单调性**：已发出的行冻结，只追加。这是目前唯一有量级希望的命中率杠杆。
3. **顺手修自检口径**：`SegStat` 改统计最终 `full_text`（`append_only` 下即冻结文本）。
4. 重跑三臂，看命中率是否进入 0.15–0.20。

即 WSC 的定位是**「用更少的 token 换略低的缓存复用」**，不是「命中率打平」。
**报「命中率低于 v6.1」时必须同时给成本**，否则会把这笔交易误读成退步。
（命中率两侧的分子分母结构不同：WSC 的 `L` = 热层 + 未触碰尾部；v6.1 的 `L` = C0/C1/C2 投影。
只有 `cost_*_total` 是在**同一批可比回合上求和**，可以直接比。）

#### ⚠️ 口径警示（本轮报告里最容易读错的三处）

1. **`hit_rate_*` 的 median 在三个 cohort 里全是 0** —— 冷启动稀释：每个会话首个可比回合没有上一轮投影，
   命中必然为 0，而本语料 235 会话 / 651 回合 ≈ **2.8 回合/会话** ⇒ 首回合约占 1/3。
   **报绝对水平必须用 `*_steady`**；原口径保留（它是含冷启动的真实平均）。
2. **`steady`（n=85）偏向长会话** —— 只有「≥2 个可比回合」的会话才贡献，与含冷启动口径**不可互换**。
3. **本表的 `latency_ms` 不可用**：两臂**并发**执行，CPU 争用把延迟抬了约一倍
   （mean 119.6 / 119.2 ms，而**串行**跑是 83.5 / 78.5 ms）。可信延迟见 11.9。

#### 已知未解（按影响排序，均需决策后再动）

1. **`[REQUESTS]` 段不在任何预算内。** 它按区域内用户节点数**线性增长**，
   单会话实测占热层 **55.5%（3664 / 6599 tok）**；而 `hot_budget_tokens`（Medium+ = 3000）
   只闸 `kept` 的选择，`overhead = pin_tokens + ws_tokens` **不含** `[REQUESTS]`/`[DECISIONS]`/`[PRUNED]`。
   ⇒ 实测热层 median 3226 **超预算 7.5%**，长会话超得更多。
   **这是账目缺口**：把 `[REQUESTS]` 计入 `overhead` 会挤掉 `[MAIN]`（那才是真正的取舍），
   需要先决定「用户原话 vs 剪枝卡」谁优先。
2. **`path` / `path_recent` 针存活率仅 ~43–47%**，是剩下最大的信息留存缺口。
   长尾路径（早期读一次、之后再没碰过）**本来就应该丢**（冷层可 expand），
   但「还在用的路径」只留住 47% 偏低。
3. **分段布局的段间排序仍是开问题**：正确的目标函数见 `wsc-offline-eval` 技能 §4.5
   （早先「只追加的段排前面无害」的表述是错的）。但对默认的日志布局**无影响**，故优先级最低。

#### 阶段 C 判定：**命中率仍未达标，但成本已显著胜出 —— 建议改为「按成本准入」**

11.8 定的判据是「命中率回到 v6.1 同量级（0.15–0.20）才有资格谈融入」。本轮 journal 布局
steady 命中率 0.4778 —— **已进入并超过该区间**（0.15–0.20 是以含冷启动的均值口径定的，两者不可直接比；
同口径下 0.1345 vs 0.1976 仍差 1.47 倍）。

真正的判据应该是**成本**：`成本 ∝ H + 30·U = 30L − 29H`，命中率每提高 1pp 都直接换成钱，
而压缩率只通过 `L` 起作用。本轮结果：

- 302 可比回合：**¥2.7952 vs ¥8.5295 = 32.8%**；
- 85 steady 回合：**75.4% vs 100%**（只省 24.6%）。

⇒ **准入建议**：以 `cost_wsc / cost_v61 < 1.0` 为门槛，**分 cohort 判定**——
短/中会话收益巨大（省 69%/74%），长会话仅省 ~25%。是否上线应由「线上会话长度分布」
决定，而不是拿一个全局平均值拍板。

### 13.2 必查 A：「上下文预算」的归属

**结论：它不是 XEYO 的机制。** 全仓检索 `上下文预算` 只命中 docs（通用概念）；
引擎里叫「预算」的只有两处且都与上下文窗口无关——单请求回合预算（wrap-up 窗，
`# Wrap-up(预算已尽)` / `# Runtime budget notice`）与服务端 goal 轮预算
（`server/goal_round_driver.py:284`）。

**「[上下文预算已耗尽]」是第五轮 agent 自己写的措辞**，用来解释「我这边会话上下文快满了」；
**措辞冒充了机制**。⇒ 后续 agent **不得**再把它当机制引用。
若确实需要「上下文窗口水位可视」，那是**新功能**，按「新功能准入」走旁路
（T_now 块登记表硬顶 20：加一块必须删一块或证明预算不破）。

### 13.3 必查 B：`env-notice` 缺口（第六轮第一手复现，附更正）

**第六轮实录（本轮实测，非转述）**：本会话里模型发起了一次空参数的
`xeyo_env_notice` 调用，**换回了完整的 `[system-environment]` 正文**
（含 `# Continue` 块与 `# Resume` 块，`Resume` 里带着**原始目标全文**）。
⇒ 与第五轮同形：**模型发起的保留名调用确实拿到了环境正文。**

**但归因要更正一处**：本轮同时观察到——该正文块**在普通工具结果后也会出现**
（`Bash` / `Read` / `Grep` 之后同一份背景被反复注入）。因此在本会话里
**「保留名被应答」与「引擎本该逐轮注入同一份正文」在模型视角不可区分**；
把前者当成「存在一个外部应答器」是**外推，不是实测**。可确定的是两条：

1. **仓库内部本来就拒**：`tool_registry.run` 对未注册名返回中性 `unknown tool: {name}`
   （`is_error=True`），从不派发、无副作用——这条路是安全的；
2. 全仓 grep `xeyo_env_` 只命中 `prompt/` `model/` `evals/` `tests/` `docs/`，
   **无 server/host 处理器** ⇒ 若真存在应答者，它在仓库外（桌面 host / 中继层），
   本轮**未能定位**（无 host 代码位置），故该项标记为「**未定位**」而非「已定位」。

**代价（本轮直观可见）**：每次这类调用会把整段背景（含原始目标全文，约 7k token）
重新灌进注意力，并把「模型幻觉调用」伪装成「引擎注入」——第五轮因此**两次误导审计**。

**本轮仓库内可做且已做（深度防御，把巧合变契约）**：

- `tools/tool_registry.py`：新增 `RESERVED_TOOL_PREFIX = "xeyo_env_"` 与
  `run()` 里的**保留前缀拒绝**（措辞中性：`reserved environment channel: {name}`），
  且**拒绝发生在注册表查询之前**——即使有人真把工具注册成保留名也走不到它；
- `tests/test_reserved_tool_prefix.py`（4 条）：保留前缀与
  `prompt.t_now_strategy.ENV_ID_PREFIX` **同源断言**（防漂移）、拒绝早于查询且无副作用、
  该名字永不进 `schemas()`、**引擎自身 env 投影照常构造**（拒绝规则不得误伤）。
- 该项是**旁路加固**，与 WSC 无关，独立提交。

按 DOD（`user` 针必须保持）**不得直接并入**；要拿到行数收益又不丢针，落点应是
**「每块保留首节点的一条 80 字符摘录 + 区间句柄」**（行数仍降 ~8 倍，
块内其余节点靠 `expand(reqs://)` 拉回），而不是整块只留句柄。

#### 13.4.2 P1-b′：区间句柄 + 块内全节点摘录（修正版）

**改法**：一个块一行，但**块内每个节点的 80 字符摘录都内联在同一行里**，行尾挂区间句柄：

```
[REQUESTS] #5…45 用户[8]: <80字符摘录5> ⏐ <摘录13> ⏐ … expand(reqs://5-45)
```

同一行省掉 7 组 `#<idx> 用户:` 头部与 `expand(...)` 尾巴（每行约 10–15 tok），
**行数仍降 ~`request_old_group_size` 倍，而文本可见性与逐节点形态相同**——
「可恢复 ≠ 可见」的正面解法。

| 指标 | pre（改动前） | P1-b（只发句柄） | **P1-b′（摘录内联）** |
|---|---:|---:|---:|
| 压缩率 median | 0.8601 | 0.8621 | **0.8632** |
| 压缩率 median（仅压缩回合） | 0.8661 | 0.8684 | 0.8701 |
| hot median | 2,964 | 2,818 | 2,918 |
| wsc median | 6,060 | 5,901 | **6,126** |
| 回放 p50 / p95 (ms) | 29.55 / 203.9 | 30.16 / 209.1 | **32.93 / 233.7** |
| `path` / `path_recent` | 0.8406 / 0.9126 | 0.8386 / 0.9114 | 0.8327 / 0.9070 |
| `failure_site` | 0.9479 | 0.9489 | 0.9433 |
| **`user` 针** | 1.0000 | **0.8320 ❌** | **1.0000 ✅** |

**结论**：
1. **阻断项已修**：`user` 针回到 **1.0000**（这正是 P1-b 唯一不可接受的地方）；
2. **压缩率 +0.31pp**（vs pre），比 P1-b 的 +0.20pp 略好；
3. **但代价转移了**：延迟 **+3.4ms p50 / +29.7ms p95**、`wsc` median **+66**（行变长 ⇒
   journal 增长更快、重冻结更频繁）、`failure_site` −0.46pp、`path*` 各 −0.6pp。
   即「用延迟与其它段预算换 `user` 可见性」。
4. **仍不可替换 C2**：压缩率 86.32% < 88%、p50 32.93ms > 20ms、`failure_site` 0.9433 < 0.95。

**下一步的落点（已由本轮证明）**：P1-b′ 的延迟与 `wsc` 回退说明**行变长本身有代价**——
应给块行加**总字符上限**（超限时只保留前 k 条摘录、其余退句柄），
让「可见性」与「行宽」都可控；这与 §6 第 2 条（卡片段治理）合流。
