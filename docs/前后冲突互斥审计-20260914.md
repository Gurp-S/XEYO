### A1（高）`title` SSE 帧前端不解析

- 后端确实在每轮起点推标题帧：`chat.py:1063-1073`，payload = `{type:"title", title, pinned, enhanced}`。
- 前端 `core.ts` 的 `parseSseBlock()` 是一条 `xy.type` if-chain，**通读全文确认无 `'title'` 分支**，落到末尾 `return null` 静默丢弃。
- 后果：新建会话的即时标题（`ensure_instant_title`）与后台增强标题（`fire_and_forget_enhance`）**无法经流更新**。侧栏标题实际来自本地 IndexedDB（`db.ts:480 loadSessions`）；`api.ts:289 listServerSessions` 只在"本地索引缺失时恢复历史"这一条路径被调用（见 `api.ts:288` 注释），日常不回拉。
- **修复建议**：在 `core.ts` 的 if-chain 加 `xy.type === 'title'` 分支 → 新增 `onTitle?: (ev:{title,pinned,enhanced, sessionId}) => void` → 在 `chatStream.ts` 事件分发处更新 `sessions` 中对应会话标题（尊重 `pinned`：pinned 为真时不得被自动标题覆盖，与 `sessions.py:466` 的后端语义对齐）。改动面 = 3 个文件、约 20 行。

### A2（高）`permission_expiring` 全链路未接线

- 生产者存在：`permission_coordinator.py:116-135` `_remind_before_expiry()` 在到期前 30s 构造 `PermissionExpiringEvent`（类型定义 `events.py:196-202`），设计文档 `permissions/pending_ttl.py:7` 明写用途"GUI 倒计时高亮"。
- **第一重断**：`_emit()` 实现是 `if self.on_event is not None: self.on_event(ev)`（`permission_coordinator.py:235-237`），而生产构造点 `query_engine.py:584-589` **显式传 `on_event=None`** → emit 静默空操作（亲验）。
- **第二重断**：即使有 sink，`chat.py` 的 SSE `_producer()` 分发链（1088-1386）**无 `PermissionExpiringEvent` 分支**（grep 全文：该类型只出现在 `permission_coordinator.py` / `events.py` / `pending_ttl.py` 文档 / 测试）。
- **第三重断**：前端 `core.ts` 无该 type 分支。
- 后果：一个 T3 设计特性（到期倒计时高亮）**三层都断**，属于"写了但没通电"。
- **修复建议**：最小可通电路径 = `query_engine.py` 构造 coordinator 时传入事件 sink → 在 `chat.py` 的 `_producer()` isinstance 链加一帧 → `core.ts` 加分支 → 消费处（`PermissionDialog`）渲染倒计时。三处齐改才有可见效果；若产品决定不做，则应删除 `_remind_before_expiry` 与 `pending_ttl.py` 的承诺，避免"文档说有、实际没有"。**不建议只补一层**（半通电路径比没有更难排查）。

### A3（中）`intent` 在 SSE 层被丢弃

- 后端 `chat.py:1275` 的 `permission_pending` 帧携带 `intent`（取值 `confirm`/`choice`/`plan-review`，来源 `permissions/pending_ttl.py:51`）。
- 前端 `core.ts:663-677` 的 `permission_pending` 分支**未读 `xy.intent`**（类型声明在 `core.ts:167`），于是 `uiChromeSlice.ts:169` 恒 `undefined` → `PermissionDialog.tsx:125` 只能自行推导（`choice⇔有 choices`）。
- 后果：普通二元与三选在行为上等价可用，但 **`plan-review` 分支永远不会出现**——计划审阅面板走不到。
- **修复建议**：`core.ts` 该分支补一行 `intent: typeof xy.intent === 'string' ? xy.intent : undefined`，并让 `PermissionDialog` 改为优先消费 `intent`、仅在缺失时回落现有推导。约 5 行。

### A4（中）`input_summary` / `parallel` 未随帧下发

- 这两个值**已经算好**：`input_summary` 在 `query_loop.py:1115`，`parallel` 在 `events.py:45`。
- 但发帧处 `chat.py:1107-1111` 只序列化 `type/name/input/tool_use_id`；前端 `core.ts:871-873` 读 `input_summary`/`parallel` → 恒 `undefined`/`false`。
- 后果：T13 的"参数摘要 + 同批并行"元数据在 SSE 层被截断（GUI 工具区少一层信息）。
- **修复建议**：`chat.py` 该帧补 `input_summary`/`parallel` 两个 key。约 2 行。同源问题见 A6（`duration_ms`/`spilled` 同理，但前端当前无消费点）。

### A5（中）归档态跨端丢失（互证）

- `/v1/sessions` 返回 `archivedAt`（`sessions.py:396-402`，取自 `engine.title.read_archive`）。
- `/v1/workspaces/sessions` **不返回** `archivedAt`（`sessions.py:451-456` 只给 id/title/createdAt/updatedAt）。
- 前端 `ServerSession` 类型无该字段（`chatStream.ts:396-401`），`importServerSessions` 不拷（`spaceHelpers.ts:142-148`）；本地另用布尔 `archived`（`types.ts:94`、`spaceSessionSlice.ts:914`、`Sidebar.tsx:894`）。
- 后果：换端 / 本地索引缺失 / 重开文件夹触发 `adoptWorkspaceSessions` 时，**已归档会话丢标记 → 重现于活跃列表**。
- **修复建议**：确立 `archivedAt` 为服务端权威 → 两个列表端点返回同一字段集 → 前端 `ServerSession` 加 `archivedAt`，import 时映射到本地 `archived`，并让本地布尔变为派生值而非独立真相。**注意**：这条与 B2 是同一处"归档语义"的两个侧面，建议合并设计一次改完。

### A6（低）前端死分支与死字段

### A7（低）`costSource` 类型比实现宽

- 后端只发 `api` / `estimate`（`budget.py:439,481`；`events.py:122` 默认 estimate），**从不发 `unknown`**。

### A8（低）建会话双通道

### B1（高）撤销家族两代互斥 —— 本次最重的一条

**两代机制**

| 代 | 实现 | 作用对象 | 持久化 | 生产调用方 | 状态 |
|---|---|---|---|---|---|
| **v3** | `rewind/hotpath.py`（`RewindHotpath`） | 对话历史截断/undo + 工作区文件 COW | `sessions/<sid>/rewind_events.jsonl`、`orphans/`、`checkpoints.jsonl`、`~/.xeyo/snapshots/<sha>` | `rewind.py:168`、`slash/dispatch.py:617`、前端 `rewindV3Store.ts:603` | **活（主路径）** |
| **v2** | `rewind/service.py`（`RollbackService`） | 对话历史**物理重写** + 工作区 **shadow-git 树**恢复 | `rollback_plans.jsonl`、`rollback_approvals.jsonl`、`recovery_jobs.jsonl`、`revisions.jsonl` | **无生产调用方**，仅路由 `sessions.py:1255-1313` 定义 | **已死但可达** |

**为什么算互斥**：两代都改**同一个 transcript 文件**（v2 物理重写、v3 追加 marker），也都回退**同一个工作区**（v2 用 shadow-git 树、v3 用 COW checkpoint）。两者并存 = 谁后执行谁覆盖前者，且 v2 重写后会回填 v3 marker（`rewind/service.py:1180-1185`）——两代共享同一 transcript 的脆弱握手。

**附带残留（同源）**：
- `engine/query_engine.py:692-698,1018-1030`：每轮仍拍 shadow-git Before/After，**唯一消费者是已退役的 v2** → 纯开销，无人回收。
- 两套 checkpoint_id：`cp_`（`rewind/checkpoint.py:20-23`）vs `cp3_`（`rewind/index.py:215-220`）；`cp_` 与 `checkpoint_cache.jsonl` **生产无读方**（只写不读）。
- 前端 v2 状态机仍编译：`lib/rollbackMachine.ts`、`chat/preStoreHelpers.ts:216-273`、`spaceSessionSlice.ts:150-154`、`api.ts:1487-1530`；`rollbackById` 恒 `idle` 且无 UI 读取（注释自认退役）。
- **回收器不覆盖 v2 产物**：`rewind/blob_gc.py:323-369` 只扫 v3/操作日志，不扫 `rollback_plans.jsonl` / `recovery_jobs.jsonl`，其引用的 `snapshot_hash` blob 可能被误回收。

**修复建议（单代收敛）**：
1. 先确认前端确无隐藏入口调用 v2（搜 `rollbackById` 的 UI 读点；子代理报告为"无"）。
2. 删除 v2：后端路由 `sessions.py:1255-1313`、`rewind/service.py`（若 v3 不依赖其中共享工具，需逐函数确认）、前端 `rollbackMachine.ts` + `api.ts` 三个封装 + `preStoreHelpers` 的 v2 段。
3. 停掉每轮 shadow-git 拍照（`query_engine.py:692-698,1018-1030`）——或转为 v3 的输入后再停，**不要先停后改**。
4. `blob_gc` 补上对 v2 产物的扫描，或随 v2 一起删。
5. 回归：`tests/test_rewind_hotpath.py`（注意其引用的 `sync_index_from_turn_diff`/`capture_turn_baseline` 是另一组旧对账实现，同样只被测试引用 → 一并判死）。

### B2（高）工作区"删除"的文案与行为互斥

- UI 弹窗：`Sidebar.tsx:996-1000` → `title: '删除工作区？'`、`body: '删除工作区「X」并删除其全部对话？'`、按钮"删除"、`danger: true`。
- 实际实现：`spaceSessionSlice.ts:461-467` 注释明写"**移除工作区 = 仅从侧栏隐藏**。会话记录与其消息原样留在 IndexedDB…不迁移、不 tombstone、不删后端"；代码只做 `markSpaceDeleted` + `deleteSpace` + 内存视图过滤。
- 且注释自带方案演进痕迹："（2026-09-05 二稿）… 一稿曾迁入默认分区，用户不需要该中间态"——说明这是**改过一次的方案**，但弹窗文案没跟着改。
- 后果：用户以为对话被删了（并且是 `danger` 强提示），实际重新打开同一文件夹会全部恢复 → 认知落差 + 对"删除"语义失去信任。
- **修复建议**：按现有实现定稿（不可逆删除风险高），把文案改为"从侧栏移除「X」？对话记录将保留，重新打开该文件夹可恢复"；`danger: true` 可降为普通样式，因为操作实际可逆。**这条建议与 A5 一起改**（归档/移除/删除三者语义需要一次讲清）。

### B3（中）侧挂模块"默认关"是失实文档

- 机制本身**合规**：`sidecar/upgrade.py` 有设计文档、总开关 `XEYO_SIDEMOD_PROMOTE`、`unapply()` 一键回退；`install()` 是 **setattr 包装原函数**（`memindex_sig_shadow.py:63-75` 存 `_ORIG__sync_table` 后替换，包装器对非目标表 `return orig(...)` 委托）——**不是两支竞争实现**，子代理"两支同在生产路径"的措辞属误读，我在此更正。
- **真问题**：`sidecar/policy.py:28-33` `sidemod_promote()` **默认 True**，`engine/query_engine.py:1391` 每次 build 都 `apply()`；而各 shadow 模块头部仍写【侧挂模块·默认关】（`memindex_sig_shadow.py:1`）、`enabled()` 注释写"默认 0=关"（`:12`）→ **文档与运行时相反**。升格状态与阅读源码得到的印象不一致，审计/排障时会走错方向。
- **修复建议**：把 6 个 shadow 模块（`_HOOKED` 列表）头部统一改为"升格后默认开；`XEYO_MEMINDEX_SIG_HASH=0` 单项关 / `XEYO_SIDEMOD_PROMOTE=0` 全局回退"；并按 AGENTS.md 第 4 条在登记表标注功能归属与收益证据。

### B4（中）旧权限判定 API 仍在，结论与现行相反

- 现行：`permissions/policy.py:1` `evaluate_policy`（三态 ASK/DENY/ALLOW），生产调用方 `tools/tool_registry.py:422`、`engine/query_loop.py:177`。
- 旧版：`permissions/gate.py:1` `can_use_tool`（**二元，ASK 强制降 DENY**），仅被 `permissions/__init__.py:13` 再导出 + 测试调用，生产不可达。
- 后果：同一问题存在两套**结论相反**的判定；任何人 import `permissions` 拿到的是旧的那个（`__init__` 再导出），极易引错。
- **修复建议**：删除 `gate.py`；或把它改成 `evaluate_policy` 的薄包装并去掉 ASK→DENY 的降级。同时清理 `permissions/__init__.py` 的再导出面。

### B5（中）删会话不清 mid-turn 队列
