# 思考强度链路：三个缺口修复记录

> 2026-09-10。起点：与 deepseek-harness 对比后误判「XEYO 没把推理强度做成可调项」，
> 实际核查发现 GUI 早已有完整 UI，但**链路有三处断开**，导致功能形同虚设。
> 本文记录缺口定位、修法与验证。

## 1. 缺口定位（全部有 file:line 实证）

原始误判的根因：只看了 `ds_adapter.ts` 的单点对比就下结论，没查自己仓库。
核查后确认链路**已通的部分**：

| 环节 | 位置 |
| --- | --- |
| 设置页多选思考等级 | `gui/src/components/ReasoningLevelsSelect.tsx` |
| 设置页默认等级 | `gui/src/components/SettingsModal.tsx` |
| 输入框手选等级 | `gui/src/components/Composer.tsx` + `ModelPicker.tsx` 模型面板 |
| 优先级 | `gui/src/lib/api/chatStream.ts`（手选 > 模型默认 > 会话级） |
| 后端接收 | `python/server/routers/chat.py` / `sessions.py` |
| DeepSeek 请求体 | `python/model/openai_compat.py` |
| 其他兼容模型 | `python/model/openai_compat.py`（透传 8 档） |

**断开的三个缺口**：

1. **`thinking` 恒为 `disabled`**（最严重）—— 全 GUI 找不到任何 `setThinking` 调用，
   唯一来源是默认值 `settingsStore.ts` 的 `thinking: 'disabled'`。而
   `openai_compat.py` 只在 `kind == "enabled"` 时才发 `reasoning_effort`。
   **后果：输入框选的等级对 DeepSeek 模型永远发不出去。**
2. **厂商 modes 未预填** —— 后端 `vendor_models.py` 已为 DeepSeek 下发
   `reasoning_effort: [low, high, max]`，前端 `usage.ts` 也定义了类型，但
   `SettingsModal.tsx::addVendorModelToDraft` 从未读 `vm.modes`（grep 零命中）。
3. **输入框等级不落盘** —— `composerDrafts.ts` 的持久化结构本来就有
   `reasoningEffort` 字段，但 Composer 只在「切会话」和「卸载」时整体保存，
   **等级变更本身不触发写入**，新建会话即回落「自动」。

## 2. 修法

### 缺口①：`thinking` 跟随等级自动推导（根因）

改在 `chatStream.ts` 下发处，而非 UI 层——这样 CLI 与其他入口同样受益：

```ts
// 思考开关与等级成对：选了等级就必须开 thinking，否则后端收不到
// reasoning_effort（DeepSeek 要求 thinking.type==="enabled" 才发等级）。
const thinking: 'enabled' | 'disabled' =
	s.thinking === 'enabled' || reasoningEffort ? 'enabled' : 'disabled';
const effectiveEffort = thinking === 'enabled' ? reasoningEffort : undefined;
```

**语义决策**：`thinking` 与 `reasoning_effort` 是**成对概念**（对齐 dsh 的
`resolveThinking`）。用户显式关思考时等级一并作废，避免发出「关了思考却带等级」
的矛盾请求。

### 缺口②：厂商 modes 预填

新增纯函数 `vendorReasoningLevels()`，**放在 `settingsStore.ts`**（那里已有
`isReasoningEffort` / `REASONING_EFFORTS`，且该文件可测）。设计要点：

- 接受 `{id, label}` 对象与裸字符串两种形态（兼容网关风格不一）；
- 非法值与重复值剔除；返回顺序按全局展示顺序，保证勾选框列出顺序稳定；
- 非数组（畸形响应）返回空数组而非抛错，语义「不限」。

`addVendorModelToDraft` 读 `vm.modes.reasoning_effort` 预填 `reasoningLevels`。
顺带解决一个隐患：默认等级若落在未勾选集合里，会被 `chatStream.ts` 判为
「不支持」而静默丢弃。

### 缺口③：等级变更写草稿

`patchComposerDraftModes` 的 `Pick<>` 白名单加入 `reasoningEffort`，
Composer 新增一个只依赖 `reasoningEffort` 的 effect 写入当前会话草稿。

  （`git status` 无记录）。属另一会话 usage 改造漏改测试 mock。

## 4. 一句话总结

**功能不在「有没有 UI」，而在「UI 的选择能不能到达厂商」**——三个缺口里，
只有第一个是致命的（整条链路空转），后两个是体验与数据完整性问题。

## 5. 未做（有意）

- **未加 `thinking` 独立开关 UI**：推导方案已让现有 UI 生效，新增开关是额外
  复杂度；若将来需要「只开思考不给等级」，再补。
- **未动 `model/openai_compat.py`**：后端逻辑本身正确（成对判断），问题在
  上游没把 `enabled` 传下来，改上游即可。
