## B.1 讲解纪律（先读这段）

**要讲的**：定位、规模、一个能讲透的机制、一个真实的取舍、一条诚实的边界。

**不要讲的**：

| 禁语 | 为什么 | 换成 |
|---|---|---|
| 「业界领先 / 非常完善 / 功能齐全」 | 是判断句不是事实 | 具体数字 + 位置 |
| 「我们实现了 XX」 | 未区分「已实现」和「已接线」 | 「已实现，产线也接了」/「已实现，执行器未接线」 |
| 「很多公司都做不到」 | 攻击性且无法验证 | 不提 |
| 「这个很简单」 | 暗示面试官判断力 | 「这里的关键是……」 |

**一条铁律**：**每一句结论后面都能接上「在 `文件:行号`」**。接不上的 ⇒ 不说。

## B.2 1 分钟版（电梯陈述）

> 我做的 XEYO 是一个**本地优先的编码 Agent**——Python 引擎 + React/Tauri 桌面壳 + Ink 终端 UI，三者共享同一个后端进程。
>
> 我的工作集中在**运行时内核**和**上下文工程**两块。
> 最想讲的一个点是**上下文工程**：我们把「每轮可能变化的模型可见内容」全部收进一条叫 T_now 的注入管线，装进一对**投影-only 的伪造 tool 对**尾插。这样静态前缀**逐字节不动**，厂商的自动前缀缓存自然命中——实测 BFCL 那批请求的输入缓存命中率是 **96.9%**。而且这条管线有**硬准入**：块登记表有硬顶，加一块必须删一块，还有契约测试机器执法。
>
> 一条边界我想主动说：我们仓库里有一个完整的 DAG 调度器，有实现有测试，但**执行器没有接线**——我核实过它只被测试调用。我在文档里如实标了「已实现、未接线」，没有把它当亮点讲。

**时长控制**：约 45–60 秒。**三件事**：定位、一个讲透的点（带数字）、一条边界。

## B.3 3 分钟版（标准项目题）

> **【背景】** 我做的是一个本地编码 Agent，产品形态是桌面应用 + 终端 UI。技术栈是 Python 引擎（FastAPI server）+ React/TS GUI（Tauri 壳）+ Ink TUI。规模上引擎侧约 750 个 Python 文件，前端 390 个文件左右。三种入口——GUI、TUI、CLI——**共享同一个后端进程**，靠一个端口文件互相发现。
>
> **【任务】** 我主要负责两块：**运行时内核**（引擎主循环、会话/事件契约、容错）和**上下文工程**（system prompt 装配、T_now 注入、压缩治理）。
>
> **【行动 —— 第一块：运行时分层】**
> 引擎切三层：`QueryEngine` 是状态容器，`query_loop` 是**无状态的 async generator**，`TurnRunner` 负责生产者-订阅者扇出。切开的标准是「谁持有状态」。
> 这样做的好处是**引擎不碰传输**——同一套 loop 能跑在 HTTP/SSE、CLI 进程内、TUI attach 三种入口上。
> 并发提交用的是**布尔标志快速失败**，不是锁排队：用户连点两次，正确行为是第二次被明确拒绝，而不是排几分钟队。
>
> **【行动 —— 第二块：上下文工程，这是我最有判断的地方】**
> 上下文工程的核心是三句话：**静态前缀只放不变的、易变内容全部尾插、注入有硬预算和硬准入**。
> 具体做法是 T_now 管线：把易变内容装进一对**仅存在于投影的伪造 tool 对**（`assistant(xeyo_env_notice) → tool_result`）。它不进 MessageStore、不进 JSONL、不进 tools 数组，所以 **KV 前缀逐字节不动**，厂商自动缓存命中。
> 另一个收益是**注意力隔离**：tool_result 是模型训练出的「环境声道」，注入内容和用户意图在消息结构上分开了，治的是「说话人混淆」类漂移。
>
> **【结果 —— 带数字】**
> 缓存命中的实测：BFCL 那批请求输入命中率 **96.9%**（64000/66021）。按定价折算，光输入成本就能降 **−95%**。
> 工具结果治理侧：`pytest` 输出 token 从 1126 降到 **78**，**−93.1%**；读一个 Python 小函数从 2 轮 20,523 token 降到 **1 轮 206 token**。
> 离线回归门 **112/112 全绿，¥0**（不需要 API key，无网络也能跑）。
>
> **【边界】**
> 两件事我想主动说清：① 那个 DAG 调度器**执行器未接线**，我核实过；② T_now 的块上限文档写 20、代码常量是 21、执法断言是 `<=`——**对外我统一说这三个数**，不说成一个数。

**时长控制**：约 3 分钟。**结构**：定位 → 任务 → 两块行动 → 三个数字 → 两条边界。

**追问预判**（这段讲完最可能被问的）：
- 「伪造 tool 对厂商会不会拒绝？」→ 会，所以有回退链（见 B.4）
- 「96.9% 是怎么测的？」→ `bfcl_results.json` 的 usage 字段，cached/prompt
- 「DAG 没接线为什么还留着？」→ 见 B.4 事故复盘三

## B.4 5 分钟版（深挖 + 事故复盘）

> 前 3 分钟同 B.3，以下是加长段。

### 加长段一：架构分层与一条硬红线

> 除了三层切开，还有一条红线我想专门讲：**工具面会话内冻结**。
> 原生工具面是**会话起点的一个快照**——attach 时按当时的启用状态决定哪些 MCP 工具进 `schemas()`。此后 **tools 数组在整个会话内冻结，绝不改动**。
> 为什么这是红线？因为 tools 数组在消息结构的最前面，**动它一个字，整个前缀缓存全废**。对按 token 计费的 Agent 来说，这是成本上最贵的一个错误。
> 那会话中途用户想启用一个 MCP 工具怎么办？**唯一通道是一个叫 `Mcp` 的网关工具**——`action=list|describe|call`。工具身份只能从**已知工具集**里解析出来，不从参数里猜。这样「不新增工具」和「能动态调用」就不矛盾了。
> 这条红线有契约测试锁死：`assert _schemas_bytes(reg) == before`——**逐字节比较**，改一个字符就红。

### 加长段二：伪造 tool 对的回退链（这是最容易被追问的技术点）

> 「伪造 tool 对」是有点冒险的做法——厂商协议上，`assistant` 的 tool_call 必须有配对的 `tool_result`。我们是**只存在于投影**地构造这一对，物理上不进消息库。
> 但确实可能被厂商以结构类 4xx 拒绝。所以有回退：**被拒且没吐任何 chunk 时**，我们记一个进程级备忘，**当场以 legacy 声道重建重试一次**。
> 这里有个细节值得说：**如果连重建也不行，就 `skip`——这一轮不注入**，而不是继续硬试。因为「不注入」只是少了一条信息，而「反复重试」会真的把这一轮搞砸。
> 另外回退的状态码集合是 `{400, 404, 405, 413, 415, 422}`——包含 **405**，这一条我们的项目文档里是漏写的，以源码为准。

### 加长段三：三个事故复盘（这是最能体现工程判断的部分）

> **事故一 · 薄壳 venv（发布事故）**
> 现象：用户装完应用打开，**连不上后端**。
> 根因：venv 的 `Scripts/python.exe` **只是一个 launcher**，真正的 DLL 和标准库在**构建机**上。拷到目标机，没有对应的 Python → 启动即死 → 壳拉不起后端 → 前端误报「无法连接后端」。
> 修复不是「下次注意」，是**结构性修复**：改用 python-build-standalone 的可重定位发行版（自带 DLL + 标准库 + VC 运行时），并加**构建期四条硬断言**——`python.exe` 存在、`python3xx.dll` 存在、`site-packages` 在 `sys.path`、`pyvenv.cfg` 的 `home` 必须是 `.`。任一不满足则**构建失败**。
> 第二个坑：`pyvenv.cfg` 写成 `home = .`（**带空格**）会被解析成空基准路径 → 所有第三方包 `ModuleNotFoundError`。
> 三问回答：**根因** = 「拷过去能用」这个假设从未被验证；**规则** = 装机正确性前移到构建期；**回归测试** = `verify()` 四条断言。
>
> **事故二 · 容器路由串容器（并发事故）**
> 现象：并发跑多个任务时，A 任务的环境状态被 B 任务读到。
> 根因：容器身份早期用**环境变量**承载，而 `os.environ` 是**进程全局**的 → 并发下互相覆盖。
> 修法：改用 **ContextVar**——它天然按 async task 隔离。
> 这个根因在仓库里还出现过一次（工具面变更的 digest 是模块级全局、没有 session key），所以我们的统一认识是：**「进程全局」的东西在多会话/多任务环境下都是隐患**。
>
> **事故三 · DAG 调度器的接线审计（不是 bug，是认知纠偏）**
> 在做全项目审计时，我用全仓 grep 核实一件事：这个调度器到底有没有被产线调用？结果是 —— `run_task_batch` 只被 `tests/` 调用；`SessionPool.scheduler_for` **零调用方**；任务分解器也没有外部调用方。
> 但**数据结构与工具函数是接了线的**（拓扑排序、工具白名单被 Agent 工具引用，修图函数在一条 dormant 链上）。
> 所以我的结论不是「删掉它」，而是**把口径统一成「已实现 + 有测试 + 执行器未接线」并写进文档、给出精确接线表**。
> 这件事我认为比讲一个功能更能体现判断力：**发现并如实披露「未接线能力」，而不是含糊地把它算成已上线。**

### 加长段四：诚实的边界（收尾，重要）

> 同样地，我也要把几件事说清楚，不让面试官误判：
> ① 我们有一份「可观测性」的实现，但**产线上真正在跑的只有一条线**（循环检测），而且它的第一消费对象是**模型**不是人——它的产物是「这个工具第 3 次返回了相同结果」这样的事实，注入给模型看；分位统计、分段计时、进程台账都**没有实时消费方**。
> ② 我们和厂商对账的「厂商权威用量」**只对 OpenAI 通路成立**——DeepSeek 没开放接口，我们代码里直接返回「拿不到」，所以 DeepSeek 只有本地账本一个口径。
> ③ 评测守卫的文档写「默认关」，但**实现上默认是开的**——这是我自己实测发现的，文档已经和实现对不上了。
>
> 我的态度是：**能讲清「哪里还没做」的人，比只会讲「做了什么」的人更值钱。**

## B.5 收尾话术（如何主动划边界）

> 这一段可以直接当「你还有什么想说」的回答。

> 我想用一句话总结我的立场：**我会主动区分「已实现」「已接线」「默认开」三件事**。
> 因为面试里最容易翻车的不是不会，而是把「写完了」说成「上线了」、把「默认关」说成「默认有」。所以我们文档里有一张专门的清单，把所有需要加限定的地方列出来——比如 DAG 调度器要加「未接线」、预算要加「墙钟和 USD 默认关」、评测分数要加「自建 lite 集不可对标榜单」。
> 如果贵司更看重「快速给出结论」，我可能会显得啰嗦；如果看重「边界清晰、可验证」，这就是我的默认工作方式。
