## 第 16 章 · S24 rewind：检查点与回滚

### 16.1 定位

rewind 回答一个具体问题：**「Agent 改了 20 个文件之后，用户想回到第 3 轮之前，怎么回？」**

它的难点不在「存快照」，而在三件事：

1. **存什么粒度**——全量树太贵，只存 diff 又无法还原被删文件；
2. **怎么保证原子**——回滚过程中进程崩了，不能留下半滚状态；
3. **和 transcript 的关系**——文件回滚了，对话历史要不要一起回滚？

XEYO 的答案是：**内容寻址 blob（SHA-256）+ 每轮 COW 检查点 + 独立 journal + 崩溃后标记 `recovery_required`**。

### 16.2 ⚠ 三轨并存：v2 / v3 / v4

**这是本章第一个必须讲清的点**——rewind 有**三代实现同时在仓库里**，但它们**不是三套并行目录**，而是「同一批文件内的版本标记 + 不同入口」。

grep 证据（`python/rewind/` 内）：

```
rewind/checkpoint.py:1      "Rewind v2 的检查点辅助函数"
rewind/hotpath.py:1         "回溯 v3 热路径事务"
rewind/hotpath.py:12        "v2 rewind.service 保持原样作降级路径"
rewind/index.py:1           "回溯 v3 热路径"
rewind/index.py:454         "v4 sync_index_from_ledger 共用"
rewind/index.py:573/582     "v4 对账（2026-09-09 v4.2）"
```

| 轨道 | 实现 | 入口 | 状态 |
|---|---|---|---|
| **v2** | `service.py:266` `RollbackService` | `/v1/sessions/{sid}/rollback/*`（`server/routers/sessions.py:1255-1303`） | **保留作降级路径**（注释明说） |
| **v3** | `hotpath.py:328` `RewindHotpath` + `index.py:128` `AgentFileIndex` | `/v1/sessions/{sid}/rewind*`（`server/routers/rewind.py`） | **当前主路径**（GUI `rewindV3Store.ts` 对接它） |
| **v4** | `index.py:573` `sync_index_from_ledger` | 内部对账（无独立路由） | 索引与 journal 的**一致性修复层** |

**面试怎么讲**：三代并存的理由不是「没清理」，而是**降级路径**——v2 保留是因为它 `preview` / `execute` 分离得更彻底（`service.py:768` / `:1363`），在 v3 热路径出问题时可以切回去。这是个「有意识的兼容债」，不是没人管。

> ⚠ 反面：这也意味着**改 rewind 必须同时考虑三条轨道**，任何「只改 v3」的改动都可能让 v2 降级路径失效。这是真实维护成本。

### 16.3 检查点：何时创建 / 存什么 / 存哪

**创建时机**：**用户消息发送时**——`engine/query_engine.py:703-732` 调 `freeze_checkpoint()`（`rewind/index.py:223`）+ `put_checkpoint_cache()`（`rewind/checkpoint.py:44`）。

这个时机的选择本身就是设计取舍：**在「模型动手之前」冻结**，而不是每轮结束。因为回滚语义是「回到你还没改之前」。

**检查点缓存路径**：`rewind/checkpoint.py:26-28` `_cache_path` → `<sessions_dir>/<session>/checkpoint_cache.jsonl`。

**三类存储**：

| 类 | 载体 | 位置 | 存什么 |
|---|---|---|---|
| **blob** | `snapshot.py:15` `SnapshotStore`，内容寻址（SHA-256） | `~/.xeyo/snapshots`（`blob_gc.py:87` `snapshot_root`） | 文件内容本身；同一内容只存一份 |
| **journal** | `journal.py:145` `OperationJournal` | `<session>/`（`journal.py:52` `_session_dir`） | 三类 jsonl：operations / turns / audit |
| **volume**（索引） | `index.py:192` `FileCheckpoint` | `checkpoints.jsonl` | `[[path, hash]]` 清单（`freeze_checkpoint` 产出） |

**为什么是「内容寻址」而不是「每轮拷贝一份树」**：

- 20 轮 × 1000 文件 × 每文件 10KB = 200MB；内容寻址后**未变的文件只存一份**，实际增量 ≈ 本轮真正改动文件的体积。
- 副作用：可以按 hash 判「这个文件在这轮有没有变过」，直接省掉 diff。

### 16.4 原子性与崩溃恢复

`hotpath.py` 的关键设计：

| 机制 | 位置 | 作用 |
|---|---|---|
| 事件追加 | `hotpath.py:111` `_append_event` | 回滚过程本身也记 journal（可审计） |
| 原子重写 | `hotpath.py:120` `_write_atomic` | transcript 重写走「临时文件 + rename」，不出现半写文件 |
| 崩溃标记 | `hotpath.py:180` `mark_crashed_rewinds` | 启动时把 orphan 回滚标为 `recovery_required` |
| 启动接线 | `server/app.py:132` | lifespan 里调用 |

**并发保护**：`locks.py` 提供三级租约——`Lease:21` / `ResourceLeaseManager:89` / `ProcessWorkspaceLock:132` / `SessionLock:153`。回滚时持租约，防止另一个会话（或另一个 Agent）同时改写同一批文件。

### 16.5 GC：blob 什么时候回收

`blob_gc.py`：

- `garbage_collect:410` —— **默认 dry-run**，必须 `XEYO_BLOB_GC_ENABLED=1` 才真删。
- 触发：`server/app.py:161` `_blob_gc_loop`，**每小时**跑一次（`:170-175`）。
- 保留策略 `retained_checkpoint_ids:230` = 「最近 `keep_recent` 个 + 最早基线 + 锚点（`anchor=true`）」；`retained_turn_ids:259` 同口径保留 turn。
- 可达集 = 上述检查点/turn 引用的全部 SHA-256（`_collect_hashes:191`、`_collect_checkpoint_entries:211`）；不在此集合的 blob 才可回收。
- 配置 `read_rewind_gc_config:122` 读 `~/.xeyo/rewind_gc.json`（`keep_recent` / `max_bytes`）。

**设计取舍（可讲）**：**默认 dry-run 是刻意的**。GC 是唯一会**不可逆删除用户数据**的后台任务，所以默认只报告不执行——与另两个 GC（`_sidechain_gc_loop:138`）保持同一纪律。

### 16.6 服务端 API（v3 主路径，全部 loopback 门禁）

`server/routers/rewind.py`（`:30` `require_loopback`）：

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/v1/sessions/{sid}/rewind` | 执行回滚（`:168`） |
| POST | `.../rewind/{id}/undo` | 撤销这次回滚（`:192`） |
| POST | `.../rewind/{id}/recover` | 从 `recovery_required` 恢复（`:210`） |
| GET | `.../rewind/{id}` | 查单次回滚状态（`:226`） |
| GET | `.../rewind` | 列出回滚事件（`:237`） |
| GET | `.../rewind/checkpoint/{mid}` | 取某条消息对应的检查点（`:243`） |
| POST | `.../rewind/checkpoint/{mid}/anchor` | 把检查点钉为「不可回收锚点」（`:267`） |

**`anchor` 这个端点是本册最值得讲的一个小设计**：GC 的保留集里除了「最近 N 个」还有「锚点」。用户可以对某个检查点打锚，从此它**永远不会被 GC 回收**——把「我记得那个状态有用」这个人类判断，变成 GC 的可达性输入。

### 16.7 面试题 + 回答模板

#### Q1：你的 Agent 怎么做「回滚到某一轮之前」？

**回答模板（90 秒）**：

> 三件事：**存什么、怎么找、怎么原子**。
> 存什么：用**内容寻址**（SHA-256）而不是快照树。同一个文件在不同轮次只有改动过才新增 blob，所以 20 轮的存储增量是「真正改动的文件体积」，不是「轮次 × 仓库体积」。
> 什么时候存：在**用户消息发出、模型动手之前**冻结一个 COW 检查点，检查点本体只是一张 `[[path, hash]]` 清单，很轻。
> 怎么原子：回滚过程中的每一步都写进独立 journal，transcript 重写走临时文件 + rename；进程如果在回滚中途崩了，启动时 `mark_crashed_rewinds` 会把它标成 `recovery_required`，等用户决定恢复还是放弃——**不留半滚状态**。
> 另外我们有三代实现（v2 降级 / v3 热路径 / v4 对账），v2 保留下来是当降级路径用的。

**追问 1**：*为什么不用 git 做回滚？*
> 两个原因。一是**语义不对**：git 的提交粒度是「你想提交什么」，而我们要的是「每一轮自动冻结」，用户不会为每一轮 commit。二是**边界不对**：仓库可能本身就有 git（那我们就用 `workspace_revision` 读它的状态），但也可能没有 git；回滚必须对「无版本控制的目录」也成立，所以底层是自建的内容寻址存储，而不是 git。

**追问 2**：*blob 回收会不会误删还要用的文件？*
> 这是最危险的操作，所以两条保险：**默认 dry-run**（要显式开 `XEYO_BLOB_GC_ENABLED=1` 才真删）；**可达性遍历**——先算出「保留的检查点 + 保留的 turn + 锚点」引用到的全部 hash，不在集合里的才可回收。另外 GC 只跑在后台每小时一次，不在关键路径上。

**追问 3**（挖坑）：*如果用户回滚了文件，但对话历史没回滚，会怎样？*
> 会不一致——模型看到的历史里它「已经改过」，但磁盘上是旧内容。我们的处理是把检查点和消息 id 绑定（`GET .../rewind/checkpoint/{mid}` 就是按消息取检查点），所以回滚是**按消息锚定**的，UI 上表现为「回到那条消息」，文件和历史一起走。这比「只回滚文件」安全得多。

## 第 17 章 · 任务编排与后台任务（S26/S27）

### 17.1 S27 · 三个不同的「任务」概念

**第一个易错点**：XEYO 有**三个名字都像「任务状态」的东西**，但它们解决完全不同的问题。

| 概念 | 定义 | 持久化 | 作用 |
|---|---|---|---|
| **Goal** | `goal_state.py:70` `Goal`（`goal_id` / `status` / `rounds` / `revision`） | `GoalStore:268`（磁盘） | 长任务的**目标**，跨轮存活 |
| **Plan** | `plan.py:18` `PendingPlan` / `:30` `PlanEngine` | 会话内 | 待审批的**计划**，审批后转正 |
| **TaskState** | `task_state.py:26` `SessionTaskState`（`status` / `turn_id` / `agent_mode`） | **进程内，不落盘** | 单会话的**回合生命周期**状态 |

⚠ **`SessionTaskState` 不是 T_now 块**：它由 `QueryEngine` 持有（`engine/query_engine.py:199`），并通过 `chat.py:1357` 发 `task_state_changed` SSE 给 UI。prompt 侧对应的是 **todo 列表**（`build_todo_hint`，`pre_llm_inject.py:1104`），不是 `SessionTaskState` 本身。**讲的时候不要把这两者混为一谈。**

### 17.2 Goal 轮驱动（`goal_round_driver.py`）

这是「让 Agent 自己接着往下做」的机制：

| 符号 | 位置 | 作用 |
|---|---|---|
| `GoalRoundDriver` | `:71` | 单会话至多一个**在途合成轮** |
| `arm` | `:130` | 武装：标记「本会话可以自动续跑」 |
| `_schedule` | `:185` | 预约下一轮 |
| `_round_task` | `:264` | 防抖 → 复检 → 提交合成轮 |
| `on_turn_settled` | `:204` | **触发点**：上一轮结算后决定要不要续 |
| `yield_to_human` | `:164` | ⚠ **人类消息让位**（见 17.4） |

**合成轮**（`synthetic_round.py`）：不是用户真的发了消息，而是引擎代发的一轮。它需要「假装」成一次人类请求，所以：

- `note_request_env:41` / `env_for:49` / `clear_request_env:54` —— 保存「最近一次人类请求的环境」；
- `submit_synthetic:142` —— 用保存的环境代发（`ASGI head:76` 直接走 ASGI）。

**为什么需要「环境复现」**：合成轮不是人类发起的，如果直接提交，模型会看到「没有人类指令的一轮」，行为会漂。把上一轮人类请求的环境（cwd、权限模式等）复现出来，合成轮在上下文里才是连续的。

### 17.3 S26 · 后台任务（`job_*` 三工具）

Bash 长命令转后台后的生命周期由这套管理：

| 层 | 符号 | 位置 |
|---|---|---|
| 工具 | `JobOutputTool` / `JobListTool` / `JobKillTool` | `tools/job_tools.py:64` / `:174` / `:232`（工具名 `job_output` / `job_list` / `job_kill`，`:24-26`） |
| 注册表 | `JobRegistry` | `server/job_registry.py:146` |
| 记录 | `JobRecord` | `:113` |
| 环形游标 | `_Ring` | `:74`（输出是**流式追加**的，游标读，不是一次性返回） |
| 超时上限 | `_job_max_timeout_ms` | `:46` |

`JobRegistry` 的方法覆盖 `get` / `kill` / `list` / `on_turn_settled` / `consume_wake`——注意 **`consume_wake`**：后台任务完成后要**唤醒**正在等待的 Agent，而不是让 Agent 轮询。

**设计取舍**：为什么输出用**环形游标 + 追加**而不是一次性返回？因为后台任务的输出可能无限长（一个 `npm run dev` 能跑几小时）。环形缓冲保证内存有界，游标保证「模型每次只看新增的部分」。

### 17.4 回合结算枢纽：单一槽 + 三租户分发

`server/turn_settlement_hub.py` 是本册**结构最干净的一个设计**：

```
on_turn_settled(:22)
  ├─ inbox(:31)    → 排队的人类消息要不要现在投
  ├─ goal(:44)     → 要不要续下一轮（Goal 驱动）
  └─ jobs(:57)     → 后台任务要不要唤醒
```

**关键点两条**：

1. **单一回调槽**：`turn_runner` 只有一个「结算」回调位，不是三个。所有想知道「这轮结束了」的子系统都注册到 hub，由 hub 依次分发。
2. **异常全隔离**：任一租户抛异常不影响其他租户。理由是**结算路径不能因为一个订阅者的 bug 而整轮失败**。

**inbox 的 drain 语义**：`inbox_registry.py:95` `InboxRegistry` → `on_turn_settled:332` → `_drain:376` / `_drain_batch:408` / `_drain_one:438`，把排队的人类消息提交为「人类续跑」。

### 17.5 ⚠ 认知纠正：`yield_to_human` 不在 `session_presence.py`

第一阶段把 `yield_to_human` 归到 `engine/session_presence.py`。**实测不在那里**：

- `yield_to_human` 定义在 **`server/goal_round_driver.py:164`** —— 语义是「**人类消息让位**：作废在途的合成轮预约」。
- `chat.py:742` 在 busy 闸之前调用它。
- `session_presence.py` 提供的是**另一件事**：peer / 文件冲突检测与 notice 队列（`queue_notice:325` / `take_notices:341`）。

**这两个机制长得很像但根因不同**：

| 机制 | 问题 | 位置 |
|---|---|---|
| `yield_to_human` | 人类发消息时，**合成轮正在预约** → 让合成轮让位 | `goal_round_driver.py:164` |
| `session_presence` notice | **多个会话/Agent** 同时改文件 → 广播冲突事实 | `session_presence.py:325` |

> 面试价值：这是一个「**同名不同责**」的例子。能说清「我们仓库里有两个都叫 yield/notice 的机制，但一个管人机让位、一个管多会话冲突」，说明你是**读进去**了，不是看目录在猜。

### 17.6 面试题 + 回答模板

#### Q1：长任务怎么自动接着做？

> 三层：**目标（Goal）** 落盘、跨轮存活；**轮驱动（GoalRoundDriver）** 在每轮结算后判断要不要续；**合成轮（synthetic_round）** 负责「代人类发一轮」。
> 最关键的细节是合成轮要**复现上一轮人类请求的环境**（`note_request_env` / `env_for`），否则模型会看到「一轮没有人类指令的对话」，行为会漂。
> 另外有两条刹车：**单会话至多一个在途合成轮**（`_round_task` 里有防抖 + 复检），以及**人类消息一到就让位**（`yield_to_human`）。

#### Q2：$（系统设计题）后台任务完成后，正在等待的 Agent 怎么知道？

> 我们不做轮询，做**唤醒**——`JobRegistry.consume_wake`。整条路径挂在**回合结算枢纽**上：`turn_runner` 每轮结束只发一个结算回调，hub 再分发给三个租户（inbox / goal / jobs），每个租户异常隔离。
> 为什么用单一槽而不是三个回调：**结算路径的失败会污染整轮**。如果三个订阅者各自直接挂到 `turn_runner`，任何一个抛异常都会让结算中断；hub 做一层隔离，代价是一次转发，收益是「后台任务崩了不会让对话轮失败」。

#### Q3：为什么后台任务输出要用环形缓冲？

> 因为输出**长度无上界**（`npm run dev` 可以跑几小时）。一次性返回会把上下文和内存打爆。环形缓冲让内存有界，游标让模型每次只读**新增部分**——这跟工具结果治理（第三册 S08）是同一个思路：**任何时候都不要让「无界的东西」直接进上下文**。

### 18.1 app 装配（`server/app.py`）

### 18.2 ⚠ CORS：显式白名单（纠正第一阶段的猜测）

第一阶段假设可能是 `allow_origins="*"`。**实测不是**，而且源码注释明确解释了为什么不能是：

```python
# 不再使用 "*" 通配符：通配符 + allow_credentials 是规范禁止的组合，
# 且等于对任意网页开放本地 API（API key 走 header 可被任意页面读取）。
```

默认白名单（`:217`，共 9 项）：`localhost:5173` / `127.0.0.1:5173` / `:1420` / `:1421`（双写）+ `tauri://localhost` / `http://tauri.localhost` / `https://tauri.localhost`。可用 `XEYO_CORS_ORIGINS` 逗号分隔覆盖。

`allow_credentials = "*" not in _cors_origins_resolved`（`:255`）——**只有用户显式配了通配符时才关凭证**，默认显式白名单下带凭证。

方法 / 头也从 `"*"` 收敛为实际清单：`_CORS_METHODS = [GET, POST, DELETE, PATCH, OPTIONS]`、`_CORS_HEADERS = [Content-Type, Authorization, X-Provider, X-Base-Url, X-Session-Id, X-Remote-Token]`。

> **这是一个很好的安全面试素材**：本地 Agent 的 API 端口如果开 `*`，任意网页可以 fetch 它并读走 API key。「本地服务也要配 CORS」这一点很多人会漏。

### 18.8 ⚠ C-09 三条旁路 & C-18 bridge 废弃

**C-09 · 三条绕开主链的写路径**（不经权限 / rewind / 审计）：

|---|---|---|

### 18.9 设计取舍汇总

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| 进程模型 | **单 worker** | 多 worker + 共享存储 | 引擎状态全在内存，多进程会让会话分裂 |
| 端口发现 | **端口文件** | 固定端口 | 端口冲突时仍能互相发现；带 `engine_version` 防错配 |
| CORS | **显式白名单** | `*` | `*` + 凭证被规范禁止；且等于对任意网页开放本地 API |
| 本地安全 | **loopback + CORS 双层** | 只靠 CORS | 非浏览器客户端完全绕过 CORS |
| 结算回调 | **单一槽 + 三租户分发** | 三个直连回调 | 结算路径不能因一个订阅者崩掉而整轮失败 |
| 后台输出 | **环形缓冲 + 游标** | 一次性返回 | 输出长度无上界 |
| blob GC | **默认 dry-run** | 默认真删 | 唯一不可逆删用户数据的后台任务 |
| 合成轮 | **复现人类请求环境** | 直接裸提交 | 否则模型看到「无人类指令的一轮」会漂 |

### 18.10 面试题 + 回答模板

#### Q1：为什么后端只跑单进程？怎么解决的横向扩展？

> 因为引擎的状态是**进程内**的：`SessionPool`、`JobRegistry`、`InboxRegistry` 都是单例，多 worker 会各自持一份，会话状态就分裂了。我们的产品形态是**本地单用户**，横向扩展本来就不是需求——真正需要的是「多入口共享一个后端」，这个用**端口文件 + HTTP/SSE** 解决了：GUI、TUI、CLI attach 三方都连同一个后端进程。
> 如果哪天真要横向扩展，第一刀是**把会话状态外置**（现在 `MessageStore` 已经是可序列化的），而不是简单加 worker。

#### Q2：$（安全题）本地 API 端口如果被恶意网页访问会怎样？你怎么防？

> 三层：**CORS 显式白名单**（只放行 5173/1420/1421 和 tauri 来源，注释里明确写了为什么不能用 `*`——`*` + 凭证是规范禁止的组合，且等于对任意网页开放本地 API，API key 走 header 能被任意页面读走）；**loopback 门禁**（校验 client host，非本机 403，除非显式开 `XEYO_ALLOW_REMOTE_CONTROL` 并用 `X-Remote-Token`）；**PNA 中间件**处理 Chrome 的 Private Network Access 预检。
> 关键认识是：**CORS 是给浏览器看的，非浏览器客户端（curl、另一个进程）完全绕过它**。所以本地服务不能只配 CORS。

#### Q3：`chat` 和 `attach` 两个命令为什么要分开？

> 它们解决的是**引擎在哪**的问题。`chat` 在**本进程内**起引擎——适合脚本和一次性任务，不依赖任何服务；`attach` 连**已经在跑的 server**——适合「GUI 已经开着，我想在终端接着看」。这个区分的价值在于：**用户不需要知道后端架构**，只需要知道「我是要新开一个，还是接上现有的」。
