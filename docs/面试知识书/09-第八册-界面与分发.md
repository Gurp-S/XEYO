### 19.2 ⭐ 渲染分层：冻结区 + 实时区（TUI 最值得讲的设计）

`tui/src/app/App.tsx` 里，时间线被切成两段：

| 区域 | 实现 | 行为 |
|---|---|---|
| **冻结区** | `<Static>`（`:633`） | **只渲染一次，永不重绘** |
| **实时区** | `liveMeta.map(...)`（`:645`） | 每帧重算（正在流式的 assistant / running 的工具） |

**为什么这是 Ink 应用的关键优化**：终端渲染是「整屏重写」模型，每次状态变化都会重新输出所有行。如果历史消息也在重绘集合里，一个 100 轮的会话每来一个 token 都要重画 100 轮内容——终端会疯狂闪烁。

Ink 的 `<Static>` 正是为这个场景设计的：**它输出过的内容从渲染树里摘出去**，此后不再参与 diff。所以 TUI 的分层不是「代码组织」，是**性能正确性**：必须把「不会再变的历史」和「正在变的一行」物理分开。

判定逻辑（`:176` / `:189-191`）：

```ts
it.kind === "assistant" && it.streaming   // → 实时区
it.kind === "tool" && it.status === "running"  // → 实时区
```

**其余全部进冻结区**——判据是「这条是否还在变」。

### 19.4 S34 · slash 命令体系

**单一事实源在 Python**，前端只是生成物：

| 环节 | 位置 | 说明 |
|---|---|---|
| 命令定义 | `python/slash/registry.py:44` `Command` dataclass | 字段：`name` / `category` / `handler` / `summary` / `usage` / `aliases` / `arg_spec` / `surfaces` / `when` |
| 命令表 | `registry.py:60-380` `_COMMANDS` | **实测 35 条** |
| 分发 | `dispatch.py:1072` `dispatch()`；处理器表 `:1047-1069` `_HANDLERS` | 命令名 → 处理函数 |
| 导出 | `export_manifest.py:25-34` `_OUTPUTS` | 生成 **2 份**：`gui/src/generated/slashManifest.ts` 与 `tui/src/generated/slashManifest.ts` |
| 门禁 | `scripts/check.ps1` 第 4 步 | `python -m slash.export_manifest --check` —— **manifest 过期即失败** |

**`surfaces` 字段是本章最值得讲的一点**：同一条命令可以声明它出现在哪些界面（GUI / TUI / 两者）。导出时按 surface 过滤，生成两份不同的 manifest。所以「加一条斜杠命令」的完整流程是：

1. 在 `registry.py` 的 `_COMMANDS` 加一条（声明 `surfaces`）；
2. 跑 `py -3.11 -m slash.export_manifest`；
3. 提交两份生成的 `.ts`；
4. `check.ps1` 会验证 manifest 与 registry 一致——**忘记重新导出，提交门直接红**。

**TUI 侧消费**：`tui/src/generated/slashManifest.ts`（35 条）→ `App.tsx:303` `parseSlashInput` 判定 → `:377` `runSlashCommand` 按 surface 走 `postSlashCommand`（POST `/v1/slash`）；补全用 `slashMatches`（`PromptLine`）。

> **这个「Python 定义 → 生成 TS → 门禁校验」的链路设计得很好**：斜杠命令是**领域逻辑**（它要调后端），不该在两个前端各写一遍。用生成物 + 门禁，既保证两端一致，又保证不会忘记同步。

### 19.5 面试题 + 回答模板

#### Q1：终端 UI 怎么避免闪烁？

> 用 Ink 的 `<Static>` 把时间线**物理切成两段**：冻结区（历史消息，只渲染一次，之后从渲染树里摘出去）+ 实时区（正在流式的 assistant、running 的工具）。
> 判据很直接——「这条内容还会不会变」：`streaming` 的 assistant 和 `running` 的工具进实时区，其余全部进冻结区。
> 这不是代码组织问题，是**性能正确性**问题：终端是整屏重写模型，历史如果参与 diff，一个 100 轮的会话每来一个 token 就要重画 100 轮。

#### Q2：斜杠命令在两个前端怎么保持一致？

> 命令的**唯一事实源在 Python**（`slash/registry.py` 的 `Command` dataclass），然后由 `export_manifest.py` 生成两份 TS manifest（GUI 和 TUI 各一份），前端只消费生成物。
> 关键在门禁：`check.ps1` 里跑 `python -m slash.export_manifest --check`，**manifest 和 registry 不一致就提交失败**。所以「改了命令忘了同步前端」这种错误在提交阶段就被挡住，而不是等用户发现。
> 另外命令带 `surfaces` 字段，可以声明它只在某个界面出现——比如某些命令在 TUI 没意义。

### 20.4 通信层：SSE + cursor 重连 + 看门狗

| 机制 | 位置 | 说明 |
|---|---|---|
| barrel 导出 | `gui/src/lib/api.ts:1-21` | 重导出 `lib/api/*` |
| 主流订阅 | `lib/api/chatStream.ts:434` `streamTurnEvents` | GET `/v1/sessions/{id}/turns/current/events?cursor=` |
| **游标重连** | `chatStream.ts:490` `rememberTurnCursor` | 断线后用 cursor 续订，**不是从头重放** |
| 断线信号 | `chatStream.ts` | `onError({kind: 'connection_lost'})` |
| **空闲看门狗** | `lib/api/core.ts:55` `createStreamWatchdog` | `STREAM_IDLE_TIMEOUT_MS = 60s`（`:25`） |

**两个设计要一起讲**：

1. **cursor 重连**：SSE 断线后如果从头重放，用户会看到重复内容。带 cursor 说明「我已经收到这里了」，重连只取增量。前提是服务端要保留事件（这就是为什么事件有 id）。
2. **空闲看门狗（60s）**：SSE 连接可能「僵而不死」——TCP 没断但服务端不再发数据。只看 `onerror` 是发现不了的。看门狗在「60 秒没收到任何字节」时主动断开并触发重连。

> 这两个是 SSE 生产化的常见坑，能主动说出来很加分。

### 20.8 面试题 + 回答模板

#### Q1：前端状态怎么管？为什么不用 Redux？

> Zustand，按**领域**切 store（chat / settings / workspace / explorer / rewind / remote…），不搞单一 store。
> 关键是**避免 store 之间循环依赖**：互相引用的入口收敛到 `storeRefs.ts`。另外 chat 这块已经大到需要分片，所以在 `stores/chat/` 下拆了子模块。
> 布局档位这类「全局但低频变化」的状态放在 `settingsStore`，但**实际渲染不走 React**——写到 `html[data-pane-layout]` 交给 CSS，切档位不触发重渲染。

#### Q2：SSE 断线怎么办？

> 两条。**游标重连**：订阅 URL 带 `cursor`（`GET /v1/sessions/{id}/turns/current/events?cursor=`），重连只取增量，不重放——否则用户会看到重复消息。**空闲看门狗**：60 秒收不到任何字节就主动断开重连，因为 SSE 可能「TCP 没断但服务端不再发数据」，只看 `onerror` 发现不了。

#### Q3：用户说「换个入口打开就看不到历史了」，你怎么排查？

> 先问是不是**换了数据源**而不是丢了数据。我们的数据是三层：权威在**后端 JSONL**（`~/.xeyo/sessions/*.jsonl`），前端 IndexedDB 只是派生缓存。
> 而 IndexedDB **按 origin 隔离**：dev 是 `http://localhost:5173`，release 是 `http://tauri.localhost`（`tauri.conf.json` 的 identifier 是 `com.xeyo.agent`）。换入口 = 换 origin = 换库。
> 所以排查第一步是：**看后端 JSONL 里数据还在不在**。在 → 那是前端读错库，不是数据丢失。

## 第 21 章 · 桌面分发与远程通道（S32 / S33）

### 21.1 Tauri 壳的职责

`gui/src-tauri/src/lib.rs` 分四段：

| 段 | 位置 | 内容 |
|---|---|---|
| 单实例锁 | `:23` `acquire_single_instance` | 防止开两个壳各拉一个后端 |
| 后端拉起 | `:383` `spawn_python`、`:883` `setup` | 先 `wait_health(3s)`，失败才 spawn |
| 进程守护 | `:930`（守护线程） | 每 **10s** 探活；连续不健康 **30s** 则杀进程树重拉 |
| 错误上报 | `:358` `BACKEND_SPAWN_ERROR`、`:372` `get_backend_error` | 静态槽 + 前端可查 |
| 路径白名单 | `:647` `assert_within_allowed`、`:667` `AllowedRoots` | 壳暴露的 git/目录命令只能访问允许根 |

**「3 秒先等、再自己拉」这个顺序很关键**：如果用户已经用 `XEYO.bat` 起了后端（或另一个入口在跑），壳不应该再起一个。先探测 3 秒，探测到就复用——这和后端的 `SessionPool` 复用 engine 是同一个思路。

**守护线程的策略选择**：不是「一发现不健康就重启」，而是**连续不健康 30 秒才重启**。理由是启动中的后端会短暂不健康，立刻重启会导致「重启风暴」。

**`identifier = com.xeyo.agent` 是 IndexedDB origin 隔离的根因**：Tauri v2 在 Windows 上的 WebView 数据目录是 `%LOCALAPPDATA%\com.xeyo.agent\EBWebView`，而页面 origin 是 `http://tauri.localhost` —— 与 dev 的 `http://localhost:5173` 完全不同源。这就是「换入口丢数据」假象的来源。

### 21.4 ⭐ 自包含 Python 打包（本册最有价值的一段）

**问题**：桌面应用要带上一个能跑的 Python 运行时装进安装包，做到「目标机没装 Python 也能跑」。

**`scripts/build_slim_venv.py` 的做法**：

| 环节 | 位置 | 说明 |
|---|---|---|
| 产物目标 | `:43` `DEFAULT_DST` = `resources/python/.venv` | — |
| pyvenv.cfg 写入 | `:345` `write_pyvenv_cfg` | ⚠ **`home=.`（无空格！）**，注释在 `:336-338` 强调 |
| **自包含断言** | `:348` `verify()` | 四条硬断言（见下） |
| 裁剪 | — | 保留 pip，裁掉 pytest / ray / sqlalchemy |

**`verify()` 的四条硬断言**：

| # | 断言 | 位置 |
|---|---|---|
| 1 | `python.exe` 必须存在 | `:354` |
| 2 | **`python3xx.dll` 必须存在** | `:356` |
| 3 | `site-packages` 必须在 `sys.path` 里 | `:357` |
| 4 | `pyvenv.cfg` 的 `home` 必须为 `.` | `:366` |

**为什么是这四条——两条真实事故**：

> **事故 A：薄壳 venv（2026-09-10）**
> venv 的 `Scripts/python.exe` **只是一个 launcher**，真正的 DLL 和标准库在**构建机**上。把这个 venv 拷到目标机 → 没有对应的 Python 安装 → 启动即死。表现是：壳拉不起后端 → 前端误报「无法连接后端」。
> **修法**：改用 python-build-standalone 的 `install_only` 包（自带 DLL + 标准库 + VC 运行时，可重定位），并把「缺 DLL」变成**构建期断言**（断言 1、2）。
>
> **事故 B：`pyvenv.cfg` 的 `home = .` 多了空格**
> `home = .`（带空格）会被解析成**空基准路径** → 所有第三方包 `ModuleNotFoundError`。所以写成 `home=.`，并且**加断言 4 把它钉死**。

**这两条是全书最好的「事故 → 结构性修复」案例**：

| 事故 | 结构性根因 | 让它在结构上不再发生的规则 | 回归测试 |
|---|---|---|---|
| A 薄壳 venv | 「拷过去能用」这个假设没有被验证过 | 改用可重定位发行版 + **构建期断言**（缺 DLL 即失败） | `verify()` 断言 1/2 |
| B `home = .` | 配置格式对空白敏感，但没人验证解析结果 | 断言 `pyvenv.cfg` 的 `home` 值（断言 4） | `verify()` 断言 4 |

**另一个运维细节**：替换 `resources/python/.venv` 前**必须先停开发态后端**，否则 Windows 文件锁导致 `WinError 5`。查 pid/port 走 `.xeyo/backend_port`。

**构建脚本的两条纪律**：
1. **禁止 `rmtree` 大目录**（会撞上批量删除确认门）→ 改**改名旁置**（rename aside）；
2. **断言失败即构建失败**，不允许「先产出再补检查」。

**`FinalOnlyRunner` 是本章的架构亮点**：远程通道（微信）不是把你接进完整的 agent 会话，而是**只跑最终回合**——用户发一个请求，得到一个结果。理由：

1. 微信这种渠道**交互节律不同**（用户不会盯着看工具调用过程）；
2. 中间过程（工具调用、权限询问）在远程渠道**没有合适的 UI 来表达**；
3. 因此远程是**降级形态**：能力受限但可用。

**`secrets.compare_digest` 细节**：令牌比较如果用 `==`，会因为「第一个不匹配字符的位置」而泄露信息（时序攻击）。这个细节能主动说出来，是很实在的安全意识。

### 21.7 ⚠「换入口丢数据」——高频误判的正确解释

**现象**：用户从 `XEYO.bat`（dev）换到安装包（release），发现历史会话不见了。

**真相**：**换了库，不是删了库。**

| 入口 | 页面 origin | WebView 数据目录 |
|---|---|---|
| dev（`XEYO.bat` → tauri dev） | `http://localhost:5173` | `%LOCALAPPDATA%\com.xeyo.agent\EBWebView` 下 `http_localhost_5173.*` |
| release（安装包） | `http://tauri.localhost` | 同目录下 `http_tauri.localhost_0.*` |

**排查顺序（可直接背）**：

1. 看**后端 JSONL**（`~/.xeyo/sessions/*.jsonl`）—— 这是权威 transcript。在 → 没丢数据。
2. 看 `%LOCALAPPDATA%\com.xeyo.agent\EBWebView` 下有几套 `http_*` 目录 —— 有几套就说明有几个 origin 的库。
3. 结论：前端读的是另一个库；要么切回原入口，要么做一次迁移。

**为什么会有这个设计**：IndexedDB 的 origin 隔离是**浏览器安全模型**，不是我们的选择。Tauri v2 在 Windows 用 `http(s)://tauri.localhost` 作为页面 origin，与 dev 的 `localhost:5173` 天然不同源。

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| 后端发现 | 端口文件 + 3s 健康探测复用 | 壳总是自己拉一个 | 多入口共享同一后端 |

### 21.9 面试题 + 回答模板

#### Q1：$（事故题）你的桌面应用装到用户机器上，打开连不上后端，怎么查？

> 分层排查：**壳能不能拉起进程 → 进程能不能跑起来 → 跑起来能不能通**。
> 第一层看壳的错误槽（`BACKEND_SPAWN_ERROR` / `get_backend_error`）；第二层看选中的解释器是不是真的可用；第三层看端口文件。
> 我们真踩过这个坑：一次发布事故的根因是 **venv 是「薄壳」**——`Scripts/python.exe` 只是 launcher，真正的 DLL 和标准库在构建机上，拷到目标机后启动即死。
> **修法不是「下次注意」，是结构性修复**：改用可重定位的 Python 发行版（自带 DLL + 标准库 + VC 运行时），并且加**构建期断言**——缺 DLL、`site-packages` 不在 `sys.path`、`pyvenv.cfg` 指向外部，任一命中就**构建失败**。这样这类问题在打包阶段就暴露，不可能到用户手里。

**追问**：*为什么不直接要求用户装 Python？*
> 会毁掉产品的第一印象。桌面 Agent 的用户预期是「双击就能用」。而且用系统 Python 还有依赖污染问题——用户环境里的包版本会和我们冲突。自包含运行时的代价是包体积（首次联网下载约 46MB），这个代价值得付。

#### Q2：$（系统设计题）本地桌面应用的 API 端口怎么保证安全？

> 见第七册 §18.10 Q2。核心是**两层**：CORS 显式白名单（给浏览器看）+ loopback 门禁（给机器看）。**只配 CORS 是不够的**——curl 完全绕过它。

#### Q3：多入口（GUI / TUI / CLI）怎么共享状态？

> 靠**一个后端进程** + **端口文件**互相发现。所以有个硬约束：后端必须单 worker（`workers=1`），因为引擎状态在进程内存里。
> 壳启动时先探测 3 秒，发现已有后端就**复用**而不是新拉一个。CLI 的 `attach` 也是连已有后端，`chat` 才是在本进程内起引擎。

#### Q4：终端和 GUI 的功能差异，是有意的还是没做完？

> **大部分是有意的**，但有一部分是**已知的维护成本**，我会分开说。
> 有意的：plan 审批、子代理地图、rewind 时间线这些需要「面板」的结构，终端里没法好好表达，所以设计上 TUI 就不做。
> 维护成本：引擎事件目前 20 个，GUI 基本全覆盖，TUI 显式只处理了 `permission_pending`，其余靠 `xy` 帧透传。**这意味着新增引擎事件时 TUI 不会自动跟上**——它不报错，只是没反应。这是真实的债，我不假装它不存在。

### 22.9 面试题 + 回答模板

**Q1（项目题）：你的前端状态管理怎么设计的？权威副本在哪？**
> zustand，`chatStore` 由 6 个切片拼装（`chatStore.ts:8-13`）。**权威副本分两层**：settings 在前端（localStorage，`settingsStore.ts:1020`），会话与消息在后端（`/v1/sessions`），前端 store 是镜像 + IndexedDB 缓存。**这个分层直接决定了『换入口丢数据吗』的答案**——settings 跟 origin 走会丢，会话跟 `~/.xeyo/` 走不丢。

**Q2（系统设计题）：SSE 断线了怎么办？**
> 自研解析（不用 `EventSource`），服务端给每个事件编号，客户端把游标写进 **sessionStorage**（`chatStream.ts:414`），重连时带 `?cursor=` 拉 `turns/current/events` **重放**（`:434-447`）。另外终止状态分「收到 `[DONE]`」和「被提前掐断」两种（`core.ts:416`）——**混为一谈就无法判断该不该提示重试**。

**Q3（追问）：前端和后端的权限档位命名对得上吗？**
> **完全对得上**，而且这一条我们专门核过：preset 是 `readonly/workspace-write/full` 两侧逐字一致，审批频率是 `always/risk/never` 两侧键集一致，全仓没有别名映射层。之前的『命名不一致』印象是**伪结论**（`01` §6.2 已结案）。**能主动说出「我们推翻过自己的一个待确认项」，比背一堆正确结论更值钱。**

**Q4（安全题）：微信通道进来的文本，你会当可信输入吗？**
> 不会。入站文本立刻过 `fence_remote_user_text(source="wechat")` 标记成不可信数据（`channels/runner.py:287`），走同一个引擎同一套围栏。而且我要主动说两条边界：通道包**没有独立审计层**（`grep audit` 零命中），也**不自带审批 UI**——权限事件发得出去，但有没有人在批取决于调用方。

**Q5（排错题）：用户说「微信里发消息没反应」，你怎么分层查？**
> 四层：① **通道层**——`ilink`/`filehelper` 的 `SeenIndex` 是否把消息当回声吞了（`seen.py:56` `peel_own_reply`）；② **队列层**——是否卡在 `InboundQueue` 的 busy session 上（`pop_idle` `:61` 只取空闲）；③ **任务层**——看 job 状态，`waiting_permission` 说明**卡在等审批**而不是没收到（`jobs.py:11`）；④ **引擎层**——才轮到主链。**顺序是从外往内，因为通道层的静默丢弃最容易被误判成「引擎坏了」。**

**另有两个正交的性能设施**，面试里可以拿来证明「性能是体系而不是零散优化」：

- **帧对齐批处理 `frameScheduler`**（`lib/frameScheduler.ts:41/45/50`）：一次 rAF 内**先跑完全部 read、再跑全部 write**（`:17-38`），避免读写交错触发强制同步布局。

> ⚠ **诚实边界**：仓库里**没有**基于 CPU / 内存 / 设备档位的「低端机自动降级」。降级只有两条路：系统 `prefers-reduced-motion` 与用户「流畅」开关（`streamSendSlice.ts:339` `isSmoothnessOn` 门控打字机）。被问「低端机怎么自动降级」时应直接说**没做**，而不是把 `prefers-reduced-motion` 说成硬件降级。

### 23.5 面试题 + 回答模板

**Q1：你们的消息列表是怎么做虚拟滚动的？为什么不用现成库？**
> 自研的，而且**按「轮」窗口化而不是按条**（`roundVirtual.ts:62`）。一轮 = 一条用户消息 + 它引发的所有 assistant 块；同一轮要么全挂要么全卸，不会出现「问题在、答案不在」的割裂。
> 没用 TanStack Virtual 的原因写在代码注释里（`roundVirtual.ts:9-11`）：虚拟列表要测高度，测高度要靠 ResizeObserver，而 ResizeObserver 回调里改 React state 会和布局形成反馈环、抖动。我们把**几何算成纯函数**（`computeRoundPrefix` 前缀和 + `roundWindowFor`），高度只存在 Map 里不回灌 state，实测回写时用 `captureViewportAnchor` 重对齐 `scrollTop`（`:87/110`）——**把「状态」和「几何」分开**是这套东西能站住的关键。
> 另外短列表根本不虚拟：`count <= 40` 直接全挂（`VirtualRoundList.tsx:40/109`）。虚拟化的收益要到几百轮才显现，为 20 轮的会话上虚拟列表是纯负债。

**Q2：流式输出每来一个 token 就 setState 会怎么样？你们怎么解决的？**
> 会打爆 React。我们做了三层：
> ① **按帧攒批**——delta 先累进 `pendingDelta`，用 rAF 每帧只 `set` 一次（`streamSendSlice.ts:651/684-805`），而且同帧的工具结果和文本一起结算；
> ② **Markdown 增量解析**——已封口的块缓存起来，每帧只重解析还没封口的尾块（`streamMarkdown.ts:590`、`incrementalBlockParse.ts:43-52`），已结束的消息进 LRU 200 的静态缓存（`markdownStaticCache.ts:21/75`）；
> ③ **代码高亮移出主线程**——Prism 跑在 Web Worker 里（`highlightWorker.ts`），主线程只管派发，而且布局忙的时候派发要排队（`highlightClient.ts:87`）。
> 有个小坑值得说：prism 在 Worker 里会注册自己的 message 监听然后 `JSON.parse` 崩掉，所以我们写了个 40 行的 `prismWorkerShim` 伪装一个最小 `document`（`prismWorkerShim.ts:1-40`）。

**Q3：zustand 的 store 你们拆了多少个切片？**
> 这里要小心别答错：`stores/chat/` 目录下有 13 个 ts 文件，但**真正的顶层切片只有 6 个**（`chatStore.ts:49-54` 展开）。另外三类混在同目录里——1 个子切片（`streamRecoverySlice.ts` 挂在 send 切片内部）、3 个**每轮新建的控制器**（`streamDrain.ts` / `streamToolSettle.ts` / `usageAccumulator.ts`，`streamSendSlice.ts:1059/550/372`）、3 个共享 helper。
> **划分标准是生命周期**：切片装长生命周期状态，控制器装「这一轮」的临时对象。如果把它们都做成全局切片，并发两轮时会互相踩。

**Q4：模型输出里的 HTML 你们怎么处理的？**
> 两道 rehype 插件分工明确：`rehypeSafeHtml` 是安全（`ALLOWED_TAGS` 白名单），`rehypeTailFade` 是视觉（尾部逐字降透明度做流式渐变）。
> 安全那边有一个细节值得讲：**危险标签是「连子树一起丢」而不是解包**（`rehypeSafeHtml.ts:41/87` `DROP_TAGS`）。解包看起来更「保内容」，但 `<script>alert(1)</script>` 解包后 `alert(1)` 会变成可见正文——**等于把攻击载荷渲染成了文案**。这是代码注释里自己写清楚的取舍。

**Q5（追问）：低端机你们会自动降级吗？**
> **不会，这个我没做。** 有的只是两条：系统 `prefers-reduced-motion`（`prefersReducedMotion.ts:21`）和用户侧的「流畅」开关（`streamSendSlice.ts:339`）。没有基于 CPU / 内存 / 设备档位的自动探测。硬要说的话，`frameScheduler` 和 `layoutBusy` 是常开的性能设施，但它们不是「降级」。
> 我认为这里该给的是**诚实**：把 `prefers-reduced-motion` 说成「硬件降级」在面试里一追就穿。
