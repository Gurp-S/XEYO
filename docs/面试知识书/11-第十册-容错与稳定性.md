## 第 25 章 · 容错与稳定性

### 25.1 定位：四种刹车 + 一条正交轴

容错不是「加 try/except」。XEYO 的容错面按**「拦什么」**分成四类，各自独立、互不替代：

| # | 刹车 | 拦的是什么 | 核心实现 | 归属功能 |
|---|---|---|---|---|
| 1 | **中止传播** | 用户/父级不想要了 | `engine/abort.py` | F007 |
| 2 | **预算硬停** | 停下来比继续更划算 | `engine/budget.py` | F008 |
| 3 | **LLM 重试** | 这次失败是暂时的 | `query_loop.py:263-1264` | F006（第一册已述，本册讲成本视角） |
| 4 | **重复抑制** | 模型在原地打转 | `engine/repeat_guard.py` + `repeat_fold.py` | F011（第五册已述） |

**正交的那条轴是「恢复」**——刹车之后怎么收拾残局：**续跑指令（F013，投影-only）** + **轮次快照（F012，崩溃恢复）** + **配对修复（F005）**。三者共同保证「停下来了，但历史仍然合法、可以接着走」。

**这一章的组织逻辑**：先讲四类刹车（25.2–25.5），再讲恢复轴（25.6–25.8），最后讲它们与 S26 后台任务的交叉（25.9）。

### 25.2 F007 · 中止传播：`LinkedAbortController` 的父子语义

**这是个只有 40 行但设计很精确的模块**（`engine/abort.py`）：

| 符号 | 位置 | 语义 |
|---|---|---|
| `Aborted` | `:5` | 异常类；`query_loop` 捕获后转 `StoppedEvent` |
| `AbortController` | `:9` | `aborted`（`:15`）/ `abort()`（`:19`）/ `raise_if_aborted()`（`:27`） |
| `LinkedAbortController` | `:33` | **子控制器**：`aborted` 继承父级（`:41`），`abort()` 不污染父级 |

**关键设计：方向是单向的。**

```
父 abort()  →  所有 Linked 子控制器 aborted = True（级联下去）
子 abort()  →  父不受影响（局部超时不会把整轮砍掉）
```

**这就是「单个工具超时」与「用户打断整轮」能被区分开的原因**：

- 工具执行拿到的是一份**子控制器**（`tool.execute(..., AbortController())` 形态）；
- 某工具自己超时 → 只 abort 自己那份 → 兄弟工具照跑；
- 用户按打断 → abort 父 → 级联把所有子工具一起带走。

**轮级检查点**（`query_loop.py:797`）：

```python
while True:
    if abort.aborted:
        yield StoppedEvent(reason="aborted")
        return
```

> **为什么是「每轮检查」而不是「每步检查」**：主循环的检查点密度是**性能与响应性的取舍**。每轮检查意味着「响应延迟 ≤ 一个 step」，而 step 本身被工具超时（S40）与子 abort 兜住。**两层刹车叠加，不必在每行加检查。**

> ⚠ 注意 `LinkedAbortController.aborted` 是**属性覆写**（`:41`）而非新增字段——即 `aborted` 的语义变成「自己或父级任一为真」。这是个很干净的做法，但读代码时容易看漏（`abort.py` 全文只有 40 行，`LinkedAbortController` 只覆写了一个属性 + 一个方法）。

### 25.3 F008 · 三轴预算：不是「一个 token 上限」

`engine/budget.py` 的预算**不是单一数值**，而是多轴 + 一个「宽限窗」模型：

| 轴 | 默认 | 环境变量 | 位置 |
|---|---|---|---|
| **回合数** | **256** | `XEYO_MAX_TURNS` | `:19/59-60` |
| **工具调用数** | **64** | `XEYO_MAX_TOOL_CALLING` | `:24/64-65` |
| **token** | `None`（不限额） | — | `:116/450` |
| **USD** | `None`（不限额） | `XEYO_BUDGET_DEFAULT_USD` / `XEYO_MAX_BUDGET_USD` | `:68/87-89` |
| **墙钟** | **默认关**（`XEYO_WALL_HARD_STOP=0`） | `XEYO_WALL_HARD_STOP` | `:43/142/160-168` |

**宽限窗模型（这是本章最值得讲的设计）**：

```
软上限首次触发
   → MAX_GRACE_TURNS = 3（:25）的收尾窗口打开
      ├─ 窗口内：模型被允许「把话说完」（forced_wrap_up = True）
      └─ 窗口耗尽 → _hard_stop_reason = grace_reason or "max_turns"（:270-272）
                     → StoppedEvent(reason=hard_stop_reason)
```

**为什么需要宽限窗**：如果在第 256 轮**当场**切断，模型的最后一条消息可能只写了一半——用户看到的是「半句话」。给它 3 轮的收尾窗，让它**自己收敛**，这是「**引擎不导演、但给足收尾空间**」的体现。

**单点出口**：`hard_stop_reason` 属性（`:349-351`）是**唯一**读硬停原因的地方，`query_loop.py:806` 消费它。

**收尾窗的配套动作**（`query_loop.py:801-812`）：

| 动作 | 位置 | 说明 |
|---|---|---|
| `forced_wrap_up` 置位 | `:801` | 标记「已进入收尾」 |
| `_publish_wrap_guide(...)` | `:809` | 发布**缺口清单 + 剩余配额**（T_now 的 `wrap_up` 块消费） |
| 收尾广播（工具层只读信号） | `:814+` | 窗口内**长命令自动后台化**，把窗口留给落盘 |
| 二次进入仍无文本 → 硬停 | `:806-808` | 维持原语义，不无限宽限 |

> **「收尾窗内把长命令后台化」这个小设计很值得说**：收尾窗的目的让模型落盘，而一个长命令会把窗口白白吃掉。工具层收到「收尾中」的只读信号后改走后台——**信号是事实（窗口开了），动作在工具层**，符合引擎理念（限制只在执行层表达）。

**⚠ 诚实点**：**墙钟硬停默认关**，`USD` 预算默认 `None`。所以**开箱即用的硬顶其实只有「256 轮」和「64 次工具调用」两个**。讲的时候不要说「我们有多轴预算」而不说默认值——那是把能力说成了默认行为。

**另一个细节**：`MAX_TOOL_CAP_STREAK = 2`（`:30`）——连续 2 轮触顶才升级处理，避免「某一轮偶然多调一次」就误伤。

### 25.4 重试：判据比退避更重要

退避曲线是次要的，**能不能重试**才是关键（`query_loop.py:1243`）：

```python
if not (failure.retryable and not saw_any and attempt < _llm_max_attempts()):
    if <empty> : raise EmptyResponseError()
    else: raise <原异常>
```

**三个条件缺一不可**：

| 条件 | 含义 | 为什么必须有 |
|---|---|---|
| `failure.retryable` | 这次失败**可重试**（网络/5xx，而非 400 参数错） | 重试不可重试的错误是纯浪费 |
| **`not saw_any`** | **本次尝试一个 chunk 都没吐出来** | ⭐ 见下 |
| `attempt < _llm_max_attempts()` | 没到上限 | — |

**⭐ `not saw_any` 是这段代码里最有价值的判断**（`:1135/1143/1158`）：

> 如果模型**已经吐了一部分**（比如 200 token）然后连接断了，**绝不重试**。
> 理由：重试会让用户看到**两段重复输出**，而且第一段可能已经被下游（SSE 订阅者 / transcript）消费掉了——重试会制造「同一轮有两个版本」。
> **宁可把这次判为失败，也不制造不一致的历史。**

**退避**（`:273-281`）：本地 `0.5 × 2^(attempt-1)`，上限 **10s**，加 **10% jitter**；若厂商给了 `Retry-After`，**取较大者**。上限 5 次（`:265-270`，`XEYO_LLM_MAX_ATTEMPTS` 覆盖，钳制 `[1,5]`）。

**事件透出**：`LlmRetryEvent`（`:1255`，含 `next_retry_ms` / `code`）在 sleep **之前**发，`LlmRetryStartedEvent`（`:1264`）在 sleep **之后**发——**UI 因此能显示倒计时**。这是「事件设计要考虑消费方时序」的好例子。

**重试失败的审计是 best-effort**（`_audit_llm_failure:292`）：审计写失败不挡主路径——**重试路径上任何非核心动作都不该成为新的失败源**。

### 25.5 重复抑制：三道防线，全部「永不拒执行」

第五册已述 C1/C2 压缩与两道防线，这里从**容错**角度看它们的**共同红线**：

| 防线 | 位置 | 触发条件 | 动作 |
|---|---|---|---|
| `RepeatCallGuard` | `repeat_guard.py:189/220` | 同**语义 key** 反复调用，档位 `(3, 5, 8)`（`:39`） | 逐档**建议**（`publish_advice:86`） |
| `ZeroHitTracker` | `:291` | 换着花样查但**全部零命中**，`ZERO_HIT_ADVICE_AT = 2`（`:288`） | 提示「换签名也没用」 |
| `IdenticalResultFold` | `repeat_fold.py:81/97` | 同签名 + 输出**逐字节相同**连续 ≥ 3（`DEFAULT_FOLD_AFTER:32`） | **折叠**成一行 |

**三条共享的红线：永不拒绝执行。**

> 这是 XEYO 理念（AGENTS.md 铁律 3）最直接的落地：**引擎可以「折叠结果」「发一句事实」，但不能替模型决定「这次调用不许执行」。**
> 对比一下常规做法——大多数 Agent 框架在检测到重复调用时会直接返回缓存或报错。XEYO 的选择是：**结果照给，但让模型看见「这是第 3 次相同结果」**。这是个**产品/理念层面的取舍**，不是技术能力差异。

**语义 key 怎么算**（`semantic_key:165`，这是「不误伤」的关键）：

| 工具 | 归一化 |
|---|---|
| Grep / Glob | 去引号包裹、path 做 `normcase` + `normpath`、`output_mode` 补默认值 |
| 其他 | `canonical_input` 精确相等 |

**豁免**（`EXEMPT_TOOLS:37`）+ **分页续读豁免**（`is_pagination_continuation:146`）——「翻下一页」和「重复同一个查询」在语义上完全不同，必须分开。**这是「误伤率」设计的核心**：宁可漏报，不可错杀。

`_equiv_enabled`（`repeat_fold.py:68`）受 `XEYO_LOOP_LEDGER` 控制——折叠与 LoopLedger（第九册 22.4）是同一消费面的两个动作。

### 25.6 F013 · 续跑指令：投影-only，不落库

`engine/resume_directive.py` 全文只有 30 行 + 一段 docstring，但解决的是一个**真实事故**：

| 符号 | 位置 |
|---|---|
| `_cv: ContextVar[str \| None]` | `:16` |
| `set_resume_directive(text)` | `:19` |
| `get_resume_directive()` | `:25` |
| `clear_resume_directive()` | `:30` |

**机制**：

```
用户发「继续」
  → 引擎生成**富化续跑指令**（含上下文、目标、断点）
  → submit_options["resume_directive"] 传入
  → T_now 注入管线在**本轮每次 model 调用前**送达
  → 轮结束 → clear_resume_directive()
```

**关键在「不落库」**（docstring `:1-10` 原文口径）：

> 富化指令**不再落库成真实 user 消息**——JSONL / 历史只存用户真实文本（如「继续」）。

**为什么这是必须的（治理目标 = 跨任务锚定）**：

> 旧任务的续跑指令如果以**用户身份永久留在历史里**，会在**后续新任务中被模型重新读取**。模型会以为「用户刚刚让我继续那个旧任务」——这是与 **L543（跨任务幽灵引用，见第九册 23.5）同族**的事故。

**所以这是一个「让信息只活一轮」的设计**：`ContextVar` 默认 `None`，轮结束即清。**两种声道都不落库**（`env_channel` 下随伪造 tool 对；`legacy` 下随尾插）——声道变了，不落库的保证不变。

> **面试价值极高**：这是一个「**为了不让引擎的辅助文本变成历史包袱，宁可不持久化**」的判断。绝大多数人会把「富化指令」当普通消息存下来，然后在新任务里被咬。能说清这个坑，说明你理解**上下文是有成本的，也是有副作用的**。

### 25.7 F012 · 轮次快照 + F005 · 配对修复：恢复轴的两层

**刹车之后要恢复。** 恢复轴有两层，**一层管运行期，一层管重启**：

| 层 | 机制 | 位置 | 管什么 |
|---|---|---|---|
| **运行期** | `_repair_unpaired_tool_calls` | `query_loop.py:218` | 内存 store 里，为**没有 tool_result 的 tool_use** 插入 `[tool aborted]` |
| **重启后** | `_repair_unclosed_tool_uses` | `session/hydrate.py:73` | 磁盘 transcript 里，为未闭合 tool_use 合成确定性结果 |

**为什么必须修**：**厂商 API 硬约束——assistant 的 `tool_use` 必须有配对的 `tool_result`**。少一条就直接 400。中断、崩溃、Plan 被拒都会造成「有 use 无 result」。

**两层的错误语义不同（这是个精细的取舍）**：

| 场景 | 合成结果 | 理由 |
|---|---|---|
| 只读工具未启动 | `TOOL_NOT_STARTED` | 可以确定「没发生副作用」 |
| 其他工具未启动 | `TOOL_OUTCOME_UNKNOWN` | ⭐ **不能假设没发生**——写操作可能已经落盘 |

> **这个区分是容错设计里最容易被忽略的一点**：恢复时**不能默认「没跑完等于没跑」**。对写工具，未知就是未知，必须如实告诉模型。

**调用密度也做了取舍**（`query_loop.py:794-795` 注释）：

```python
# 配对修复只在 submit 入口（及 abort 路径的 _fill_missing）做一次，
# 不在每轮模型请求前全量扫 store。
_repair_unpaired_tool_calls(store, "aborted")
```

即：**代价可控（一次扫）优先于绝对严密**——因为「未配对」只可能在少数几个入口产生，不需要每轮防御。

**`TurnSnapshot`（F012）**（`engine/turn_snapshot.py`）：

| 字段 | 位置 | 说明 |
|---|---|---|
| `status` | `:35` | 默认 `succeeded`；活动态集合 `_ACTIVE`（`:48`） |
| `incomplete_tool_uses` | `:40` | 快照里的「未闭合工具调用」清单（与 hydrate 层联动） |
| `path_for` / `hydrate` | `:74/78` | 定位与读取 |
| `flush` | `:122` | **原子写：tmp + `os.replace`（`:135`）** |
| `clear` | `:142` | 正常结束后清除 |
| `list_recoverable` | `:151` | 列出「活动态或 `recovery_required`」的快照 |
| `mark_crashed_as_recovery` | `:167` | 重启后把 `running/stopping/queued` → `recovery_required`；`waiting_permission` 另有一条（`:177-178`） |

**与 S24 rewind 的 `mark_crashed_rewinds`（第七册 16.4）是同构的两个机制**：都在 lifespan 里、都把「崩溃残留」标成「需要人决定」。**面试里把这两个并列讲，能体现「同一套崩溃语义被复用了两次」。**

> ⚠ **`waiting_permission` 单独处理是个好细节**：等待用户审批时进程重启，语义与「跑到一半崩了」不同——它没有中间副作用风险，所以标记也走独立分支。这类「同一状态的不同崩溃含义」是容错设计里最见功力的地方。

### 25.8 S26 交叉：后台任务的两条容错边界

第七册已讲 S26 的结构（`job_registry.py` / `turn_settlement_hub.py`），这里补**容错视角**的两条：

**① 后台 job 的硬上限（本册修正一条过时叙述）**

| 项 | 值 | 位置 |
|---|---|---|
| 上限 | **6 小时**（`JOB_NO_TIMEOUT_MS = 6 * 3600_000`） | `server/job_registry.py:43` |
| 可配 | `XEYO_JOB_MAX_TIMEOUT_MS` | `:46-59` |
| 执法（正常路径） | 传 `timeout_ms` 给 `run_command`（`:275`） | — |
| 执法（adopt 路径） | 独立 deadline 忙等 + 超时 `handle.kill()` + 返回 `job exceeded max runtime` | `:335-352` |

代码注释（`:40-42`）**自述了改动原因**：

> ……根本不检查它——等于事实上无上限。runaway job（例如卡在等 stdin）会让该忙等线程永远转下去。改为可配置的 6h 上限：足够长，不破坏「后台可长跑」的产品承诺，同时挡住真正的僵尸。

> ⚠ **N10-1（本册修正的项目既有叙述）**：`01` §6.2 的 C-09 与 `08-第七册` 的 N7-2 都把「后台 bash job」列为「**事实上的无超时**」。**实测已不成立**——现在有默认 6h 上限且两条路径都执法。C-09 的**其余部分（不经权限 / rewind / 审计）仍然成立**，但「无事实超时」这一子项**已被修复**。本册与 `01`/第七册已同步更正。

**② 后台 job 的 abort 是独立的**

`server/job_registry.py:255` 的注释写得非常明确：

```python
"""Bash 生产方：独立本地 abort（kill 走 job_kill；会话 abort 不杀 job）。"""
```

> **这是刻意的**：后台任务的产品语义就是「你去做你的事，我不因为它占着轮次而杀掉它」。所以**会话 abort 不会级联到后台 job**，要停它必须显式 `job_kill`。
> 代价：**用户按「打断」时后台 job 还在跑**。这个取舍必须主动说明，否则会被当成 bug。

**唤醒而不是轮询**：`consume_wake`（`:595`）——后台任务完成时唤醒正在等待的 Agent。整条路径挂在**回合结算枢纽**（`turn_settlement_hub.py:22`，单一槽 + 三租户 inbox/goal/jobs 分发，异常全隔离）。**这是「异步完成」与「同步对话」之间的桥**。

### 25.9 设计取舍汇总

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| abort 父子 | **单向级联**（子不污染父） | 双向共享 | 要区分「单工具超时」与「整轮打断」 |
| abort 检查密度 | **每轮检查** | 每步检查 | 性能；step 已被工具超时与子 abort 兜住 |
| 预算耗尽 | **3 轮宽限窗** | 当场切断 | 当场切会留半句话，给模型自收敛的空间 |
| 收尾窗内长命令 | **工具层自动后台化** | 直接禁止长命令 | 信号走事实、动作在执行层（引擎理念） |
| 部分流后失败 | **不重试**（`not saw_any`） | 重试以「补齐」 | 重试会产生两段重复输出 + 两版历史 |
| 重复检测 | **只建议 / 只折叠，永不拒执行** | 返回缓存或报错 | 理念铁律 3：限制只在执行层，不替模型决策 |
| 重复判定 key | **语义归一化 + 分页豁免** | 字面相等 | 宁可漏报，不可错杀 |
| 续跑富化指令 | **投影-only，不落库** | 存成 user 消息 | 防跨任务锚定（L543 同族事故） |
| 未闭合工具结果 | 只读 → `NOT_STARTED`；其他 → `OUTCOME_UNKNOWN` | 统一「未执行」 | 写操作的副作用不可假设为未发生 |
| 配对修复时机 | **submit 入口一次** | 每轮全量扫 | 代价可控优先于绝对严密 |
| 后台 job 上限 | **6h**（可配） | 不检查（原有） | runaway job 会让忙等线程永远转 |
| 后台 job 与会话 abort | **不级联** | 一起杀 | 后台的产品语义就是脱离轮次存活 |

### 25.10 面试题 + 回答模板

#### Q1：$ 用户点了「打断」，你怎么保证干净地停下来？

> 四件事：**方向、密度、清理、恢复**。
> 方向：abort 是**单向级联**的——`LinkedAbortController`（`abort.py:33`）的 `aborted` 继承父级，但子 abort 不污染父。所以「某个工具自己超时」不会把整轮砍掉，「用户打断」才会级联到所有子工具。
> 密度：主循环**每轮检查一次** `abort.aborted`（`query_loop.py:797`），不在每步插检查——step 层已经被工具超时和子 abort 兜住了。
> 清理：打断后内存里可能留下「有 `tool_use` 没有 `tool_result`」的消息，这在厂商 API 是硬错误。所以有一层配对修复（`query_loop.py:218`）补一条 `[tool aborted]` 的错误结果。
> 恢复：如果进程在打断过程中崩了，磁盘那边还有一层（`hydrate.py:73`）在 hydrate 时补未闭合的 tool_use——而且**只读工具标 `NOT_STARTED`，其他标 `OUTCOME_UNKNOWN`**，因为写操作不能假设「没跑完就等于没发生」。
>
> **追问**：*后台任务也会被一起打断吗？*
> **不会**，这是刻意的。`job_registry.py:255` 的注释写得很直接：「独立本地 abort（kill 走 `job_kill`；会话 abort 不杀 job）」。因为后台任务的产品语义就是「脱离轮次存活」。要停它必须显式调 `job_kill`。代价是用户按打断后后台还在跑——这是取舍不是 bug。

#### Q2：预算超了怎么处理？直接切断吗？

> 不直接切，有 **3 轮宽限窗**。
> 软上限一触发就打开窗口（`MAX_GRACE_TURNS = 3`，`budget.py:25`），窗口内模型可以「把话说完」；窗口耗尽才置 `hard_stop_reason` 并停（`:270-272`），硬停原因从唯一出口 `hard_stop_reason`（`:349`）读出。
> 为什么给窗口：当场切断会留下半句话。这个设计符合我们的引擎理念——引擎不导演模型怎么收尾，但**给足收尾空间**。
> 配套还有两个小设计：进窗时会发布「缺口清单 + 剩余配额」（`query_loop.py:809`，T_now 的 wrap_up 块消费）；并且**收尾窗内长命令自动后台化**，把窗口留给落盘而不是等着跑命令。
> **诚实补一句**：多轴预算里**墙钟硬停默认是关的**，USD 预算默认 `None`。开箱即用的硬顶实际只有「256 轮」和「64 次工具调用」两项。我不会说「我们默认有全方位预算」。

#### Q3：$ 模型吐了一半突然断了，你会重试吗？

> **不会**。重试判据里有三个条件（`query_loop.py:1243`）：可重试、**没吐过任何 chunk（`not saw_any`）**、没到尝试上限。`not saw_any` 是刻意加的。
> 理由：如果已经吐了 200 token，重试会让用户看到**两段重复输出**，而且第一段可能已经被 SSE 订阅者或 transcript 消费了——重试等于制造「同一轮有两个版本」。**宁可标记失败，也不制造不一致的历史。**
> 退避本身是小事：本地指数退避封顶 10s + 10% jitter，厂商给 `Retry-After` 就取较大者，最多 5 次。另外两个重试事件分别发在 sleep 前后，UI 才能显示倒计时。

#### Q4：$ 模型反复调用同一个工具，你怎么处理？

> 三道防线，**共同的红线是「永不拒绝执行」**：`RepeatCallGuard` 在 3/5/8 次时逐档**建议**；`ZeroHitTracker` 检测「换着花样查但全部零命中」；`IdenticalResultFold` 把「同签名 + 输出逐字节相同」连续 3 次的结果**折叠**成一行。
> 都不阻止执行。`repeat_fold.py` 和 `repeat_guard.py` 里都明确写着这个约束。
> 原因是引擎理念：**限制只在执行层表达，引擎不替模型做决策**。我们不会「检测到重复就返回缓存」——结果照给，但让模型看见「这是第 3 次相同结果」这个事实。
> 另外为了不误伤，判定用的是**语义 key**（Grep/Glob 会归一化引号、路径、默认参数），而且**分页续读豁免**（`is_pagination_continuation:146`）——「翻下一页」和「重复同一查询」语义完全不同。这里宁可漏报，不可错杀。

#### Q5：$ 你们的「继续」功能有什么坑？

> 坑在**跨任务锚定**。如果「继续」的富化指令（带上下文、目标、断点）**以用户身份存进历史**，那在后续新任务里模型会重新读到它——以为「用户刚刚让我继续那个旧任务」。这跟我们漂移判定里的 L543（跨任务幽灵引用）是**同族事故**。
> 所以我们的续跑指令是**投影-only**：`resume_directive.py` 用 `ContextVar` 存，经 T_now 在本轮每次模型调用前送达，**轮结束立即清**；JSONL 里只存用户的真实文本（就是「继续」两个字）。
> 这个设计的要点是：**信息可以有作用域，作用域到轮为止**。不是所有进过上下文的东西都该被持久化。
