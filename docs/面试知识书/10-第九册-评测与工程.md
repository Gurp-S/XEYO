## 第 22 章 · 用量、审计与可观测（S35 / S36 / S41）

### 22.0 定位：三个问题，三条互不相通的管道

这一章讲三件经常被混为一谈的事：

| 系统 | 回答的问题 | 数据落点 | 谁消费 |
|---|---|---|---|
| **S35 用量与成本** | 这次花了多少钱、花在哪个模型上 | `~/.xeyo/usage/events.jsonl` | 用户（`/v1/usage`）、预算 |
| **S36 审计** | 谁在什么时候请求了什么权限、跑了什么工具 | `xeyo_data_root()/audit/audit.jsonl` | 合规查询（`/v1/audit/events`） |
| **S41 可观测性** | 循环是否在重复、进程有没有泄漏、哪个阶段慢 | 内存 + prompt 注入 | 引擎自身（**不是人**，见 22.4） |

**它们不共用载体、不共用端点、不共用锁**。面试里如果把这三者讲成「一套可观测体系」就会失真——它们只是**同一层能力域的三个独立实现**。

### 22.1 S35 · 成本流转链：上报 → 归因 → 合并

**完整链路（带行号）**：

```
模型适配器（deepseek.py:106 / openai_compat.py:219 / anthropic.py:544）
  └─ record_from_openai_usage(usage, ...)        usage/ledger.py:45
       └─ _append(...)  open("a") + _lock        usage/ledger.py:133 / :136
            └─ ~/.xeyo/usage/events.jsonl        usage/ledger.py:27
canonical_vendor(...)  真实厂商归因              usage/attribution.py:153
compose_usage_report(vendor, local)              usage/combine.py:45
  └─ GET /v1/usage                               server/routers/usage.py:30
```

**三条最容易讲错的事实**：

**① 计费按 `vendor`，不按 `provider`**（`usage/ledger.py:88/95`）。
「通道」和「厂商」是两回事：同一个 OpenAI 兼容通道可以指向 DeepSeek、Qwen 或自建网关。若按通道计费，就会出现「用 DeepSeek 的 token 套 OpenAI 的价」。所以账本字段是 `vendor`，由 `canonical_vendor` 做三级回落：

| 级 | 判据 | 位置 |
|---|---|---|
| 1 | `local` / `fake` → 直接判定 | `attribution.py:153` |
| 2 | **base_url 主机名** → 厂商（`api.deepseek.com` → deepseek） | `_HOST_VENDOR:27` |
| 3 | **模型名前缀**（`deepseek` / `gpt` / `qwen`…） | `_MODEL_PREFIX_VENDOR:45` |
| 4 | 回退通道名 | 同上 |

读旧账本时若缺 `vendor` 字段，`event_vendor:177` 会**现场推断**——这是「防迁移遗漏」的兼容设计。

**② 定价表是「低峰价 + 倍率」，不是一个价**（`usage/pricing.py:26-29`）：

```python
# (cache_hit, cache_miss, output) 元 / 百万 token
_DEEPSEEK = {
    "flash": ((0.05, 1.5, 4.5), (0.10, 3.0, 9.0)),   # (低峰, 高峰)
    "pro":   ((0.15, 4.5, 13.5), (0.30, 9.0, 27.0)),
}
```

- 高峰窗口：**北京时区 09:00–12:00、14:00–18:00**（`_DEFAULT_TIME_TIERS:51-58`）。
- 高峰倍率 **2.0**（`multipliers.peak`），低峰 1.0。
- 窗口与倍率可用 `XEYO_TIME_TIERS_JSON` 整体覆盖（`:63`）——**厂商改窗口不用发版**，这是「把易变的商业规则做成配置」的标准做法。

**③ 厂商权威只在能拿到时才生效**（`combine.py:45-62`）：

```python
vendor_ok = bool(vendor.get("vendor_ok"))
use_vendor_core = vendor_ok and report_has_usage(vendor)
core = vendor if use_vendor_core else local
source = "vendor" if use_vendor_core else "local"
```

> ⚠ **N9-1（实测，与「双口径」叙述不符）**：`usage/vendor.py:319` `_fetch_deepseek` **硬编码 `vendor_ok=False`**（DeepSeek 未开放历史用量接口），`_fetch_openai:379` 才真的 GET `/organization/usage/completions`。
> **结论**：对 DeepSeek（项目的主力模型）而言，「厂商权威用量」**永不生效**，`/v1/usage` 事实上一直回退本地账本。面试若被问「你们怎么和厂商对账」，正确答案是「**OpenAI 通道能对，DeepSeek 通道对不了，所以本地账本是唯一口径**」——而不是「我们以厂商为准」。

**多代理成本**单独落 `~/.xeyo/metrics/multi_agent.jsonl`（`multi_agent_metrics.py:26`，`record_subagent_usage:171` 带 `agent_id`）——**与计费账本物理分离**。理由：计费要「按会话/按 key 汇总」，多代理要「按 agent 归因」，两个维度混在一张表里查询会互相污染。

**端点**（`server/routers/usage.py`）：`GET /v1/models`（`:15`）· `GET /v1/usage`（`:30`，vendor + local + compose）· `GET /v1/usage/balance`（`:67`，仅 DeepSeek `/user/balance`）。

> ⚠ 两个工程细节：`_read_events` 有 `_MAX_LINES = 80_000` 上限（`ledger.py:16`），**逐行读到第 8 万行就 `break`**（`:166-167`）——即**保留的是最早 8 万行、更晚的记录读不到**（不是「取最近 8 万行」），长期使用需注意口径；并按 mtime+size 缓存（`:142-157`）。锁是 `threading.Lock`（`:15`），**只保证进程内线程安全**，跨进程并发写 JSONL 不保证原子。

### 22.2 S36 · 审计：最小事件集 + 命令摘要是脱敏边界

**最小事件集只有 5 类**（`audit/log.py:3-5`）：

```
permission.pending · permission.resolved · permission.denied
tool.started · tool.finished
```

**为什么「最小」是优点**：审计日志会长到无限（**无轮转**，见下），事件类型越多、噪声越大。只记「谁要权限、准没准、跑了什么工具」——这恰好覆盖了「事后追责」的最小充分集。

**调用方（生产环境）**：

| 事件 | 发出点 |
|---|---|
| `tool.started` / `tool.finished` | `tools/tool_registry.py:140/151/169` |
| `permission.*` | `engine/permission_coordinator.py:100/174`；`permissions/store.py:180/351/398`；`permissions/workspace_policy.py:132`；`permissions/bash_policy.py:412` |

**脱敏规则**（`audit/redact.py:11-23` `_SECRET_RX`）：覆盖 `Bearer <tok>`、`api_key/token/secret/password/authorization=` 赋值、`sk-/pk-/ghp-/glpat-/xox-` 前缀、`AKIA…`、`AIza…`、`eyJ….`（JWT）、`-----BEGIN…-----`（PEM）、长 hex。命中 → `***`；命令另做 **200 字符截断**（`command_summary:46`）。

> ⚠ **N9-2（实测，脱敏不递归）**：`scrub_audit_fields`（`redact.py:56-67`）**只对顶层已知字符串键**（`command` / `prompt` / `tool_input` / `content`…）做脱敏，**不递归进 `tool_input` 对象内部**。
> 后果：`{"tool_input": {"headers": {"Authorization": "Bearer sk-..."}}}` 里的密钥**不会被替换**（因为脱敏函数把 `tool_input` 当作一个值处理，而正则若不匹配嵌套结构就漏过）。
> 面试口径：能主动说「我们的脱敏是**顶层字段级**、不是深度遍历，嵌套在对象里的凭据是已知缺口」，比声称「全部脱敏」安全得多。

> ⚠ **N9-3（实测，审计无轮转）**：`audit/log.py` 只有 append（`:41-44`），**没有大小/日期轮转**（对比：usage ledger 至少有 `_MAX_LINES`）。`audit.jsonl` 会无限增长。docstring `:8` 自己也标注了「跨进程不保证」。

### 22.3 S36 · 查询：坏行容忍 + 前缀语义

`audit/log.py`：

| 能力 | 位置 | 说明 |
|---|---|---|
| 排除坏行 | `:59`（`read_all`）/ `_read` | 单行 `JSONDecodeError` 跳过，**不让一行坏数据毁掉整个查询** |
| kind 前缀匹配 | `:90` | 以 `.` 结尾的 kind 视为前缀（`permission.` → 匹配全部 permission.*） |
| 时间窗 + 分页 | `:63-110` | 新→旧，支持 session_id / kind / 时间窗过滤 |
| 落点 | `:117-125` | `XEYO_AUDIT_LOG` 覆盖，默认 `xeyo_data_root()/audit/audit.jsonl` |

**面试点**：「坏行容忍」是 JSONL 作为日志载体的必备属性——进程在写一半时崩溃会留下半行 JSON。**读的时候必须假设文件里存在垃圾**，这与第五册 transcript 的「崩溃修复」是同一类思路。

### 22.4 S41 · 可观测性：一条真正的「不给人看」的观测线

**这是本册最反直觉的一节**，也是最能体现「引擎理念」的一节。

先看四个组件的**真实消费方式**：

| 组件 | 位置 | 产出 | 谁消费 |
|---|---|---|---|
| `LoopLedger` | `engine/loop_ledger.py:106` | 三信号计数（s1 结果等价 / s2 内容已见 / s3 首句重复） | ⭐ **`query_loop.py:781` 持有 → `render():207` → `pre_llm_inject.py:1092` 注入给模型** |
| `IdenticalResultFold` | `engine/repeat_fold.py:81` | 折叠计数 | 与 `LoopLedger` 同一消费面（消融开关 `XEYO_LOOP_LEDGER`，`repeat_fold.py:69`） |
| `prof_stats` | `engine/prof_stats.py:13/25` | `{count,min,mean,p50,p90,p95,p99,max}` | ⚠ **当前无实时消费方**（docstring 写「报告脚本消费」） |
| `stage_clock` | `engine/stage_clock.py:14/40/55/65` | 命名阶段耗时（ms），经 `sink` 回调 | ⚠ **当前无实时消费方** |
| `process_ledger` | `engine/process_ledger.py:134/200/237` | PROC / PORT / LOCK 生命周期台账 | ⚠ **仅 CLI `selfcheck`/`snapshot`（`:374`）+ `leftovers()` 诊断；受 `XEYO_PROC_LEDGER` 门控，默认关**（`bash_tool/runner.py:312`） |

**这一节的教学价值在于那个「⭐」**：

> **XEYO 的可观测性产物，第一消费对象是模型，不是人。**
> `LoopLedger.render()` 输出**不超过 3 行纯计数**（`loop_ledger.py:207`），经 T_now 注入管线进上下文。模型看到的是「事实」——「这个工具的第 3 次调用返回了逐字节相同的结果」。它**不评价、不建议**，是否改变策略由模型自己决定（AGENTS.md 理念铁律 1/2）。
> 换句话说：**这套「监控」的意义不是让人看仪表盘，而是让引擎把「你正在重复」这个事实以最便宜的方式告诉模型。**

**工程细节**：

- `prof_stats.percentile`（`:13`）用 **nearest-rank** 而非插值——分位数实现最简、无歧义，适合小样本。
- `stage_clock` 的阶段名**由调用方任意定义，无固定枚举**（docstring）——不预设「哪些阶段该被计时」，避免把阶段划分写死在库里。
- `process_ledger.sweep`（`:237`）**孤儿回收 + 60s grace**；`reap`（`:200`）先 probe：死 → 静默除名，活 → cleanup；Windows 走 `taskkill /T /F`（`:100`）。

> ⚠ **N9-4（实测，S41 大半未接线）**：`prof_stats` / `stage_clock` / `process_ledger` 在 `python/` 内**没有实时消费方**（`stage_clock` 的 docstring 明写「query_loop 收口后接入」）。而且 `server/routers/audit.py:14` **只暴露 permission/tool 事件，不承载任何 S41 指标**。
> **所以「我们有一套可观测体系」这句话必须拆开讲**：真正在产线跑的是 **LoopLedger 一条线**（而且它的第一消费者是模型）；其余三个是「已实现、有单测、待接线」。

### 22.5 设计取舍汇总

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| 计费维度 | 按 `vendor` | 按 `provider`（通道） | 同一兼容通道可指向不同厂商，按通道套价会算错钱 |
| 价格来源 | 低峰基价 + 倍率表（可 env 覆盖） | 硬编码单一时价 | 厂商改峰谷窗口不需要发版 |
| 厂商对账 | 能拿则用、拿不到回退本地 | 强制以厂商为准 | DeepSeek 不开放接口（`vendor.py:319` 实证） |
| 多代理成本 | **独立文件** | 混进计费账本 | 归因维度不同，混表互相污染 |
| 审计事件集 | **最小 5 类** | 全量记录 | 日志无轮转，越少越能长期用 |
| 审计脱敏 | 顶层字段级 | 深度递归 | ⚠ 事实上的折损（N9-2），但实现简单、无性能风险 |
| 循环观测 | **注入模型**（≤3 行事实） | 落盘给人看 | 引擎理念：能进注意力的只有信息，且「能静默就不说话」 |
| 分位数算法 | nearest-rank | 线性插值 | 小样本下无歧义、实现最简 |

### 22.6 面试题 + 回答模板

#### Q1：Agent 的成本怎么算准？你怎么保证不套错价？

> 三件事：**归因、时价、合并**。
> 归因：我们**按 `vendor` 计费而不是按通道**——因为同一个 OpenAI 兼容通道可以指向 DeepSeek、Qwen 或自建网关，按通道套价会算错钱。厂商判定是三级回落：`base_url` 主机名 → 模型名前缀 → 通道名（`attribution.py:27/45/153`）。
> 时价：定价表是「**低峰基价 + 峰谷倍率**」，高峰窗口（北京 09–12/14–18）倍率 2.0，且窗口与倍率可以用环境变量整体覆盖，厂商改规则不用发版（`pricing.py:51-71`）。
> 合并：能拿到厂商权威数据就用厂商的，拿不到用本地账本，`source` 字段标注来源（`combine.py:45`）。
>
> **追问（挖坑）**：*那你们和 DeepSeek 官方对得上账吗？*
> **对不上**——这是必须诚实的地方。DeepSeek 没开放历史用量接口，我们代码里 `_fetch_deepseek` 直接返回 `vendor_ok=False`（`vendor.py:319`）。所以**本地账本是 DeepSeek 通道的唯一口径**，「厂商权威」这件事只在 OpenAI 通道成立。我不会说「我们以厂商为准」。

#### Q2：审计日志里会不会泄漏 API key？

> 有防线，但有**已知缺口**，我分开说。
> 防线：写入前过一层脱敏（`redact.py:11-23`），覆盖 Bearer token、`api_key/secret/password=` 赋值、`sk-/ghp-/glpat-` 前缀、AWS/GCP key、JWT（`eyJ.`）、PEM 块；命令另做 200 字符截断。
> 缺口：脱敏是**顶层字段级、不递归**（`scrub_audit_fields:56`）。如果密钥嵌在 `tool_input` 的嵌套对象里，**不会被替换**。另外审计日志**没有轮转**，会无限增长。
> 我的态度是：这是一个**需要补的已知项**，不是「已经安全了」。

#### Q3：$ 你们怎么观测 Agent 是不是卡在死循环里？

> 我们的做法和常规监控不一样：**这套观测的第一消费对象是模型，不是人**。
> `LoopLedger`（`loop_ledger.py:106`）统计三类信号——同一工具结果逐字节等价、内容已见、首句重复——然后 `render()` 输出**不超过 3 行纯计数**，经 T_now 注入进上下文（`pre_llm_inject.py:1092`）。模型看到的是「这个工具第 3 次返回了相同结果」这个**事实**，怎么处理它自己决定。
> 这么设计的原因是我们的引擎理念：**能进注意力的只有信息，不出现命令**。所以不做「检测到循环就打断」，也不写「请换个策略」。
> 另外要诚实说清：**只有这一条线真正在跑**。`prof_stats`（分位统计）、`stage_clock`（分段计时）、`process_ledger`（进程台账）目前**没有实时消费方**，属于「已实现、有单测、待接线」。

## 第 23 章 · 评测与基准（S37）

### 23.1 定位：两件事，一条分界线

评测要回答两个不同问题：

1. **能力多强**——BFCL / HumanEval / MBPP 这类基准（**要 API key、要花钱**）；
2. **改动有没有用**——变更收益侦测（**零成本、确定性**）。

分界线很清楚：**能被穷举验证的东西不调模型，需要统计判断的东西才调模型**。整章的设计都是这条线的推论。

### 23.2 三个「要 key」的 lite 基准

| 基准 | 规模 | 判分方式 | thinking | 产物 |
|---|---|---|---|---|
| **BFCL lite** | 代码侧构造 `simple + parallel + irrelevance` 三组（`main:368-369`）；**落盘产物 `cases_total: 100`** ⚠ | 函数名 + 参数**完全匹配**（数值按值、字符串去空白、顺序无关），确定性 | disabled | `bfcl_results.json` + `bfcl/items.jsonl` |
| **HumanEval lite** | **164 题**（官方全量） | **pass@1**：子进程 `< 20s` 退出码 0 | enabled | `humaneval_results.json` |
| **MBPP lite** | **100 例**（`XEYO_EVAL_MBPP_N` 可调，按 task_id 排序取前 N） | 全量 `test_list` 退出码 | enabled | `mbpp_results.json` |

证据：`evals/bfcl_lite.py:126-196/199-274/313-334/337-360`；`humaneval_lite.py:53-57/68-89/183`；`mbpp_lite.py:28/42-63/114-135/233`。

> ⚠ **一处需注意的口径不一致**：`bfcl_lite.py` 的 docstring 写「100 例（simple 50 + parallel 50）」，而 `main:368-369` 实际构造的是 `simple + parallel + **irrelevance**`（`build_irrelevance_cases:277`，另有 6 例）——按此组合总数应为 106。但**落盘产物 `bfcl_results.json` 的 `cases_total` 是 100**。

### 23.7 `changedetect`：L0 / L1 / L2 三层金字塔

`evals/changedetect/`（12 个模块）回答的是**下一个问题**：*「这次改动，到底让 XEYO 变好了还是变坏了？」*

`changedetect/__init__.py:5-21` 给出的三层（**按「噪声从零到有」排列**）：

| 层 | 名称 | 对象 | 噪声 | 灵敏度 | 成本 | 耗时 |
|---|---|---|---|---|---|---|
| **L0** | `surface` | **模型可见文本面**（system / tools / T_now / slash manifest） | **零** | **1 字符** | 零 | 秒级 |
| **L1** | `trace` | 引擎决策轨迹（注入载荷 + FakeModel 回放事件） | **零** | **分支级** | 零 | 秒级 |
| **L2** | `ab` | 配对 A/B（真模型） | **有** | **= 预算的函数** | 真钱 | 分钟级 |

**三层的关系（原文口径）**：

> **互补而非替代**。L0/L1 能告诉你「变了一定发生了」，但不会告诉你「这是好事」；L2 能告诉你「是不是好事」，但它对小改动天生无力——所以它**必须自报 MDE**，低于 MDE 的差异一律标 `inconclusive`，**不允许被读成「没变化」**。

**这句话是本章的精华**：它把「统计层不可能完美」这件事，从「含糊其辞」变成了「把不可能性量化成『再花多少样本』」。

`changedetect/__main__.py` 的子命令即三层入口：`surface check|update`（L0）、`trace check|update`（L1）、`check`（提交门，L0+L1 字节级 + 应试性扫描，`:231-237`）。L2 不挂门（需 `--budget` + 真 key，`budget.py:113-131`：不传 budget 就 `allowed: False`——**先看报价再决定**）。

**成本常量**（`changedetect/budget.py`）：

| 常量 | 值 | 位置 |
|---|---|---|
| `PRESET_OFFICIAL_NEW` | hit **0.02** / miss **1.0** / out **4.0**（元/百万） | `:18` |
| `REFERENCE_TOKENS_PER_TASK_RUN` | `{input_hit: 757000, input_miss: 34400, output: 62000}` | `:25-29` |
| `DEFAULT_COST_PER_TASK_RUN_CNY` | **¥0.2975**（P2 全量 89 题 ¥26.48） | `:21` |

> ⚠ **N9-5（与 N9-1 同源的口径漂移）**：`changedetect/budget.py:18` 的基准价是**新价**（hit 0.02 / miss 1.0 / out 4.0），而 `usage/pricing.py:26-29` 的本地定价表**仍是旧价**（flash 低峰 `(0.05, 1.5, 4.5)`），且仍保留 peak×2 倍率。
> **两处口径不一致**：评测预算按新价算，运行时账本按旧价算 → 同一个会话，「评测预估成本」和「账本实际成本」会系统性偏差。**这是需要对齐的一项**（对外讲时必须说清「预算用的是评测侧新价」）。

### 23.7.1 应试性报警器与裁决合并（第四轮补全）

`changedetect` 里此前未展开的两个文件，恰好是「**发现 → 裁决**」的两端。

**① `compliance.py` —— 应试性规则扫描（是报警器，不是判官）**

`scan_added_lines`（`evals/changedetect/compliance.py:87`）只扫 **diff 的新增行**（`+` 开头且非 `+++`），逐条匹配 `_RULES`（`:41`）。规则表共 **7 条（实测：4 条 `fail` + 3 条 `warn`）**，**这张表本身就是一份「什么算应试」的书面定义**，代表性条目：

| 规则 | 严重度 | 匹配特征 | 说明 |
| --- | --- | --- | --- |
| R2 | **fail** | `XEYO_BENCH_MINIMAL` | 评测专用开关：只允许影响工具集，不得影响信息正确性 |
| R2 | **fail** | `容器路由\|container_rout\|harbor_route\|in_container` | 评测容器路由分支：产品路径不得因评测环境改变行为 |
| R2 | **fail** | `terminal_bench\|tb21\|bench_minimal\|BENCH_BUILD` | **「任何 `if 评测` 分支都是应试」** |
| R4 | **fail** | 读 `/tests`、按任务名分支等（第 4 类规则） | 针对评测用例本身的特判 |
| R3 | warn | `你应该\|请务必\|建议你\|不要再\|优先选择\|必须先` | **模型可见文本里的导演型措辞**（对应 AGENTS.md「注意力里只出现信息」） |

> **口径注意**：`_RULES` 是**唯一权威**，共 7 条；本书不再另写条数（原稿曾误记为 18 条，已按实测更正）。**引用条数前请以 `compliance.py:41` 为准。**

**⚠ 边界要说清**：**命中 ≠ 违规**——规则是正则，会误报。所以它的定位是**报警器**：命中必须**逐条解释**，而不是自动判死。这个「不把启发式当判决」的定位本身就是可讲的取舍。

**② `verdict.py` —— 合并裁决，保守优先**

`build`（`:62`）把 L0 + L1（确定性）+ L2（统计）+ compliance 合并成 `overall`：

| 机制 | 事实 | 位置 |
| --- | --- | --- |
| 排序 | `_VERDICT_RANK = {"pass": 0, "inconclusive": 1, "fail": 2}` | `:36` |
| 合并方向 | **保守优先**：取 rank 最大值 ⇒ **compliance 出现 fail → 整体 fail** | `:146-154` |
| 关键规则 | **改了 L0/L1 却没跑 L2 → `inconclusive`**（不是 pass） | `:11`/`:153` |
| 输出 | `render_markdown`（`:158`）生成「变更收益裁决」报告 | `:159` |

**面试怎么讲**：「裁决层只有一条原则：**保守优先**。任一维 fail 就整体 fail；改了可见面却拿不出 L2 证据，结论是 `inconclusive` 而**不是** pass——**不允许把『没测』读成『没变化』**。另外应试性扫描是**报警器不是判官**：正则命中必须逐条解释，因为启发式一定会误报，把误报当判决比不查更糟。」

### 23.8 评测诚实度：4 个守卫，以及一处「文档说关、实际开」

`evals/` 下有 4 个专门的**诚实度**侧挂模块：

| 模块 | env | 干什么 | fail-open 行为 |
|---|---|---|---|
| `reporting_shadow.py` | `XEYO_EVAL_REPORTING` | 规范化报告口径，**禁止只报单一 `accuracy`**（恒含 standard/strict/Δ/leakage_rate 四字段） | 异常 → 返回带 `standard` 兜底的字典，**绝不丢分**（`:38-67`） |
| `strict_env_shadow.py` | `XEYO_EVAL_STRICT` | 评测前隔离 git 历史（防偷看提交记录） | 失败 → 恢复 `.git` 并显式报错，**绝不留半剥离状态**（`:110-124`） |
| `pollution_gate_shadow.py` | `XEYO_EVAL_POLLUTION_GATE` | 环境干净度校验 | 校验异常 → **默认拦**（`fail_open_block=True`，`:55`） |
| `blind_audit_shadow.py` | `XEYO_EVAL_BLIND_AUDIT` | 盲审 transcript | 无 key / 失败 → `available=False`，**不影响主路径**（`:119-120`） |

**「只报单一 accuracy」为什么危险**：它混淆「纯编码能力」和「编码 + 检索能力」。如果开了检索而只报一个 accuracy，涨了分也说不清是谁的功劳——这正是 reward-hacking 的温床。

> ⚠ **N9-6（本次实测新增发现，重要）**：
> 这 4 个模块的 docstring 都写着「**默认 0 = 关**」；但它们的 `enabled()` 实际调用 `sidecar.policy.side_enabled`（如 `reporting_shadow.py:30-34`），而 `side_enabled` 对「**未注册进 `memory_switches` 的键**」在专用 env 未设置时**回退到 `sidemod_promote()`**（`sidecar/policy.py:38-58`），后者**默认 `True`**（`:28-33`，注释明写「全部升格（除 ⑫）」）。
> 实测：`grep XEYO_EVAL_REPORTING python/memory/memory_switches.py` → **0 命中**（4 个键都没注册）。
> **结论：不显式设 `XEYO_EVAL_REPORTING=0` 时，这 4 个「诚实度门」实际默认是开的。** 其中 `pollution_gate` 的 fail-open 是**默认拦**，影响面最大。
> 这是一条典型的「**文档描述的是设计意图，实现被后来的全局升格决策覆盖了**」漂移。面试口径：主动说出这个不一致，比照着 docstring 说「默认关」安全。

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| 用例集 | **自建 lite** | 官方全量 | 快、便宜、可复现；代价是**不能与榜单对标** |

### 23.10 面试题 + 回答模板

#### Q1：你怎么证明「这次改动真的有收益」？

> 分三层，按噪声排：**L0 文本面 → L1 决策轨迹 → L2 配对 A/B**。
> L0 比的是**模型可见文本**（system / tools / T_now / slash manifest）的字节级快照——**1 个字符的变化必然被检出，零成本、秒级**，而且进了提交门（`py -3.11 -m evals.changedetect check`）。L1 比的是引擎决策轨迹（注入载荷 + FakeModel 回放事件），**分支级敏感、同样零成本**。
> L2 是真模型的配对 A/B（McNemar + bootstrap）。
> **最关键的是 L2 的自报 MDE**：统计层不可能完美，所以我们强制它输出「最小可检测效应」；低于 MDE 的差异一律标 `inconclusive`，**不允许被读成「没变化」**。而且 L2 不挂提交门——不传 `--budget` 直接拒绝运行，避免无意识烧钱。
> 另外 L0/L1 只能告诉你「变了」，不能告诉你「变好了」——这个边界我会主动说明，不会把它包装成「自动验证收益」。

#### Q2：$ 你们的评测会不会自欺？

> 有四道专用的诚实度守卫（`evals/*_shadow.py`）：**报告口径**（禁止只报单一 accuracy，必须带 standard/strict/Δ/leakage_rate 四字段）、**严格环境**（评测前隔离 git 历史，防偷看提交记录）、**污染门**（环境不干净就拦）、**盲审**（transcript 送第三方盲审）。
> 它们的共同约定是 **fail-open**：守卫本身出问题时不能把分数搞丢。
> 但我要主动披露一个不一致：这四个模块的 docstring 写「默认关」，实际因为后来的「侧挂模块全部升格」决策（`sidecar/policy.py` 里 `XEYO_SIDEMOD_PROMOTE` 默认 1），**未设专用 env 时它们默认是开的**。文档和别人脑子里的模型已经对不上了——这是我们自己要修的。

#### Q3：$ 你们为什么不上向量检索？（结合评测答）

> 因为我们**做过对照实验**，而不是拍脑袋。`evals/retrieval_bench.py` 是纯离线的：基线是词法检索（notes 走关键词、code 走 trigram），指标是 **hit@k**。
> 结果很有说服力也很有分寸：**code 域 hit@k = 1.0（5/5），notes 域 = 0.4（2/5）**。代码符号是精确 token，词法够用；中文自然语言查询和笔记标题之间没有共享词，词法就不够了。
> 所以我的结论不是「向量没用」，而是**「向量该上的地方是 notes 检索，不是代码导航」**——先把 ROI 最高的那块做了。这比笼统地讲「我们不需要向量」有价值得多。

|---|---|---|---|---|
| `extension/mcp_name_manifest_shadow.py` | `XEYO_MCP_NAME_MANIFEST` | 会话建立时的 tools 快照（`build_snapshot:45-82`） | schema 收缩为「name + 短描述」+ `_xeyo_full_schema` 指针按需 `Mcp(describe)` 取回 | 回退原 schema（`:81-82`） |

**三条侧挂契约（这套体系能成立的原因）**：

1. **fail-open**：任何异常/缺失都交回原函数或返回安全兜底 —— 侧挂模块**绝不能让主链失败**。
2. **不触碰冻结面**：`mcp_name_manifest_shadow` 明确「不碰冻结面」（`:20-22`），改的是快照内容而非 schema 缓存。
3. **有对比脚本**：`scripts/bench_sidemod_benefit.py`（`main:224-250`）实测「开启 vs 基线」——⑧.5 memindex 同秒检测（`:41`）、⑧ content_index 缓存重算（`:108`）、⑮ 重排（`:163`）、④ 污染门（`:172`）、⑤ 报告口径（`:190`）、① 冷记忆（`:201`）。

> ⚠ **侧挂体系的两个边界**：
> ① ②（严格档）与 ③（盲审）**离线不可量化**（`bench_sidemod_benefit.py:249` 明写），其「收益」依赖真实回路，**没进自动证据链**；
> ② 该 bench 脚本**只 print 不落盘**，结果不可回溯。
> 面试口径：「我们的侧挂验证是**有脚本的**，但有 2 项离线测不了、结果也没落盘——这是一条**半自动**的证据链，不是全自动的。」

### 24.6 设计取舍汇总

| 决策 | 选择 | 被否决的方案 | 理由 |
|---|---|---|---|
| 提交门 | **本地脚本 + CI 双轨** | 只靠 CI | 本地能提前拦住；代价是「靠人跑」（无 pre-commit） |
| 失败语义 | `Stop`（硬中断） | 收集所有错误再报告 | 简单、快；代价是漏报后段结果 |
| 契约测试 | **逐字节比较** | 语义相等 | 描述文本是模型可见产物，改一个字就是变量 |

| 新功能入口 | **旁路（shadow）→ 有数据 → 并入** | 直接进主链 | `AGENTS.md:31` 明规则；失败可零成本回退 |
| 侧挂失败 | **fail-open** | fail-closed | 侧挂是「验证中」的模块，不能让主链为它陪葬 |

### 24.7 面试题 + 回答模板

#### Q1：你们的提交门长什么样？

> 一个本地脚本 `scripts/check.ps1`，**三段**：Python（装依赖 → pytest `-m "not live"` → slash manifest 漂移 → `changedetect check`）、GUI（typecheck + vitest）、tui（typecheck）。**共 10 条命令**，`$ErrorActionPreference="Stop"`，任一步挂了后面不跑。
> CI 是 **3 个互相独立的 job**，比本地门**少一步**（不跑 `changedetect check`）。
> 我要诚实说三个缺口：① **没有 pre-commit**，本地门靠人跑，CI 只在 push 后才兜；② 本地门是串行硬中断，pytest 挂了就看不到前端结果（CI 那边反而是独立的，更友好）；③ pytest 用 `-m "not live"` 排除了所有需要真实模型的测试。
>
> **追问**：*那你们靠什么防止「测试全绿是假的」？*
> 两点。一是 **xfail 只有一处**（`test_bash_isolated.py:25`，且只是 Windows pwsh 条件标记），**没有大面积挂账**；二是契约测试用**逐字节比较**锁工具面（`assert _schemas_bytes(reg) == before`），改一个字符就红——这类测试没法「糊弄过去」。

#### Q2：$ 你们怎么保证「新功能真的有用」再合进主链？

> 用**侧挂（shadow）机制**，这是写进项目规则里的（`AGENTS.md:31`）：新行为先以旁路形态上线，**有数据证明收益才并入主链**。
> 落地就是 `*_shadow.py` 一族，三条契约：**fail-open**（侧挂失败就交回原函数，绝不让主链陪葬）、**不触碰冻结面**、**配对比脚本**（`scripts/bench_sidemod_benefit.py` 实测「开 vs 关」）。
> 举个具体例子：`memindex_sig_shadow` 把笔记签名从 `(mtime, size)` 换成 `(size, content_sha)`，治的是「同一秒内编辑两次导致漏检」——这个改动先只对 notes 生效、有 bench 数据，验证后才固化。
> 诚实的边界：这个 bench **只 print 不落盘**，而且有两项（严格环境 / 盲审）**离线测不了**。所以它是**半自动**证据链，我不会说「全自动」。

#### Q3：$ 顺带问：你们的评测守卫默认开还是关？

> 按 docstring 是「默认关」，但**按实现是默认开**——这是我实测发现的，我直接说结论。
> 那 4 个诚实度守卫（报告口径 / 严格环境 / 污染门 / 盲审）的 `enabled()` 都走 `sidecar.policy.side_enabled`，而这个函数对**未注册进 `memory_switches` 的键**会回退到全局升格谓词 `sidemod_promote()`，后者**默认 `True`**（`sidecar/policy.py:28-33`）。我 grep 过 `memory_switches.py`，这 4 个键**一个都没注册**。
> 所以文档描述的是设计意图，实现被后来的「全部升格」决策覆盖了。这是我们自己文档与代码对不上的一处，值得修。

**B. M-04 发布副本一致性：从「需校验」升级为「已实证陈旧」**

`gui/src-tauri/src/lib.rs:64-85` `python_root()` 决定后端跑哪份代码：

|---|---|---|
| **dev（`debug_assertions`）** | `<repo>/python`（`lib.rs:69-71` **直接返回**） | **当前源码** ✅ 不受副本影响 |
| **release** | 优先 `resource_dir/python`（`:73-78`），缺失才回退源码 | **打包副本** ⚠ |

而打包副本的实际状态：

| 路径 | `engine/query_loop.py` | mtime | 体积 |
|---|---|---|---|
| `python/engine/query_loop.py`（源码） | **2000 行** | 2026-09-10 17:45 | — |
| `gui/src-tauri/resources/python/…` | **1973 行** | **2026-09-07 20:06** | 544 MB |
| `gui/src-tauri/target/debug/python/…` | **1973 行** | 2026-09-07 20:06 | 575 MB |
| `gui/src-tauri/target/release/python/…` | **1973 行** | 2026-09-07 20:06 | 575 MB |

⇒ **三份副本一致地落后源码 27 行 / 3 天**。含义：**release 路径（装机版）跑的是 09-07 那一版引擎**，而不是 `python/` 里的当前源码；dev 路径不受影响（所以本地开发感觉不到）。

**为什么说它与 `21.4` 是同一条根因**：`21.4` 的薄壳 venv 事故是「**构建产物不自包含、且构建期没有断言，装到目标机才炸**」；这里是「**构建产物是源码副本、且没有一步负责刷新它，装到用户机上才发现跑的是旧引擎**」。两者都是 **构建产物缺自检**。所以修法同形：像 `verify()` 检查 DLL 那样，加一条**副本新鲜度断言**（构建期对比 `python/` 与 `resources/python/` 的关键文件哈希，不一致即失败）。

> ⚠ **诚实边界（两点）**：
> 1. 本册**未找到**负责刷新这份源码副本的构建步骤（`scripts/build_slim_venv.py` 按设计只替换 `resources/python/.venv`）——是否另有步骤在 release 前同步源码，**建议开源前核实**；本结论只到「仓库当前状态 = 副本陈旧」这一层，不外推「一定发旧代码」。
> 2. `target/{debug,release}/python` 是构建中间产物，两套共 **~1.15 GB**；与 `resources/` 合计 **~1.7 GB** 常驻磁盘。缓存可清，但要先确认没有脚本按该路径解析。
