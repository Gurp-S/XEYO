## 1. 背景与症状

用户报告两类高频问题：

1. **经常回溯不了**：编辑历史消息并提交后，回溯经常失败，或提示「找不到可回溯的用户消息」。
2. **历史发送按钮数据丢失**：编辑历史消息后点发送，明明已发送，却显示「无法回溯/消息丢失」，随后**前端直接把需要回溯的那段消息整段消失**，且无法找回。

契约本身（后端 `POST /rewind` + orphan + 原子重写 transcript + 异步工作区恢复）是健壮的：服务端幂等、undo、状态轮询、checkpoint 查询都已实现。**问题集中在客户端 `rewindV3Store` 的乐观截断与失败恢复路径**。

---

## 2. 根因（基于当前代码定位）

### R1 · poll `failed` 不回滚，且提前删兜底 —— 对应症状 2 的「消息消失」

`rewindV3Store.ts:342-353`（`confirm('continue')`）：

```
const settled = await pollSettled(...);
dropFallback(sessionId);                    // 兜底先删
if (settled && settled.status === 'failed') {
    set(... phase: 'error' ...);            // 只置错误态
    return false;                           // 本地列表保持截断，永不复原
}
```

- 同帧截断把 `messages.slice(0, targetIdx)` 写回 `messagesById`（`:279-284`），
- 但回滚入口 `restoreDialogState` **只在 `rewindHotpath` 抛错时被调用**（`:371-373`）。
- 当 POST 成功返回 `rewind_id`、随后 **poll 判 `failed`** 时，走不到恢复分支 → 列表保持截断、兜底已删 → **这段消息前端直接消失**。

### R2 · 幂等键含 `Date.now()`，幂等形同虚设 —— 对应症状 1/2 的重复截断与分叉

`rewindV3Store.ts:328`：

```
idempotencyKey: `${sessionId}:${targetId}:${action}:${Date.now()}`,
```

- 后端 `rewind/service.py` 对 key 强绑定（`by_idempotency`、`idempotency key is bound to another plan`、`reused` 重放）。
- 但客户端每次重试都生成**新 key**，所以：
  - 同一次操作重试 = **新建一条 rewind**，孤儿、文件恢复重做；
  - 若上次客户端丢响应、服务端其实已 commit，重试反而因「同 key 绑定到不同 plan」报 `idempotency_conflict`，或直接再截断一次 → 与服务端 transcript 分叉。

### R3 · `restoreDialogState` 只在「request 抛错」时恢复，丢响应即本地/服务端分叉 —— 对应症状 2 的「无法回溯」

- POST 抛错 → `restoreDialogState` 恢复本地列表（`:300-308`），但**服务端可能已 commit**（响应在网络中丢失）。
- 此时本地显示完整列表、服务端已截断成孤儿 → 重载后 `hydrate` 读 transcript 前缀，出现「会话 transcript 与 rewind 记录不一致」。
- 且 `restoreDialogState` 恢复的是 `messages.slice(targetIdx)`（**旧文本**），编辑后的 `editedText` 并未恢复进列表。

### R4 · 客户端 `bySession` 不持久化，进行中回溯态重载即丢失 —— 对应症状 1 的「一次性、无法续」

`rewindV3Store.ts` 的 `bySession` 是纯内存（`:53-76`、`:188-189`），只有 `persistFallback` 把截断后缀写进 localStorage（`:98-107`）。

- 重载后 `bySession` 归 `idle`，`phase='running'/'done'/'error'` 全丢；
- 兜底只存了「截断后缀」，**没有存 rewind_id、attemptId、目标消息、检查点、整体状态机**；
- 因此「POST 已受理、后台恢复中」的场景在刷新后变成孤悬状态，用户无从 undo / retry。

### R5 · v3 与 v2 双状态竞态 + 静默降级 —— 对应症状 1 的「经常回溯不了」

- 同一次编辑存在两套弹窗 / 状态机：v3 `RewindV3Dialog`（`rewindV3Store.bySession`）与 v2 `WorkspaceRevertDialog`（`chatStore.rollbackById`），互不知情。
- `preStoreHelpers.shouldFallbackToLocalResend` 在厂商错误 / rewind 未就绪时**静默退化为「本地截断+重发」并清空 `rollbackById`**（`rollbackSlice.ts:184-192`）。服务端**没有 rewind revision** → 下一次真想回溯时后端报「找不到可回溯的用户消息」，本地却已被截短。

## 3. 本轮加固（先止血）：目标与设计

本轮只修客户端 `rewindV3Store`（+最小后端无改动，幂等契约已具备），目标是**任何失败都不丢消息、都能恢复**。收敛架构（单 owner）见第 4 节。

### 3.1 核心不变式（本轮的"安全性质"）

> **H0 · 截断与回滚必须成对。** 客户端只在拿到「服务端已提交该 rewind」的确定性证据后才允许把截断视为终态；在此之前，被截断的消息（`suffixBackup`）一直保留且可一键还原。

由 H0 派生的规则：

- **H1 兜底不提前删**：`dropFallback` 只在「终态成功」或「已 undo」时调用；`failed`/`partial`/超时**都保留**。
- **H2 失败必回滚列表**：任何未达终态成功的退出（request 抛错、poll `failed`、poll 超时且服务端未 commit）都恢复 `suffixBackup` 到 `messagesById`。
- **H3 幂等键确定性**：同一次逻辑重试共用同一 key，重试走后端 `reused` 重放，不新建 rewind。
- **H4 未决态持久化**：进行中回溯态写持久层，重载后按 `rewind_id` 重对齐（poll→settle / undo / retry）。

### 3.2 数据模型（`RewindV3BySession` 持久化扩版）

```ts
// 持久化字段（写入 localStorage `xeyo.rewindV3.state.{sessionId}`）
interface RewindV3Persisted {
  phase: 'idle' | 'dialog' | 'running' | 'done' | 'error';   // 现有五态
  targetMessageId: string | null;
  editedText: string;
  action: RewindV3Action | null;                 // 'restore' | 'continue'
  checkpointId: string | null;
  rewindId: string | null;                       // 服务端 rewind_id，重载对齐用
  attemptId: string | null;                      // 幂等键的稳定部分
  summary: string | null;
  error: string | null;
  suffixBackup: ChatMessage[] | null;            // 被截断的同帧后缀（截断一瞬间定格）
  settled: boolean;                              // 终态成功 | 已 undo | 已明确放弃
  settledAt: number | null;
}
```

- `suffixBackup` 取代现有 `persistFallback` 的「只存 suffix」——一并承担 3.3/R3 的「找不回 editedText」问题，因为 `editedText` 已在字段里。
- 内存态仅保留弹窗边缘（`pillRewindId`、`dialog` 开/关）；其余全走持久层，`useRewindV3Store` 改为读持久化的 `bySession`。

### 3.3 `confirm('continue')` 时序（加固后）

```
用户点「改用这段文案重新发送」
 1  attemptId = existing ?? uid('rw')                      // 重试复用；新确认才新建
 2  idempotencyKey = `rw:${sid}:${targetId}:${attemptId}:${sha1(editedText)[:8]}`
 3  同帧截断：suffixBackup = messages.slice(targetIdx)
    · 写 persisted.suffixBackup (localStorage)
    · messagesById ← slice(0, targetIdx)
 4  POST /rewind { confirmed:true, idempotencyKey, ... }
    ├─ 成功 →
    │     persist.rewindId = result.rewind_id
    │     pollSettled(rewindId)                            // 后台续跑，成功前不判 done
    │     ├─ committed / partial：settled=true → dropFallback → done
    │     ├─ failed：恢复 suffixBackup；settled=false；error 态；保留兜底
    │     └─ 超时(服务端未 commit)：恢复 suffixBackup；error 态；保留兜底
    └─ 抛错（可能服务端已 commit）：
          · 用同一 idempotencyKey 重试一次（幂等重放）
          · 仍失败：恢复 suffixBackup；settled=false；error 态；保留兜底
 5  error 态弹窗展示「撤销回溯 / 重试 / 放弃」：
    · 撤销 → POST /rewind/{rewindId}/undo → 恢复 suffixBackup → settled=true
    · 重试 → 复用 attemptId+key 回到步骤 4
    · 放弃 → 保留本地当前列表 + 兜底，settled=true（不再自动任何事）
```

关键变化（相对现状）：

- **幂等键确定化**（`attemptId` + 内容摘要），去掉 `Date.now()`；丢响应后重试是**安全重放**而非新建/冲突。
- **终态前一律不删兜底**；`failed` / 超时**必先恢复列表**再报错。
- **恢复用的是 `suffixBackup` 定格快照**，含 editedText，避免 R3 的「恢复回旧文本」。
- **`running` 期间列表保持截断，但 `settled=false`**；弹窗一直可「撤销回溯」直到 `settled=true`。

### 3.4 重载恢复（hydrate）

本会话 `hydrate`（`rewindV3Store` 载入持久层）时：

```
若 persisted.rewindId 且 !settled：
  poll GET /rewind/{rewindId}
    ├─ committed → 用 loadSessionMessagesWithBackfill 拉服务端前缀；settled=true
    ├─ failed    → 恢复 suffixBackup（若仍有）；error 态；未 settle
    └─ 404/不可达 → 保留 error 态 + 兜底，给出「撤销 / 重试」按钮（不静默丢失）
```

- 这取代「刷新即忘」：进行中回溯_rewind 重载后可接着 settle / undo。

### 3.5 冲突与忙碌

- `session_busy` 409：与现状一致不 interrupt；但在**弹窗内**反馈「Agent 正运行，停止后再试」，不再静默降级截断。
- `idempotency_conflict`：走 3.3 的「丢响应重试」判定 —— 优先用 `undo(rewindId)` 对齐，再给用户重试/放弃。

### 3.6 静默降级收敛（本轮最小化处理）

`shouldFallbackToLocalResend` 这轮**保留为兜底但不静默、不截断**：当服务端 rewind 不可达时，把「仅截断对话（不动文件，服务端无 revision）」作为**显式选项**写入 error 态弹窗，由用户确认；确认前不修改 `messagesById`、不清 `rollbackById`，并给该会话打 `diverged` 标记，UI 提示「下次无法文件级回溯」。这直接缓解「经常回溯不了」。

## 4. 下轮收敛（架构）：单 owner

本轮之后再做，方向：

1. **唯一执行者 = v3**：`rewindV3Store` 是唯一「编辑-回溯」入口；v2 `rollbackById` 降为只读兼容，删除其乐观/恢复路径（`rollbackSlice.executeRollback` / `recovery_required` / `restoreOptimisticTruncate`），仅保留 `preview/execute` 后端测试接口。
2. **唯一弹窗 = `RewindV3Dialog`**：合并 v2 的 `WorkspaceRevertDialog`（blocked/recovery/resend 全部收敛进 v3 状态机 + 统一 recovery UX）。
3. **消除 `shouldFallbackToLocalResend` 的截断路径**：只保留「本地仅重发、不动文件」的非破坏入口，其余一律走 v3。
4. **后端对齐**：确认 `rewind/service` 与 `hotpath` 的 `partial` 状态在客户端有明确语义；`recovery_required` 语义统一收敛（当前 v2 有、v3 无）。
5. **测试**：补 `rewindV3Store.test.ts`（poll failed 不回滚、幂等键确定、重载 hydrate、undo 恢复）——现状 `gui/src/stores/chatStore.test.ts` 只测了 v2 路径。

## 5. 验收 / 回归清单（本轮）

1. 编辑历史消息→「改用这段文案重新发送」，模拟后端在 poll 前返回 `failed`：**被截断消息必须回到列表**，弹窗给「撤销/重试/放弃」。
