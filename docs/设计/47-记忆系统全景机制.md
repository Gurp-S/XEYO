## 1. 设计背景：四个约束决定全部形态

1. **模型无跨会话记忆**——需要把"项目惯例 / 用户偏好 / 关键事实"跨会话保留并送回上下文。
2. **Token 经济**——记忆不能无脑塞上下文；核心张力是"什么信息、什么时机、多大体积"。
3. **KV 前缀缓存稳定**——请求开头改一字节，后面缓存全废。铁律：**易变内容只挂请求尾部
   （T_now 管线），绝不碰 system 段与对话前缀**。
4. **防污染（证据先行）**——弱模型会把背景信息误当任务执行（事故 sess_mtiche8l：
   glm-4.5-air 把记忆索引条目当任务对象）。因此自动注入极度收缩，主动检索是主通道。

## 2. 六层地图与数据流

```
L0 原始历史 ──每轮投影──► L1 压缩投影（发给模型的东西）
  │                        │
  │ 会话进行中(每8个工具调用) │ 压缩时抓快照
  ▼                        ▼
L2 session.md ◄──跨会话读── L3 跨会话检索（读别的会话的 L2）
  │
  │ 会话结束
  ▼
L5 rollout 归档 ──► L6 NightShift ──晋升──► L4 长期记忆库（topics/ + 索引）
                                          ▲
                              Memory.search 三路并发查 L4/L3/L5
```

| 层 | 记什么 | 寿命 | 进上下文方式 |
|---|---|---|---|
| L0 | 一切原文 | 永久（本地） | 投影后发模型 |
| L1 | 压缩态 | 本会话 | 就是每轮请求本体 |
| L2 | 本会话任务态 | 会话生命周期 | 跨会话被 L3 检索 |
| L3 | 别的会话的任务态 | 同 L2 | Memory.search |
| L4 | 长期事实/偏好/反馈 | 永久（只剪尸体） | 索引块 + Memory.search |
| L5 | 单任务全过程 | 滚动 20 份 | Memory.search |
| L6 | ——（裁判，不存数据） | —— | —— |

一句话：**L0 是事实，L1 是预算，L2/L3/L5 是任务记忆（短期、语义化），L4 是长期记忆
（治理最严），L6 是唯一有晋升权的守门人。**

## 3. 各层机制

### L0 原始历史（MessageStore / JSONL）

只增不减的事实底账。每条消息原样追加，**永不修改/删除**。全系统唯一事实源，
其余各层都是它的派生物——任何一层出 bug，损失上限是"检索不到"，不是"数据没了"。
会话回滚（rewind）= 回到 L0 某位置重放。

### L1 单会话压缩（`memory/runtime.py` 投影层，每轮跑）

三档手段从轻到重：

- **C0 截断**：超长单条工具输出截为占位。
- **C1 冻结**：`c1_frozen_until` 游标左侧冻结为稳定紧凑形态。作用是保护 KV 前缀缓存。
- **C2 摘要折叠**：游标左侧整段折叠为摘要。三个配套机制（均已固化恒开）：
  - **citation 锚点**：每条压进行带 `⟦notes:msg:<i>:<kind>⟧`，摘要可溯源；
  - **A2 碎片还原**：压缩时抓拍结构化原子入 sqlite，`Memory(action=retrieve)` 按锚点找回原文；
  - **A3 逃生舱**：最近 1 条完整报错栈 + 最后 3 个文件路径强制原文保留。

触发由 **Path A 公式**（面板三开关）裁决：压力门 = `当前token/真实窗口 ≥ (l_hard_send −
output_reserve − tail)/window`（窗口自适应；1M + overlay 50000 ≈ 94.6%），收益门 =
"改写的一次性 cache miss 能被剩余轮次 × 每轮省 token 摊平"。两门齐过才压**一次**
（稀发事件）；窗口将溢时 HardTop 无视一切强制压。压缩收益用经济公式（C2_GAIN/
EXTEND），保尾 = 每轮均 token × 3 轮（C2_TAIL 公式，固化删除——它本来就没有读取点）。

### L2 session.md（`memory/session_md.py`）

会话进行中**每累计 8 个工具调用**触发一次 `maybe_update`，用七段模板重写本会话笔记：
`Goal / Current state / Completed / Important discoveries / Key facts / Open questions /
Next action`。硬规则：

- **禁止机器状态入内**（`_FORBIDDEN`：compact_cursor、hit_tokens、`- [ ]` 等）——
  语义笔记，不是调试转储；
- **A5 差分重写**（固化）：只把变化的节追加进 delta 日志，工程侧合并；
- 会话回滚时 `clear_after_rollback` 同步清笔记（与 L0 一致）。

与 L4 分工：L2 记"**这个会话在干什么**"（任务态），L4 记"**长期有效的事实**"。

### L3 跨会话检索（`search.search_session_notes`）

把**同工作区其他会话**的 L2 文件当检索语料。候选来源两路合并：落盘 `ws_index`
（跨重启）+ 进程内 presence 表（标题最准）。命中带 citation（`notes/session/<sid>.md`
+ 来源会话 id）。子代理链（`__agent__` 作用域）排除，不串话。

### L4 长期记忆库（memdir）

磁盘布局：

```
~/.xeyo/memory/<workspace_id>/
├── workspace.json        # 状态：上次整理、候选数、diff 基线
├── MEMORY.md             # 一行索引（200 行/25KB 上限；实测 27 行 ≈0.7k tok）
├── topics/*.md           # 一条记忆一文件（frontmatter: type/scope/status/confidence/source）
├── tombstones.jsonl      # 墓碑，永不复活
├── candidates.jsonl      # 候选池（草案，非记忆）
└── rollout_summaries/    # L5
```

独立镜像 `~/.xeyo/memory/user/` 存跨工作区的用户域记忆。

三个构件：
- **存储**：如上；
- **治理**（`governance.py`，纯规则无 I/O）：晋升闸 `can_promote`、置信度封顶
  （agent 0.6 / diff 佐证 0.85 / 用户确认 1.0）、墓碑永不复活、冲突 supersede、
  7 天保留期剪枝（只剪非 active 尸体）；
- **检索**（`search.py`）：纯词法（NFKC + 拉丁 AND / CJK bigram OR + 命中门槛），
  打分 = F4 广度封顶（固化）+ 置信度 + 近因 + ⑮采用偏好（固化）。零模型调用。

### L5 rollout 归档（`archive_session_rollout`）

会话结束且像"干完一个任务"时，整会话蒸馏为 `rollout_summaries/<sid>.md`
（frontmatter 带 session_id），**滚动保留 20 份**。检索第三路——L4 记**事实**
（"用 pnpm"），L5 记**过程**（"先改 schema 再迁移再补测试"）。

### L6 NightShift（`memory/nightshift.py`）

**L4 的一切写入中，模型/收割只能产生候选；唯一能把候选变成正式记忆的通道是
NightShift。** 会话 submit 结束后 `maybe_schedule` 异步跑：文件锁 + PID 回收
（防并发/崩溃残留）、6h 成功冷却压例行、急件必跑（待 forget/未消解冲突/可晋升候选）、
followup 链收敛（链上限防死循环）、每轮晋升限频 8 条（防晋升风暴）。

固定八步：①保留期剪枝 → ②diff 佐证（相对基线一次，4MB 截断）→ ③墓碑 →
④过期 → ⑤冲突消解（输家 superseded，绝不物理删 active）→ ⑥候选晋升（过闸+限频）
→ ⑦**仅变更时** rewrite_index 一次（workspace + user 两域）→ ⑧清 diff 工件/刷状态。

## 4. 一条记忆的流水线实例（虚构剧本）

**S1 第 3 轮**："这个项目统一用 pnpm，别用 npm。" → 记忆系统**什么都不做**
（不实时写，不打断干活）。

**S1 结束**：收割 → 候选草案入池：

```json
{"id":"cand_a1b2","type":"feedback","content":"shop 项目统一用 pnpm，不要用 npm",
 "evidence":["agent_harvest"],"source":{"kind":"agent","session_id":"sess_s1"}}
```
`write_policy` 体检（非目录树/一次性计划/路径堆砌）→ 放行 → 排 NightShift。

**当晚 NightShift**：diff 佐证发现 `pnpm-lock.yaml` 真的改了 → 证据升为
`verified_by_diff` → 过闸 → 置信度 **0.85** → 写 `topics/feedback-pnpm.md` →
索引多一行。

**两周后 S7 第 1 轮**："帮我把 dayjs 升级一下" → 模型
`Memory(action="search", query="shop dayjs 依赖")` → 纯词法命中 `feedback-pnpm.md`
（词法分 + 0.85 置信 + 近因）→ touch `last_used_at`（⑮ 偏好素材）→ 带 citation
返回 → 模型用 `pnpm update` 回答。上下文尾部同时有 ≈0.7k tok 的索引块（INDEX_LIVE）。

**S7 拖长到 95%**：C2 触发，摘要行带 `⟦notes:msg:5⟧` 锚点；30 轮后需要第 5 轮
完整原文 → `Memory(action="retrieve", id="notes:msg:5")` 碎片还原；会话结束
rollout 归档。

**S9 改口**："以后还是用 npm" → NightShift `resolve_conflict` 判同 scope 互斥 →
旧 note superseded、新 note 入库；补一句"就这么定" → user_confirm → 置信 1.0。
"把某条删了" → forget → tombstone，**永不复活**（后续相同内容候选晋升前被拦）。

## 5. v61 机制说明

**v6.1 = 记忆压缩的每轮决策引擎**（`memory/simulator/decision.py` 的 `decide`）：
每轮对 keep / C1 / C2 三动作打分——Q（质量）/ H（缓存命中损失，输入 ρ̂：TTL 表 ×
ω 冷却平滑）/ U（效用）合成 J 投票；剩余轮数 r_gate、保尾预算、Horizon 参与。
纯本地数学，零 token。代价：每轮跑一遍（CPU）+ 改写前缀掉缓存命中。

**两种运行模式**（`XEYO_L5`）：

| 模式 | 每轮 | C2 触发 |
|---|---|---|
| `project`（生产默认） | C0+C1 快路径，不跑 decide | Path A 压力/收益公式 |
| `v61`（实验通道） | 完整 decide | decide 自主 |

**v61 建议采纳**（`docs/实施计划/v61建议采纳说明.md`）是改进方案的决策记录：

- ✅ 完全采纳已进生产（多数已固化）：A1 ω 平滑 / A2 碎片还原 / A3 逃生舱 /
  A4 sqlite 索引 / A5 差分重写 / A6 真录评测管线；
- 🟡 条件采纳、卡证据门（面板 `XEYO_V61_PARETO/SI/DYNAMIC_R`，默认关）：
  B1 Pareto 替代加权 J / B2 内容驻留分 s_i / B3 动态 Horizon；
- 🔵 地基：C1 因果边表、C3（RL 取思想不取训练）；⏳ 远期：DAG 全图压缩（v7）、
  三档冷热分层；✔️ 已存在：`/compact`、渐进披露、LLM 摘要旁路。

**治理协议**：改 v6.1 数学框架必须先在冻结真录（200 轮）上离线重放证明收益才可合
主干。工具：`scripts/v61_evidence_gate.py`（收益门 + scale-drift 护栏：改标尺的开关
让 Q 分布漂出 [0.5,2.0] 带 → REFUSE）。上线门：A1（200+ 轮 live）+ A3（日监控）。

### 5.2 v61 收益实测（2026-09-06，live 命中率 + 证据门 + LoCoMo）

**① live 命中率/成本分档对比**（`--hitrate-live`，真实源 615 行/35 轮，ultra 分档）：
`sess_mtlpmznl_0iapt2`（A3 监控会话，循环副本=1，健康 ✓）。

**1a. 逐枪明细（ultra/project vs ultra/c2，35 枪，prompt tokens / hit / miss / 命中率 / 单枪成本 / 累计）**
（全文见 `.tmp/hitrate_live_out.txt`；此处给特征段）

| 阶段 | project 单枪 | c2 单枪 | 说明 |
|---|---|---|---|
| 压缩前（枪 0-3） | prompt 11.7k→48k / rate 50→89% / ¥0.009-0.011 | 同 project（尚未压缩） | 两者同输入 |
| **压缩瞬间（c2 枪 4-7）** | prompt 48k 继续涨 | **prompt 骤降 48k→2.7k→19k**，rate **9.9%~31.3%**，单枪 ¥0.0035-0.021 | transition=8 的第一次：命中崩塌、prompt 砍 17 倍 |
| 压缩平稳（c2 枪 8-31） | prompt 一路涨到 175k / rate 86-100% | prompt 维持在 7k-36k（波动） / rate 43-98%（多次二次压缩再崩） | 每 trans=8 一次，8 次压缩间隔散布全期 |
| 末段（枪 32-34） | 175k / 99-100% | 12k-16k / 52-86% | c2 全程均值大幅低于 project |

**一句话逐枪特征**：project 是"单调涨"（prompt 11.7k→175k、命中率趋 100%）；c2 是"**锯齿**"（每次压缩 prompt 暴跌 10 倍、命中率从 90%+ 跌到 10-60%、然后再爬回 90%+）——**8 次锯齿对应 8 次压缩**（trans=8）。

**1b. 聚合对比（live 口径 = 温缓存实测 / 干净口径 = 冷启动全 miss 复算）**

| 指标 | project | c2（压缩） | 对比 |
|---|---|---|---|
| 全期命中率（live） | **98.04%** | 85.35% | -12.7pp |
| 稳态命中率 | 98.16% | 89.56% | -8.6pp |
| 尾20 命中率 | 98.99% | 87.48% | -11.5pp（<A1 99% 门） |
| 末轮命中率 | 99.99% | 85.92% | -14.1pp |
| 输入 tokens | 4,470,910 | **712,359** | **-84%** |
| **成本（干净口径）** | **2.091 元** | **1.444 元** | **-31%**（此处才体现真实省钱） |
| 干净口径命中率 | 99.02% | **98.38%** | -0.64pp（干净口径几乎持平！） |
| 干净 tail20 | 99.42% | 99.22% | -0.2pp（A1 达标） |
| transition | 0 | 8 | 每次压缩命中跌至 9.9~67% |

**关键澄清（live vs 干净口径）**：live 口径（0.61 vs 0.61 持平）是**"温缓存已热"的假象**——
首次 0 枪命中所致；**干净口径（冷启动复算：增量全 miss）才是真实成本** ——
**c2 省 31%（2.09→1.44 元）**，且干净口径下**命中率只差 0.64pp**（98.38 vs 99.02），
**尾20 99.22% 达标 A1**。**结论：c2 真实收益 = 省 84% 输入 + 省 31% 成本 + 命中率几乎持平；
live 口径的"85.35%"是温缓存假象（压缩瞬间的 8 次 transition 拉低均值）。**

**1c. 长/中会话分档（历史 hitrate 行）**

| 档 | project 命中 | c2 命中 | 输入差 | trans |
|---|---|---|---|---|
| long80 | 96.84% | **97.06%** | -4.6% | 1 |
| long140 | 99.12% | 98.32% | -5.0% | 1 |
| locomo ultra | 98.96% | 98.79% | **-40%** | 1 |
| ultra（本测） | 98.04% | 85.35% | **-84%** | 8 |

**分档结论**：**会话越长 C2 收益越大**——locomo（ultra 40 万）hit 98.79% 且省 40%、long80/140 几乎打平且省 5%；**唯一"命中率大降"是本测 ultra（trans=8 的锯齿）**——那是**8 次压缩的代价**，不是常态（长会话压缩 1 次省 40% 还很稳）。

**1d. 是否变笨（回答正确率，独立于命中率）**

**表A-real（24 题，同轮 A/B）：v61 **83.3%**（20/24）vs project **79.2%**（19/24）→ **+4.2pp**，v61 独有零3=[]（r10/r13/r18/r21 全是 project 也零3 的难题）。**

**结论：压缩后模型不变笨，反而略优**——命中率（性能成本）与正确率（智能）完全独立：
c2 压缩瞬间命中低（重算）但**答案质量不降**（表A +4.2pp）。"8 次 transition 命中低"是

## 6. 投影缓存与 C2 gate 的耦合（γ4）及其解耦

**原设计**：`use_proj_cache = project模式 and (gate关 or 已压缩)`。gate 开意味着
decide 每轮可能推进 C1/触发 C2，投影缓存的六元组签名（消息数/冻结点/cursor/摘要
指纹）随时可能失效；当年 gate 是灰度，保守取"gate 开就不缓存"。

**2026-09 解耦**（gate 默认开后落地）：

1. **缓存解耦**（`engine/query_loop.py`）：`use_proj_cache` 不再看 gate。正确性依据：
   决定投影结果的全部可变字段（frozen/cursor/摘要指纹/消息数）**本来就在缓存签名里**——
   输入不变则 decide（确定性纯函数）结论不变，复用投影逐字节安全；输入变了签名失配，
   自然回落全量投影。aging 边界在命中路径上显式先行推进。
2. **decide 路径去重复计算**（`memory/runtime.py`）：一次投影内 `sim_project(s0)` 的
   结果在 r_gate / 压力门 / 保尾预算多处重复计算，memo 化为一次（O(历史) → 1 次）。
3. **保留项**：decide 本身仍是"gate 开才加载/运行"（T38 解耦语义不变）；
   若长会话实测 CPU 仍明显，下一档是"压力远低于阈值时跳过 decide"的预门
   ——但那改变 decide 触发语义（C1 推进时机），须走证据门重放后再做。
