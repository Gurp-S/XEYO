# 49-推理循环全景机制（query_loop / 轮次 / 重试 / 可恢复）

> 定稿：2026-09-05。本文是推理循环（query_loop）的**机制全景**：一轮请求的七步地图、
> 每步的具体设计、一轮带工具失败的完整实例、重试与恢复体系、优点/缺点与未完成清单。
> 权威口径上游：`44-LLM失败语义协议化设计.md`、`32-LLM调用前注入选型冻结.md`（装配时序）、
> `46-回溯replace事件化设计.md`（中断锚）。

## 1. 设计背景：四个约束决定全部形态

1. **KV 前缀稳定是最高约束**——循环的每一步（投影、注入、schema 组装）都必须保证
   "输入不变 → 发给模型的字节逐位不变"，否则缓存全废。循环因此被组织为
   "先投影后注入、易变内容永远尾插"的固定时序。
2. **失败是常态**——厂商限流/欠费/结构 4xx/网络断流都会发生；重试策略必须区分
   "可重试"与"不可重试"，且**已吐给用户的内容绝不重试**（防止重复副作用）。
3. **崩溃是常态**——进程可能在任意两个工具调用之间死掉；循环必须在每轮边界留下
   可恢复现场（配对修复 + 中断锚）。
4. **单循环多职责的代价被接受**——投影、注入、权限、plan、ask 全在一个 1895 行的
   函数里（反巨石规矩下它被定性为"接线点"），换来的是时序绝对可控。

## 2. 一轮请求的七步地图

```
while True:  # query_loop.py:757
  ① project_for_model      投影：C0/C1/C2 压缩历史（memory/runtime.py）
  ② apply_tool_output_fences  γ4 围栏：所有 tool_result 包 untrusted
  ③ run_pre_llm_inject     T_now：易变块伪造 tool 对尾插（压缩之后！）
  ④ model.stream           发请求（稳定 system + 投影历史 + env 假对 + 冻结 schemas）
  ⑤ 解析                    OpenAI tool_calls / 裸 XML 双入口 → ToolUse
                           → _admit_tool_use（预算检查 → 权限裁决 → ASK 挂起）
  ⑥ run_tools_partitioned  执行：安全批并发 + 不安全（Edit/Write/Bash）串行
  ⑦ 落盘                    结果入 MessageStore → JSONL → 回到 ①
  无 tool_use → FinalEvent 出循环 → turn 结算
```

| 步 | 关键文件 | 不变量 |
|---|---|---|
| ① | `memory/runtime.py project_for_model` | 投影缓存签名（消息数/冻结点/cursor/摘要指纹）失配才重算 |
| ③ | `prompt/pre_llm_inject.py` | env 假对**不进** MessageStore/JSONL |
| ④ | `model/openai_compat.py` | schemas 逐字节复用 `_schemas_cache` |
| ⑤ | `engine/query_loop.py:974`、`engine/xml_tool_call.py` | 双入口都产 ToolUse，共用裁决，不绕权限 |
| ⑥ | `tools/orchestration.py:286` | 不安全工具串行（读写竞态），安全批并发 |
| ⑦ | `session/message_store.py` | narration 剥离点；`known_ids` 防重复落盘 |

一句话：**①-③ 是"翻译"（装配层），④ 是一次豪赌（缓存与钱），⑤-⑥ 是"纪律"
（裁决与分区），⑦ 是"底账"。出循环只有一条正门（FinalEvent）和三条侧门
（abort / 预算超限 / 崩溃）。**

## 3. 关键机制

### 3.1 投影缓存与字节稳定

`use_proj_cache` 不再看 C2 gate（2026-09 解耦）：决定投影结果的全部可变字段
（frozen_until/cursor/摘要指纹/消息数）都在缓存签名里——输入不变则投影逐字节复用；
aging 边界在命中路径上显式先行推进。**两次压缩之间，前缀逐字节不动**——这是
KV 命中率 median 93.9%（47 号 §5.2）的直接来源。

### 3.2 流解析与 tool_use 双入口

- **OpenAI 结构化**：`_openai_common.consume_sse_line_with_usage:82`——tool_call 按
  `index` 分桶（乱序/跨 chunk/部分 JSON），`_emitted` 防重复 emit，流尾
  `_finish_tool_bufs` 兜底未闭合 buffer；reasoning 只取 `delta.reasoning_content`；
- **裸 XML 第二入口**（GLM 类）：`engine/xml_tool_call.py` 的 `XmlToolCallBuffer.feed`
  产出同样的 ToolUse 合入主线。已知弱点：参数值含 `</tool_call>` 字面量会被提前截断、
  未闭合块滞留 buffer 直到流末（六轮审计）；
- **重试安全门**：`saw_any`（`query_loop.py:1068`）——只要吐过一个 chunk 就不再原地
  重试（防重复计费/副作用），失败 chunk 永不入史。

### 3.3 LLM 失败分类与重试（单一权威）

`common/errors.py classify_llm_failure:77` → `LlmFailure(code, retryable, retry_after_ms)`：

| 类别 | 处置 |
|---|---|
| 429 / 408 / 5xx / 网络错 | retryable → 退避重试 500ms→10s（`query_loop.py:237`） |
| 401/403 | auth 错，不重试，友好化上抛 |
| **结构类 4xx** `ENV_FALLBACK_STATUS={400,404,405,413,415,422}` | env_channel **未吐 chunk** 时触发 env_channel→legacy 声道回退重建重试（`t_now_strategy.py:75`，进程级备忘防反复）；与消息结构无关的 402/429/5xx **不**回退 |
| 400 超长上下文 | 不重试，提示压缩 |

已知盲区（六轮审计）：httpx 路径的流中异常（`RemoteProtocolError/ReadTimeout`）
不在捕获/分类集——半截消息丢失且不可重试；无流空闲超时（总超时 180s）。

### 3.4 工具执行分区与结算

`run_tools_partitioned`（`orchestration.py:286-323`）：安全工具（读类）批并发 +
不安全工具（Edit/Write/Bash）串行——读写竞态在结构上避免。每个 tool_use 先过
`_admit_tool_use`：预算检查（超限即 grace 提醒/硬停）→ `evaluate_policy` 三态裁决 →
ASK 挂起（`PermissionCoordinator`，TTL 180/60s）→ 放行执行 → `_execute_audited`
（tool.started/finished 审计）→ 输出预算 + spill（16000 字符闸）→ 结果落盘。

### 3.5 崩溃恢复三件套

1. `_repair_unpaired_tool_calls:181`：流中断留下的未配对 tool_use 在恢复时修复；
2. `_persist_interrupted_anchor:274`：中断锚写入转录，重启后标 recovery_required；
3. `hydrate._repair_unclosed_tool_uses`（`hydrate.py:73-114`）：加载时只读工具合成
   `TOOL_NOT_STARTED`、写工具 fail-closed 合成 `TOOL_OUTCOME_UNKNOWN`（不假装成功）。

## 4. 一轮带工具失败的完整实例（虚构剧本）

**枪 N**：①投影命中缓存（签名未变，0ms）→ ③注入本轮"jobs 补投"块（env 假对尾插，
前缀不动）→ ④发出：prompt 48k，命中 47.9k（99.6%），单枪 ¥0.004。

**枪 N+1**：模型吐 tool_use `Bash(git push)` → ⑤裁决：bash_policy 黑名单未命中 →
策略规则命中（push 属写操作）→ **ASK** → `PermissionCoordinator.request` 写
`permission.pending` 审计 → SSE 推 `PermissionPendingEvent`（choices/intent/expires_at）→
用户 40s 后 allow → grant 落库（指纹=Bash+`git push` 前缀）→ 执行 → push 网络错
`NetworkError`（retryable，但工具层不重试，错误文本进 tool_result）→ ⑦落盘。

**枪 N+2**：模型看到失败原因，改走 `git push --no-verify`？——被 bash_policy 密钥/
规则层 DENY（-no-verify 在禁用表）→ DENY 文本进 tool_result → 模型换正确路径。
第三次 DeepSeek 5xx：`classify_llm_failure` → retryable → 退避 2s 重试成功。

**枪 N+3 断电**：进程死在第 ⑥ 步中途 → 重启 → `mark_crashed_as_recovery` →
hydrate 合成 `TOOL_OUTCOME_UNKNOWN` → 中断锚告诉模型"上一轮工具结果未知" →
模型重查状态后继续。**全程没有任何一步需要人工修数据。**

## 5. 优点 / 缺点与情况说明

### 5.1 优点

1. **时序确定性**：七步顺序固定、投影缓存签名完备——"输入不变则字节不变"被
   结构保证，这是 KV 命中率 93.9% 的根；
2. **失败语义单一权威**：`classify_llm_failure` 一处分类，下游零字符串猜测；
   `saw_any` 门 + "失败 chunk 不入史" 让重试天然幂等；
3. **可恢复闭环完整**：配对修复 + 中断锚 + fail-closed 合成结果——崩溃后无需
   人工修数据即可续跑；
4. **双入口一纪律**：OpenAI 结构化与裸 XML 两个解析入口汇入同一 ToolUse/裁决/
   审计管道，无旁路；
5. **分区执行**：读写竞态在编排层结构性避免（不是靠约定）。

### 5.2 缺点与情况说明

1. **1895 行单函数巨石**（`query_loop.py:691`）：投影/early/权限/plan/ask/abort
   全混在主循环——时序可控的代价是可测性差，决策闭环无法单测（反巨石规矩把它
   定性为接线点，但它已经远超接线点体积）；
2. **无反思环节**：循环只有"执行→下一枪"，没有"上一轮结果对不对"的显式判定
   （对照 47 号记忆系统的 NightShift 守门，循环没有对应的自检步骤）；
3. **httpx 异常盲区**：`aiter_lines()` 无 try，断流抛出的 httpx 异常既非
   ProviderError 也非 OSError → 半截消息丢失且不可重试（六轮审计 #14）；
4. **无流空闲超时**：只有总超时 180s，慢供给"吐一字后停滞"要等满 180s；
5. **术语双关**：内层 Turn（预算轮）与外层 Turn（submit）同名——读代码时
   必须靠上下文区分；
6. **XML 第二入口健壮性弱**：闭合标签无转义、畸形块滞留 buffer（兜底够用但
   不建议依赖）。

## 6. 耦合与解耦

- **循环 × 装配层**：①-③ 的顺序是硬契约——投影在注入之前（env 假对永不进压缩区）；
  若未来新增模型调用点（如摘要旁路）必须复用同一链路，否则绕过 γ4 围栏
  （六轮审计 §6 旁路风险）；
- **循环 × 预算**：预算检查点嵌在 ⑤ admit 阶段——超限是"提醒一次（grace）再硬停"，
  不是立即死；
- **循环 × 回溯**：⑦ 落盘经过 `RewindExecutionContext`（contextvars 注入），文件工具
  借此记录 before/after 快照——循环为容错层提供钩子但不感知其存在；
- **循环 × server**：通过 turn_runner 的监听反转解耦，循环内无一行 server import。
