# 53-验证门控收敛架构设计（Verification-Gated Convergence）

> 2026-09-06。动机：Terminal-Bench 实测暴露的"真不会"失败类——**模型用小用例自测通过即宣布完成，
> spec 边界从未验证**（circuit-fibsqrt #1：32 位电路过小用例，n=1682 起全错，134k token 就交卷；
> 同题充分探索版 1.44M token 解出）。这不是提示词问题，是引擎状态机缺一个环节。
> 原则：**"完成"从模型的声明，变成引擎拥有的状态转移。**

---

## 一、失败的结构性归因（为什么 skill 治不了）

当前 query_loop 的收敛路径：

```
… → tool_loop → 模型输出"我做完了" → 会话结束 → 判分
```

三处结构缺陷：

| # | 缺陷 | 证据 |
|---|---|---|
| S1 | **完成 = 模型声明**，引擎无验证环节。模型的"自认完成"直接是终态 | TB#1 失败 trial：模型自报 done，判分 0 |
| S2 | **自测域由模型自选**，引擎不检查自测是否覆盖 spec 声明的域 | 模型只用 32-bit 用例自测（`2147483648 … OK`），spec 里 n≤48401（结果 49 位） |
| S3 | **早弃不可拦截**：budget 只防"无限跑"，不防"未验证就停" | 同题 134k token 放弃 vs 1.44M token 解出 |

skill/提示层修复的本质是把"请记得验证大数"写进上下文——模型可以遵守也可以不遵守，**没有强制力**。架构修复让"跳过验证"在引擎层不可表达。

---

## 二、核心设计：完成门控（Completion Gate）

### 2.1 新状态机（query_loop 改造点）

```
… → TOOL_LOOP → DONE_PROPOSED（模型声明完成）
                      │ 引擎拦截，进入：
                      ▼
                 VERIFYING ──全部证据绿──→ DONE（终态，允许会话收敛）
                      │任一证据红/证据不足
                      ▼
                 REPLANNING（失败证据注入为下一目标，探索预算续扣）
                      │验证轮次超限（默认 2 轮）
                      ▼
                 DONE_AS_IS（如实收敛，标记 verification_failed，不伪装成功）
```

- `DONE_PROPOSED` 是**唯一**的收敛入口；模型直接停止时引擎视为 DONE_PROPOSED 并进入 VERIFYING（对 stop 语义的拦截，与权限层"DENY 先于 grant"同一设计哲学：**引擎对终态拥有否决权**）。
- `DONE_AS_IS` 保证诚实边界：修不好就是修不好，标记失败原因，不伪装——收益报告与判分都吃得到真实信号。

### 2.2 验收证据对象（AcceptanceEvidence，一等数据，不是提示词）

新增引擎数据结构，挂在 `task_state`（goal_state 已有目标判据位，扩展即可）：

```python
@dataclass
class AcceptanceItem:
    check_id: str          # 如 "range-max-n"
    source: str            # "spec" | "test-suite" | "property"
    statement: str         # 机器可执行断言的描述
    command: str | None    # 引擎可执行的验证命令
    status: Literal["pending", "green", "red"]
    last_output_digest: str | None
```

- **证据从哪来**（引擎推导，非模型自由发挥）：
  1. `spec`：任务指令中的数值范围/规模/格式约束（TB 场景即 instruction.md 的可执行化；生产场景即用户验收标准/CI 用例）；
  2. `test-suite`：环境里现成的测试/检查命令（TB 的 `/tests` 不可见，但任何"给定测试"都属此类）；
  3. `property`：引擎按条目类型套用的**性质模板**——数值类必查"spec 声明的最大规模"，文件类必查"产物存在+规模+语法有效"，服务类必查"端口/进程存活"。
- **完成门控规则**：`DONE ⇔ ∀item.status == green`。规则在引擎，模型无法绕过。

### 2.3 覆盖差距检测（治 S2 的引擎机制）

VERIFYING 入口做一次**静态覆盖比对**：收集模型本轮自测过的输入域（工具调用里可观测：跑过哪些用例/测试），与 spec 推导域对比。
差距检测的最小实现（够用且确定性强）：

- spec 声明了最大规模/量程 ⇒ 至少一条证据的验证输入 ≥ 该规模的 90%；
- spec 声明了格式/协议 ⇒ 至少一条证据做过产物语法校验；
- 自测输入域 ⊊ spec 域 ⇒ 自动补一条 `property` 证据。

circuit-fibsqrt 案例回放：spec 含 n=48401 ⇒ 引擎要求"满量程验证"证据 → 模型的 32-bit 自测不满足覆盖 ⇒ 自动补跑全量测试 → 溢出当场暴露 → REPLANNING。**#1 的失败在架构下不可发生**。

### 2.4 双预算制（budget.py 改造点）

| 预算 | 内容 | 默认 |
|---|---|---|
| 探索预算 | 模型主循环的轮次/token（现状） | 不变 |
| **验证预算（独立保护）** | VERIFYING 阶段的验证命令执行与修复轮 | 每收敛尝试 2 轮；token 上限 = 主循环的 25% |

关键性质：验证预算**独立记账、不可被探索挪用**——防止"token 快用完所以跳过验证"的隐性挤压（这正是 Terminus-2 #1 早弃的结构诱因之一）。

### 2.5 分层验证（成本优化：门控的 token 开销 <3%）

初版设计把 VERIFYING 想成"模型再跑一轮验证"——贵的是推理 token（P1 实测 output 4.5 元/M 是成本主驱动）。分层后，**验证的主要工作从模型挪到引擎**：

| 层 | 谁执行 | 干什么 | token 成本 |
|---|---|---|---|
| **L0 静默门控** | **引擎**（确定性代码） | 机械推导证据清单（regex/规则解析 spec，非模型生成）+ **引擎直接执行验证命令**（跑测试/查产物），全部绿 → 放行，**模型全程无感** | **≈0** |
| **L1 结构化自审** | 模型（**用户提案：自问一遍**） | 收敛前一轮**定长 schema 自审**（JSON：最大规模测了吗/溢出查了吗/边界条目逐条 yes-no+一行证据），引擎用它**挑选**还需补跑的证据，不被信任、只做路由 | ~1-2k tok，**+1-3%** |
| **L2 修复轮** | 模型（仅当 L0/L1 出红） | REPLANNING：失败证据注入，think 封顶（防推理风暴） | 只在失败 trial 发生——**这钱买的正是解决率** |

关键性质：
- **全绿路径成本≈0**：好 trial 的门控开销只有 L1 的 ~1-2k token（占 0.46 元 trial 的 ~1.5%），取代初版"+20-40%"的全量验证轮；
- **自审不可信但有用**：L1 的价值不是"模型说验证过了就算过"（那是 skill 层老路），而是①让模型显式暴露"我没测满量程"这类缺口，②给引擎的 L0 提供补跑路由——**执行权始终在引擎**；
- **坏 trial 才付 L2**：初版 20-40% 的开销现在只在失败 trial 发生，且恰好对应它换来的解决率增量；
- 早弃拦截（双预算）保持零成本不变。

修正后的成本账：全绿 trial +1~3%，失败 trial +20-40%（买解决率），按 P1 比例（约 1/3 trial 需修复轮）**期望开销 ≈ +8-15%，较初版砍半以上**。

### 2.6 失败证据回流（与记忆层的接口，非 skill）

REPLANNING 与 DONE_AS_IS 时，引擎把**结构化失败记录**（失败证据 check_id、判分输出摘要、失败类标签：overflow/timeout/infra/wrong-approach）写入记忆层（走 `memory/write_policy` 正常门禁）。消费点：同类任务下次进入时，`task_state` 挂载历史失败类标签作为验收清单的先验条目。这是数据流，不是往 prompt 里塞语录。

## 三、与现有模块的映射（改造成本评估）

| 改造点 | 落在 | 改动量级 |
|---|---|---|
| DONE_PROPOSED/VERIFYING/REPLANNING 状态 | `engine/query_loop.py`（现七步循环的收敛分支） | 中：新增 1 个状态 + 1 个拦截点 |
| AcceptanceEvidence 存储 | `engine/task_state.py` / `engine/goal_state.py`（判据位扩展） | 小：一个 dataclass + 持久化字段 |
| 覆盖差距检测 | 新模块 `engine/verification.py`（spec 解析 + 覆盖比对 + 性质模板） | 新文件，~400 行 |
| 双预算 | `engine/budget.py`（预算类型加枚举） | 小 |
| stop 拦截 | query_loop 收敛分支（abort.py 同款互斥语义复用） | 小 |
| 结构化失败回流 | `memory/write_policy.py` + `memory/governance.py`（新 failure 记录类型） | 小 |
| 汇报与审计 | narration 事件 + 审计日志加 `verification` 事件类 | 小 |

总量级：**新模块 ~400 行 + 五处小改**，无迁移、无接口破坏。`plan.py` 的人工审批闸保留，VERIFYING 的自动收敛与其正交（人工审批的是"计划"，门控的是"完成"）。

## 四、成本与收益测算（用 P1 实测数据，分层门控修正版）

- 验证轮开销（分层后）：全绿 trial 仅 L1 自审 ~1-2k token（+1~3%）；失败 trial 才进 L2 修复轮（+20-40%），按 P1 失败率折算**期望开销 ≈ +8-15%**（初版设计为 +20-40%，分层砍半以上）；
- 收益：消灭"未验证即交卷"类失败（P1 失败样本中该类占 1/2；行业上这类"自认完成"失败通常占 agent 失败的 30-50%）；
- 净效应：以 ~8-15% 成本换预计 10-25pp 解决率提升（31 题子集上验证），**性价比显著为正**，且产出可写进简历的架构级差异点。

---

## 五、P3 实验协议（量化验证本设计）

1. **对象**：P2 完成后取失败子集（预计 6-10 题）+ 3 题已解题（回归组，验证不伤好题）；
2. **A/B**：同模型（deepseek-v4-flash）、同 k=3，XEYO（含验证门控）vs P2 基线分数；
3. **指标**：解决率差值（主）、验证轮拦截次数、早弃率、单 trial 成本、DONE_AS_IS 诚实率；
4. **预期**：circuit-fibsqrt 类（可修能力题）转绿；cobol 类（infra 已修）归零；若某题验证后仍红 → DONE_AS_IS 如实计 0，不污染数据；
5. **成本**：失败子集重跑 ~10-20 trials ≈ 5-15 元。
