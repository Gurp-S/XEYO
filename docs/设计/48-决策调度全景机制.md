## 1. 设计背景：四个约束决定全部形态

1. **单用户桌面场景**——没有服务端集群与租户隔离需求，调度优先解决"单会话内多任务
   不打架、多会话不互踩"，而不是吞吐与负载均衡。因此没有引入常驻调度器，而是
   "模型自主派生 + 确定性护栏"。
2. **决策边界：能引擎强制的不过模型**——任务是否"完成"由引擎信号（todo 全 done、
   子代理全成功）派生，不由模型自评；审批（plan / 危险命令）由人工决议。模型只负责
   "提议"，引擎负责"记账与放行"。
3. **可恢复优先**——armed 状态只存内存、重启不自动续跑（`goal_state.py:11`）；
   任务状态机落盘（`os.replace` 原子写）。宁可"重启后停住等指令"，不可"恢复即跑飞"。
4. **反失控是硬门槛**——模型派生的并发必须被三重预算（轮次 / 工具调用 / 唤醒次数）
   兜住；一切自动推进都有"人类恢复"通道。

## 2. 三层地图与数据流

```
用户 submit ──► turn_runner（DetachedTurn：一次 submit 的生命周期）
                    │
                    ▼
        query_loop 主循环（决策执行体，见 49 号全景）
                    │
      ┌─────────────┼──────────────┐
      ▼             ▼              ▼
  Agent 工具    TodoWrite       ExitPlanMode
      │             │              │
      ▼             ▼              ▼
 subagent_runner  task_state     plan.py（人工审批闸）
 （协程并发，      SessionTaskState（进程内权威状态机）
  深度≤1）
      │
      ▼ 异常/未带回
 agent_settlement ──下轮 T_now 注入──► 主循环
      │ 成功信号（todo 全 done / 子代理全成）
      ▼
 goal_state.Goal（被动候选，pending_complete）
      │ server 侧 goal_round_driver 推进
      ▼
 合成轮（synthetic_round，无用户输入自动推进）
```

| 组件 | 职责 | 寿命 | 持久化 |
|---|---|---|---|
| turn_runner / turn_snapshot | 一次 submit 的生命周期、SSE 订阅、崩溃恢复 | 单 turn | turn 快照 |
| SessionTaskState | 进程内权威任务状态机 | 会话 | 落盘 |
| plan.py PlanEngine | ExitPlanMode 的人工审批暂存 | 单次审批（TTL 180s） | 无（进程内） |
| goal_state.Goal | 目标 5 态状态机（被动候选） | 会话+跨重启 | 原子写 |
| goal_round_driver（server） | 合成轮推进 Goal | armed 期间 | 无（armed 内存态） |
| scheduler（DAG） | 任务图调度 | —— | **未接线（死路径）** |
| subagent_runner / AgentTool | 子代理生命周期 | 单次调用 | 结算记录 |
| budget / repeat_guard / abort | 三重护栏 | 会话 | 部分落盘 |

一句话：**turn 是壳，query_loop 是执行体，Goal 是候选，goal_round_driver 是唯一的
自动推进器，scheduler 是已建成未通车的备用线，三重护栏是底网。**

## 3. 各组件机制

### 3.1 turn_runner / turn_snapshot（submit 生命周期）

一次用户 submit = 一个 `_DetachedTurn`（`turn_runner.py:58`）：持有 SSE 订阅者、
任务状态、快照。设计要点：

- **SSE 仅是订阅者**：客户端断连只 `note_client_disconnect`，**不 interrupt**——
  turn 转 detached 继续跑完（GUI 断线重连靠 cursor 回看补帧）；
- **崩溃恢复**：进程重启时 `mark_crashed_as_recovery`（`turn_snapshot.py:167`）把
  running 标为 recovery_required，配合中断锚（`query_loop._persist_interrupted_anchor:274`）
  与未配对 tool_use 记录恢复现场；
- **结算监听反转**：`set_turn_settlement_listener`（`:39/354`）由 server 反向注入回调，
  engine 不 import server，依赖方向干净。

### 3.2 SessionTaskState 与双状态机问题

`task_state.py:26` 是进程内权威：idle → running → waiting_* → settling → done/error。
**已知债务**：它与 `TurnSnapshot` 的 status 枚举并存、语义重叠（六轮审计"双份状态机"
模式）；且内层预算 `Turn`（模型轮，`budget.py:3`）与外层 `turn_runner.Turn`
（submit 生命周期）同名异义——跨层契约靠注释约定。

### 3.3 plan.py：人工审批闸（非任务分解）

`plan.py` 只做一件事：ExitPlanMode 触发时创建 `PendingPlan`（进程内、按 turn_id 索引、
TTL 180s），前端 `POST /v1/plan/{turn_id}/approve` 批准/拒绝后同一事件流恢复执行。
**它不是规划器**——没有任务分解、没有 Plan→Act→Check 结构。规划的真身在 Goal。

### 3.4 goal_state.Goal：被动候选状态机

- **5 态合法迁移表**（`goal_state.py:70` 起）+ CAS 修订（`GoalConflict:241`）+
  `os.replace` 原子写；
- `pending_complete` 是**软信号**：由"TodoWrite 全 done / 子代理全成功"派生
  （`derive_candidate:147`，query_engine `_maybe_advance_goal_round:439` 只 mark）；
  完结"由外层决定"（`:5`）——引擎自己不收口；
- **armed 只在内存**：重启不自动续跑，防"恢复即跑飞"。

### 3.5 goal_round_driver：唯一的自动推进器（server 侧）

`server/goal_round_driver.py`：arm → `_schedule`（防抖 2s）→ `_precheck` →
`submit_synthetic`（ASGI 自调 chat 接口，复用整条管线，`synthetic_round.py:41`）→
drain SSE → `admit_round` CAS 推进。**三重失控护栏**：

1. `resolved_max_rounds` 默认 32 轮硬顶；
2. 共享唤醒预算 `MAX_CONSECUTIVE_WAKES=3`（`job_registry.py:32`，与后台 jobs 共用）——
   ≥3 次连续自动轮自动停；
3. 只有 `restore_wake`（人工）能恢复——入口受路由级 loopback 门禁保护
   （`goals.py:27`）。

### 3.6 scheduler：已建成未通车的 DAG（死路径）

`scheduler.py:357 Scheduler.run`：Task 拓扑序 + scope 冲突串行 + `prepare_for_resume:851`。
但 `run_task_batch` 在生产路径（HTTP/主循环）**零调用方**（grep 全仓仅 tests）。
50+ 用例高强度覆盖的是这条死路径——"测试绿"给"已接线"的假象（四轮审计结论）。

### 3.7 subagent_runner / AgentTool：主副关系

- **派生**：主循环同轮并发调 Agent 工具 → `run_tools_partitioned`（`orchestration.py:247`）
  `asyncio.gather` 协程并发（非进程隔离）；
- **裁剪**：工具面按 scope 裁（`scheduler.py:191`，空 scope=只读工人）；
  `FORBIDDEN_SUB_TOOLS`（含 `_agent` 自身）永不下发（`subagent_context.py:49`）；
  `MAX_DEPTH=1` 递归防火墙（`agent_tool.py:32`）；
- **写入**：子 agent 写工具注入 WriteStore（乐观锁 + 作用域硬门），写范围过宽自动降只读；
- **回流**：结果包 ToolResult 回主会话；异常逃逸记 `agent_settlement`（FIFO 16 条），
  下轮 T_now 注入归因块（`agent_settlement.py:16-78`）；follow-up inbox "park 不 inject"，
  settle 时 drain（`live_agents.py:68-96`）；
- **并发上限**：`_agent_slots = Semaphore(8)` 模块级全局（跨会话共享）。

### 3.8 三重护栏

| 护栏 | 机制 | 参数 |
|---|---|---|
| BudgetTracker | 轮次/工具调用/USD 三维，grace 窗口只提醒一次防单轮爆发误触收尾 | max_turns=256、max_tool_calling=64（`budget.py:19-25`） |
| RepeatCallGuard | 重复调用检测 + ZeroHitTracker | **只提醒永不拒执行**（`repeat_guard.py:7/216`） |
| AbortController 树 | LinkedAbortController 局部超时联动 | abort 整批取消 |

## 4. 一个目标任务的流水线实例（虚构剧本）

**T1 第 2 轮**：用户"把迁移做完" → 模型 TodoWrite 4 条 + 调 Agent（scope=fileA）
并发跑两个只读工人 → 一个工人 `Bash: python -m pytest` 超轮次被 BudgetTracker 掐断 →
`record_agent_settlement` → 下一轮主循环 T_now 收到"子代理 X 因超轮次终止，已完成 2/4 步"。

**T1 第 5 轮**：todo 全 done → `_maybe_advance_goal_round` 把 Goal 标
`pending_complete`（候选，不收口）→ 用户"继续" → server 侧 arm goal_round_driver。

**T2 起**：driver 每 2s 防抖后发合成轮（无用户输入），模型自查补漏；第 3 个合成轮
再次全 done → `admit_round` CAS 推进 → 第 4 轮前唤醒预算 ≥3 触发 → 自动停，
面板显示"需人工 restore_wake"→ 用户确认完成 → Goal → completed（原子写落盘）。

**T3 中途用户改口**："先别做迁移了，去修登录 bug" → 模型 ExitPlanMode 提交新 plan →
人工批准 → 旧 todo 被 TodoWrite 全量替换 → Goal 重新派生候选。全程没有任何
"模型自评完成"的环节——收口永远有引擎信号或人工。

## 5. 优点 / 缺点与情况说明

### 5.1 优点

1. **turn 与 SSE 解耦是同类项目少见的设计**：断线不杀任务、重连 cursor 补帧、
   detached 落账，配合崩溃恢复（recovery_required + 中断锚 + 配对修复）构成完整可恢复闭环；
2. **Goal 状态机工程严谨**：5 态合法迁移 + CAS 修订 + 原子写 + armed 不持久，
   "恢复即跑飞"在结构上被排除；
3. **合成轮三重护栏是真实有效的失控防线**：32 轮硬顶 × 唤醒预算 3 × 人工恢复，
   且入口有门禁（对照审计：这是 server 层做得最好的部分）；
4. **子代理安全裁剪完整**：scope 白名单、空 scope 只读、深度防火墙、FORBIDDEN 表、
   结算注入——失控子代理的爆炸半径被压到会话内；
5. **护栏参数全部有据**：grace 窗口防误触收尾（`budget.py:77-80`）、结算 FIFO 16 条
   防注入膨胀。

### 5.2 缺点与情况说明

1. **无真调度策略（最大缺口）**：活路径没有任务队列/依赖图/优先级，多任务并行是
   "模型涌现 + 全局信号量"；Scheduler 是死代码，`prepare_for_resume` 未接线——
   中断的批任务无法恢复；
2. **协程级"伪并行"**：子代理共享事件循环，任一阻塞调用饿死全部；无 worker 进程池，
   无墙钟超时（只有轮次上限——廉价工具死循环可无限挂钟）；
3. **无优先级/抢占**：abort 只能整批取消，无单任务优雅抢占；`_agent_slots=8`
   跨会话共享，无 aggregate 配额；
4. **双状态机 + 术语双关**：SessionTaskState vs TurnSnapshot、内层 Turn vs 外层
   Turn——跨层契约靠注释，重构高风险区；
5. **无反思/验证环节**：决策层只执行不判定"对不对"（对照 47 号：记忆系统有
   NightShift 守门，决策层没有对应物）——收口/重规划全靠外层（server 合成轮）；
6. **活路径可恢复性弱于批路径**：任务级 checkpoint 只在死路径 scheduler 里有。

## 6. 耦合与解耦

- **goal_round_driver × job_registry 共享唤醒预算**：全仓唯一的跨机制资源协调点
  （`MAX_CONSECUTIVE_WAKES=3`），没有中央调度器——两个"自动推进源"靠共享计数器互斥；
- **turn_runner × server**：依赖反转（监听注入），engine 无 server import——方向正确；
- **scheduler × 活路径**：物理隔离（无调用），但测试资产投在死路径上，产生"已接线"
  认知错觉——建议二选一：接线（把 run_tools_partitioned 的批量场景迁入）或删除。

## 7. 未完成清单（更新至 2026-09-05）

- **P0**：子代理墙钟超时（现仅轮次上限）；scheduler 接线或删除（终结死路径）；
- **P1**：turn 统一命名（外层 Run/Submit，内层 Round/Step）；SessionTaskState 与
  TurnSnapshot 合并或明确主从；全局 aggregate 配额（token/进程数）；
- **P2**：任务级 checkpoint/resume（活路径）；单任务优雅抢占；worker 进程池隔离
  （子代理真并行）；
- **P3**：反思/验证钩子（turn 边界对照 Goal/todo 的轻量自检）；Goal 稳定 N 轮后
  引擎自动合成验收（现由 server driver 承担，引擎侧无此能力）；
- **持续**：`agent_slots` 等散落上限（10/8/10/64）收敛为单一配置源。
