# 54-契约驱动执行与承诺结算（Verification-Gated v2 → Contract-Driven）

> 2026-09-06。53 号把修复设计成"交卷前的验证门"，仍带着基准的形状。
> 本文是重新框定：**引擎不是"完成任务后去对答案"，而是"持有一份契约，在预算内维护一组不变量，
> 结算时如实报告每条承诺的兑现状态"**。基准只是契约的一种来源。

---

## 一、为什么 53 号仍偏"做题 agent"（自我批判）

| 53 号机制 | 做题味在哪 |
|---|---|
| 验证门控（DONE_PROPOSED→VERIFYING） | 隐含"存在一个考官"——真实用户场景里没有考官，只有"我要的东西拿到没有" |
| 覆盖差距检测 | 形状像"猜考纲"：按 spec 声明的维度补测试 |
| 净室重执行 | 形状像"模拟判分环境" |
| 交付清单核对 | 形状像"对着评分表打勾" |

共同问题：**它们都在"任务完成"这个时刻点做一次性补救**。真实世界的好 agent 不是交卷前突击检查，
而是**从头到尾以可交付的方式工作**。

## 二、判据：什么才算"架构"而不是"做题"

> **同一性判据**：一个机制如果换到"用户在 IM 里让 XEYO 修一个 bug"的场景，
> 是否逐字同样触发、同样有益？只有在非基准场景同样成立的机制才进架构。
> （基准专属的旁路、题目知识、判分器特化，一律不进。）

按此判据重审，发现我要的东西其实早有"真实世界孪生"：

| 机制 | 基准场景 | 真实孪生（必须同一实现） |
|---|---|---|
| 交付物核对 | 对测试断言 | 用户要的文件/接口真的给出且可用 |
| 词汇一致性 | spec 字段名 | **用户指定的接口/路径/命名必须逐字尊重**（把 `value` 写成 `val` 对真实用户同样是事故） |
| 净室执行 | 模拟判分环境 | **交付物离开我的会话上下文仍然可用**（可复现性——第三方拿到就能跑） |
| winding-down | 抢在超时前落盘 | **预算耗尽时交出"可用的部分成果+如实的状态报告"**，而不是无声蒸发 |

结论：机制本身多数是对的，**错的是挂载点（挂在任务终点）和驱动源（挂在判分器视角）**。

## 三、重新设计：三个一等公民对象

### 3.1 契约对象（Contract）——一切机制的单一驱动源

任何请求源（用户消息 / 基准指令 / 工单 / 定时任务）在进入引擎前**归一化**为一个契约：

```python
@dataclass
class Contract:
    deliverables: list[Deliverable]     # 交付物：路径/接口/形式（用户或 spec 声明）
    vocabulary: set[str]                # 请求方使用的命名实体（字段/路径/参数名）——逐字约束
    dimensions: dict[str, list]         # 声明的维度域（规模/并发数/位宽…）
    budget: Budget                      # 时间/token/金钱 三桶（见 3.2）
    acceptance: Acceptance | None       # 验收程序（若请求方给出；TB=隐藏测试，用户=口述标准）
```

- TB 的 instruction.md 只是**契约的一种解析来源**，与"解析用户消息里的交付要求"走同一条管线；
- 契约在 plan 阶段落定（模型声明交付物清单 = 补全契约的 deliverables 槽），引擎此后一切调度都对着契约。

### 3.2 预算即资源调度（三桶保留制）——winding-down 的去基准化

时间/token/金钱是**保留式资源**（reservation semantics），不是事后统计：

```
探索桶（默认 70%）— 发现与实现
验证桶（保护 15%）— 验证交付物满足契约（净室执行、维度扫描）
结算桶（保护 15%）— 收尾：落盘、报告、清理
```

- 桶不可互相挪用；**引擎按桶调度长命令**（探索桶里的命令 >60s 自动后台化——XEYO 的
  `run_in_background` 机制从"模型可选项"升级为"调度器策略"）；
- **落地状态（2026-09-06）**：调度器强制后台化**已在引擎中实现并默认生效**——
  `bash_tool.py` 两阶段前台执行：`BASH_PROMOTE_DEFAULT_MS = 45_000`，前台命令 45s 未结束即
  `_promote_running()` 晋升为 registry job（**进程不重启**、已累积输出随晋升返回模型、完成后自动通知，
  `XEYO_BASH_PROMOTE_MS` 可覆盖）；工具提示词已告知该语义。`tests/test_bash_promote.py` 12/12 通过。
  这是 XEYO 相对 Terminus-2（无此机制，P2 的 A 类失败直接源于此）的既有结构优势；P3 的 XEYO 臂天然继承。
- 探索桶耗尽即进入结算态（winding-down 的本质）：不是"抢分"，是**预算纪律**——
  任何有预算的真实 agent 都该如此（用户的 5 美元配额不能全烧在探索上然后什么都不交付）。

### 3.3 持续不变量（不是终点检查）——净室的去基准化

净室不再是一次性终检，而是**引擎在工作过程中持续维护的不变量**：

> **INV-1（可交付性）**：引擎通过 WriteStore 的写路径追踪，始终知道哪些文件是"候选交付物"；
> 契约 deliverables 中的路径一旦出现，即进入交付物账本。
>
> **INV-2（上下文无关）**：候选交付物必须只依赖契约声明的输入。引擎在**每次写入交付物路径时**
> 静态检查其引用（路径/配置），发现依赖会话私有上下文即标记污染——path-tracing 的
> jail 依赖会在写入时就被标记，而不是判分时才爆炸。
>
> **INV-3（词汇符合）**：候选交付物对契约 vocabulary 的符合性**随写随查**（token 级比对），
> kv-store-grpc 的 `val≠value` 在第一次写 proto 时即红灯。

不变量由引擎的写路径（WriteStore 拦截点）持续执法——**没有"终点突击"**，判分时刻只是不变量状态的读取。

## 四、承诺结算（Settlement）——取代"验证门控"的终点语义

收敛时引擎产出的不是"通过/不通过"，而是一份**承诺账本**（对用户=交付报告，对基准=判分输入）：

```
承诺账本（settlement report）
├─ deliverable: /app/move.txt        → ✅ 已交付，净室验证通过（INV-2 ✔）
├─ deliverable: /app/results.json    → ⚠️ 部分交付（4/7 项完成，WAL 解密未实现，原因：…）
├─ constraint: 字段名 value           → ✅ 词汇符合
├─ dimension: world_size ∈ {1,2,4}   → ❌ 仅 1 验证通过，2/4 未通过
└─ budget: 探索 100%｜验证 100%｜结算 62%
```

- 对真实用户：这份账本就是"**我做到了什么、没做到什么、为什么**"的诚实交付报告——
  这比假装完成更有价值（用户至少拿到能用的部分 + 准确状态）；
- 对基准：测试只是对账本的一种解读方式，引擎不需要知道判分器存在；
- 模型唯一声明的东西是"我认为可以结算了"，**结算的合法性由引擎按契约+不变量裁定**——53 号的门控语义被完整保留，但驱动源从"考官"换成了"契约"。

## 六、防做题红线（实现时的自查清单）

1. `contract.py` 的任何 parser **不得 import 任何基准专属符号**；TB parser 与"用户消息 parser"同级同层；
2. 不变量检查只消费契约字段与写路径可见数据，**不消费题目语义**；
3. 结算报告对"没有验收程序的契约"（纯用户请求）必须同样有意义（诚实状态报告）；
4. 每个机制合入前回答一次：**"用户 IM 场景下它何时触发？"**——答不出即不进引擎。

## 七、P3 实验口径（不变）

失败子集 20 题 + 3 回归 + 7 基建重测，同模型 k=1 对照；预期 60.7% → 75-80%。
实验只是验证：**同一套契约驱动机制，在基准上自然表现为分数提升**——提升是副产品，不是设计目标。

## 八、【v2 重构】从"执法"到"禀赋"——只保留让 agent 本身变强的部分

> 2026-09-06 用户裁决：Contract/不变量/Settlement 仍是"做题味"，驳回。
> 重审后的结论：问题出在**挂载方式**——同样的需求，用"引擎执法"表达就是闸门，
> 用"引擎给模型新感官"表达就是能力。以下只保留禀赋型机制，执法型全部移除。

### 8.1 需求的本质重述

模型在 A/B/C/D 类失败里的缺陷，本质是**三个感官缺失**（不是纪律缺失）：

| 缺失的感官 | 人类工程师的对应物 | 失败表现 |
|---|---|---|
| 时间感 | 看表/日历 | 不知道自己快超时，还在开新实验 |
| 交付感 | 交付物清单贴在显示器上 | 忘了要产出 move.txt/primers.fasta |
| 隔离感 | "能不能在别人机器上跑"的下意识 | 交付物依赖自己会话的私有文件 |

**执法方案错在**：用闸门惩罚没有这些感官的模型（在出口拦截）。
**禀赋方案**：直接给模型这三个感官，让它像资深工程师一样自主行动——没有闸门，失败是模型自己的判断失误，成功是能力。

### 8.2 禀赋一：预算镜像（时间感的来源）

引擎每回合把**真实预算状态**渲染进模型的计划视图：`剩余时间 38% ｜ 已声明交付物: move.txt(未写), results.json(部分) ｜ 后台任务: ocr#3 运行中`。

- 模型**无法自己感知时间流逝**——这不是提示词技巧，是信息供给（与 getTime 同性质）；
- 载体是 XEYO 已有的 plan/Todo 视图（`plan.py` + TodoWrite merge 通道），预算行由引擎注入，交付物行由**模型自己的计划**维护（计划阶段声明交付物，是计划的自然组成部分，不是引擎强加的表单）；
- **没有任何拦截**：模型看到"剩余 10%、交付物未写"后自己决定收尾——判断失误就是能力问题，引擎不兜底。
- 落点：`turn_snapshot` / pre-LLM 注入通道（复用 T_now legacy 机制），预算数据来自 budget.py（已存在）。

### 8.3 禀赋二：隔离执行工具（隔离感的来源）

Bash 增加一个模型可主动调用的参数：`run_isolated=true` —— 在一个**只含声明输入的干净目录**里执行命令。

- 这不是引擎在出口偷偷做净室测试，而是给模型一个**更好的仪器**：像 IDE 的"Run in clean env"按钮；
- path-tracing 案例：模型写完二进制后主动 `run_isolated` 一把 → 发现 jail 依赖 → 自己修。不用它的模型就是没这个习惯——失败归它；
- 落点：`bash_tool` 增加参数（执行前按声明清单组装临时目录），~80 行。

### 8.4 禀赋三：经验记忆回路（把失败变成肌肉）

A 类失败的教训（"长任务先估算、超 60s 立即后台化"、"先声明交付物再动手"）由 XEYO 的记忆系统按 governance 门禁写成**惯例**（convention），后续任务的计划阶段自动携带——这是模型"越用越强"的来源，也是基准测不出来的真实成长。

### 8.5 杜绝 A 类的完整链路（全部禀赋，零闸门）

```
45s promote（已有）→ 长命令永不阻塞主循环
+ 预算镜像（8.2）→ 模型提前 20% 预算就知道该收尾
+ 交付物声明进计划（8.2）→ 收尾时知道要落盘什么
+ 经验回路（8.4）→ 下次任务从第一步就按纪律干活
= 超时截断在 XEYO 臂的结构性消灭：不是被拦住，而是它根本不会走到那一步
```

### 8.6 裁决记录

- ❌ 驳回（做题味）：引擎出口验证门控、净室强制执行、结算合法性裁定、Contract 执法语义；
- ✅ 保留（禀赋）：预算镜像、`run_isolated` 工具、经验记忆回路、45s promote（已有）；
- 待验证：P3 用同一把尺子量——若 XEYO 臂 A 类失败归零且分数提升，证明"禀赋 > 执法"。

## 九、三禀赋落地明细（文件级）

### ① 预算镜像——载体复用度 ~80%，新增 ~60 行

**载体现状**（全部已存在）：
- `prompt/pre_llm_inject.py`：注入通道 + `pending_jobs_block()`（后台任务镜像**已有**）+ `InjectContext`；
- `engine/budget.py`：`BudgetTracker`（turns/tool-calls/token/USD 四维追踪 + 软上限 notice 队列）**已有**；
- `tools/todo_write_tool/store.py`：todo 持久 store（merge 语义）**已有**。

**新增（~60 行）**：
1. `pre_llm_inject.py` 加 `budget_mirror_block(session_id)`，与 `pending_jobs_block()` 同区同层（动态注入区，不进 KV 稳定前缀）；
2. `engine/budget.py` 加 `wall_remaining()`（~15 行：task 起始时间 + agent timeout_sec → 剩余墙钟；TB 的 timeout 来自 TaskConfig，会话场景来自用户预算）；
3. 渲染格式（每回合 2 行）：

```
[预算] 回合 12/40 · $0.31/$2.00 · 剩余时间 18m
[交付] move.txt(未写) · results.json(部分)  ← 来自 todo store，如实渲染，零新表单
```

**交付物从哪来**：模型用 TodoWrite 正常写计划时自然列出（与现有 todo 流完全一致）；镜像只**如实渲染** todo 中未完成项 + 引擎可见的写路径状态（WriteStore 已知哪些契约路径已写）。无声明就无可渲染——那是模型自己的计划质量问题。

### ② Bash `run_isolated`——bash_tool ~80 行

- `BashToolInput` 增加 `run_isolated: bool = False`、`isolation_inputs: list[str] = []`；
- 执行路径：临时目录 → 拷贝声明输入 → 执行 → 返回输出 + 新产出文件清单（默认不回写原 cwd，只读隔离）；
- 失败语义：隔离目录缺文件而失败 → 输出原样返回，**引擎不解读、不补救**——信息给足，判断归模型；
- 测试：`tests/test_bash_isolated.py`（干净执行成功 / 缺输入失败如实返回 / 产出清单正确）。

### ③ 经验记忆回路——**零新机制，三个既有件**

| 环节 | 复用 |
|---|---|
| 写入 | `memory/write_policy.py` + `memory/governance.py` 既有门禁路径（教训作为 convention 类记忆走既有审批流） |
| 读取 | `memory/memindex` 既有检索（计划阶段模型本可召回） |
| 触发 | 既有回合末写入钩子加一行 failure→convention 分类 |

**诚实标注**：基准最小档案（`XEYO_BENCH_MINIMAL=1`）下 memory 关闭 ⇒ 经验回路在 P3 **不参与**（跨 trial 无记忆收益）。它是产品能力，不是分数手段——正好通过"它在基准里无效"反向证明它不是做题手段。

### 落地顺序

`run_isolated`（80 行，独立可测）→ `wall_remaining` + `budget_mirror_block`（60 行）→ ③（~20 行分类钩子）。合计 ~160 行，零新依赖，全部复用现有通道。
