# 全项目审计 · 修复收益分析（2026-09-10）

> 承接 `docs/全项目审计-20260910.md`（清单）与 `docs/全项目审计-详析与解决方案-20260910.md`（方案）。
> 本文回答第三个问题：**"每一点修完之后，到底得到了什么？"**
>
> 口径要求（本文件的自我约束）：
> 1. **收益必须是可核验的**——凡写"减少 N 行 / 关闭 X 风险 / 省 Y 元"，都附本次实测数字或代码事实；
> 2. **不做假设性放大**——算不出的地方明确写"无法量化"，不用形容词顶替；
> 3. **收益分四类**，因为它们的"价值兑现方式"完全不同：
>    - **S（安全面）**：关闭一条攻击链 / 缩小一处暴露面 → 收益 = 风险归零，不可用工作量折算；
>    - **D（数据面）**：消除一个数据丢失窗口 / 恢复一条回滚能力 → 收益 = 事故概率 × 损失；
>    - **M（维护面）**：删除死代码 / 消双轨 / 定主从 → 收益 = 可减行数 + 后续每次改动的省力；
>    - **C（成本面）**：省 token / 省算力 → 收益 = 可直接乘单价折算。
>

## 一、三条横切模式的收益

### 1. 模式 3「旁路绕主链」——收益最高，因为它消灭的是**边际成本**

**修法**：不在 3 条旁路（`workspace_fs` / 后台 job / WriteStore）各自补 `rewind` 调用，而是**下沉到共享 write gate**。

**为什么这才是收益最大的**：逐个补调用的收益是"3 条路径被修好"（一次性）；下沉到 gate 的收益是"**第 4 条路径出现时自动被覆盖**"（结构性）。前者随路径数线性衰减，后者是常数。

**具体收益拆解**

| 维度 | 修复前 | 修复后 | 实测依据 |
|---|---|---|---|
| rewind 覆盖 | 只有 3 个直写工具记账（`file_write_tool.py:486`、`file_edit_tool.py:614`、`notebook_edit_tool.py:335`） | 全部写路径记账 | 本次 grep `record_file_mutation` 全仓，生产调用点恰为上述 3 处 |
| 审计一致性 | `workspace_fs._audit_write` 失败静默吞（`workspace_fs.py:42-51`） | 失败必告警 | 直读确认 `except Exception: pass` |
| 后台 job 快照 | `destructive_guard.py:28-31` 自认不快照 | 显式 cwd 传入后快照可用 | 该文件注释自承 |
| WriteStore 账本 | 写的是 `memory.journal`（审计流水），与 rewind Before 快照**是两套账** | 一套账 | `write_store.py:25/255/318` |

**可量化收益**：
- **消掉"两套账"**——`write_store.py` 走 journal，`rewind` 走 content-addressed snapshot，两者对"文件被谁改过"给出**可能矛盾的答案**。修完后"文件历史"只有一个真相源。这是**消灭一类未来 bug**，不是修一个 bug。
- **`incomplete_tool_uses` 接线后**：崩溃恢复时未配对 tool_use 会被修复。现状是 3 个写入点 / **0 个消费点**（实测 grep）。这是一个真实功能缺口——会话被 abort 后重启，残留的悬空 tool_use 不会自愈。

**无法量化的部分**（诚实披露）："消灭未来 bug"的价值不能折算成小时数。它的真实收益体现在**代码评审时不再需要问"这条新写路径记账了吗"**——问题从"每次都要记得"变成"结构上不可能漏"。

**修法**：每处只允许两种处置——**接线**（加生产调用点 + 端到端回归）或**删除**（`git rm` + CHANGELOG 记录）。

**实测可删行数（本次逐文件 `wc -l` 与零 import 验证）**

| 模块 | 行数 | 零消费验证 | 处置建议 |

| `codeindex/cgraph.py` | 287 | `grep "codeindex.cgraph"` **零命中**，docstring 自认"离线证据门原型" | **删** |

| `tools/stub.py` | 12 | 返回 "not implemented"，无调用者 | **删** |
| **小计（零风险）** | **420** | | **可立即删** |
| `engine/scheduler.py` 主执行链 | ~600（`Scheduler` 类 `:249-897` + `run_task_batch` `:1054-1110`） | `run_task_batch` / `prepare_for_resume` 生产引用 **0**；`scheduler_for()`（`session_pool.py:871`）**定义了但从未被调用** | **处置需裁决**（见下） |

| `clear_wrap_window` | ~5 | 全仓无调用（`wrap_window.py:46`） | 接线或删 |
| **合计** | **≈1,900** | | 约占生产 Python 的 **1.8%**（105,842 行基数） |

**★ scheduler 的正确处置（本次核实后修正了首轮判断）**

首轮说"1110 行是死代码"，**不准确**。实测：`scheduler.py` 里**活着**的符号比想象中多——

```
活着（有生产消费方）：
  Task                      ← agent_tool.py:444, subagent_runner.py:924/1104
  build_tool_whitelist      ← agent_tool.py:444
  scope_conflicts           ← subagent_runner.py:978（子代理写范围互斥判定）
  MAX_DECOMPOSE_TASKS       ← subagent_runner.py:1030/1104/1232
  repair_task_graph         ← subagent_runner.py:1030
  read/clear_scheduler_checkpoint, checkpoint_is_incomplete ← chat.py:968-981

死了（零生产引用）：
  Scheduler 类（～650 行，含 _can_start/_resolved_agent_id/_persist 等 30+ 方法）
  run_task_batch / prepare_for_resume
  scheduler_for()（session_pool.py:871 — 定义了 Scheduler 实例化，但自身从未被调用）
```

**所以正确做法不是"删 1110 行"，而是"抽 5 个活符号出去，再删剩下的"**——预估净删 **~600 行**，且**不损失任何活功能**。

**可量化收益**
- **净删 ~1,900 行**（含 420 行零风险）→ 按 105,842 行生产代码算，**减 1.8%**；
- **`scheduler_for()` 是"沉默的死路"**：它存在会让读者以为"HTTP 层可以做多任务分发"（它的 docstring 就这么写的），实际上没有任何 handler 调用它。**修掉它 = 消灭一个会让新人做错假设的错觉**；
- **测试掩护被拆掉**：`test_multiagent_hardening.py` 有 6+ 处 `run_task_batch` 调用，全绿 → 给出"调度在工作"的假象。这是模式 2 最阴的部分——**测试覆盖率成了死代码的掩护**。

**收益的边际效应**：删掉后每次重构不再需要"顾着这些永不执行的分支"。按项目 30 天 118 次提交的节奏（实测 `git log --since="30 days ago"` = 118），这 1,900 行的阅读税是**每次改动都在交**。

### 3. 模式 1「双轨并行」——收益是"把 5 个 bug 面变成 0"，且其中一条是真实安全洞

**修法**：定主从 + 合并。**注意这一项不是纯卫生——第 3 组（ASK 面板）是**安全面**。

**逐组收益**

| # | 双轨 | 修复动作 | 收益 | 类别 |
|---|---|---|---|---|
| 1 | **回滚** v3 在线 / v2 降级端点 | 砍 v2 出生产（仅测试 fixture 保留） | v2 的 preflight 已被 v3 的 `GET /rewind/checkpoint/{id}` 覆盖 → **净删端点 + 消"改一处漏一处"**（内存对齐契约 `drop_engine` vs `resync_after_rewind` 不同） | M |
| 2 | **MCP 执行** 直挂 / 网关 | 裁其一 | 同一能力两套计量与审计语义 → **审计口径统一**。网关路径（`mcp_gateway.py:171`）直接 `target.execute` 仅 4KB 裁剪，绕过 `registry.run` 的编排/预算 seam | M + S |
| 3 | **ASK 面板** 权限 store / ask_store | 合并，AskUserQuestion 复用权限 store | ★ **这是真实安全洞**：`permissions/ask_store.py` 全文**零 audit 调用**，且 `resolve` 无鉴权。而权限 ASK 路径有审计 + TTL。合并后 AskUserQuestion **首次获得审计** | **S** |
| 4 | **C2 决策** formula / `a_star=="C2"` / `force_compact` | 收敛为单 `decide_c2()` | 三处各自维护 cursor 前进 + 事件记账 → **三处 → 一处**，改压缩逻辑只需改一个地方 | M |
| 5 | **SSE 消费** GUI / TUI（TUI 内还有 3 份） | 见新-1 | 见新-1 | M |

**可量化收益**
- 第 3 组：**"零审计的审批路径"关闭**。AskUserQuestion 是模型主动向用户提问的通道，现状是**问过什么、用户答什么，不留痕**。这在开源后可审计性上是硬伤。
- 第 1、4 组：合计可减 **~300 行**（v2 rollback 端点 + C2 两个冗余分支）。
- **共同收益——"改一处漏一处"消失**。这是 5 组双轨的统一收益：每组的 A/B 两轨实现同一个不变量，但**契约不同名不同义**（`drop_engine` vs `resync_after_rewind`）。定主从后，不变量只有一个实现点。

**为什么这条最容易被低估**：双轨的 bug 不在当下，而在**未来某次只改了 A 轨的提交**。它不会立刻报错，会在 B 轨被启用时（通常是 A 轨出问题的降级时刻）爆炸——**正好是最不能出错的时候**。

## 二、6 项 P0 的收益

> 统一前提：这 6 项的收益**全部是"关闭危险路径"**，不是"新增能力"。
> 因此衡量单位不是"提升了多少"，而是"**少了一个什么量级的事故可能**"。

### P0-1　`workspace_fs` 直写绕过引擎三链路

**修复动作**：Step 1 默认反转（显式 `XEYO_WORKSPACE_FS_WRITABLE` 才可写）+ 审计失败告警；Step 2 收敛进共享 write gate（获 rewind）。

**收益**

| 维度 | 修复前 | 修复后 |
|---|---|---|
| **暴露面** | 本机任意进程（loopback 内）可 `PUT`/`DELETE` 工作区任意文件，含 `recursive=true` 整棵删目录 | 默认 403，需显式开关 |
| **可回滚性** | ✘ **零** — GUI Explorer 里手动改的文件**不进 rewind**，改错了无法撤销 | ✔ 进 rewind 账本，可回滚 |
| **可审计性** | △ `_audit_write` 存在，但失败静默吞 | ✔ 失败必告警 |
| **既有边界** | ✔ 路径约束 `resolve_in_workspace` + `_EXCLUDED_DIRS`、`_MAX_TEXT` | 不变（这些是做对的） |

**收益的关键点**：**用户手动编辑首次可回滚**。

现状是——用户在 GUI 里编辑一个文件并保存，走的是 `FilePreview.tsx:451` → `explorerStore.ts:298-299` → `api.ts:738 writeWorkspaceFile` → `workspace_fs.write_file`。这条路径**完全不在 rewind 视野内**。但用户直觉是"我在 XEYO 里改的东西应该能撤销"。

**Step 2 修完后，`grep record_file_mutation` 的生产调用点从 3 处扩展到覆盖全部写路径**——这是模式 3 收益的具体兑现。

**代价提示**（必须同批做）：反转默认会**改变产品行为**（GUI 编辑器保存失败），所以必须同批改前端 `explorerStore.saveFile` 给出明确提示。这是"默认拒绝 + 显式开关"的标准做法。

### P0-2　`usage.py` 开放 SSRF 代理面

**修复动作**：推荐 C 方案——**复用 `tools/web_common.py:19-73` 已有的 SSRF 门**（scheme 白名单 / 私网 / metadata IP / DNS 逐地址复查 / 每跳重定向复检），而不是新写一份。

**收益**

| 攻击 | 修复前 | 修复后 |
|---|---|---|
| **带凭据 SSRF** | 本机任意进程可设 `X-Base-Url`，让 XEYO **带用户 API key** 请求任意地址 → **key 外泄** | 403（不在已配置白名单） |
| **云元数据探测** | `X-Base-Url: http://169.254.169.254/` 可通 | 403（metadata IP 阻断） |
| **内网服务扫描** | 可扫 `http://localhost:PORT/` | 403（loopback/private 阻断） |
| **自建中转（合法需求）** | ✔ 可用 | ✔ 用户在设置里显式保存过的地址仍可用 |

**实测范围确认**：三个端点全部受影响——`fetchVendorModels`（`usage.ts:134` `/v1/models`）、`fetchUsage`（`:216` `/v1/usage`）、`fetchUsageBalance`（`:256` `/v1/usage/balance`），三者都发 `X-Base-Url` 头（`usage.ts:129/207/249`）且都带 `Authorization: Bearer <key>`（`:131/213/253`）。

其中最危险的是 balance：`usage.py:79-92` 用 `urlopen` **直连**（不走 http client 封装），且**显式附加 Bearer**。

**额外收益（结构性）**：选 C 方案而非 A/B，**同时消掉一个新的双轨**——否则会出现"WebFetch 有一套 SSRF 门、usage 又有一套"，正好重蹈模式 1。这是"修一个洞的同时不挖一个新洞"的做法。

**收益量级**：API key 外泄是本机多进程环境下的**凭据失窃**，量级等于用户在该供应商账户上的全部消费能力。**这是 6 项 P0 里收益最高的之一**，而成本只有 ~0.5 天（因为门已经写好了）。

### P0-3　Tauri 自定义 command 可写全盘

**修复动作**：`assert_within_workspace`（**必须用 canonicalize**，否则 `..` 逃逸可穿过 `starts_with`）+ `reveal_in_folder` 引号转义 + per-window ACL。

**收益**

| command | 修复前危害 | 修复后 |
|---|---|---|
| `save_text_file`（`lib.rs:483-490`） | 仅判非空 → `std::fs::write` **任意绝对路径** | 越出工作区即拒 |
| `create_directory`（`:579-586`） | 任意目录创建 | 同 |
| `git_init`（`:589-593`） | 任意位置 `git init` | 同 |
| `git_clone`（`:596-607`） | 任意位置克隆 | 同 |
| `reveal_in_folder`（`:494-511`） | `raw_arg` 拼 `/select,"{path}"`，**引号可被破坏** | 转义 / 独立参数 |
| **pet 窗口** | 与主窗口**同权**，无 ACL | 独立 capability，最小权限 |

**收益的关键点**：`abs_path()`（`:540-550`）的语义是"确认这是绝对路径"，**不是**"确认这在允许范围内"。函数名本身就说明了定位偏差——修完是 `assert_within_workspace`，**名字与语义对齐**。

**★ 与 P0-4 是组合拳（必须强调）**：P0-4 提供入口（模型输出 `data:text/html` → 可执行上下文），P0-3 提供破坏力（该上下文可调无边界 command）。**单独修任一个都不闭合**。这也是把它们排在同一批的理由。

**收益量级**：从"模型可影响输入"到"**任意文件写入**"的完整链路被切断。在本机 agent 产品里，这是最高危的一类。

### P0-4　预览 iframe 仍 `allow-same-origin`

**修复动作**：Step 1 移除 `allow-same-origin`（**一行**）；Step 2 `normalizeUrl` 加 scheme 白名单；Step 3 CSP `frame-src` 去 `data: blob:`。

**收益**

| 维度 | 修复前 | 修复后 |
|---|---|---|
| **可执行上下文** | 模型发 `data:text/html,<script>…` → `normalizeUrl`（`:24-40`）**放行任意 scheme** → 直达可执行 | 仅 http/https |
| **sandbox 有效性** | `allow-scripts` + `allow-same-origin` **同时存在 ⇒ sandbox 基本失效**（iframe 内脚本可移除自己的 sandbox 属性） | opaque origin，sandbox 生效 |
| **父页面访问** | 同源 ⇒ 可访问父（Tauri 主窗口）DOM / IPC | `parent.document` 抛 SecurityError |
| **SmartScreen** | `tauri.conf.json:28` **显式禁用** `msSmartScreenProtection` | 建议恢复 |

## 五、必须同时说的三件事（避免收益被高估）

### 1. 有一项"收益"其实是**正确的产品决策**，不该被当缺陷修

**P0-5 的 abort 解绑**：`adopt_bash` 注释明写"会话 abort 不杀 job——42 号冻结口径"。这是**刻意的产品决策**（后台作业本来就该活过会话中断）。修 P0-5 时**不要顺手改这个行为**——只加物理上限 + 补提示。

### 2. 有一项首轮严重度高估，收益接近于零

**新-3（C2 chars/4）**：首轮说"中文差 3 倍"，经数学验证**不成立**（`/4` 两边约掉）。**当前行为收益 = 0**，收益全部在"防未来的单边改动"。已降级为 P2。

### 3. 有四项收益**必须先实验才能确认**

| 项 | 为什么不能直接做 |

| **新-5** | 厂商配对行为未验证——直接改"追加"可能 400，比缓存损失更严重 |

这四项按 AGENTS.md 第 4 条（"新行为先以旁路形态验证收益，有数据证明才并入主链路"）**都应该先旁路/实验**。**这是项目自己的规矩，遵守它本身也是收益**——它把"投入了但没收益"的风险挡在前面。

```

─────────────────────────────────────────────────────────────
 6 项 P0（~5 天）           →  6 条危险路径关闭
                              其中 2 条（P0-2 / P0-3+P0-4）是「凭据失窃 / 任意文件写入」量级

```

**核心结论**：

> **XEYO 这一批修复的收益，主要不是"变得更强"，而是"变得可信"。**
>
> 开源后，用户不会因为 XEYO 少一个功能而离开，但会因为**"装了个 agent，结果它能写我全盘文件 / 我的 API key 明文躺在 localStorage / 我改的东西撤不回来"**而离开。
>
> 6 项 P0 全部属于后者。这就是为什么它们的收益量纲是"事故"而不是"效率"——**也正因为如此，它们的优先级不该用 ROI 排序，而该用"暴露面大小"排序**，这才有了 §四 里 P0-4 排第一（一行改动、入口最上游）。
