# 输入链·维持项裁定（2026-10-07）

范围：输入链普查（goal 常驻，2026-10-05 起）登记的 5 条「维持现状」项的最终裁定、
事实依据与重启入口。其余 14 条已落地或另册；本文只落「为什么不改」，防止后续会话重复翻案。

## #1 submission_unknown：GUI 双策略 + TUI 通用守卫 —— 维持

事实（`gui/src/stores/chat/streamSendSlice.ts`）：

- 初始 POST 未收到 HTTP 响应（`kind: 'submission_unknown'`，定义见 `gui/src/lib/api/core.ts`）时，GUI 按受理状态分两支：
  - **队列路**（忙时排队提交的流）：撤回乐观气泡 + banner「消息提交状态未确认；原文保留在输入框。
    请先检查排队列表和会话记录，再决定是否重发」+ **立即 `refreshInbox` 按 message_id 对账**（不邀请重发）。
  - **直发路**（回合已上屏）：保留会话记录中的原文 + banner「连接已恢复，但原消息的提交响应丢失…
    原文保留在会话记录中」+ `refreshInbox` 对账 + `recoverAfterDisconnect` 重连成功后再次对账。
- 不变量（两支共同）：**原文至少留一处 + 必出声 + 必对账**。
- TUI 无该类型分流，走通用发送守卫（`tui/src/app/App.tsx::sendTurn`）：未上屏 ⇒ 草稿回填 + error 出声；
  已上屏 ⇒ 气泡为准不清草稿。

裁定：维持。两支差异来自**受理状态**不同（排队未上屏 vs 直发已上屏），不是同一场景的摇摆；
统一成一支必然在队列路丢草稿、或在直发路留幽灵气泡。TUI 以「是否会重复发送」为准绳即可。

重启入口：若未来要统一三端口径，先证明两支在对方场景下可替代（尤其：直发路不可回填草稿，
因为回合已在跑）。

## #6 归档后 ChatPage 交接时序 —— 维持

事实：归档动作后主区视图交接的时序非确定（有时立即、有时晚一步）；侧栏（会话列表）视角始终正确。
决定性观测量只有主区一帧级过渡差异，无数据错位。

裁定：维持。仅为动画/过渡精准度去动路由效应不划算；已有探针带重试环容忍该差异。
重启入口：仅在出现用户可见的真实错位（如残留旧会话内容）时再查。

## #12 Py-CLI ask 空回车且无 default —— 维持现状

事实：`prompt_ask` 空回车 → 回 default；**无 default 时空串被当作空答案提交**（`""` 与「没作答」
在回执里不可区分，登记为 #12）。

裁定：维持。修法=引入「跳过」标记会改**模型可见文本**（答案通道承载的语义变化），按引擎铁律
（注意力里只出现信息）须先过注意力设计；只给 CLI 加标记则三端语义分裂。CLI 该使用面窄。
重启入口：若远端/TUI 也需要「跳过」语义，三端一起设计再动。

## F2 会话后台化缺失 + Ctrl+B 键义冲突 —— 维持

事实：无「撤离整个会话 / 放后台」显式入口；断连时回合以 detached 方式续跑（代码层已存在，
`turnDetached`）但没有 UI 暴露。Ctrl+B 在 XEYO=沉浸侧板开关（`ImmersiveLayer`），
与 Claude 的「整会话后台化」同键异义。

裁定：维持。显式后台化=新状态机（可见性/通知/恢复入口），收益未证；键位冲突只在跨产品
肌肉记忆层面。重启入口：真需求出现时优先给「后台化」安排新键位，而不是夺 Ctrl+B。

## F4 回合级 pause / resume —— 不实现（边界文档化）

事实：stop=不可续（恢复路径=重发或队列补投）；市场参考（Claude / DSH 全树）无回合级 pause 概念；
XEYO 独有的是 **goal 级**暂停/恢复（SessionGoalDock）。

裁定：不做。回合中段快照/续跑是引擎原子性设计议题（预算、工具半途、transcript 原子性），
成本远超收益。重启入口：作为引擎级设计议题立项，而不是输入链候补。
