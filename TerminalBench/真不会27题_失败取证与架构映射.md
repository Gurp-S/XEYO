# 27 题"真不会"失败取证与架构问题映射

> 数据源：P2 全量 89 题 × k=1 的逐 trial 轨迹（jobs_p2/）——每题的 verifier 判分输出 + agent 停止现场 + 异常栈（forensics_27.txt，58KB 全证据）。
> 结论先行：**27 题里没有几道是"模型智力不够"，绝大多数是工程纪律缺口**，且每一种缺口都对应一个可落地的引擎机制。

---

## 一、五大失败模式（按题数排序）

### 模式 A｜Agent 超时截断，产物根本没生成（≈10 题，最大头）

**证据**：异常栈清一色 `asyncio.wait_for → terminus_2`（agent 撞上时间预算被强杀），
verifier 报 `FileNotFoundError: /app/xxx`——**产物文件压根不存在**：

| task | 死亡现场 |
|---|---|
| rstan-to-pystan | **MCMC sampling 92%（7400/8000）被杀**——再给 2 分钟就出结果 |
| extract-moves-from-video | OCR 并行进程还在跑（tesseract 活跃），`^C` 一条 94 秒命令后被杀，solution.txt 未写 |
| chess-best-move | 还在打印棋盘 ASCII 分析，move.txt 未写 |
| gpt2-codegolf | 还在解析 GPT-2 权重（124M 参数已列出），gpt2.c 未写 |
| make-doom-for-mips / make-mips-interpreter | 还在写 syscall shim（lseek/SYS_time），从未跑到产出 frame.bmp |
| write-compressor | 还在探索文本重复片段（压缩思路对了），data.comp 未写 |
| raman-fitting | 拟合进行到一半（A2/B1/B2 峰已拟合），results.json 未写 |
| gcode-to-text | 还在排查 G-code token，out.txt 未写 |
| dna-assembly | gblock.txt 已产出且自检全绿，**但 primers.fasta 没来得及写** |

**架构问题**：引擎把"时间预算"当成唯一终止条件，**没有时间感知的收尾机制**——agent 不知道自己快死了，还在探索；引擎也没有在预算尾部强制"先落盘已有成果"。Terminus-2 无 `run_in_background`，长命令（94s OCR、数分钟 MCMC）串行占满预算，加剧截断。
**修复**：①**deadline-aware winding-down**：时间预算用到 80% 时，引擎强制注入"立即产出最终交付物"指令并停止启动新的长命令；②长命令强制后台化+心跳（XEYO 的 `Bash run_in_background` 天生就有）；③验证门控的 L0 在时间尾部仍能机械检查"产物文件是否存在"，不存在就降级输出部分成果。

### 模式 B｜自测域 ⊊ 验证域（≈7 题）——53 号设计的靶心

**证据**（每题 agent 的自测都过了，verifier 的条件不同）：

| task | 自测通过 | verifier 实际要求 |
|---|---|---|
| torch-tensor-parallelism | world_size=1 全绿 | world_size=2/4 全炸（8 failed）——**没测多 rank** |
| torch-pipeline-parallelism | 同上模式 | transformers 位置编码 API 差异未测 |
| kv-store-grpc | 用自己的 proto 自测 set/get 成功 | 测试期望字段名 `value`，agent 命名 `val` → `ValueError: has no "value" field` |
| path-tracing | `/app/reconstructed.ppm` 与原图 `cmp SAME`（重建完全正确！） | verifier 把二进制放进 **/jail chroot** 重跑，`/app/image.ppm` 不在 jail 里 → 跑不出输出 |
| regex-chess | 初始局面 + 一个边例 | 被过路兵吃子规则打崩（move 3 后合法着法 1 vs 28） |
| db-wal-recovery | 自检"恢复成功" | WAL 解密没做（id=1 的 update 未应用），7 项测试过 5 项就停 |
| video-processing | 自己调用 OK | 测试传参约定不同（int vs list）→ `TypeError` |

**架构问题**：**自测域由模型自选，验证域由测试方定义，两者无引擎强制对齐**。模型天然测"自己写的东西好不好使"，不测"验收方会怎么调它"。
**修复**：53 号的覆盖差距检测直接对症——①验证命令必须在**验收方的调用约定**下执行（jail/字段名/传参形状）；②`property` 证据模板强制"spec 声明的每个秩/规模/字段名至少跑一次"；③kv-store-grpc 类的**交付契约核对**（proto 字段名、产物路径、调用签名）机械可查。

### 模式 C｜交付契约未核对（≈4 题，与 B 交叠）

install-windows-3.11（**4 项测试过 3 项**，只差 qemu 参数里镜像路径用 `/tmp/win311-patched.img` 而非要求的 `/app/isos/win311.img`——万里长征最后一步跑偏）、dna-assembly（产物名不对）、chess-best-move（产物缺失属 A 类但契约同样未核对）。
**修复**：DONE_PROPOSED 时的 L0 机械核对"验收清单"——每条 = 文件路径 + 存在性 + 关键参数断言，全部来自 instruction 的可执行化。这条是 53 号证据对象的最简单子集，优先实现。

### 模式 D｜有度量不用度量（≈4 题）

| task | 现场 |
|---|---|
| train-fasttext | **自己测出 P@1=0.613 < 阈值 0.62，然后停了**——度量明明在手，缺"不达标就继续调"的门控 |
| count-dataset-tokens | 算出 63841，答案 79586（计数口径/数据范围错） |
| mteb-leaderboard / mteb-retrieve | 查询/排序错一行（result.txt 内容错） |
| model-extraction-relu-logits | steal.py 接口与 forward 模块不匹配（自测没覆盖） |

**修复**：验证门控的**度量门控证据**——任务给出可度量指标时（准确率阈值、计数正确性），L0 强制"跑度量 → 达标才放行"，不达标自动 REPLANNING（这是 53 号最有直接 ROI 的一条：train-fasttext 这类题只差一次再训练）。

### 模式 E｜方法性死路，无升级路径（≈2-3 题）

extract-elf（JS 手写 ELF 解析，0% 匹配 reference——方法选错，应换 readelf/objdump 或换解析路线）、model-extraction（提取接口猜错后继续在同一路线上打转）。
**修复**：REPLANNING 的**失败分类器**——证据连续 2 次同模式失败 ⇒ 引擎强制方法切换（换工具/换库/换路线），并把失败标签写入记忆供建议后续任务。

## 二、跨题洞察（比单题更有价值）

1. **能力在场，纪律缺席**：path-tracing 的重建逐字节 SAME、dna-assembly 的结构自检全绿、install-windows 装好了整个 Win311——**"会做"与"交付"之间隔着的全部是验证与交付纪律**，这正是引擎该接管的部分。
2. **超时是第一杀手**：11/27 的 trial 有 agent 超时异常，其中至少 5 题模型正走在正确道路上（rstan 92%、pov-ray 式长跑）。**时间感知收尾 + 长命令后台化**的杠杆比换模型大。
3. **KV 命中率不是问题**：27 题命中率 75-98%（median ~91%）——上下文经济学在这批失败里零责任，**分数瓶颈全部在验证与交付纪律**。这给 53 号设计的优先级提供了最强证据。
4. **成本与失败负相关不成立**：失败题平均花费 0.55 元 vs 全局 0.37——失败题不是"没舍得花 token"，是**花了 token 但没有收敛门**。

## 三、架构问题 → 机制映射总表

| 失败模式 | 题数 | 对应架构缺口 | 修复机制 | 出处 |
|---|---:|---|---|---|
| A 超时截断产物缺失 | ~10 | 无时间感知收尾；无长命令后台化 | deadline winding-down + 强制后台化心跳 + 尾部产物落盘 | **53号新增** |
| B 自测域 ⊊ 验证域 | ~7 | 覆盖差距不检测 | L0 覆盖差距检测 + 验收方调用约定执行 | 53号 §2.3 |
| C 交付契约未核对 | ~4 | 交付清单不核对 | L0 交付物清单机械核对 | 53号 §2.2 |
| D 有度量不用度量 | ~4 | 度量不达标可停 | L0 度量门控证据（不达标 → REPLANNING） | 53号 §2.2 |
| E 方法死路 | ~3 | 无失败分类与强制换路 | REPLANNING 失败分类器 + 方法升级 | 53号 §2.5 L2 |

**结论：27 题失败里，53 号设计直接覆盖 B/C/D/E（~17 题），A 类（超时）需要新增"时间感知收尾"机制——这是本轮取证对 53 号的唯一实质修订。**

## 四、P3 实验的修正案

1. 实现范围在原 53 号基础上**加 deadline winding-down**（P0 级，与验证门控同批）；
2. 失败子集重测从"27 题"修正为 **"27 题 - 7 基建已修" = 20 题 + 3 题回归组**（约 15-20 元）；
3. 预期提升的重算：B/C/D 三类合计 ~14 题是门控的可修对象（路径正确 + 阈值可达），A 类 5-8 题依赖收尾机制生效比例——**目标：60.7% → 75-80%**（对齐 StateM 基线水位，且是在更严的 k=1 口径下）。
